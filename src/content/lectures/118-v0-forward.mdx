我们手里有一个 1.5 GB 的文件 `model.safetensors`，和一句提示 “The capital of France is”。这一讲的目标只有一个：**不用 transformers，自己写代码，让这个文件算出下一个词是 “Paris”**，而且接下来生成的 32 个 token 和 HuggingFace 一个不差。

这就是 v0。它很慢（下一讲就会看到慢在哪里），但它是后面所有版本的地基：模型前向写对了，之后的 KV Cache、批处理、分页都只是在“怎么组织调用”上做文章。

## 权重文件里有什么

先打开文件看一眼。safetensors 是一种很简单的格式：文件头是一段 JSON，记录每个张量的名字、形状、数据类型和在文件里的位置，后面是连续存放的原始数据。

<RunOutput cmd=".venv/bin/python bench/inspect_weights.py" file="outputs/inspect_weights.txt" caption="图 118-2　Qwen3-0.6B 的权重：311 个张量，BF16。这里只列出第 0 层和层外的张量，其余 27 层的名字和形状都一样。" />

对照第 34 讲的完整前向，每个名字都能对上号：

- `embed_tokens`：嵌入表，[151936, 1024]，每个 token 一行 1024 维（第 22 讲）。
- 每层 4 个注意力投影：`q_proj` 是 [2048, 1024]，`k_proj`、`v_proj` 是 [1024, 1024]，`o_proj` 是 [1024, 2048]。注意 q 的输出是 2048 维 = 16 个头 × 128，而 k、v 只有 1024 维 = 8 个头 × 128：这就是 GQA（第 39 讲），两个查询头共用一组 K、V。还要注意 16 × 128 = 2048 比隐藏维度 1024 大，Qwen3 的头维度不等于 d ÷ 头数。
- `q_norm`、`k_norm`：只有 128 个数。这是 Qwen3 特有的：在 RoPE 之前，对每个头的 q、k 各做一次 RMSNorm，让注意力打分更稳定。
- 每层 3 个 FFN 矩阵：`gate_proj`、`up_proj` 是 [3072, 1024]，`down_proj` 是 [1024, 3072]，这是 SwiGLU（第 38 讲）。
- 两个 RMSNorm 的缩放（各 1024 个数），加上最后的 `model.norm`。
- `lm_head`：输出层，[151936, 1024]。它和嵌入表一模一样（`tie_word_embeddings`），文件里存了两份，所以 752 M 个参数里有 1.56 亿是重复的，模型实际约 6 亿参数，这就是“0.6B”。

PyTorch 的线性层把权重存成 [输出, 输入]，所以 y = x · Wᵀ。后面的代码里到处是 `x @ W.T`，就是这个原因。

这是这一讲的主体。整个 Qwen3 的前向只有 59 行，用到的运算只有矩阵乘、逐元素运算、softmax 和查表。左边是代码，右边逐段解释；点步骤或者“下一步”，左边会高亮对应的行。

<Note kind="warn">写模型前向时，最容易出错的四个地方：RoPE 的配对方式（前后两半，而不是相邻两维）；GQA 的复制方式（<code>repeat_interleave</code>，而不是 <code>repeat</code>）；Qwen3 在 RoPE 之前对 q、k 做的 RMSNorm；位置从 0 开始数。这四处任何一处写错，模型都还能输出看似通顺的文字，只有和参考答案逐 token 比对才能发现。</Note>

## 它慢在哪里

上面生成 32 个 token 用了约 7 秒，平均每个 200 多毫秒。看起来每个 token 的耗时差不多，那是因为提示很短。把提示加长到 199 个 token、生成 64 个，每一步的耗时就看得出变化了（这个压测下一讲会完整展示）：第 1 步约 419 ms，第 64 步约 724 ms，64 步一共约 34 秒。

原因就在生成循环里：第 n 步要算 199 + n 个 token 的前向，越往后越长。总计算量大约是 64 × 230 ≈ 15,000 个 token 的前向，而真正“新”的只有 199 + 64 = 263 个。

前面的 token 每一步都在重算，结果却和上一步一样。能不能把算过的东西存下来？第 68、69 讲已经给出了答案：把每层的 K、V 存起来，新 token 只需要和存好的 K、V 做注意力。

## 回顾

v0 用四个文件让 Qwen3-0.6B 跑了起来：config.py 读模型的 10 个尺寸，weights.py 把 311 个张量读进字典，model.py 用 59 行写出完整的前向（RMSNorm、RoPE、q/k 归一化、GQA、因果注意力、SwiGLU、残差），engine.py 用一个循环做贪心生成。和 HuggingFace 比对，4 条提示的 32 个 token 全部一致。

它的毛病是每生成一个 token 都要把整段序列重算一遍：199 个 token 的提示，第 64 步要算 263 个 token，耗时从 419 ms 涨到 724 ms。下一讲：**KV Cache**。
