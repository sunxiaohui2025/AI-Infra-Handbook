到 v4 为止，每个请求每一步 decode 只出一个 token。第 119 讲测过，decode 一个 token 要 63 ms，而 prefill 199 个 token 只要 357 ms：一次前向多算几个 token，时间涨得很少，因为大头是把权重读一遍。

第 96 讲的投机解码就是利用这一点：先用一个很便宜的办法**猜**接下来的几个 token（草稿），再让模型一次前向把它们全部**验证**一遍。猜对了几个，这一步就多出几个 token；猜错了，最多只损失这一步多算的那几个位置。在贪心采样下，它生成的结果和不投机时**完全一样**。

## 设计：草稿从哪里来

第 96 讲的标准做法是用一个小模型起草。我们用一个更简单、完全不需要第二个模型的办法：**n-gram 查找**（也叫 prompt lookup decoding）。

思路是：很多生成任务会大段地重复已有的内容。改写代码时，大部分代码原样抄过来；总结文档时，会引用原文的短语；多轮对话里，会重复上一轮提过的名字。所以，看看当前序列结尾的几个 token，**在前面出现过没有**；出现过，就把那次出现之后紧跟着的几个 token 当作草稿。

```text
已有的 token： … for i, v in enumerate(values):  …  total += v  …  for i, v in
结尾 3 个：                                                       [for, i, v]
前面出现过，后面跟着：                     [in, enumerate, (, values]          ← 草稿（k = 4）
```

先找结尾 3 个 token，找不到就退到 2 个、1 个；从近往远找，越近的上下文越可能相关。整个过程只是在列表里做比较，比一次前向便宜几个数量级。

## 设计：一次前向怎么验证

草稿接在最后一个真实 token 后面，一起送进模型。设最后一个真实 token 是 t，草稿是 d₁ d₂ d₃ d₄，送进去的就是 5 个 token：t d₁ d₂ d₃ d₄，位置连续。模型对这 5 个位置各给出一个“下一个 token”的贪心预测 p₀ … p₄：

- p₀ 是看完 t 之后的预测。如果 p₀ = d₁，说明草稿第一个猜对了。
- p₁ 是看完 t d₁ 之后的预测。如果前面猜对了，而且 p₁ = d₂，第二个也猜对了。
- 依此类推，直到第一个不一致的位置。

假设 d₁、d₂ 对了，d₃ 错了：这一步接受 d₁、d₂，再加上 p₂（模型在“看完 t d₁ d₂”之后真正想要的 token），一共新增 **3 个** token。全猜错也有 p₀，至少和不投机一样多出 1 个。

为什么结果和不投机完全一样？因为每个被接受的 token，都是模型在“同样的前缀”下的贪心选择，和一步一步生成时选的完全相同（第 96 讲）。

**KV 怎么办。**这一步把 5 个位置的 K、V 都写进了缓存。被接受的位置（t、d₁、d₂）的 K、V 是正确的；被拒绝的位置（d₃、d₄）写进去的是错的。不需要专门去删：把 `num_computed` 只推进到被接受的位置，那两格就算作“没写过”，下一步会被新的 token 覆盖。这就是投机解码的“回滚”，在分页的块里只是一个数的事。

## 测一测：抄得多，猜得准

投机解码的收益完全取决于草稿猜得准不准。用两种请求对比：一种是“给一个函数加上类型标注，其余不变”，答案大部分是在抄输入的代码；另一种是自由地写一段说明。

<RunOutput cmd=".venv/bin/python bench/spec.py" file="outputs/bench_spec.txt" caption="图 124-5　改写代码：128 个 token 只用了 34 步 decode，接受了 93 个草稿，平均每次前向 3.66 个 token，用时从 9.4 s 降到 6.6 s。自由生成：53 步，平均每次前向 2.37 个 token，用时从 9.2 s 降到 8.0 s。两种情况的输出都和不投机时完全一致。" />

**步数大幅减少。**改写代码时，n-gram 草稿 128 个 token 里猜对了 93 个，decode 从 127 步降到 34 步。连自由生成也有 2.37 个 token 一步：这个小模型在贪心解码下很容易重复自己说过的话，n-gram 正好抓住了这一点。

**时间没有按步数同比例减少。**步数降到约四分之一，时间只降到七成。原因是每一步不再只算 1 个 token，而是 5 个；在 CPU 上，多算 4 个 token 并不是免费的（不像在 GPU 上那样，decode 时算力大量闲置）。第 96 讲的加速比公式里，这对应“验证 k 个草稿的代价”这一项；CPU 上这一项比 GPU 上大得多，所以同样的接受率，CPU 上的加速比更小。

**猜不准时也不亏多少。**草稿全错时，这一步仍然出 1 个 token，只是多算了几个位置。草稿在 batch 很大时会更“贵”：每个请求多出的 k 个位置都要算，batch 已经让硬件很忙时，多算的部分就不再藏在读权重的时间里了。这也是工业引擎在高负载时会自动减少、甚至关闭投机的原因。

<Note kind="point">投机解码 = 便宜地起草 + 一次前向验证。n-gram 起草在已有 token 里找和结尾相同的片段，把后面的几个 token 当草稿；验证时逐个比较草稿和模型的贪心预测，接受到第一个不一致处，再加上模型自己的那个 token。被拒绝的草稿位置只要不推进 num_computed 就自动作废。贪心采样下结果和不投机完全一样。</Note>

## 回顾

v5 新增 spec.py：`propose` 用 n-gram 在已有 token 里找草稿，`verify` 按模型在每个位置的贪心预测决定接受到哪里。引擎在 decode 请求后面接上草稿一起送进模型，模型按 `out_idx` 返回需要的几个位置的打分；回滚只需要把 `num_computed` 推进到被接受的位置。和 HuggingFace 仍然逐 token 一致。改写代码时平均每次前向出 3.66 个 token，用时从 9.4 s 降到 6.6 s；自由生成也有 2.37 个。
