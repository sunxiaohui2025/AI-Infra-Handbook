上一讲的结论是有些 kernel 必须自己写。写之前要选语言，而这个选择不只是“用哪种语法”：它决定了这份代码能跑在几种硬件上、写一遍要多久、能逼近硬件上限的几成。

这一讲把同一个算子——RMSNorm——用四种方式写出来摆在一起，并在本机把其中两种真实跑起来量出数字。RMSNorm 是个好例子：数学只有三步（平方求均值、开倒数平方根、乘权重和缩放），但它受带宽限制，所以“写法”带来的差别全部来自访存和下发，没有算力的因素干扰。

## 四种写法

<KernelCompare caption="图 144-1　同一个 RMSNorm 的四种写法。切换标签看代码和它要自己操心什么。Metal 那一份是本机真实编译运行的；Triton 和块级 DSL 的片段没有在本机运行（本机没有这两个后端），代码按各自文档的常见形式写。" />

四种写法的分水岭有两条。

第一条在**要不要写线程**。框架算子组合和 Triton 都不写线程编号：前者连块都不管，后者以“一个程序处理一整块数据”为单位（第 88 讲）。厂商 kernel 语言要写到通道级：谁读哪一列、归约分几步、什么时候同步。

第二条在**搬运是不是显式的**。Triton 里 `tl.load` / `tl.store` 的背后，编译器自己决定要不要经过片上存储；块级 DSL（TileLang 这一类）要求你声明缓冲、写出搬运语句。多一层控制，换来的是能表达显式搬运硬件所需要的调度（第 135 讲的 NPU 路线）。

## 在本机真的跑一遍

下面这份脚本在 Apple M2 的 GPU 上对比三种写法：基础算子组合、组合但只让归约升精度、以及一个手写的融合 kernel。本机的“厂商 kernel 语言”是 Metal，它的结构和 HIP、CUDA 是同构的——一个线程组处理一行，组内先做 SIMD 组归约，再跨组归约，然后写回。

四个结论。

**融合 kernel 在 decode 形状上快 4.6 倍**（25.9 μs → 5.6 μs）。这个形状只有一行、4 KB 数据，时间几乎全是固定开销：组合写法要下发五个 kernel，融合写法只下发一个。这正是第 142 讲说的 decode 阶段的典型瓶颈。

**在 prefill 形状上快 10.6 倍**（122.2 μs → 11.5 μs）。这里数据量够大（199 行 × 1024 列 × 4 字节 ≈ 800 KB），固定开销被摊薄，差距来自访存：组合写法要把张量读写五遍，融合写法一遍。按第 83 讲的融合账本，这个比例应该在 5 倍左右，实测 10 倍——多出来的部分是中间张量的分配和逐元素 kernel 本身的效率。

**“有效带宽”这一列的两个反常值要解释**。prefill 行的 141.3 GB/s 高于这台机器的内存带宽，因为 800 KB 的数据留在缓存里了，根本没走内存；换成 4096 行（32 MB，放不进缓存）后降到 85.1 GB/s，这个数才是接近内存带宽的真实值。**量带宽时一定要确认数据量超过缓存**，否则量到的是缓存带宽——这是性能测试里最常见的自欺。

**三种写法的误差都在 5e-8 量级**。融合 kernel 在片上用 FP32 累加，和组合写法的数值行为一致。顺带回答了第 142 讲留的那个问题：“组合 + 归约用 FP32”这个微优化在 decode 形状上只快了 14%（25.9 → 22.3 μs），而写一个融合 kernel 快 4.6 倍——**要改就改到位，不值得在组合写法里做微调**。

<Note kind="point">这个实验可以照搬到任何一块新卡上，而且不需要厂商的 profiler：选一个带宽受限的算子，写三个版本（组合、Triton、手写），在三种形状（decode 一行、prefill 几百行、超过缓存的大 batch）上各量一次，算出有效带宽。拿到的这张表直接回答两件事——这块卡的融合收益有多大、手写值不值得。</Note>

## 怎么选

把四种写法放进一张决策表：

| 情况 | 选什么 | 理由 |
| --- | --- | --- |
| 适配初期，先要跑通 | 框架算子组合 | 零成本、正确性有保证（第 140 讲） |
| 逐元素、归一化、激活、RoPE 这类带宽受限的算子 | Triton（有后端）或厂商语言 | 融合收益大、逻辑简单，写一次能用很久 |
| 注意力 | 优先找厂商移植版，其次 Triton | 算法复杂（在线 softmax、分页读 KV），自己从零写容易出错 |
| 矩阵乘的常规形状 | 厂商库 | 库里为这些形状调过（第 143 讲） |
| 矩阵乘的 decode 小 M 形状 | 厂商语言手写 | 要控制分块、对齐和矩阵指令，Triton 的抽象够不着最后那几成（第 151 讲） |
| 要跨多家硬件维护一份代码 | Triton 或块级 DSL | 牺牲一点性能换可移植性 |
| 硬件要显式搬运（NPU 路线） | 厂商语言或块级 DSL | Triton 的模型里表达不出搬运调度 |

一个常被忽略的成本是**维护**。手写 kernel 要跟着架构代号走：海光那个小 M kernel 里就有三套分支（`gfx928`、`gfx936` 用一条内建指令，`gfx938` 用另一条，其他架构直接陷阱），每出一代新卡都要加一个分支（第 151 讲）。Triton 的代码不用改，但调好的参数要重调。所以“写几个 kernel”这件事要控制数量：只写占时间的那几个，其余交给库和框架。

<Note kind="warn">自写 kernel 是精度问题的主要来源（第 139 讲）。三条纪律：入口处把假设写成检查（形状、对齐、数据类型不满足就走回退路径，像第 143 讲那个 `supported()` 函数那样）；归约和同步的每一步都对照参考实现验证；每个新 kernel 配一个单算子对比测试，而不是只在整个模型里测。</Note>

## Triton 在新硬件上的现实

Triton 常被当成“写一次、到处跑”的答案，这个期待要打两个折扣。

**第一个折扣是有没有后端**。Triton 的编译器要为每种架构实现一个后端（指令选择、寄存器分配、共享内存布局）。NVIDIA 和 AMD 的后端由项目自己维护，其他厂商要么自己接、要么等。海光的容器镜像里确实装了 Triton（第 148 讲会看到构建脚本里 `das-install triton==3.6.0`），说明这条路是通的。

**第二个折扣是参数要重调**。同一份 Triton 代码，块大小、`num_warps`、流水级数在不同架构上的最优值不同——因为片上存储容量、线程组宽度、矩阵指令形状都变了（第 135 讲）。常见做法是用自动调优（autotune）在目标卡上扫一遍参数，把结果缓存下来；代价是第一次运行很慢，所以要在服务的预热阶段做掉。

还有一类现实选择：**用 Triton 写非矩阵乘的算子，用厂商库和手写 kernel 覆盖矩阵乘和注意力**。海光插件的注意力后端里就能看到这个分工——有 Triton 版的注意力后端作为兜底，也有厂商移植的 FlashAttention 作为首选（第 152 讲）。

## 回顾

同一个 RMSNorm 的四种写法，差别在两条分水岭：要不要写线程编号，搬运是不是显式的。本机的实测给出了融合的真实收益：手写 Metal kernel 在 decode 形状上比基础算子组合快 4.6 倍（固定开销从五次下发降到一次），在 prefill 形状上快 10.6 倍（张量从读写五遍降到一遍），而三种写法的数值误差都在 5e-8 量级。量带宽时要让数据量超过缓存，否则会量到缓存带宽（本机 800 KB 的形状量出 141 GB/s，32 MB 的形状才是 85 GB/s）。选语言按算子分工：带宽受限的小算子用 Triton 或厂商语言融合，矩阵乘常规形状交给库，decode 的小 M 和注意力按情况手写或用厂商移植版，跨硬件维护一份代码时才牺牲性能换可移植性。
