第 2 篇里，网络的输入一直是数字：一个 x，或者一对甜度和酸度。可是语言模型的输入是文字。“我爱学AI”这几个字，要先变成数字，网络才能处理。这一篇（第 21–24 讲）就沿着这条路走一遍：文字先切成一个个小块，每块对应一个编号（这一讲）；编号再变成向量（第 22 讲）；模型根据这些向量预测下一个小块（第 23 讲）；一个接一个地预测，就生成了一段话（第 24 讲）。

这一讲回答第一步：**文字怎么切？**切出来的小块叫 **token**，切的过程叫**分词**（tokenization），负责切分的程序叫**分词器**（tokenizer）。我们会看到，今天的大模型几乎都用同一种思路：BPE，它是通过“数数”从数据里学出来的。

## 按字切，还是按词切

最直接的想法有两种。

**按字切**：每个字（英文是每个字母）一个 token。“我爱学AI”切成 我 / 爱 / 学 / A / I，五个 token。好处是词表很小，常用汉字几千个，英文字母加符号一百来个，而且任何文字都能切，不会遇到“不认识”的字。坏处是序列很长：一个英文单词要拆成好几个字母，模型要处理的 token 数成倍增加。后面会看到，模型的计算量和显存都随 token 数增长，序列长是很贵的。另外，单个字母几乎不带含义，模型得花很大力气才能从字母里拼出“词”的意思。

**按词切**：每个词一个 token。“我 / 爱 / 学 / AI”，四个 token，每个都有完整的含义。坏处是词表会非常大：光英文就有几十万个词形（play、plays、played、playing 各算一个），还有人名、地名、新词、拼写错误，永远也收不全。词表里没有的词，模型就完全不认识。中文还多一个麻烦：词与词之间没有空格，“按词切”本身就是个难题。

所以实际用的是两者之间的折中：**常见的字组合成一个 token，不常见的就拆开**。“推理”常常一起出现，就当成一个 token；一个罕见的人名，就拆成几个字甚至更小的单位。这种切法叫**子词**（subword）分词。剩下的问题是：哪些组合算“常见”？BPE 的回答是：从数据里数出来。

## BPE：把常一起出现的合并

**BPE**（Byte Pair Encoding，字节对编码）原本是一种数据压缩方法，后来被用来学分词规则。它的步骤只有两条，反复执行：

1. 数一数语料里所有**相邻的两个 token** 各出现了多少次。
2. 把出现次数最多的那一对，**合并成一个新 token**，加进词表，记下这条合并规则。

一开始，每个 token 都是单个字符。拿一段很小的语料来看：

<div class="ai-formula">我爱学AI。我爱推理。学AI的人爱推理。AI推理很快。我学推理。</div>

先按句号切成 5 段（合并不跨过句号），每段拆成单字。出现过的字有 11 个：我、爱、学、A、I、推、理、的、人、很、快，这就是初始的词表；整段语料一共 27 个 token。

**第 1 次合并。**数相邻的对：“推”后面跟“理”出现了 4 次（第 2、3、4、5 段各一次），是最多的。于是把“推 理”合并成新 token“推理”。语料变成：我 爱 学 A I / 我 爱 推理 / ……

**第 2 次合并。**重新数：“A I”出现了 3 次，最多。合并成“AI”。

**第 3 次合并。**这时出现最多的对都只有 2 次了：“我 爱”2 次，“学 AI”2 次，“爱 推理”2 次。次数相同，我们约定选在语料里最先出现的那一对：“我 爱”，合并成“我爱”。

**第 4 次合并。**“学 AI”2 次，合并成“学AI”。之后，所有相邻的对都只出现 1 次了，合并结束。

最后的词表是 11 个单字加 4 个合并出来的 token，共 15 个；语料从 27 个 token 缩短到了 16 个。

注意第 3、4 次合并的结果：“我爱”“学AI”并不是我们心目中的“词”。BPE 不懂语法，它只看哪些字经常挨在一起。在这段小语料里，“我爱”恰好出现了两次，就被合并了。语料大了以后，真正常见的组合（常用词、常见的词缀）会被优先合并，切出来的结果才会大体像“词”，但也总会有一些看起来奇怪的 token。

<Note kind="point">BPE 从单个字符出发，一遍遍地把最常相邻出现的两个 token 合并成一个新 token。合并多少次，词表就多出多少个 token；合并的规则和顺序都要记下来。</Note>

## 用学到的规则切新句子

学完规则，怎么切一句新的话？做法是：先拆成单字，然后**按学到的顺序**，把每条合并规则依次应用一遍。

拿“你爱学AI推理”试试。拆成单字：你 / 爱 / 学 / A / I / 推 / 理。应用第 1 条“推 + 理”：你 / 爱 / 学 / A / I / 推理。第 2 条“A + I”：你 / 爱 / 学 / AI / 推理。第 3 条“我 + 爱”：没有“我”，不变。第 4 条“学 + AI”：你 / 爱 / 学AI / 推理。最终切成 4 个 token。

每个 token 在词表里有一个编号：按初始单字的顺序编 0 到 10，合并出来的按合并顺序编 11 到 14。“爱”是 1，“学AI”是 14，“推理”是 11。这串编号，就是模型真正看到的输入。

问题出在“你”。它在训练语料里没出现过，不在词表里，没有编号。按字切和按词切会遇到的“不认识”问题，在这里也出现了。

## 从字节开始

真实的分词器用一个巧妙的办法彻底消灭了这个问题：**不从字符开始，而从字节开始**。

计算机里，所有文字最终都存成一串字节。最常用的编码 UTF-8 里，英文字母占 1 个字节（“A”是 41，用十六进制写），常用汉字占 3 个字节（“我”是 e6 88 91，“你”是 e4 bd a0）。一个字节只有 256 种可能的取值。所以，把初始词表设成这 256 个字节，**任何文字、任何符号、甚至表情符号，都一定能切成词表里的 token**，最坏的情况也就是退回到一个个字节。

在字节之上再做 BPE：常见汉字的 3 个字节会很快被合并成一个 token，常见的词再进一步合并；罕见的字可能保持 2 个或 3 个 token。这就是今天 GPT、Llama 等模型用的“字节级 BPE”（byte-level BPE）。

## 用代码复现

下面的代码用十几行实现了 BPE 的训练和切分，结果和演示一致；然后看了几个字符的 UTF-8 字节，最后算一下 Llama-3-8B 的词表要占多少参数。

```python
from collections import Counter

corpus = "我爱学AI。我爱推理。学AI的人爱推理。AI推理很快。我学推理。"
chunks = [list(c) for c in corpus.split("。") if c]       # 按句号切段，每段先拆成单字
base = list(dict.fromkeys(ch for c in chunks for ch in c)) # 初始词表：出现过的单字，按出现顺序
print("初始词表：", "".join(base), f"（{len(base)} 个），语料共 {sum(map(len, chunks))} 个 token")

def merge(seq, a, b):                                    # 把相邻的 a、b 合成一个 token
    out, i = [], 0
    while i < len(seq):
        if i + 1 < len(seq) and seq[i] == a and seq[i + 1] == b:
            out.append(a + b); i += 2
        else:
            out.append(seq[i]); i += 1
    return out

merges = []
while True:
    pairs = Counter(p for c in chunks for p in zip(c, c[1:]))   # 数相邻的一对；Counter 按第一次出现的顺序排
    (a, b), n = max(pairs.items(), key=lambda kv: kv[1])         # 次数相同时 max 取最先出现的
    if n < 2:
        break
    merges.append((a, b))
    chunks = [merge(c, a, b) for c in chunks]
    print(f"第 {len(merges)} 次：{a} + {b} → {a + b}（{n} 次）｜", " / ".join(" ".join(c) for c in chunks))

vocab = base + [a + b for a, b in merges]
tokens = list("你爱学AI推理")
for a, b in merges:                                      # 新句子：按学到的顺序逐条合并
    tokens = merge(tokens, a, b)
print("切分：", tokens, " 编号：", [vocab.index(t) if t in vocab else None for t in tokens])

# 真实的分词器从 UTF-8 字节开始合并：任何文字都能拆成 256 种字节之一
for ch in ["我", "A", "你"]:
    print(ch, "的 UTF-8 字节：", " ".join(f"{b:02x}" for b in ch.encode("utf-8")))

# 词表大小直接决定嵌入表和输出层的大小（Llama-3-8B：词表 128256，隐藏维度 4096）
V, d = 128256, 4096
print(f"嵌入表 + 输出层：2 × {V} × {d} = {2 * V * d / 1e9:.2f} B 个参数")
```

## 到了大模型里

Llama-3 的分词器是字节级 BPE，词表有 128256 个 token。词表大小是一个需要权衡的设计：

**词表越大，模型的两头越大。**第 22 讲会讲到，每个 token 在模型的入口有一行嵌入向量，在出口（输出层，第 33 讲）也有一列权重。Llama-3-8B 的隐藏维度是 4096，嵌入表和输出层合起来是 2 × 128256 × 4096 ≈ 10.5 亿个参数，占了整个模型的 13% 左右。而且第 16 讲说过，每生成一个 token，都要在整个词表上算一遍 softmax。

**词表越大，同样的文字切出来的 token 越少。**一个 token 能装下更多的字，一段话需要的 token 就少。这一点非常重要，因为几乎一切都按 token 计：模型能处理的上下文长度（比如 8K、128K）指的是 token 数；推理的计算量和第 8 篇要讲的 KV Cache 的显存，都和 token 数成正比；调用大模型 API 的价格，也是按输入、输出的 token 数收费的。同一段中文，用一个中文语料训练得充分的分词器，可能比用一个以英文为主的分词器少切出很多 token，推理就便宜、快得多。Llama-3 把词表从 Llama-2 的 32000 扩大到 128256，一个重要的目的就是提高这种“压缩率”。

**分词在 GPU 之外。**分词是在 CPU 上做的字符串处理，发生在模型计算之前。推理服务里，它通常不是瓶颈，但在请求量很大时，分词和反分词（把生成的编号还原成文字）也要占一部分 CPU 时间。

## 容易混淆的地方

1. **token 不等于字，也不等于词。**一个 token 可能是一个字、一个词、半个词、几个字节，甚至带着前面的空格（英文分词器里，“ the”和“the”常常是两个不同的 token）。说“这段话有多少 token”，一定要说清楚是用哪个分词器切的。
2. **编号本身没有大小的含义。**“学AI”是 14、“推理”是 11，不代表“学AI”比“推理”大。编号只是词表里的位置，像学号一样。下一讲会看到，模型是用编号去查表，而不是拿编号本身做计算。
3. **分词器和模型是绑定的。**模型训练时用的是哪个分词器，推理时就必须用同一个。换一个分词器，同样的编号对应的就是完全不同的 token，模型的输出会变成乱码。词表里还有一些特殊 token，比如表示“一段文本结束”的 `<eos>`（Llama-3 里写作 `<|end_of_text|>` 等），它们不对应任何文字，用来标记结构。

## 回顾

模型只能处理数字，所以文字要先切成 token，再换成编号。按字切词表小但序列长，按词切含义完整但词表无穷大，实际用的是折中的子词分词。BPE 从单个字符（真实系统里是 256 个字节）出发，反复把最常相邻出现的两个 token 合并成新 token，合并规则按顺序记下来；切新句子时，先拆开，再按顺序应用这些规则。从字节开始，就永远不会遇到不认识的字。词表大小是一个权衡：大了模型两头的参数多，但同样的文字切出的 token 少，而推理的成本、上下文的长度、API 的价格，全都按 token 计。

现在，“你爱学AI推理”变成了一串编号 [?, 1, 14, 11]。可编号只是词表里的位置，14 和 11 之间的距离、大小都没有意义。模型怎么从这些编号里得到能做计算、带着含义的东西？下一讲：**词嵌入**。
