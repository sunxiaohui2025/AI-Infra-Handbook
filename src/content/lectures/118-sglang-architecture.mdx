SGLang 和 vLLM 是今天用得最多的两个开源推理引擎。它最初来自一篇论文（Zheng 等，*SGLang: Efficient Execution of Structured Language Model Programs*），要解决的问题是：一个 LLM 应用往往不是一次调用，而是一串调用（多轮对话、思维链、先生成再检查、按 JSON 格式输出），这些调用之间共享大量的前缀，输出还要满足格式约束。论文提出了两样东西：**RadixAttention**（用一棵基数树做前缀缓存，自动复用任意请求之间的公共前缀）和**压缩的有限状态机**（加速约束解码）。后来的版本又加上了**零开销调度**（CPU 调度和 GPU 计算重叠）。

这一讲读这三样，以及 SGLang 的整体结构。读的是 2026 年 11 月 9 日 main 分支的提交 `48da6bd`（Apache-2.0 许可），只取下了 `srt/managers`、`srt/mem_cache`、`srt/model_executor`、`srt/constrained` 等几个目录。和上一讲一样，只读源码，没有运行。

## 三个进程

<EngineProcs engine="sglang" caption="图 118-1　SGLang 的进程结构：主进程（HTTP 和分词）、每张卡一个调度器进程（调度和执行模型在同一个进程里）、一个反分词进程。点“下一步”看一个请求的路径。" />

和 vLLM 一样，SGLang 也把分词、调度、反分词放在不同的进程里。最大的不同在中间：vLLM 的 EngineCore 只有一份，调度结果广播给各个 worker 进程；SGLang 是**每张卡一个调度器进程**，调度器和执行模型的 `TpModelWorker` 在同一个进程里。rank 0 从 ZMQ 收到请求后，用 `broadcast_pyobj` 发给其余的 rank（`managers/scheduler_components/request_receiver.py`），每个 rank 各自跑一遍同样的调度，得到同样的结果，然后各自执行。

这样做省掉了“调度结果每步跨进程发给 worker”这一步：调度器直接在本进程里调用模型。代价是每张卡都重复做一遍调度的 CPU 工作，并且必须保证各 rank 的调度结果完全一致。

## RadixAttention：前缀缓存是一棵树

第 110 讲、nano-vllm 和 vLLM 的前缀缓存都是“块哈希”：把序列切成固定大小的块，每块按“前面所有块 + 本块”算哈希，只能整块地命中。SGLang 换了一个数据结构：**基数树**（radix tree，压缩的前缀树）。

- 每个节点存一段 token（`key`）和这些 token 的 KV 在内存池里的槽位（`value`）。
- 从根到某个节点的路径，拼起来就是一段完整的前缀。
- 一个节点的孩子按第一个 token 区分，同一段公共前缀只存一次。

插入（第 712–767 行的 `_insert_helper`）和匹配几乎一样：沿树往下走，在分叉处劈开节点，最后把没匹配上的部分作为一个新的叶子挂上去。请求结束时，它的全部 token（提示 + 输出）都插入树中，KV 的槽位交给树管理，而不是还给内存池。下一轮对话进来时，就能匹配上整个上一轮。

### 内存：槽位是一个个 token，不是块

基数树的 `value` 是逐个 token 的槽位编号，这背后是 SGLang 的两级内存池（`mem_cache/memory_pool.py`）：

<CodeWalk file="third_party/sglang/python/sglang/srt/mem_cache/memory_pool.py" from={381} to={478} steps={[

第二级是 KV 池（`token_to_kv_pool`）：一个按槽位编号的大张量，存每一层每个 token 的 K、V。分配器在 `mem_cache/allocator` 里。打开 `page_size` 大于 1 时，分配、匹配和淘汰都按页对齐，粒度变粗，但有的注意力后端要求按页存（和 nano-vllm 的 256、vLLM 的块是同一类约束）。

把两种前缀缓存放在一起比较：

| | 块哈希（vLLM、nano-vllm、miniinfer） | 基数树（SGLang） |
| --- | --- | --- |
| 命中粒度 | 整块（16–256 个 token） | 1 个 token（或一页） |
| 查找 | 逐块算哈希、查表 | 沿树往下比较 token |
| 结构维护 | 哈希表 + 空闲队列 | 劈开、插入节点；锁要一路加到根 |
| 淘汰 | LRU 的空闲块队列，倒着还让前缀留得久 | 从叶子开始的 LRU，公共前缀自然最后被淘汰 |
| 跨机器共享 | 哈希可以跨进程稳定，便于做全局的 KV 池 | 需要额外给页算哈希（节点上的 `hash_value`） |
| 额外开销 | 每块一次哈希 | 树的 Python 操作，前缀很多时匹配较慢 |

两者在实际的命中率上差得并不多（块足够小时），差别更多在工程上：基数树天然适合“多轮对话、思维链分叉”这类前缀呈树状的负载；块哈希更简单，也更适合跨机器的 KV 共享。

两个值得注意的细节：等待队列超过 128 个请求时，lpm 会退化成 fcfs（`_determine_active_policy`，第 312 行），因为对每个请求做匹配再排序太慢了；这个提交里默认的策略是 fcfs（`srt/arg_groups/fields/schedule.py`），缓存感知的排序要显式打开。缓存感知的调度能提高命中率，但会让前缀不常见的请求等得更久，默认值偏向公平。

重叠有一个隐含的前提：调度第 i + 1 步时还不知道第 i 步采样出的 token。SGLang 让 GPU 上的输入直接引用第 i 步的输出张量（token 不回到 CPU 再送下去），所以 i + 1 步的输入在 GPU 上自然就是对的。这和 vLLM 的占位是同一个思路的两种写法。重叠模式默认打开，`--disable-overlap-schedule` 可以关掉。

### 调度规则：prefill 优先，可以混合

`get_next_batch_to_run`（`managers/scheduler.py` 第 4158 行）的主干是：先把上一步的 prefill 批并入运行中的 batch；然后尝试组一个新的 prefill 批（`get_new_batch_prefill`）；组得出来就跑 prefill，组不出来才跑 decode（`update_running_batch`，KV 不够时会“撤回”一部分请求，相当于抢占）。这和 nano-vllm 的 prefill 优先一样。打开 `--enable-mixed-chunk` 后，分块 prefill 的批可以把运行中的 decode 请求也带上（`mix_with_running`，第 4701 行），一步里混合两种，这又接近 vLLM 的做法了。

## 回顾

SGLang 和 vLLM 走到了相近的地方：都分了进程、都有分页（或逐 token）的 KV 和前缀缓存、都让调度和执行重叠、都支持投机解码和约束解码。差别主要在几处取舍：前缀缓存用树还是用哈希；调度结果是广播给 worker，还是每张卡各算一遍；prefill 和 decode 默认分开跑还是混着跑。读懂这些取舍背后的原因，比记住哪个引擎有哪个功能更有用，因为功能会互相借鉴，取舍的道理不会变。

下一讲把视野放宽：TensorRT-LLM、LMDeploy、llama.cpp 这些引擎各自的定位，以及 PD 分离、大规模专家并行在这些引擎里是怎么落地的。下一讲：**其他引擎与规模化部署**。
