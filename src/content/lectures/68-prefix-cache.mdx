真实的推理请求里，有大量重复的开头：

- **系统提示**：一个产品里所有的对话，开头都是同一段几百到几千 token 的系统提示（“你是某某助手，请遵守以下规则……”）。
- **多轮对话**：第 2 轮的输入，是第 1 轮的全部内容加上新的问题；第 10 轮的输入，包含了前 9 轮的全部历史。每一轮都把越来越长的历史重新送一遍。
- **长文档问答**：用户上传一份几万 token 的文档，接连问十几个问题，每个问题前面都是同一份文档。
- **智能体（Agent）**：一个任务里反复调用模型，每次的输入都是前面所有步骤的记录，再加上一点新内容。

第 61 讲的 KV Cache 只在一个请求的内部起作用，请求结束就释放了。下一个请求的开头即使一模一样，也要把这几千个 token 重新 prefill 一遍。**前缀缓存**（Prefix Caching）要做的，就是把这些已经算过的前缀的 KV Cache 留下来，让后面开头相同的请求直接复用。上一讲的分页让这件事变得自然：KV Cache 本来就是以块为单位、可以被多个请求共享的。

## 为什么可以复用

第 27 讲证明过：因为因果掩码，每个 token 在每一层的 k、v，**只取决于它自己和它前面的 token**。两个请求只要前 n 个 token 完全相同，它们这 n 个 token 的 KV Cache 就完全相同，不管后面接的是什么。

所以，只要能快速判断“这个新请求的开头，有多长和以前算过的某个请求一样”，这一段就可以直接复用，不用再算。

## 给每个块一个指纹：块级链式哈希的底层实现

怎么快速判断“开头相同”？如果对整段提示词直接算一个哈希，只要后面追加了一个新字，整个哈希值就彻底变了，根本无法复用前面的公共前缀；如果给每个 token 单独建哈希表，几十万个 token 的索引开销又太沉重，而且 GPU 显存是以 16 个 token 的物理块为单位分配的，单个 token 的命中无法在底层单独分配半个物理块。

所以，最佳的粒度是**块级别**（Block-level）。vLLM 等推理引擎给每个写满的物理块计算一个哈希值作为它的唯一“指纹”。

### 为什么必须是链式哈希

看到这里你可能会想：直接把当前块里的 16 个 token 拼起来算一个哈希不就行了吗？

我们看一个具体的例子。假设有两个不同的请求：
- 请求 A：`“你是一个专业的法文翻译助手：[前16个词] 苹果含有丰富的维生素……[中间16个词]”`
- 请求 B：`“你是一个严肃的儿童营养学专家：[前16个词] 苹果含有丰富的维生素……[中间16个词]”`

这两个请求在第 1 块（中间 16 个词）的内容完全一模一样，都是“苹果含有丰富的维生素……”。如果只对当前块的内容算哈希，这两个请求在第 1 块算出的哈希值是完全相等的。

但是，请求 B 能直接拿请求 A 的第 1 块 KV Cache 来用吗？**绝对不能**。

因为在 Transformer 的多层自注意力计算中，第 1 块里的每个 token，都在每一层中回头看了第 0 块的所有内容！请求 A 的第 1 块 Key 和 Value 向量融合了“法文翻译助手”的上下文信息，而请求 B 的第 1 块则需要融合“儿童营养学专家”的上下文信息。它们的 KV 向量在数值上差得十万八千里。如果强行复用，模型输出的结果就会彻底发疯。

结论是：**因果注意力决定了任何一个块的 KV Cache，都由从第 0 个 token 到该块末尾的全部因果历史共同决定。**

因此，哈希必须是**链式**（Chained）的：

<div class="ai-formula">`hash_0 = H(None, tokens[0:16], extra)`</div>
<div class="ai-formula">`hash_1 = H(hash_0, tokens[16:32], extra)`</div>
<div class="ai-formula">`hash_2 = H(hash_1, tokens[32:48], extra)`</div>

每一块的哈希输入，严格包含了**前一块的哈希输出**加上**当前块的 16 个 token**。

这样一来，每个块的哈希值在数学上就成了“从第 0 个 token 到当前块末尾”整段历史序列的全局唯一摘要。只要前面有任何一个 token 不同，或者顺序不同，后面的所有链式哈希就会全部不同。

公式里的 `extra` 是什么？它是环境元数据。即使输入 token 完全一样，如果请求 A 挂载了某个特定的微调适配器（LoRA），或者包含了不同的多模态图像特征，算出来的 KV 也是不同的。把 LoRA 标识符或环境盐值一起混入哈希计算，就能防止不同配置之间的缓存误命中。

### 调度器内部的查表与执行流转

在推理引擎的调度层内部，维护着一张全局哈希表：`全局映射表[块哈希] = 物理块编号`。

当一个新请求带着提示词到来时，调度器会严格执行以下五步：

1. **分块与前缀哈希计算**：调度器把请求的提示词按 16 个 token 一块切开（不足 16 个的尾部余数先不切），在 CPU 上迅速计算出一条链式哈希序列 `[hash_0, hash_1, hash_2, ...]`。这一步非常轻量，几十微秒就能算完。
2. **从头逐块查表，遇断则停**：调度器拿 `hash_0` 去全局哈希表查，如果命中了物理块 $P_7$，就继续查 `hash_1`……假设一直查到了 `hash_5`，但 `hash_6` 没有查到，**查找立即停止**。即使后面的 `hash_7` 在表里碰巧存在（比如一段通用的模版文字），也绝不能用，因为前面的因果链已经断了。
3. **物理块复用与引用加一**：命中的前 6 个物理块（包含前 $6 \times 16 = 96$ 个 token 的 KV）直接放进这个新请求的块表（`block_table`）里，这 6 个物理块的引用计数各加 1。
4. **部分 Prefill**：GPU 算力得到解放！那 96 个 token 的 Key 和 Value 向量已经在显存里躺着了，完全不需要重新计算。调度器只需要给未命中的剩余 token 分配新的物理块，并让 GPU 只对这部分新 token 进行 Prefill 计算。注意力算子拿到拼接好的块表，新 token 的 $Q$ 向量直接去查新老物理块中的所有 $K$ 和 $V$。
5. **新块登记入表**：未命中的部分计算完成后，其中新装满的物理块会继续沿着链式哈希公式算出它们自己的哈希值，登记进全局哈希表，留给以后的请求复用。

下面用一个缩小的例子看看（一个字当一个 token，每块 4 个 token）。4 个请求依次到达，共用同一段系统提示：

- **请求 1**：缓存是空的，31 个 token 全部要算，算完后留下 7 个整块。
- **请求 2**：系统提示加“问：”正好是 24 个字，6 个整块全部命中，只需要算剩下的 8 个 token。
- **请求 3**：多轮对话的第 2 轮，开头是请求 1 的全部内容。请求 1 的 7 个整块全部命中，28 个 token 不用再算；请求 1 最后那 3 个字所在的块没装满，没有被缓存，要重新算。
- **请求 4**：系统提示只把第一个字“你”换成了“您”。第 1 块的指纹变了，因为每块的指纹包含了前面的全部内容，**从第 1 块开始往后全都不命中**，31 个 token 全部重算。

## 缓存的生命周期：物理块如何跨请求存活

很多初学者看到这里会有一个根本性的疑问：**一个请求执行完毕、客户端连接都断开了，它的物理块为什么还能留在 GPU 显存里给下一个请求用？显存难道不回收吗？**

这正是前缀缓存设计的精巧之处。在引擎内部，一个物理块有三种不同的生存状态：

1. **活跃状态（Active）**：某个正在执行的请求正在读取或写入它，物理块的引用计数 `ref_count > 0`。这个块绝对受保护，不可被修改，更不可被回收。
2. **空闲保留状态（Inactive / Cached）**：当请求完成退出时，调度器遍历该请求的块表，把每个物理块的引用计数减 1。当引用计数降到 0 时，**引擎绝对不会调用 CUDA 函数释放显存，也不会清空显存里的数据！** 引擎只是把这个物理块放进一个由双向链表维护的**空闲 LRU 队列**（最近最少使用队列）中。此时，它在全局哈希表中的映射关系依然完好保留。
3. **被驱逐淘汰（Evicted）**：如果一段时间内没有新请求使用它，而且系统的物理显存完全耗尽、必须分配全新物理块时，调度器才会从 LRU 队列的头部（最久没被访问过的块）挑选牺牲者。此时才把它的哈希映射从全局哈希表中抹去，把它当作全新的空白块分配给急需显存的新请求。

也就是说，**只要显存还有空余，算过的 KV 就永远留在 GPU 显存里**。新请求到来时，如果算出的哈希命中了这些 `ref_count == 0` 的块，调度器就把它从 LRU 队列里“捞出来”，引用计数重新加 1，零成本实现了跨请求的“唤醒”。

而且淘汰总是自底向上进行的：优先淘汰前缀链条最末端的“叶子节点”。因为一旦中间某个块被淘汰，因果链断开，它后面的所有块即使还在显存里，也再也不可能被新请求命中了。

## 几个必须讲透的底层细节

在工程实践中，有几个技术细节至关重要，也是写好前缀缓存系统必须知道的边界：

### 1. 为什么未装满的末尾块绝不缓存

如果一个块只能装 16 个 token，而请求的提示词末尾只剩 5 个 token，这个未装满的块绝对不能登记到全局哈希表中。

因为这个块处于未定型状态，后续进入自回归生成阶段时，模型生成的新 token 还要继续往这个块的剩余槽位里写入。如果把它提前缓存并共享给其他请求，其他请求并发写入时就会产生严重的数据覆盖冲突。因此，前缀缓存的命中粒度永远是 16 个 token 的整数倍。

### 2. 整段提示完全命中时，为什么最后一个 token 仍然必须重算

假设一个用户发来一段长达 2000 个 token 的文本，碰巧前 125 个物理块在显存里全部命中（$125 \times 16 = 2000$）。引擎是不是可以 100% 跳过 Prefill 阶段，直接开始输出回答？

答案是：**不能！提示词的最后一个 token 必须单步执行一次前向计算**。

这是很多教程没有讲透的底层原理：生成第一个回答 token 所需的概率分布（Logits），来自于提示词的**最后一个 token 经过最后一层 Transformer 后输出的隐藏状态**（Hidden State），再与词表头投影矩阵（LM Head）相乘得到。

而 KV Cache 里面存储的，仅仅是自注意力层内部的 Key 向量和 Value 向量，**压根没有保存最后一层的输出隐藏状态或 Logits**！

如果把整段提示词完全跳过不计算，模型手里根本没有最后一个词的 Logits，就无法通过采样得到第一个生成的词。因此，在底层实现中，前缀缓存最多只能复用前 `prompt_len - 1` 个 token 的 KV，最后一个 token 必须单步走一遍前向计算（以这个 token 为 $Q$，去读前面命中缓存的所有 $K$ 和 $V$），从而拿到它的输出 Logits 来采样出第一个回答 token。

### 3. 写时复制（Copy-on-Write）

当多个请求共享了一段前缀的物理块后，各自开始独立生成回答。由于各个回答的内容不同，它们各自生成的后续 token 必须写入各自私有的物理块中。如果前缀共享部分的最后一个块刚好未满且需要被写入，引擎必须触发写时复制，先为该请求单独复制一份物理块，再往新块里写入数据，确保原本只读共享的前缀物理块不被破坏。

## 能省多少

命中的部分不用 prefill，直接省下的是计算和 TTFT。拿 Llama-3-8B、一张 H100（第 60 讲的估算）算一个典型的情况：系统提示 2000 个 token，用户的问题 100 个 token。

- **不命中**：prefill 2100 个 token，约 31.9 ms（计算受限）。
- **命中系统提示**：只需要 prefill 100 个 token，约 4.8 ms（此时已经变成了读一遍权重的时间）。

TTFT 降到了约六分之一。多轮对话和长文档问答的收益更大：第 10 轮对话时，前面 9 轮的几千个 token 全部命中，只需要算最新的那几十个 token。

省下的计算也直接变成了成本的下降（第 64 讲）。这也是为什么很多大模型 API 对“命中缓存的输入 token”大幅打折：服务商真的不用为它们花多少算力。

## 另一种组织方式：前缀树（RadixAttention）

除了 vLLM 的块级哈希表，SGLang 提出了另一种组织方式，叫 **RadixAttention**：把所有缓存的前缀组织成一棵**基数树**（Radix Tree，一种压缩前缀树）。

树的根节点是空的，树枝上的每一条路径代表一段 token 序列，树节点中保存着这段序列对应的物理 KV 块指针。
- **前缀匹配**：新请求进来，沿着基数树自顶向下比对 token。匹配到哪里，哪里之前的物理块就直接命中；
- **分叉与合并**：当新请求在某个节点中间产生分歧时，基数树会自动把该节点拆分为两个子节点（分叉）；当某个分支被释放或变空时又可以合并；
- **淘汰机制**：当显存吃紧需要腾空间时，基数树从最深层的叶子节点开始按 LRU 顺序剪枝，永远不会误删公共的前缀根节点。

我们把两种实现方式对照来看：

| 对比维度 | vLLM（块级哈希表） | SGLang（RadixAttention 基数树） |
| --- | --- | --- |
| **核心数据结构** | 扁平哈希表（`Hash -> Block`） | 压缩前缀树（Radix Tree） |
| **命中粒度** | 块级别（固定 16 个 token） | 可支持细粒度到单个 token |
| **前缀共享机制** | 链式哈希 + 物理块引用计数 | 树的父子节点继承 + 读写锁 |
| **本质** | 完全相同：依靠因果掩码的确定性，按 token 前缀复用物理 KV Cache | 完全相同：依靠因果掩码的确定性，按 token 前缀复用物理 KV Cache |

哈希表的好处是实现简单、查询复杂度稳定是 $O(1)$，天然与物理块对齐；基数树的好处是结构上天然契合多分支搜索、智能体多轮探索（如 MCTS 搜索树），而且能更自然地做到单 token 级别的精细复用。

## 用代码复现

下面的代码实现了按块算链式哈希、逐块查表的前缀缓存，模拟了上面 4 个请求；最后用第 60 讲的方法估算命中前后的 prefill 时间。

```python
import hashlib

B = 4                                                    # 每块 4 个 token（这里用一个字当一个 token，方便看）

def block_hashes(tokens):
    """只给装满的块算哈希；每块的哈希 = 哈希(前一块的哈希 + 这一块的内容)，所以它代表“从开头到这一块为止的全部内容”。"""
    hs, parent = [], ""
    for i in range(len(tokens) // B):
        parent = hashlib.sha256((parent + "|" + tokens[i * B:(i + 1) * B]).encode()).hexdigest()[:8]
        hs.append(parent)
    return hs

cache = set()                                            # 已经算过、还留在显存里的块（按哈希索引）
def serve(name, text):
    hs = block_hashes(text)
    hit = 0
    for h in hs:                                         # 从头开始找，遇到第一个没命中的块就停
        if h in cache: hit += 1
        else: break
    cache.update(hs)                                     # 算完以后，这个请求的块也留在缓存里
    print(f"{name}：{len(text)} 个 token，{len(hs)} 个整块，命中 {hit} 块（{hit * B} 个 token 不用再 prefill），要算 {len(text) - hit * B} 个")

sys_prompt = "你是一个乐于助人的助手，请用简洁的中文回答。"
serve("请求 1", sys_prompt + "问：什么是注意力？")
serve("请求 2", sys_prompt + "问：什么是残差连接？")
turn1 = sys_prompt + "问：什么是注意力？答：每个词按相关程度收集其他词的信息。"
serve("请求 3（多轮的第 2 轮）", turn1 + "问：那多头注意力呢？")
serve("请求 4（系统提示改了第一个字）", "您" + sys_prompt[1:] + "问：什么是注意力？")

# Llama-3-8B + H100：系统提示 2000 个 token、问题 100 个时，命中与不命中的 prefill 时间（第 60 讲的估算）
def prefill_ms(n):
    return max(2 * 7.5e9 * n / 989e12, 16.06e9 / 3.35e12) * 1e3
print(f"不命中：prefill 2100 个 token ≈ {prefill_ms(2100):.1f} ms；命中系统提示：只算 100 个 ≈ {prefill_ms(100):.1f} ms")
```

输出：

```text
请求 1：31 个 token，7 个整块，命中 0 块（0 个 token 不用再 prefill），要算 31 个
请求 2：32 个 token，8 个整块，命中 6 块（24 个 token 不用再 prefill），要算 8 个
请求 3（多轮的第 2 轮）：60 个 token，15 个整块，命中 7 块（28 个 token 不用再 prefill），要算 32 个
请求 4（系统提示改了第一个字）：31 个 token，7 个整块，命中 0 块（0 个 token 不用再 prefill），要算 31 个
不命中：prefill 2100 个 token ≈ 31.9 ms；命中系统提示：只算 100 个 ≈ 4.8 ms
```

前四行就是 4 个请求的命中情况，和演示一致：请求 2 命中 6 块，请求 3 命中 7 块，请求 4 一块也没命中。最后一行是 Llama-3-8B 上的 prefill 时间：31.9 ms 对 4.8 ms。

## 到了大模型里：从单请求到 Agent 做到 95% 缓存命中

前缀缓存最能发挥威力的地方，是智能体（Agent）场景。

一个典型的 Agent 循环包含大量循环迭代：
$$\text{[系统提示 + 工具定义]} + \text{[多轮历史步骤]} \rightarrow \text{模型输出工具调用} \rightarrow \text{执行工具并追加结果} \rightarrow \text{再次调用模型}$$

在每一轮中，模型的输入都是“上一轮的全部内容加上一小段工具执行结果”，而模型输出的工具调用指令通常只有几十个 token。输入和输出的 token 数量可以相差一到两个数量级。这意味着绝大部分输入都是前缀重复！

前缀缓存命中的理论上限非常高：
$$\text{命中率上限} \approx \frac{\text{上下文总长} - \text{本轮新增长度}}{\text{上下文总长}}$$

例如上下文已经积累到了 50K token，本轮工具结果只增加了 1K token，理论命中率上限高达 $98\%$。在实际生产系统中，很多优化良好的 Agent 都能稳定做到 $90\%$ 到 $95\%$ 的缓存命中率。

但是，要达到这个数字，必须遵循严格的工程规则：

1. **易变内容绝对后置**：所有规则的核心都在于“前缀必须逐 token 绝对稳定”。最常见的反面例子是在系统提示的第一行写上 `“当前时间：2026-11-08 09:38:00”` 或动态生成的 `Session-ID`。由于第一块的第一个 token 每秒都在变，链式哈希从第 0 块就彻底崩塌，后续 5 万个 token 的命中率直接归零！任何动态时间戳、随机数、用户信息，真要使用必须放到输入的最末端。
2. **上下文只追加（Append-Only）**：严禁随意修改、删除或重新排序历史消息。常见的错误做法是“滑动窗口截断”——每轮为了省显存把最老的一条消息删掉。老消息一删，后面所有的 token 往前平移几位，位置编码一变，链式哈希完全不匹配，导致前缀大面积失效。
3. **序列化必须确定**：JSON 字段顺序、空格缩进、换行符、浮点数格式必须保持严格一致。在程序逻辑上虽然 `{"a": 1, "b": 2}` 和 `{"b": 2, "a": 1}` 语义完全相同，但分词出来的 token 序列完全不同，哈希表无法命中。
4. **工具定义不要中途动态增删**：工具定义（Tool Schemas）通常位于提示词非常靠前的位置。如果在第 3 轮临时加了一个新工具，后面的所有前缀缓存全部报废。规范的做法是保持工具定义列表始终固定，如果在某些步骤需要限制模型调用的工具，通过约束解码（第 71 讲）在采样时屏蔽非法 token，而不是修改提示词。
5. **网关层做会话粘性路由（Cache-aware Routing）**：GPU 显存里的前缀缓存是单台机器独立的。如果你的服务部署了 10 台 8 卡实例，而网关层采用随机轮询做负载均衡，那么用户连续两次请求落到同一台机器的概率只有 $10\%$，前缀缓存命中率直接跳水。网关必须根据用户会话 ID 或前缀哈希进行会话保持，把相同的会话粘在同一台实例上（第 102 讲）。

## 容易混淆的地方

1. **只能复用前缀，不能复用中间的片段。**两个请求中间有一段相同的内容，但前面不同，这段内容的 KV Cache 也不同（每个 token 的 k、v 取决于它前面的全部内容），不能复用。
2. **复用的是 KV Cache，不是答案。**前缀缓存只省 prefill 的计算，模型还是要为新请求生成全新的回答。它和“相同的问题直接返回上次的答案”的语义缓存（Semantic Cache）是两回事。语义缓存不进模型、答案可能不准；前缀缓存进模型、计算结果与不缓存完全一致。
3. **位置也要一致。**同样的内容出现在不同的位置（比如前面多了一个 token），位置编码不同，KV Cache 也不同（第 25、37 讲）。所以只有从头开始完全相同的部分才能命中。

## 回顾

很多请求有相同的开头：系统提示、多轮对话的历史、同一份长文档。因果掩码保证相同前缀的 KV Cache 完全相同，所以可以算一次、存起来复用。vLLM 给每个装满的物理块（16 个 token）计算链式哈希作为指纹，把上一块的指纹作为本块的输入，从数学上保证它代表了从开头到该块末尾的完整因果上下文；新请求从头逐块查表，命中的物理块直接放进块表，只对剩下未命中的部分做 Prefill。引用计数降到 0 的物理块不会被立即释放，而是保留在显存的空闲 LRU 队列中，随时等待被后续相同前缀唤醒。SGLang 则用基数树（Radix Tree）以树状结构组织前缀，支持细粒度的节点匹配与剪枝。在 Agent 场景中，只要遵守“易变内容后置、上下文只追加、粘性路由”等规则，缓存命中率可高达 95% 以上，大幅降低延迟与硬件开销。

前缀缓存能让很多请求跳过一大段 prefill。可没有命中的长提示怎么办？一个几万 token 的 prefill 要算好几秒，这期间所有正在 decode 的请求都被卡住了。下一讲：**Chunked Prefill**。
