到目前为止，我们估算 decode 一步的时间，只看 GPU：读一遍权重、读一遍 KV Cache，除以带宽（第 68 讲）。可 GPU 上的每个 kernel，都是 CPU 一个一个发射过去的。第 83 讲数过，一层 Transformer 里有十几个 kernel，32 层加起来就是好几百个。如果 CPU 发射一个 kernel 要几微秒，几百个就是好几毫秒，和 GPU 真正计算的时间差不多了。

这一讲讲这种“CPU 跟不上 GPU”的情况什么时候会发生，以及推理引擎怎么用 **CUDA Graph** 消除它。

## CPU 发射，GPU 执行

在 PyTorch 里写 `y = x @ w`，背后发生的是：Python 解释器执行这一行，PyTorch 检查张量的形状、类型、设备，选出合适的 kernel，准备好参数，再通过 CUDA 驱动把这个 kernel 放进 GPU 的任务队列。这一整套在 CPU 上要花几微秒到十几微秒。这种逐个算子执行的方式，叫 **eager 模式**。

好在发射是**异步**的：CPU 把 kernel 放进队列就返回，不等 GPU 算完，接着发射下一个。GPU 从队列里一个接一个地取出来执行。只要 CPU 发射得比 GPU 执行得快，CPU 就会一路跑在前面，队列里总有活，GPU 不会停下来，发射开销被完全藏住了。

反过来，如果 GPU 执行一个 kernel 的时间比 CPU 发射一个还短，GPU 算完这一个，下一个还没发过来，只能空等。这时一步的时间就由 CPU 决定了：**一步 ≈ kernel 数 × 每次发射的 CPU 时间**，GPU 算得再快也没用。

## 什么时候 CPU 会跟不上

代码里用一个粗略的模型估算了几种情况（批大小 1 的 decode；每层 4 个矩阵乘法按读权重的时间算，另有 11 个约 2 μs 的小 kernel；假设 eager 模式下 CPU 发射一个 kernel 约 8 μs，这些数字只代表量级）：

- **Llama-3-8B，1 张卡**：481 个 kernel，GPU 计算约 5.18 ms；CPU 发射全部要 481 × 8 μs ≈ 3.85 ms，比 GPU 快，发射被藏住了，eager 一步约 5.19 ms，GPU 几乎一直在忙。
- **Llama-3-8B，8 张卡张量并行**（第 13 篇）：权重分到 8 张卡上，每张卡的矩阵乘法只剩八分之一，每层又多了 2 次卡间通信，一共 545 个 kernel，GPU 只需约 **1.93 ms**；可 CPU 发射要 545 × 8 μs ≈ 4.36 ms，eager 一步约 **4.40 ms**，GPU 有一半多的时间在空等。
- **Llama-3.2-1B，1 张卡**：小模型，241 个 kernel，GPU 约 1.09 ms，eager 一步约 2.08 ms，GPU 只忙了一半。

规律是：**模型越小、并行的卡越多、批越小，每个 kernel 越短，CPU 越容易成为瓶颈。**而这些正是延迟敏感的在线服务常见的情况。GPU 越来越快，CPU 却没有快那么多，这个问题只会越来越明显。

## CUDA Graph：录一次，放很多次

decode 的每一步，执行的 kernel 序列几乎一模一样：同样的几百个 kernel，同样的顺序，只是输入的数据不同。既然如此，何必每一步都让 CPU 重新走一遍 Python、PyTorch、驱动的流程？

**CUDA Graph** 就是为此设计的。它分两个阶段：

1. **捕获**（capture）：让 CPU 照常执行一遍这一步，但 kernel 不真正执行，而是被记录下来：哪些 kernel、什么顺序、什么参数、读写哪些显存地址，组成一张“图”。
2. **回放**（replay）：之后每一步，CPU 只需要一次调用，把整张图交给 GPU。GPU 按图一个接一个地执行这几百个 kernel，中间没有 CPU 参与。

回放一张图，CPU 只花几十微秒。上面的例子里，8 卡张量并行时一步从约 4.40 ms 降到约 **1.95 ms**，1B 模型从约 2.08 ms 降到约 1.11 ms，GPU 几乎一直在忙。

下面的时间线把 CPU 和 GPU 画成两条线。eager 模式下，CPU 那条线上每一小段是发射一个 kernel，GPU 那条线上每一小段是执行一个 kernel；GPU 线上的空白就是在等 CPU。换一换模型，调一调 CPU 发射的时间看看。

## 代价：形状和地址都要固定

CUDA Graph 录下的是具体的 kernel 和具体的显存地址。回放时不能改变这些东西，这带来几个限制：

**输入要放在固定的地址。**每一步的输入（token、位置、块表）不能新建张量，而要先拷贝到捕获时用的那块“静态”缓冲区里，再回放。输出也写在固定的位置。

**形状要固定。**一张图对应一个固定的批大小。可连续批处理里，每一步的批大小都在变（第 74 讲）。vLLM 的做法是预先为一组批大小（比如 1、2、4、8、16、24、32……直到几百）各捕获一张图；实际的批大小是 13 时，就补齐到 16，用 16 的那张图，多出来的 3 个位置算了也不用。

**不能有 CPU 端的判断。**图里不能有“根据中间结果，CPU 决定下一步调哪个 kernel”的逻辑。所以一步里依赖动态信息的部分要放在图外面。

**占显存，也要时间。**每张图都要预留它用到的中间缓冲区，捕获几十张图，启动时要多花几十秒，也要占一些显存。vLLM 启动日志里的 “Capturing CUDA graphs” 就是在做这件事；调试时可以用 `enforce_eager` 关掉它，看看差别。

**prefill 通常不用。**prefill 的 token 数每次都不同，变化范围又大，不适合按形状预先捕获。好在 prefill 的 kernel 都很大，GPU 时间远大于发射时间，本来也不需要。vLLM 的新版本还把模型切成几段，注意力（形状最不固定）留在图外，其余部分用图，这叫分段的 CUDA Graph。

## 固定地址的代价：输入复制

上面说输入要先拷到捕获时的静态缓冲。这次拷贝要多久，会不会把省下的时间吃掉？算一个例子：普通执行时 GPU 计算 20 μs，再加上等主机逐个提交的 20 μs，一共 40 μs；改成图重放，重放加准备元数据只要 5 μs，原本能省 15 μs。

可新输入要先拷到图记录的地址。拷贝读一遍源、写一遍目标，按 RTX PRO 6000 的显存带宽 1792 GB/s：

- 输入 [256, 4096] 的 BF16 是 2 MiB，拷贝约 **2.3 μs**，图执行共 27.3 μs，比普通执行少 12.7 μs。
- 输入 [2048, 4096] 是 16 MiB，拷贝约 **18.7 μs**，图执行共 43.7 μs，**比普通执行还慢**。

省下的主机时间是固定的 15 μs，拷贝时间却随输入变大。两者相等时 2X ÷ B = 15 μs，临界输入 X ≈ **12.8 MiB**。所以选哪些操作放进一张图，要同时比较省下的提交时间和多出来的拷贝时间。更好的做法是让上游算子直接写进图的固定缓冲，这次拷贝就没了。

## GPU 越快，越要看主机

第 66 讲的时间线里，GPU 等主机的时间一直存在。把它写成流水来算：一共 100 段工作，每段主机准备 20 μs、GPU 计算 20 μs。严格串行要 4000 μs；主机准备下一段时 GPU 算当前段，变成流水，只要 **2020 μs**。

现在把 GPU 计算缩短到 5 μs。主机仍然每 20 μs 才准备好一段，总时间是 **2005 μs**，只少了 15 μs：GPU 越快，等得越久。只有把主机准备也压到 5 μs，才降到 **505 μs**。流水的节拍由较慢的一侧决定，这和第 86 讲的双缓冲是同一个规律。

vLLM 在 2024 年 9 月的 v0.6.0 版本就遇到了这个问题。发布前的剖析显示：单张 H100 跑 Llama-3-8B 时，一步里 API 服务器占 33%，调度占 29%，GPU 执行只占 38%。原因是 API 服务器和推理引擎在同一个 Python 进程里，两者争用 GIL（Python 的全局解释器锁）。v0.6.0 做了三件事：把 API 服务器拆到单独的进程、用消息队列通信；多步调度，一次调度连续跑几步；输出处理改成异步，和下一步的执行重叠。8B 的吞吐提高到原来的 **2.7 倍**，70B 提高到 1.8 倍。这些改动没有碰任何 kernel，也没有换硬件。

能复用的不只是提交序列，还有提交之前的准备。推理算子库 FlashInfer 把注意力分成 plan（按本步每个请求的长度和 KV 的位置选 kernel、划分任务、安排工作区，并把这些元数据拷到 GPU）和 run（按计划执行）两步。同一步里 36 层的请求长度和 KV 布局都一样，可以共用一份 plan。在 RTX PRO 6000 上的对照中，从每层都 plan 改成只 plan 一次，36 层注意力的时间从约 2.0 ms 降到 0.72 ms，主机到 GPU 的拷贝从 144 次降到 4 次，GPU 上的 kernel 数没变。反过来，请求长度变了就必须重新 plan，沿用旧计划会算错。

## 怎么计时才对

最后补一个容易出错的地方：同一次调用，在不同的位置计时，得到的是三种不同的时间。设 CPU 用 3 μs 提交全部任务，GPU 依次做 H2D 8 μs、kernel 20 μs、D2H 4 μs：

- 在异步调用的前后读 CPU 时钟，测到的是**提交时间**：3 μs。
- 用 CUDA event 在 GPU 的任务流里打点，测到的是**GPU 执行时间**：kernel 20 μs。
- 等结果回到 CPU 才停表，测到的是**结果可用的时间**：第 35 μs。

把 kernel 优化到 5 μs，快了 4 倍，结果却是在第 20 μs 可用，整次调用只快了 1.75 倍，剩下的 15 μs 是提交和拷贝。所以报告加速比时，要说清楚是从哪里计到哪里。用 profiler 把主机调用、GPU 计算和拷贝画在同一条时间线上，才能看清时间花在哪一段。

## 其他省 CPU 时间的办法

CUDA Graph 解决的是“发射 kernel”的开销。一步里 CPU 上还有别的事：调度器决定这一步跑哪些请求、准备输入张量、采样后处理（第 81 讲）。推理引擎也在想办法压缩或藏住它们：

- **算子融合**（第 83 讲）直接减少了 kernel 的数量。
- **torch.compile** 把模型编译成更少、更大的 kernel，还可以和 CUDA Graph 一起使用。
- **CPU 和 GPU 重叠**：GPU 在执行第 n 步时，CPU 就开始为第 n + 1 步做调度和输入准备，而不是等第 n 步结束。vLLM 和 SGLang 都有这类“异步调度”或“重叠调度”的机制。
- **把 Python 挪出热路径**：调度逻辑、输入准备尽量用向量化的张量操作，甚至用 C++ 实现。

## 用代码复现

下面的代码按上面的粗略模型，模拟 CPU 逐个发射、GPU 按顺序执行的过程：GPU 开始一个 kernel 的时刻，是“它被发射完”和“GPU 做完上一个”中较晚的那个。分别算 eager 和 CUDA Graph 下一步的时间。

```python
# decode 一步（批大小 1）里的 kernel：CPU 逐个发射，GPU 按顺序执行。粗略模型，数字是假设的量级
BW = 3.35e12                                             # H100 显存带宽
SMALL, LAUNCH, GRAPH = 2e-6, 8e-6, 20e-6                 # 小 kernel 在 GPU 上约 2 μs；eager 模式 CPU 发射一个 kernel 约 8 μs；回放一张图约 20 μs

def kernels(d, dff, L, kv_dim, vocab, tp=1):
    """每层：4 个矩阵乘法（读权重，时间 = 字节 ÷ 带宽），11 个小 kernel（归一化、RoPE、注意力、激活、相加……）；多卡时每层多 2 次 all-reduce。"""
    ks = []
    for _ in range(L):
        for rows, cols in [(d + 2 * kv_dim, d), (d, d), (2 * dff, d), (d, dff)]:
            ks.append(max(SMALL, rows * cols * 2 / tp / BW))
        ks += [SMALL] * 11 + ([10e-6] * 2 if tp > 1 else [])
    return ks + [vocab * d * 2 / tp / BW]                 # 最后的输出层

def step(ks, graph):
    cpu, gpu = (GRAPH, 0.0) if graph else (0.0, 0.0)
    for g in ks:
        if not graph: cpu += LAUNCH                      # eager：CPU 发射完这个 kernel，GPU 才能开始它
        gpu = max(gpu, cpu) + g
    return gpu

print("模型 | kernel 数 | GPU 真正在算的时间 | eager 一步 | CUDA Graph 一步")
for name, cfg in [("Llama-3-8B，1 张卡", (4096, 14336, 32, 1024, 128256, 1)),
                  ("Llama-3-8B，8 张卡张量并行", (4096, 14336, 32, 1024, 128256, 8)),
                  ("Llama-3.2-1B，1 张卡", (2048, 8192, 16, 512, 128256, 1))]:
    ks = kernels(*cfg)
    busy, e, g = sum(ks), step(ks, False), step(ks, True)
    print(f"{name} | {len(ks)} | {busy * 1e3:.2f} ms | {e * 1e3:.2f} ms（GPU 忙 {busy / e:.0%}） | {g * 1e3:.2f} ms（GPU 忙 {busy / g:.0%}）")
```

输出：

```text
模型 | kernel 数 | GPU 真正在算的时间 | eager 一步 | CUDA Graph 一步
Llama-3-8B，1 张卡 | 481 | 5.18 ms | 5.19 ms（GPU 忙 100%） | 5.20 ms（GPU 忙 100%）
Llama-3-8B，8 张卡张量并行 | 545 | 1.93 ms | 4.40 ms（GPU 忙 44%） | 1.95 ms（GPU 忙 99%）
Llama-3.2-1B，1 张卡 | 241 | 1.09 ms | 2.08 ms（GPU 忙 52%） | 1.11 ms（GPU 忙 98%）
```

三行分别对应上面的三种情况。Llama-3-8B 单卡时，eager 和 CUDA Graph 几乎一样（5.19 ms 对 5.20 ms），因为 CPU 发射本来就跑在前面；8 卡并行和 1B 模型时，eager 的 GPU 只忙了 44% 和 52%，用 CUDA Graph 后接近 100%。

这个模型里每个数字都是假设的量级：实际的发射开销取决于 CPU、框架和驱动，从两三微秒到十几微秒不等；小 kernel 的执行时间也取决于具体的实现。真实的情况要用 Profiler 看时间线（第 66 讲）。

第二段代码复现这一讲后半部分的数字：主机准备与 GPU 计算的流水、三种计时位置，以及图重放的输入复制与临界大小。

```python
# 1. 主机准备和 GPU 计算流水：100 段，谁慢谁决定节拍
def pipe(host, gpu, n=100): return host + (n - 1) * max(host, gpu) + gpu
print(f"串行 {100*(20+20)} μs；流水 {pipe(20, 20)} μs；GPU 提速到 5 μs：{pipe(20, 5)} μs；主机也到 5 μs：{pipe(5, 5)} μs")

# 2. 一次调用的三种计时：提交 3 μs，H2D 8 μs，kernel 20 μs，D2H 4 μs
for k in [20, 5]:
    print(f"kernel {k:>2} μs：CPU 提交用 3 μs，GPU 计时 {k} μs，结果在第 {3 + 8 + k + 4} μs 可用")
print(f"kernel 快 4 倍，整次调用只快 {(3+8+20+4)/(3+8+5+4):.2f} 倍")

# 3. CUDA Graph 要先把新输入复制到图记录的地址：复制要读一遍、写一遍
BW, saved = 1792e9, 15e-6                       # RTX PRO 6000 显存带宽；图重放省下的主机准备时间
for rows in [256, 2048]:
    x = rows * 4096 * 2
    copy = 2 * x / BW
    print(f"输入 [{rows}, 4096]（{x/2**20:.0f} MiB）：复制 {copy*1e6:4.1f} μs，图执行共 {(5e-6 + copy + 20e-6)*1e6:.1f} μs（普通执行 40 μs）")
print(f"输入小于 {saved * BW / 2 / 2**20:.1f} MiB 时，图重放才划算")
```

输出：

```text

kernel 20 μs：CPU 提交用 3 μs，GPU 计时 20 μs，结果在第 35 μs 可用
kernel  5 μs：CPU 提交用 3 μs，GPU 计时 5 μs，结果在第 20 μs 可用
kernel 快 4 倍，整次调用只快 1.75 倍
输入 [256, 4096]（2 MiB）：复制  2.3 μs，图执行共 27.3 μs（普通执行 40 μs）
输入 [2048, 4096]（16 MiB）：复制 18.7 μs，图执行共 43.7 μs（普通执行 40 μs）
输入小于 12.8 MiB 时，图重放才划算
```

对照正文：流水 2020 μs，GPU 提速后 2005 μs，主机也提速后 505 μs；kernel 快 4 倍、整次调用只快 1.75 倍；2 MiB 输入图执行 27.3 μs，16 MiB 输入 43.7 μs，临界约 12.8 MiB。

## 容易混淆的地方

1. **CUDA Graph 不让 kernel 本身变快。**它省的是 kernel 之间的空隙。如果 GPU 本来就没有空等（大模型、大批量、prefill），用不用 CUDA Graph 差别不大。
2. **“GPU 利用率 100%”不代表 GPU 在全力计算。**`nvidia-smi` 显示的利用率，只表示这段时间里有 kernel 在运行，哪怕是一个只用了几个 SM 的小 kernel。看 GPU 有没有空等，要看 Profiler 的时间线。
3. **异步发射意味着 CPU 上测的时间不准。**CPU 发射完就返回，在 Python 里用计时器量 `y = x @ w`，量到的只是发射时间。要测 GPU 上的真实时间，需要先同步（`torch.cuda.synchronize()`），或者用 CUDA 事件计时。

4. **图重放不总是更快。**新输入要先拷到图的固定地址，输入大到一定程度（本例约 12.8 MiB），拷贝时间就超过了省下的提交时间。
5. **kernel 的加速比不等于调用的加速比。**提交、拷贝和同步不随 kernel 变快；计时的起止位置不同，测到的是不同的东西。

## 回顾

GPU 上的每个 kernel 都由 CPU 发射。eager 模式下，每发射一个要经过 Python、框架和驱动，花几微秒；发射是异步的，只要 CPU 跑在 GPU 前面，这些开销就被藏住了。可是模型小、多卡并行、批量小时，每个 kernel 只要一两微秒，CPU 发射不过来，GPU 就在 kernel 之间空等：Llama-3-8B 8 卡张量并行时，GPU 只需 1.93 ms 的一步，eager 要 4.40 ms。CUDA Graph 把一整步的 kernel 序列捕获成一张图，之后每步只发射一次，一步降到约 1.95 ms。代价是输入地址和形状要固定，所以要按一组批大小分别捕获、实际批大小向上补齐，prefill 一般不用。

主机和 GPU 是一条流水，节拍由较慢的一侧决定：GPU 从 20 μs 提速到 5 μs，主机仍要 20 μs，100 段工作只从 2020 μs 降到 2005 μs。vLLM v0.6.0 把 API 服务器拆出进程、多步调度、异步输出处理，没改任何 kernel，吞吐就提高到 2.7 倍。图重放的输入要拷到固定地址，输入超过约 12.8 MiB 时拷贝就吃掉了全部收益。

第 11 篇到这里结束了。我们看到，推理快不快，最后往往落在“读写了多少字节”上：权重、KV Cache、中间结果。既然读写的字节决定了速度，能不能让每个数本身占的字节少一点？把 16 位的权重换成 8 位、4 位，速度和显存会怎样，精度又会损失多少？下一讲进入第 12 篇：**量化基础**。
