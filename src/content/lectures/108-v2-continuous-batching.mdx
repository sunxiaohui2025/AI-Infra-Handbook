v1 的 decode 每步约 65 ms，几乎全花在把 3 GB 的权重从内存读一遍上，而这一遍读取只为一个请求算出一个 token。第 62 讲算过：decode 是读内存受限的，batch 里多放几个请求，读一遍权重就能同时为它们各算一个 token，每步的耗时增加得很少。

v1 的 `generate(prompt)` 一次只能接一个请求。这一讲把引擎改成真正的“服务”：请求随时进队列，引擎一步一步地跑，**每一步由调度器决定 batch 里有谁**；生成完的请求立刻离开，空出的位置马上给等着的请求，这就是第 66 讲的 continuous batching。

## 设计：从“一个循环”到“一步一步”

v1 的结构是“一个请求从头跑到尾”。要同时服务多个请求，得把这个循环拆开：

- **请求要有自己的状态**。每个请求处在不同的阶段：有的还在排队，有的刚进来要做 prefill，有的已经生成了 50 个 token。每个请求自己记住 token 序列、已经算进缓存的位置数、状态和它的 KV Cache。这就是 `Sequence`。
- **每一步做什么由调度器决定**。调度器维护两个队列：等待中的和运行中的。每一步，运行中的请求各 decode 一个 token；batch 里还有空位，就从等待队列放新请求进来做 prefill。
- **引擎只负责“执行一步”**。`step()`：问调度器要这一步的 batch，把所有请求要算的 token 拼成一批送进模型，采样，更新每个请求，生成完的交给调度器移出。

模型这一侧的问题是：一个 batch 里的请求长度各不相同，prefill 的请求一次送进几十个 token，decode 的只有一个。常见的做法是**把所有请求这一步的 token 首尾相接拼成一维**，再记下每个请求占其中哪一段。线性层、RMSNorm、SwiGLU 都是逐 token 的，拼起来直接一次算完，batch 的收益就在这里；只有注意力要按段分开，每个请求只和自己的上下文做注意力。这种“拼成一维”的格式叫 varlen（变长），vLLM、nano-vllm 都是这样组织 batch 的。

用一个例子看拼出来的样子：请求 A 正在 decode，已有 20 个 token；请求 B 刚进来，提示 6 个 token。

```text
tokens = [A 的第 20 个 token,  B 的 6 个提示 token]      共 7 个
pos    = [19,                 0, 1, 2, 3, 4, 5]
segs   = [(0, 1, A 的缓存),   (1, 7, B 的缓存)]           每个请求占 tokens 的哪一段
```

模型算完，A 取第 0 个位置的打分，B 取第 6 个位置的打分，各自得到下一个 token。

## 测一测：16 个请求

16 个请求同时到达，每个要生成的 token 数从 8 到 96 不等，一共 792 个 token。比较三种跑法：一个一个跑（`max_num_seqs=1`，相当于 v1）、静态批处理（8 个一批，整批结束才换下一批）、continuous batching（8 个槽，有空就补）。

<RunOutput cmd=".venv/bin/python bench/batching.py" file="outputs/bench_batching.txt" caption="图 108-4　同样 792 个 token：一个一个跑 792 步；静态批处理 192 步；continuous batching 160 步，吞吐是一个一个跑的 1.9 倍。" />

先看步数。一个一个跑，每步只出一个 token，要 792 步。静态批处理分两批，每批要跑到这批里最长的请求结束：两批里都有要生成 96 个 token 的请求，所以各要约 96 步，共 192 步。continuous batching 只要 160 步。

再看每一步的耗时：一个一个跑约 69 ms 一步，continuous batching 约 180 ms 一步，每步的请求平均 5 个。每步的请求是 5 倍，每步的耗时只是 2.6 倍，所以吞吐从 14.5 提高到 27.5 token/s。这就是第 62 讲的结论在 CPU 上的样子：多出来的请求共享了读权重的那一遍。

下面是两种批处理每一步 batch 里实际有谁（来自同一次运行的记录）：

<StepTrace file="outputs/batching_steps.json" runs={['静态批处理（8 个一批）', 'continuous batching（8 个槽）']} caption="图 108-5　静态批处理：第一批里短的请求早早结束，它们的槽一直空到这一批最长的请求（96 个 token）结束，才放第二批进来。continuous batching：请求 2（8 个 token）结束后，下一步请求 8 就补了进来。" />

切换两种运行对比：静态批处理 192 步 × 8 个槽里，空着 48%；continuous batching 空着 38%。continuous batching 还有不少空槽，是因为 16 个请求很快全都进了 batch，最后只剩几个长请求在跑，没有新请求可以补。真实的服务里请求源源不断地到来，这部分空槽会被填上。

<Note kind="point">continuous batching 的关键是“每一步重新决定 batch”：运行中的请求各 decode 一个 token，有空位就放新请求进来 prefill，生成完的立刻离开。模型这边把所有请求的新 token 拼成一维，线性层一次算完，只有注意力按请求分段。</Note>

## 还剩什么问题

v2 给每个请求按“提示 + 最大输出”预留一整份 KV Cache。KV 的空间有限时，能同时运行的请求数就由这个“最大值”决定，而不是由实际用了多少决定。比如每个请求声明最多生成 512 个 token、实际只生成了 50 个，预留的空间九成是空的，却挡住了后面的请求。下一讲的压测会看到，KV 空间紧张时，这个毛病直接限制了吞吐。

## 回顾

v2 把引擎拆成三部分：Sequence 记每个请求的状态（关键是 `num_computed`），Scheduler 每一步决定 batch（运行中的先 decode，有空位再放新请求 prefill），`step()` 把这一步所有请求的 token 拼成一维送进模型，注意力按请求分段。和 HuggingFace 仍然逐 token 一致。16 个请求、792 个 token，continuous batching 用 160 步、27.5 token/s，是一个一个跑的 1.9 倍，比静态批处理少用 32 步。

每个请求按最大长度预留 KV，空间不够时放不下几个请求；而且这块空间必须是连续的。下一讲：**v3 · 分页 KV 管理**。
