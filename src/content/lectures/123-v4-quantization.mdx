到 v3 为止，miniinfer 的权重全是 FP32：28 层的线性层加起来 1680 MiB，再加上嵌入表和输出层（各 593 MiB），约 2.8 GiB。在 GPU 上，权重占的显存越多，留给 KV 块池的就越少，能同时服务的请求也越少（第 99 讲）；decode 每一步又要把权重读一遍，权重越大，每一步越慢（第 70 讲）。

第 90 讲讲过量化：用更少的位数存权重，计算时再换算回来。这一讲实现最常见的一种：**只量化权重的 INT8，每个输出通道一个 scale**（权重 8 位、激活保持高精度，常写作 W8A16）。新增一个 35 行的 `quant.py`，模型里把 `x @ W.T` 换成一个 `linear(x, W)` 函数。

## 设计：量化什么，怎么量化

**量化哪些权重。**只量化每层的 7 个线性层（q、k、v、o 投影和 FFN 的 3 个矩阵），它们占了 28 层权重的绝大部分。嵌入表是查表，不做矩阵乘，量化它省的是内存而不是计算；输出层直接决定 15 万个词的打分，对误差最敏感；RMSNorm 的缩放只有几千个数。这三样都保持原样。

**一个 scale 管多少个数。**INT8 只有 −127 到 127 这 255 个整数（对称量化，不用 −128），要用一个 scale 把它们映射回实数。scale 管得越细，误差越小，存 scale 的开销越大（第 90 讲）。这里每个**输出通道**（权重矩阵的每一行）一个 scale：q_proj 是 [2048, 1024]，就有 2048 个 scale，平均每 1024 个权重多存 4 字节，开销 0.4%。

按行取 scale 还有一个好处：矩阵乘的结果可以先算、后缩放。y 的第 j 个输出 = x · W[j] = x · (q[j] × s_j) = (x · q[j]) × s_j。所以

<div class="ai-formula">y = x · Wᵀ = (x · qᵀ) ⊙ s　　s 是每个输出通道的 scale，⊙ 按列相乘</div>

不用先把整个矩阵还原成 FP32，只需要在矩阵乘之后，对每一列乘一个数。

**每个通道的 scale 怎么定。**最简单的对称量化：s = 这一行的最大绝对值 ÷ 127，每个权重除以 s 再四舍五入。最大的那个数正好映射到 ±127，其余的数按比例落在中间（第 90 讲的 RTN，round-to-nearest）。

## 结果和 HuggingFace 不再完全一样

量化有意改变了权重的数值，生成结果不再保证和 HuggingFace 一致。先看检查的结果：

<RunOutput cmd=".venv/bin/python tests/check.py v4" file="outputs/check_v4.txt" caption="图 123-3　v4 的检查：4 条里 3 条仍然逐 token 一致；中文那条在中途开始不同。" />

<RunOutput cmd=".venv/bin/python bench/quant_diverge.py" file="outputs/quant_diverge.txt" caption="图 123-4　不一致的那一条，前 25 个 token 和 HuggingFace 相同，第 26 个开始走上了另一条路。" />

第 26 个 token 处，FP32 的模型选了 “问题”，INT8 的模型选了 “1.”。这时两个候选的打分本来就很接近，权重的微小误差让排名翻了过来；一旦选了不同的 token，后面的上下文就不同了，生成的内容自然越走越远。这不说明量化后的模型变差了，“1.” 接在 “答案：” 后面同样通顺。

“逐 token 一致”这个标准对量化太苛刻了，要换一种衡量方法：**让两个模型读同一串 token，比较每一步的打分**。下面让 FP32 的模型先生成 128 个 token，再让两个模型都按这串 token 一步一步地读，看每一步的最高分 token 是否相同，以及两个概率分布的 KL 散度（第 16 讲）有多大。

<RunOutput cmd=".venv/bin/python bench/quant.py" file="outputs/bench_quant.txt" caption="图 123-5　线性层权重从 1680 MiB 降到 421 MiB；128 步里最高分的 token 全部相同，平均 KL 散度 0.0011；但在 CPU 上，INT8 版本反而慢了约 20%。" />

**内存：3.99 倍。**线性层从 1680 MiB 降到 421 MiB，多出来的 0.01 是 scale 的开销。嵌入表和输出层（各 593 MiB，FP32）没有量化，整个模型从约 2.8 GiB 降到约 1.6 GiB。

**精度：几乎没有损失。**128 步里每一步的最高分 token 都相同，平均 KL 散度 0.0011：两个模型给出的概率分布几乎重合。每通道 INT8 对 Qwen3-0.6B 这样的模型足够精确；第 91 讲说过，真正难量化的是有离群激活的大模型，或者 4 位这样更低的位宽。

**速度：反而慢了。**单请求生成 64 个 token，FP32 用 4.27 s，INT8 用 5.11 s。原因就在 `linear()` 那一行：每次矩阵乘之前，都要把 int8 的矩阵转换成一份临时的 FP32 矩阵。转换本身要读 1 字节、写 4 字节，再由矩阵乘读一遍这 4 字节，比直接读 FP32 的权重还多了一道工序。

量化要变快，前提是**计算时直接读 int8**：在 GPU 上，一个融合的 kernel 把 int8 权重从显存读进片上，在寄存器里换算成 BF16 再做乘加（第 83、91 讲），显存只读了四分之一（相对 FP32）或一半（相对 BF16）的字节，decode 才能跟着快起来。这需要专门写 kernel，第 16 篇看 nano-vllm 和 vLLM 时会碰到。我们这一版拿到的是内存的收益：同样的内存，可以把省下来的约 1.2 GiB 给块池，多放约 360 个块。

<Note kind="point">每通道的 INT8 权重量化：每一行一个 scale = 最大绝对值 ÷ 127，矩阵乘时先算 x · qᵀ 再按列乘 scale。线性层内存降到四分之一，Qwen3-0.6B 的打分几乎不变。但在没有专门 kernel 时，每次计算都要把 int8 转回浮点，速度反而变慢；量化的速度收益要靠“直接读 int8 的 kernel”才能兑现。</Note>

## 回顾

v4 新增 quant.py：加载权重后，把每层 7 个线性层量化成 INT8，每个输出通道一个 scale；模型的矩阵乘统一走 `linear()`，量化时先算整数矩阵乘、再按列乘 scale。线性层从 1680 MiB 降到 421 MiB；4 条检查里 3 条仍然逐 token 一致，读同一串 token 时 128 步的最高分 token 全部相同，KL 散度 0.0011。在 CPU 上因为每次都要把 int8 转回浮点，单请求反而慢了约 20%。

到这里，引擎每一步 decode 仍然只为每个请求出一个 token。能不能一步多出几个？下一讲：**v5 · 投机解码**。
