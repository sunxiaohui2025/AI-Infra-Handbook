在第三章里，KV Cache 一直待在一张卡的显存里：请求开始时分配，结束时释放（第 67 讲），前缀缓存让它多留一会儿（第 68 讲）。到了集群里，它开始“流动”起来：

- PD 分离（上一讲）要把它从 prefill 实例的显存**传到** decode 实例的显存；
- 显存放不下的前缀缓存，可以**挪到** CPU 内存、SSD，甚至远端的存储里，等需要时再读回来；
- 一台机器算过的前缀，可以被**另一台机器**拿去用。

这一讲先算一笔最基本的账：一段已经算过的 KV，从哪一层存储读回来，比重新计算更快？然后看 KV 在这些层级之间流动时要注意什么。

## 读回来，还是重算

一段 n 个 token 的前缀，如果它的 KV 存在某个地方，用的时候有两个选择：

- **读回来**：耗时 = n × 每 token 的 KV 字节数 ÷ 存储到显存的带宽。
- **重新 prefill**：耗时 ≈ n × 2 × 激活参数 ÷ 算力（prefill 是计算受限的，第 60 讲；这里只算线性层）。

两者都和 n 成正比。所以比较的是**每个 token**：读它的 KV 要多久，重算它要多久。两者相等时的存储带宽叫**分界带宽**：

<div class="ai-formula">分界带宽 = 每 token 的 KV 字节数 ÷ 每 token 的重算时间</div>

比分界带宽快的存储，读回来更划算；比它慢的，不如重算。代码算了三个模型：

- **Llama-3-8B**：每 token KV 128 KiB，重算 15.2 μs，分界带宽 **8.6 GB/s**。
- **Llama-3.1-70B**：320 KiB，140.5 μs，分界带宽 **2.3 GB/s**。
- **DeepSeek-V3**：MLA 每 token 只有 68.6 KiB，重算 37.4 μs（FP8），分界带宽 **1.9 GB/s**。

模型越大，每个 token 算得越久；KV 越小（GQA、MLA），读得越快。这两点都让分界带宽变低，**连很慢的存储都值得用来存 KV**。

## 存储的层级

再看各层存储的带宽（示意的量级，按一台 8 卡服务器）：

| 存储 | 到 GPU 的带宽 | 容量 |
| --- | --- | --- |
| 本卡显存 HBM | 约 3.35 TB/s | 约 50 GB（扣掉权重后） |
| 同机其他卡（NVLink） | 约 450 GB/s | 约 400 GB |
| CPU 内存（PCIe） | 约 50 GB/s | 1–2 TB |
| 别的机器（RDMA 网络） | 约 50 GB/s | 整个集群 |
| 本机 NVMe SSD | 约 10 GB/s | 几十 TB |
| 远端分布式存储 | 约 3 GB/s | 几乎无限 |

拿 Llama-3-8B 一段 8000 token 的前缀算一下（KV 共 1.05 GB，重算约 121 ms）：从 CPU 内存读回约 21 ms，从别的机器读约 21 ms，从本机 SSD 读约 105 ms，都比重算快；从远端存储读要 350 ms，就不如重算了。换成 70B，重算要 1124 ms（单卡计；多卡张量并行时两者按同样比例缩小），连远端存储（874 ms）都比重算快。

容量上，CPU 内存比显存大几十倍：2 TB 的内存能存 Llama-3-8B 的约 1500 万个 token 的 KV，DeepSeek-V3 的约 2800 万个。显存里放不下的前缀缓存，挪到内存里，命中率就能高得多。

<Note kind="point">一段算过的前缀，读回它的 KV 还是重算，取决于存储带宽是否高于分界带宽 = 每 token KV ÷ 每 token 重算时间。Llama-3-8B 约 8.6 GB/s，70B 约 2.3 GB/s，DeepSeek-V3 约 1.9 GB/s：CPU 内存、RDMA 网络、甚至 SSD 都比重算快。所以 KV Cache 可以从显存扩展到内存、SSD 和整个集群，成为一个分层的缓存。</Note>

## 流动时要注意什么

上面的账只算了带宽，真实的系统还要处理几件事：

**和计算重叠。**读回一段前缀，不必等全部读完才开始算：先读第 1 层的 KV，第 1 层就可以开始算新 token，同时读第 2 层。PD 分离的传输也一样，prefill 每算完一层就开始传这一层（上一讲）。做得好的话，传输的时间大部分被藏住了。

**传输的粒度。**分页的块只有 16 个 token（第 67 讲），一层一块只有几十 KB，一块一块地传，α 的开销太大（第 91 讲）。传输时要把很多块合并成大的传输，或者用支持“分散-聚集”的 RDMA 操作。

**不要绕道 CPU。**GPU 之间、GPU 和网卡之间的数据，最好直接走 GPUDirect RDMA，不经过 CPU 内存中转，否则要多拷贝一次，还会抢 PCIe 的带宽。

**谁有哪段前缀。**KV 散落在各台机器的显存、内存、SSD 里，就需要一个“目录”：记录每段前缀（按第 68 讲的块哈希）存在哪里。请求来了，先查目录，再决定是读回、还是重算，以及把请求发给谁（下一讲）。

**淘汰策略。**每一层都会满，按 LRU 等策略把冷的数据往下一层挪，最后丢弃。热门的前缀（比如常用的系统提示）留在上层。

## 存多久：容量和复用间隔

上面的账只问了“读回来快不快”。可一份 KV 要能读回来，前提是它还在。缓存要多大，取决于它要保存多久。

换一个具体的例子：Qwen3-8B（每 token 144 KiB），一张 A100，按峰值 50% 计，重新 prefill 一段 8192 token 的前缀要 0.856 s（第 100 讲）。如果这张卡一直在做没有命中的 8K prefill，每 0.856 s 就产生一份 1.125 GiB 的 KV，产生速率

<div class="ai-formula">r = 1.125 GiB ÷ 0.856 s ≈ 1.41 GB/s</div>

注意，r 正是上一节的**分界带宽**：每 token 的 KV 字节数除以每 token 的重算时间。

所有新 KV 都写进某一级、按先后淘汰时，容量为 C 的一级大约能保留最近 C ÷ r 秒内产生的 KV：HBM（扣掉权重约 63.6 GB）约 **45 s**，每卡 256 GiB 的主机内存约 **195 s**，一块 3.84 TB 的 SSD 约 **2721 s**（45 分钟）。反过来，同一前缀两次使用的间隔是 T，要让间隔 T 以内的复用都能命中，这一级的容量至少要

<div class="ai-formula">C ≥ r × T</div>

T 由谁发起下一轮决定。阿里云一项基于线上请求记录的研究发现：面向个人用户的对话里，80% 的复用发生在 10 分钟以内；面向企业的 API 调用里，80% 的复用发生在 10 秒以内。10 秒只要 14.1 GB，HBM 就够；10 分钟要约 **847 GB**，超过了每卡的主机内存，要加上 SSD。

**容量越大，命中率涨得越慢。**不是每份 KV 都会被再用。Mooncake 公开的 Kimi 线上一小时采样记录里，按 LRU 淘汰，缓存从 1000 块（每块 512 token）加到 50,000 块，命中率只从 30% 升到 50%；容量不限也只有 51%。这份记录中超过一半的块从未被再次使用，另一些块却被访问上万次。所以加容量之前，要先看命中率曲线是不是已经平了。

## 读回来：多少次才回本，怎么和计算重叠

**保存也要花时间。**把一份 KV 存下来，将来复用 k 次，比每次都重算更快的条件是

<div class="ai-formula">T_写 + k × T_读 < k × T_重算</div>

经 25 GB/s 的链路，写、读各约 48.3 ms，复用一次就回本。链路降到 2 GB/s，读一次要 604 ms，要复用 3 次才回本。降到 10 GbE 的 1.25 GB/s，读一次 966 ms，已经比重算的 856 ms 还慢，怎么复用都不划算。临界点就是 r：链路比 GPU 产生 KV 的速度还慢，读回来就不如重算。

**读和算重叠。**命中之后，只需计算 256 个新 token，约 30.9 ms。历史 KV 在主机内存里，整份读回要 48.3 ms，先读后算共 **79.2 ms**，读比算还长。

Transformer 是一层一层算的，第 i 层只用第 i 层的 KV。所以可以**逐层预取**：GPU 算第 i 层时，PCIe 在读后面的层。可每层读要 1.34 ms、算只要 0.86 ms，每层的计算都在等读取，总时间约 **49.2 ms**，仍由读取决定。

再进一步：在这个请求开始之前，利用上一个 batch 的执行时间，先把前面若干层读进显存里预留的缓冲区。缓冲区要装下的，正是读比算多出来的字节：

<div class="ai-formula">缓冲 = 链路带宽 × (T_读 − T_算) = 25 GB/s × (48.3 − 30.9) ms ≈ 436 MB，即 14 层</div>

提前读入 14 层，剩下 22 层的读取被计算完全盖住，总时间降到计算本身的 **30.9 ms**。新 token 达到约 400 个时，计算就长过读取，不需要缓冲。CachedAttention 在 LLaMA-13B 上实测，逐层预取让 prefill 缩短 35%，再加 15 层的缓冲区缩短 61%。

<LayerPrefetch caption="图 101-2　命中 8K 前缀后，读历史 KV（橙）和算 256 个新 token（绿）的时间线。先读后算 79.2 ms；逐层预取 49.2 ms，每层都在等读取；提前读入 14 层，总时间就是计算本身的 30.9 ms。换成 SSD，读一层要 4.73 ms，提前读入的层数要多得多。" />

**用排队时间从 SSD 预取。**SSD 读一层要 4.73 ms，是算一层的 5.5 倍，逐层预取只能盖住一小部分。可以利用排队时间：请求还在队列里时，调度器已经知道它要哪份前缀，先把它从 SSD 读到主机内存；只要排队时间长过约 170 ms，这次读取就不在关键路径上。主机内存装得下多少份，就为队列最前面的多少个请求预取；换出时，先换出下次使用最晚的。这比只看过去访问的 LRU 好得多：CachedAttention 回放 ShareGPT 的多轮对话，按队列预取和换出时命中率 86%，LRU 只有 58%。

## SSD：带宽够，寿命不够

SSD 的读写带宽都比 r 高，写入 1.41 GB/s 也只占 PCIe 的一小部分。真正的限制是**写入寿命**。数据中心 SSD 常标“1 DWPD”：五年内每天可以写满一次。3.84 TB 的盘平均每秒只能写 **44.4 MB**，只有 r 的 **3.1%**。如果把所有新 KV 都写进 SSD，五年的寿命不到两个月就用完了。

所以写入 SSD 之前要先判断值不值得：比如只写已经被复用过的前缀，或者还没结束的多轮会话。前面看到超过一半的块从来不会再用，这样的准入判断能省下大部分写入。

## 到了大模型里

**推理引擎的支持。**vLLM 支持把 KV 卸载到 CPU 内存，并通过 LMCache 等插件接入更大的存储；SGLang 的 HiCache 把前缀缓存分成显存、内存、存储三层。它们都配合 NIXL、Mooncake Transfer Engine 这类传输库，在 GPU、CPU、网卡之间高效地搬运 KV。

**以 KV 为中心的架构。**月之暗面的 Mooncake 把整个集群的 CPU 内存和 SSD 组成一个分布式的 KV 缓存池，PD 分离的 prefill、decode 实例都从这个池子里读写。它的出发点就是这一讲的结论：对长上下文的对话服务，存起来复用比重算划算得多。

**API 的缓存价格。**DeepSeek 等厂商的 API 提供“上下文缓存”（DeepSeek 称为硬盘缓存），命中缓存的输入 token 按低得多的价格计费（第 64、68 讲）。MLA 让每个 token 的 KV 很小，存在 SSD 上也划算，这正是它能把缓存做到磁盘上的原因。

## 用代码复现

下面的代码列出各层存储的带宽，对三个模型算出每 token 的 KV 大小、重算时间和分界带宽，并比较一段 8000 token 的前缀从各层读回和重算的时间；最后算 2 TB 的 CPU 内存能存多少 token。

```python
# 一段已经算过的前缀，再用到时：从某一层存储把它的 KV 读回来，还是重新 prefill？
# 存储层级（带宽是示意的量级；容量按一台 8 卡服务器估）
TIERS = [("本卡显存 HBM", 3350e9, "约 50 GB（扣掉权重）"), ("同机其他卡 NVLink", 450e9, "约 400 GB"),
         ("CPU 内存 经 PCIe", 50e9, "1–2 TB"), ("别的机器 经 RDMA 网络", 50e9, "整个集群"),
         ("本机 NVMe SSD", 10e9, "几十 TB"), ("远端分布式存储", 3e9, "几乎无限")]
# 模型：每个 token 的 KV 字节数，重新 prefill 每个 token 的计算时间（计算受限，2 × 激活参数 ÷ 算力）
MODELS = {"Llama-3-8B": (131072, 2 * 7.5e9 / 989e12),
          "Llama-3.1-70B": (327680, 2 * 69.5e9 / 989e12),
          "DeepSeek-V3（MLA，FP8 计算）": (61 * 576 * 2, 2 * 37e9 / 1979e12)}
n = 8000                                                 # 一段 8000 token 的前缀（比如一份长文档或长对话历史）
for name, (kv, t_tok) in MODELS.items():
    print(f"{name}：每 token KV {kv / 1024:.1f} KiB，重算每 token {t_tok * 1e6:.1f} μs → 分界带宽 {kv / t_tok / 1e9:.1f} GB/s")
    print(f"   {n} token：KV {n * kv / 1e9:.2f} GB，重新 prefill 约 {n * t_tok * 1e3:.0f} ms；读回来：" +
          "，".join(f"{t[0].split()[0]} {n * kv / t[1] * 1e3:.0f} ms" for t in TIERS))

# 一台机器的 CPU 内存能存多少段前缀
dram = 2e12
print(f"2 TB 的 CPU 内存能存 Llama-3-8B 的 {dram / 131072 / 1e6:.0f}M 个 token，DeepSeek-V3 的 {dram / (61 * 576 * 2) / 1e6:.0f}M 个 token")
```

输出：

```text
   8000 token：KV 1.05 GB，重新 prefill 约 121 ms；读回来：本卡显存 0 ms，同机其他卡 2 ms，CPU 21 ms，别的机器 21 ms，本机 105 ms，远端分布式存储 350 ms
Llama-3.1-70B：每 token KV 320.0 KiB，重算每 token 140.5 μs → 分界带宽 2.3 GB/s
   8000 token：KV 2.62 GB，重新 prefill 约 1124 ms；读回来：本卡显存 1 ms，同机其他卡 6 ms，CPU 52 ms，别的机器 52 ms，本机 262 ms，远端分布式存储 874 ms
DeepSeek-V3（MLA，FP8 计算）：每 token KV 68.6 KiB，重算每 token 37.4 μs → 分界带宽 1.9 GB/s
   8000 token：KV 0.56 GB，重新 prefill 约 299 ms；读回来：本卡显存 0 ms，同机其他卡 1 ms，CPU 11 ms，别的机器 11 ms，本机 56 ms，远端分布式存储 187 ms

```

每个模型两行：第一行是分界带宽，第二行是 8000 token 前缀的读回时间和重算时间。8B 时 SSD（105 ms）勉强比重算（121 ms）快，远端存储（350 ms）不如重算；70B 和 DeepSeek-V3 时，所有层级都比重算快。最后一行是内存的容量。

第二段代码复现后半部分的数字：KV 产生速率和各级能保留多久，复用间隔对应的容量，保存再取回的回本次数，逐层预取的三种时间线，以及 SSD 的写入额度。

```python
# Qwen3-8B 的 8192 token 前缀（1.125 GiB），一张 A100（按峰值 50%：156 TFLOP/s）
V, layers = 8192 * 144 * 1024, 36
recompute = 0.856                                   # 在 A100 上重新 prefill 这 8192 个 token（第 100 讲）
r = V / recompute                                   # GPU 连续 prefill 时，每秒产生的 KV 字节数
print(f"KV 产生速率 r = {r/1e9:.2f} GB/s")

# 1. 存多久：容量 C 至少要 r × 复用间隔 T
for name, cap in [("HBM（扣掉权重）", 63.6e9), ("主机内存（每卡 256 GiB）", 256 * 2**30), ("本地 SSD", 3.84e12)]:
    print(f"{name}：能保留最近 {cap / r:,.0f} 秒产生的 KV")
for T in [10, 600]:
    print(f"复用间隔 {T} 秒：至少要 {r * T / 1e9:,.1f} GB")

# 2. 保存再取回，什么时候比重算快：T_写 + k·T_读 < k·T_重算
for bw in [25e9, 2e9, 1.25e9]:
    w = rd = V / bw
    k = next((k for k in range(1, 100) if w + k * rd < k * recompute), None)
    print(f"链路 {bw/1e9:5.2f} GB/s：读一次 {rd*1e3:6.1f} ms，" + (f"复用 {k} 次就回本" if k else "怎么复用都不如重算"))

# 3. 命中后只算 256 个新 token：先读后算、逐层预取、提前读入几层
t_new = (2 * 6.95e9 * 256 + 4 * 32 * 128 * 36 * (8448**2 - 8192**2) / 2) / 156e12
t_read = V / 25e9                                   # 从主机内存经 PCIe 读回
per_r, per_c = t_read / layers, t_new / layers
serial = t_read + t_new
layerwise = per_r * layers + per_c                  # 每层的计算都在等这一层读完，最后一层读完再算一层
buf = 25e9 * (t_read - t_new)                       # 读比算多出来的字节，要提前读进缓冲
pre = -(-buf // (V / layers))
print(f"计算 {t_new*1e3:.1f} ms；先读后算 {serial*1e3:.1f} ms；逐层预取 {layerwise*1e3:.1f} ms")
print(f"提前读入 {buf/1e6:.0f} MB（{pre:.0f} 层），总时间降到计算本身的 {t_new*1e3:.1f} ms")
print(f"新 token 至少 {256 * t_read / t_new:.0f} 个，计算就能完全盖住从主机内存的读取")

# 4. SSD 的寿命：1 DWPD（五年内每天写满一次）
budget = 3.84e12 / 86400
print(f"SSD 每秒平均只能写 {budget/1e6:.1f} MB，是 r 的 {budget/r*100:.1f}%")
```

输出：

```text

HBM（扣掉权重）：能保留最近 45 秒产生的 KV
主机内存（每卡 256 GiB）：能保留最近 195 秒产生的 KV
本地 SSD：能保留最近 2,721 秒产生的 KV
复用间隔 10 秒：至少要 14.1 GB
复用间隔 600 秒：至少要 846.7 GB
```

## 容易混淆的地方

1. **分界带宽只是第一道判断。**它没算读的延迟、和其他传输的争抢、以及读回时显存要先腾出空间。真正决定是否读回，还要看当时的负载。
2. **CPU 内存的带宽受 PCIe 限制。**CPU 内存本身很快，但到 GPU 要经过 PCIe，一张卡大约 50 GB/s；多张卡同时读时，还可能共享 CPU 的内存带宽。
3. **把 KV 存下来不改变模型的输出。**读回来的 KV 和重算的完全一样（第 68 讲的前缀缓存同理），只要前缀逐 token 相同。

4. **缓存够大不等于命中率够高。**命中率随容量增长很快就饱和，很多 KV 根本不会再用。容量按 C ≥ r × T 估计，再看命中率曲线。
5. **SSD 的瓶颈常常不是带宽，而是写入寿命。**按 1 DWPD 算，一块盘每秒只能写几十 MB，写入前要做准入判断。

## 回顾

在集群里，KV Cache 要在 prefill 和 decode 实例之间传递，也可以从显存卸载到 CPU 内存、SSD 和远端存储。一段算过的前缀，读回还是重算，看存储带宽是否高于分界带宽 = 每 token KV ÷ 每 token 重算时间：Llama-3-8B 约 8.6 GB/s，70B 约 2.3 GB/s，DeepSeek-V3 约 1.9 GB/s。8B 的 8000 token 前缀从 CPU 内存读回约 21 ms，重算约 121 ms。模型越大、KV 越小，越慢的存储也值得用。KV 流动时要逐层与计算重叠、合并成大的传输、走 GPUDirect RDMA，并维护一个“谁有哪段前缀”的目录。

缓存还要回答“存多久”：容量至少是 KV 产生速率 r × 复用间隔，r 就是分界带宽（Qwen3-8B 在 A100 上约 1.41 GB/s）；命中率随容量很快饱和。读回时逐层预取，再提前读入读比算多出来的那部分（8K 前缀约 14 层），读取就能被计算完全盖住。SSD 带宽够，但 1 DWPD 的寿命只允许写入约 3% 的新 KV。

有了分布在各处的 KV 缓存，新的问题来了：一个请求进来，该发给哪一台机器？发给有它前缀缓存的那台，能省掉 prefill；可如果大家的前缀都在同一台上，那台就会被挤爆。下一讲：**缓存感知路由与负载均衡**。
