第 113 讲测过，miniinfer 在 CPU 上的时间 76% 花在线性层、24% 在注意力；同时也指出，换到 GPU 上，注意力里“逐请求循环 + 复制 KV”的写法、每个运算一次的 kernel 发射，会变成主要矛盾。上一讲看到，nano-vllm 比 miniinfer 多出来的约 800 行，几乎都在执行一侧。这一讲逐项读这部分：

1. **启动**：怎么装权重、怎么算出能放多少个 KV 块；
2. **拼输入**：一步的请求怎么变成 GPU 上的几个数组；
3. **注意力**：写 KV 的 Triton kernel，和两个 flash-attn 函数；
4. **CUDA Graph**：decode 怎么按 batch 大小分档录图、重放；
5. **张量并行**：每种线性层怎么切，进程之间怎么同步；
6. 几个小的优化：合并矩阵、融合逐元素运算、在 GPU 上采样。

### 装权重：一个参数一个 weight_loader

HuggingFace 的权重文件里，q、k、v 是三个矩阵，gate、up 是两个矩阵；nano-vllm 的模型里，它们分别合成了一个 `qkv_proj` 和一个 `gate_up_proj`（一次矩阵乘算出三样或两样，少发射几个 kernel）。张量并行时，每张卡还只要其中自己那一片。所以“把文件里的张量拷进参数”这件事，每种层的做法都不一样。

nano-vllm 的办法是：每个参数身上挂一个 `weight_loader` 函数，由定义这个参数的层自己说明怎么装。读权重的代码只负责把名字对上：

这一步替代了 miniinfer 里手动指定的 `num_blocks=256`。它让 nano-vllm 在不同的卡上都能“尽量用满显存”，这也是第 88 讲说的：权重和激活之外的显存，越多留给 KV，能同时服务的请求就越多。

## 拼输入：prepare_prefill 和 prepare_decode

miniinfer 的注意力是“按请求循环”的：`segs` 记下每个请求占哪一段，Python 循环里一个一个算。GPU 上要的是**一个 kernel 处理整个 batch**，所以执行器要把这一步的全部请求描述成几个一维数组，交给 kernel：

- `input_ids`、`positions`：所有请求这一步的 token 和位置，拼成一维。
- `cu_seqlens_q`、`cu_seqlens_k`：前缀和，第 i 个请求的查询是 `[cu_q[i], cu_q[i+1])`，键的个数是 `cu_k[i+1] − cu_k[i]`（含已缓存的部分）。这是 flash-attn 变长接口的约定。
- `slot_mapping`：每个新 token 的 K、V 写到块池的哪个槽位。槽位号 = 块号 × 块大小 + 块内偏移，把整个块池看成一个一维的数组。
- `block_tables`：每个请求的块表，补齐成一个矩形（短的行补 −1）。
- `context_lens`：decode 时每个请求有多少个位置的 K、V。

几个读代码时容易忽略的点：

**为什么要自己写 Triton kernel 写 KV。**用 PyTorch 写就是一行 `k_cache.view(-1, D)[slot_mapping] = k`。问题出在 −1：CUDA Graph 补齐出来的空位，槽位填的是 −1（下面会看到），而 PyTorch 的下标里 −1 表示“最后一个”，空位的垃圾数据就会写进块池的最后一个槽位，把别人的 KV 覆盖掉。要跳过 −1，在 PyTorch 里得先用布尔掩码挑出有效的行，而布尔掩码选出多少行要等 GPU 算完才知道，CPU 必须同步等待，这在 CUDA Graph 里是不允许的。Triton kernel 里一个 `if slot == -1: return` 就解决了，形状固定，可以录进图里。顺带，K 和 V 在同一个 kernel 里写完，少一次发射。

**为什么块大小是 256。**`Config` 里有一条 `assert kvcache_block_size % 256 == 0`。这是 flash-attn 分页 KV 接口（传 `block_table` 的用法）的要求：块大小必须是 256 的倍数。上一讲说过这让前缀缓存的粒度变粗；vLLM 的注意力后端支持更小的块（早期版本默认 16，第 117 讲读的提交里默认 64）。

**输出层只算需要的位置。**`ParallelLMHead`（`layers/embed_head.py` 第 56–66 行）在 prefill 时用 `cu_seqlens_q[1:] − 1` 取出每个请求最后一个位置的向量，只算这几行的打分。decode 时每个请求本来就只有一个位置。这和 miniinfer v1 起的做法一样（第 107 讲）。

## CUDA Graph：decode 按 batch 分档录图

第 79 讲讲过 CUDA Graph 解决的问题：decode 一步要发射几百个 kernel，每个都很小，CPU 发射的速度跟不上 GPU 执行的速度，GPU 就在 kernel 之间空等。把一整步提前录成一张图，之后 CPU 只发射一次。

图有一个硬限制：录的时候张量的形状、地址都固定了，重放时只能换内容，不能换形状。而 decode 每一步的 batch 大小都在变。nano-vllm 的办法是**分档**：为几个固定的 batch 大小各录一张图，运行时挑不小于实际 batch 的最小那一档，多出来的行补成空位。

## 张量并行：线性层怎么切，进程之间怎么同步

### 四种线性层

第 93 讲的 Megatron 切法：一对线性层，第一个**按列切**（每张卡算一部分输出），第二个**按行切**（每张卡用自己那部分输入算出一个部分和），最后 All-Reduce 把部分和加起来。中间的逐元素运算（激活函数）各卡独立做，不用通信。

## 几个小的优化

**合并矩阵。**q、k、v 三个投影合成一个矩阵乘，gate、up 合成一个。矩阵乘的总计算量不变，但 kernel 数从 5 个降到 2 个，读一遍输入就够了。

**融合逐元素运算。**`RMSNorm`、`SiluAndMul`、`RotaryEmbedding` 的 forward 都加了 `@torch.compile`：PyTorch 把一串逐元素运算编译成一个 kernel，中间结果不写回显存（第 74 讲的算子融合）。其中 RMSNorm 还把**残差相加**融合了进来：

**在 GPU 上采样。**`Sampler` 只有一行核心代码：概率除以一个服从指数分布的随机数，取最大值。

<div class="ai-formula">argmaxᵢ pᵢ ⁄ Eᵢ，　Eᵢ ~ Exp(1) 相互独立　⟺　按概率 pᵢ 抽出 i</div>

原因是：Eᵢ ⁄ pᵢ 服从参数为 pᵢ 的指数分布，几个相互独立的指数分布里，第 i 个最小的概率恰好是 pᵢ ⁄ Σpⱼ = pᵢ。所以“除以 Eᵢ 取最大”就是“按概率抽样”，而且整个 batch 在 GPU 上一次完成，不用把 15 万维的概率拷回 CPU，也不用 `torch.multinomial`。

nano-vllm 不允许温度为 0（`SamplingParams` 里有 assert），也就不支持纯贪心；想要贪心效果，可以给一个极小的温度。它也没有 top-k、top-p、重复惩罚。

<Note kind="point">nano-vllm 执行一侧做的事：启动时用预热量出激活峰值，把剩余显存全部切给 KV 块；每一步把请求描述成 cu_seqlens、slot_mapping、块表等一维数组，写 KV 用一个能跳过 −1 的 Triton kernel，prefill 和 decode 各用一个 flash-attn 函数直接按块表读 KV；decode 按 batch 分档录 CUDA Graph，补齐的行靠 −1 和长度 0 变成空操作；张量并行用列切、行切一对线性层，每层两次 All-Reduce，rank 0 通过共享内存广播命令。</Note>

## 回顾

和 miniinfer 对照，nano-vllm 在执行一侧补上了第 113 讲表里的这几项：

| 第 113 讲的差距 | nano-vllm 的做法 | 代码 |
| --- | --- | --- |
| 注意力逐请求循环、复制 KV | prefill 用变长 FlashAttention，decode 按块表读，一个 kernel 处理整个 batch | `layers/attention.py` |
| 写 KV 逐位置下标 | Triton kernel 按 slot_mapping 一次写完，跳过 −1 | `layers/attention.py` |
| 每个运算一次发射 | decode 分 36 档录 CUDA Graph；合并矩阵；torch.compile 融合逐元素运算 | `engine/model_runner.py` |
| 块数手动指定 | 预热量峰值，剩余显存全给 KV | `engine/model_runner.py` |
| 只有贪心 | GPU 上的温度采样 | `layers/sampler.py` |
| 不支持多卡 | 张量并行，共享内存广播命令 | `layers/linear.py`、`engine/model_runner.py` |
