v2 给每个请求按“提示 + 最大输出”预留一整块连续的 KV Cache。请求刚进来时，它只用了提示那一小段，后面的空间要等它慢慢生成才用得上；可这块空间从一开始就被占住了，别的请求用不了。KV 的空间一紧张，能同时跑的请求数就由“最大长度”而不是“实际用了多少”决定。

第 75 讲的 PagedAttention 给出了办法：把 KV 的空间切成固定大小的块，所有请求共用一个块池；每个请求用一张**块表**记下自己的 KV 放在哪些块里，用到哪里拿到哪里。这一讲把它写进 miniinfer，顺带处理分页带来的新问题：块用完了怎么办。

## 设计：块池、块表、和一个“看起来连续”的视图

三样东西：

- **块池**（KVPool）：一开始就分配好一大块内存，形状 [层数, 块数, 块大小, KV 头数, 头维度]，K、V 各一份。块大小取 16 个位置，Qwen3-0.6B 在 FP32 下一个块（28 层合计）是 16 × 224 KiB = 3.5 MiB。
- **块表**：每个请求一个整数列表。第 j 项是“我的第 j 个 16 位置的段，放在池子里的第几块”。位置 p 在第 `table[p // 16]` 块的第 `p % 16` 格。
- **块管理器**（BlockManager）：一个空闲块的列表。请求进来时按提示长度拿块；decode 时位置跨进新块，再拿一块；请求结束，块还回来。

用一个例子看块表：块大小 16，请求 A 有 20 个 token，请求 B 有 40 个。

```text
块池：  [ 0 ][ 1 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ][ 7 ] …
         A    B    A    B    B
A 的块表 = [0, 2]       位置 0–15 在块 0，16–19 在块 2 的前 4 格
B 的块表 = [1, 3, 4]    位置 0–15、16–31、32–39
```

A 的两个块在池子里并不相邻，中间夹着 B 的块，这正是分页的意义：不需要连续的空间。

模型怎么办？注意力要的是“从位置 0 到现在的全部 K、V”。我们给每个请求包一个小对象 `SeqKV`，它和 v1 的 `KVCache` **接口完全一样**（`write(layer, pos, k, v)` 和 `read(layer, end)`），内部按块表把位置换算成块和格子。这样 model.py 一行都不用改：模型只管调用 write 和 read，不知道背后是一整块还是很多小块。

## scheduler.py：按块放行，块不够就抢占

分页之后，调度器要回答的问题变了：v2 问的是“KV 空间够不够预留一整份”，现在问的是“空闲块够不够”。还多了一种情况：请求进来时块是够的，可它一边生成一边要新块，几个请求一起长，池子可能在半路用完。这时要有人让出来，这就是第 78 讲的**抢占**。

## 测一测：同样只有 320 个位置

还是第 120 讲的 16 个请求，这次把 KV 的空间限制在 320 个位置（20 个块）。v2 按“提示 + 最大输出”整份预留；v3 按块按需分配。

<RunOutput cmd=".venv/bin/python bench/paging.py" file="outputs/bench_paging.txt" caption="图 121-6　KV 空间只有 320 个位置时：v2 平均每步只能放 3.3 个请求，240 步、17.0 token/s；v3 平均每步 4.7 个，167 步、22.8 token/s，期间抢占 9 次。" />

v2 每个请求要预留“十一二个 token 的提示 + 8 到 96 个输出”这么多位置，320 个位置只够同时放 3 到 4 个请求，8 个槽有一半空着。v3 进来时只要提示的 1 个块，8 个槽很快坐满；它们一起往下生成，块用完了就抢占最晚进来的，等有空再重算。抢占了 9 次，多做了 9 次 prefill，但每步多跑的 1.4 个请求远远抵得过，吞吐提高了 34%。

如果 KV 的空间足够大（比如第 120 讲那样不设限），两者就没有区别了：v2 预留的空间本来就够用。分页的价值，在 KV 空间成为瓶颈时才显现出来，而真实的服务几乎总是如此：显存扣掉权重之后剩下的那部分，决定了能同时服务多少个请求。

<Note kind="point">分页把“每个请求一整块连续的 KV”换成“共用的块池 + 每个请求一张块表”。请求只按现在要算的 token 拿块，decode 每跨进一个新块再拿一块，结束时还回去。代价是池子可能在半路用完，需要抢占：最晚进来的请求还回所有的块，回到队首，之后连同已生成的 token 一起重算。</Note>

## 回顾

v3 新增 block_manager.py：KVPool 是一大块按 [层, 块, 16, 头, 维] 分好的内存；BlockManager 管空闲块和引用计数；SeqKV 按块表把位置换算成块和格子，接口和 v1 的 KVCache 一样，所以模型不用改。调度器按空闲块数放行，运行中的请求拿不到新块时抢占最晚进来的那个，被抢占的请求回到队首重算。和 HuggingFace 仍然逐 token 一致，块池只有 6 块、发生抢占时也一样。KV 只有 320 个位置时，吞吐从 v2 的 17.0 提高到 22.8 token/s。

块表还带来一个新的可能：两个请求的提示开头一样（比如同一段系统提示），它们的前几个块里存的 K、V 也一模一样。能不能让第二个请求直接用第一个请求的块？下一讲：**v3+ · 前缀缓存**。
