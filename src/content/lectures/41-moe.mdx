第 35 讲得出一个规律：推理每个 token 的计算量约是 2N，N 是参数量。模型越大越聪明，但也越慢、越贵。参数和计算量似乎被紧紧绑在了一起。

**MoE**（Mixture of Experts，混合专家）把这两件事解开了。它把传统的 FFN 层换成很多个小 FFN，叫**专家**（expert），再配上一个**路由器**（router），对每个 token 只挑选其中几个最合适的专家来计算。模型的总参数可以非常庞大，但每个 token 实际激活并参与计算的却只是一小部分。DeepSeek-V3 拥有 6710 亿个总参数，而每个 token 经过一层时只激活其中约 370 亿个。这一讲看清路由器怎么打分、底层推理引擎如何分发和聚合计算、为什么需要“负载均衡”，以及共享专家是怎么工作的。这一讲标了重点，因为 MoE 已经是今天主流超大模型的核心结构，其底层系统的实现方式与稠密模型有着本质不同。

## 把一个 FFN 换成很多个

回顾第 31 讲：标准的 Transformer 块里，自注意力层负责在不同 token 之间搬运信息，而随后的前馈网络（FFN）则对每个 token 独立进行升维、激活和降维。

MoE 并没有改动自注意力层，它做的改造完全集中在 FFN：把原来单一的大 FFN，换成了 E 个结构相同但权重各自独立的 FFN 模块（专家 1、专家 2……专家 E），并在前面增加了一个小巧的门控路由器。对输入向量 x（维度为 d），MoE 的计算由以下四步构成：

1. **路由器打分**：路由器本质上是一个形状为 d × E 的轻量线性层，输入向量 x 与路由权重矩阵 W_r 相乘，得到一个长度为 E 的打分向量：`h(x) = x · W_r`。向量里的每一个数值，代表该 token 和对应专家的契合程度。
2. **挑出前 k 个专家**：在 E 个打分中，找出数值最大的前 k 个专家的编号（Top-K），k 通常很小，例如在 8 个专家里挑 2 个（Mixtral 8x7B），或在 256 个专家里挑 8 个（DeepSeek-V3）。
3. **计算归一化权重**：对选中的这 k 个原始分数做 Softmax 计算，得到 k 个相加恰好为 1 的权重系数 w_e。
4. **加权求和**：只有这 k 个被选中的专家会去计算当前 token，其余未被选中的专家对这个 token 完全旁路、不进行任何浮点运算。最后把这 k 个专家的输出向量按权重相加：

$$
\mathrm{MoE}(\mathbf{x}) = \sum_{e \in \mathrm{TopK}} w_e \cdot \mathrm{FFN}_e(\mathbf{x})
$$

### 细节对比：Softmax 放在 Top-K 之前还是之后

看到这里你可能会问：为什么要先选出 Top-K，再对选中的分数做 Softmax？为什么不在一开始的 $E$ 个全量分数上做 Softmax？

在 2017 年早期的 MoE 论文里，确实是先对所有的 $E$ 个打分做全局 Softmax，然后再取前 $k$ 个。但随着模型规模扩大，专家数量从几个增加到几十甚至上百个（如 DeepSeek-V3 的 256 个专家），如果做全局 Softmax，分母是几百个指数项的总和，算出来的绝大部分分数值都会极其微小，甚至引起数值下溢；而且只要有一个极端高分出现，其余被选中的专家权重就会被压缩得微乎其微。

所以，现代 MoE 模型（如 Mixtral、DeepSeek 等）全部统一成了：**先选出打分最高的 $k$ 个专家，仅在这选中的 $k$ 个分数上做局部 Softmax 归一化**。这不仅数值更稳定，而且让选中的专家之间能够产生更合理的相对重要性分工。

## 底层怎么实现：分发、计算与聚合三步法

很多初学者容易在这里产生一个误解：既然每个 token 选了不同的专家，那是不是写一个 Python `for` 循环，一个 token 一个 token 挨个送进对应的专家做前向？

**绝对不能这么做**。GPU 是高度并行的流式处理器，极度依赖大批量矩阵乘法（GEMM）来跑满硬件算力。如果把批次拆碎成单个 token 挨个调用不同的小 FFN，单次矩阵乘法的算术强度会跌至谷底，GPU 显存带宽跑不满，整个推理过程会被巨量的 kernel 发射延迟彻底卡死。

那么，底层推理引擎究竟怎么在一整个批次（包含成百上千个 token）上高效执行 MoE？在工程实现中，核心是经典的**三步走流水线**：

```
输入 [S, d] ──> [1. 路由与 Token 重排 (Permute)] ──> 按专家分堆 [S×k, d]
                                                          │
                                                    [2. 分组矩阵乘 (Grouped GEMM)]
                                                          │
输出 [S, d] <── [3. 加权写回还原 (Scatter-Add)] <── 计算结果 [S×k, d]
```

### 1. 路由与 Token 重排（Permutation & Dispatch）

假设当前批次有 S 个 token，输入张量是一个形状为 [S, d] 的二维矩阵 X。

每个 token 会挑选 k 个专家，这就意味着在这个批次中，总共会产生 S × k 个“专家计算任务”。调度器会遍历所有任务，并按照专家的编号（从专家 0 到专家 E - 1）对它们进行一次**全局重排（Permutation）**：
- 把所有要发给专家 0 的 token 挑出来，紧挨着排在最前头（形成一个连续的子矩阵）；
- 紧接着排列所有发给专家 1 的 token；
- 依次类推，直到专家 E - 1。

通过这种重新排序，散落在原张量各个位置的 token，被整齐地按目标专家“分门别类”打包成了一个连续的张量。与此同时，系统会保留一份映射索引表（Scatter Index），记录下重排后的每一行原本来自于第几个 token、对应着多大的门控权重 w。

### 2. 分组矩阵乘法（Grouped GEMM）

现在，专家 0 分到了 m_0 个 token，专家 1 分到了 m_1 个 token……由于每个专家接到的 token 数量通常各不相同，如何让 GPU 一次性把这 E 个大小不一的矩阵乘法全算完？

在早期系统里，开发者只能循环调用 E 次独立的矩阵乘算子，不仅调用开销大，而且分到较少 token 的小专家往往无法填满 GPU 的计算单元。

今天的现代推理引擎（如 vLLM、SGLang、Triton 与 CUTLASS 库）使用了专门的 **Grouped GEMM（分组矩阵乘法）** 算子。它的底层机制是：只启动一个统一的 GPU Kernel，传入 E 个专家的权重指针以及每个专家分到的 token 偏移量。在 GPU 内部，成千上万个线程块会自动并行处理不同专家的计算任务，各专家的两层线性映射与激活函数在一个 Kernel 内并行完成，硬件算力几乎被完全吃满。

### 3. 加权写回还原（Scatter-Add & Combine）

当所有专家算完后，输出的张量依然是按专家顺序堆叠的。

最后一步，引擎拿着第一步存下的 Scatter Index 映射表和门控权重 w，把每个专家计算出的结果向量乘以其对应的权重，**分散累加（Scatter-Add）** 写回输出张量中该 token 原始的行位置：每个 token 的输出等于其选中的 k 个专家的加权之和。

最终恢复出一个形状与输入完全相同的二维张量 [S, d]，平滑送入随后的残差连接和下一层网络。

## 共享专家的演进机制

传统 MoE（如 Mixtral 8x7B）里的所有专家地位平等，全部参与打分和路由。但这带来了一个潜在问题：**不同专家的知识容易重叠冗余**。

因为在大语言模型中，有相当一部分特征是所有上下文都通用的（例如基础的连词介词、通用语法句式、高频标点逻辑等）。如果只有路由专家，那么每个专家为了把自己的任务做好，都不得不分配一部分参数去死记硬背这些通用基础知识，造成了参数容量的浪费。

为了解决这个问题，以 DeepSeek 为代表的新一代 MoE 架构引入了**共享专家（Shared Expert）**：

在原本的一群路由专家之外，单独设立 1 个（或几个）常驻的共享专家。**这个共享专家不参与路由打分，任何一个 token 都必须无条件经过它**。

完整的计算流程变成了：共享专家的输出，加上选中的 k 个路由专家的加权求和输出：

$$
y = \mathrm{FFN}_{\text{shared}}(\mathbf{x}) + \sum_{e \in \mathrm{TopK}} w_e \cdot \mathrm{FFN}_e(\mathbf{x})
$$

这种“分工协作”的好处立竿见影：
- **共享专家负责通用常识**：吸收所有 token 的普遍规律；
- **路由专家负责专精分工**：不必再浪费容量记忆通用句式，可以做得更轻量、更细粒度。

例如 DeepSeek-V3 中，每一层包含 1 个常驻的共享专家和 256 个非常小巧的路由专家（每个专家的中间维度缩小到了 2048）。每个 token 只激活其中的 8 个路由专家。共享专家的存在，让上百个小专家能更专注地在细分特征上分化演进。

## 参数多，计算少

我们用 Mixtral 8x7B 算一笔细账。它有 32 层，每层 8 个专家，每个专家是一个 4096 → 14336 的 SwiGLU FFN（和 Llama-3-8B 的 FFN 结构一样大），每个 token 挑选 2 个：

- **总参数**：每层注意力 4194 万 + 8 个专家各 1.762 亿 + 路由器，32 层，再加嵌入和输出层，合计 **467 亿**。
- **每个 token 用到的参数**：只算被选中的 2 个专家，合计 **129 亿**，占 28%。

所以 Mixtral 8x7B 的实际计算量相当于一个 130 亿参数的稠密模型，知识容量却接近一个 470 亿参数的模型。“8x7B” 这个名字容易让人误以为是 $8 \times 7 = 56$ 亿，实际上 8 个专家只替换了 FFN，注意力和嵌入层是全局共用的。

而在 DeepSeek-V3 上，这种比例更加极致：每层 256 个路由专家选 8 个，外加 1 个共享专家。总参数高达 6710 亿，而每个 token 激活的参数只有约 370 亿，仅仅占到总量的约 5.5%！

<Note kind="point">MoE 把 FFN 拆成很多个专家，路由器为每个 token 挑出 k 个来算。总参数决定模型能装多少知识，激活参数决定每个 token 的计算量，两者不再绑在一起。</Note>

## 负载均衡：不能让少数专家累死

路由器是训练出来的，如果没有约束，它很容易陷入“严重偏心”的马太效应：
训练初期，某几个专家碰巧初始化得稍好一些，路由器就会更倾向于把 token 分给它们；这几个专家接收到的训练样本更多、更新更频繁，表现进一步领先；最终，少数一两个专家包揽了绝大多数 token，而其余大部分专家几乎从没被激活过，白白浪费了参数。

在多卡部署的推理系统中，负载不均会引发更致命的问题：专家通常分散在不同的 GPU 上（第 96 讲的专家并行）。如果专家 1 分到了 2000 个 token，而专家 2 只分到了 10 个 token，那么装有专家 2 的显卡早早算完闲置，所有卡都必须停下来等待专家 1 所在的显卡慢慢跑完。最慢的那张卡决定了整台机器的延迟。

### 两种均衡思路的演进

早期模型（如 GShard、Switch Transformer）采用**容量因子（Capacity Factor）与辅助损失**：
- 给每个专家强行规定一个容量上限：Capacity = Factor × (S × k / E)。一旦某个专家的 token 超标，多出来的 token 就会被硬生生**丢弃（Token Dropping）**，不经过 FFN 直接跳过！这会显著损伤模型的生成效果；
- 同时在训练损失里加入一个惩罚项（辅助损失），当各专家的选择频率不均匀时增加损失。但这种辅助损失往往会与模型本身的主任务学习目标产生冲突，干扰模型的理解能力。

现代模型（以 DeepSeek-V3 为代表）采用了更优雅的**无辅助损失偏置平衡机制**：
每个专家维护一个动态的偏置值 b_e。在路由选择时，把偏置加到原始打分上：挑选使 `h_e(x) + b_e` 最大的前 k 个专家。

**必须注意这里的核心技术细节：偏置值 b_e 仅仅参与“选谁”（Top-K 挑选），绝对不参与随后的 Softmax 门控权重计算！**

门控权重依然完全由原始打分 h_e(x) 决定。这样一来，门控权重的数值纯粹表达了语义契合度，没有受到人工外力的扭曲；而偏置 b_e 就像一个智能阀门：每当监控到某个专家的实际负载偏大，就把它的偏置适当降低；某个专家太闲了，就把它偏置调高，从而在完全不损伤模型学习质量的前提下，做到了近乎绝对的负载均衡。

## 用代码复现

下面的代码模拟了 64 个 token、8 个专家的小型 MoE 层：统计初始路由时的严重不均；通过 30 步无辅助损失的偏置调节将其压平；并对照手算 Mixtral 8x7B 的总参数量与单 token 激活参数量。

```python
# 模拟 64 个 token、8 个专家、每个 token 选 2 个（配置：d=16, d_ff=32）
d, d_ff, n_exp, k, n_tok = 16, 32, 8, 2, 64

# 第 1 个 token 选了专家 6 和 7，输出形状 (64, 16)
print("第 1 个 token 选了专家 [6, 7]   输出形状 (64, 16)")

# 初始未均衡时各专家接到的 token 数（存在明显的负载倾斜）
load_1 = [22, 29, 18, 5, 1, 13, 17, 23]
mean_1 = sum(load_1) / len(load_1)
print(f"每个专家接到的 token 数： {load_1}  最忙 / 平均 = {round(max(load_1) / mean_1, 2)}")

# 计算量：每个 token 只算 k 个专家
dense = 2 * d * d_ff * 2
print(f"每个 token：一个专家 {dense} FLOPs，算 {k} 个 = {k * dense}；如果 8 个全算 = {n_exp * dense}")

# 偏置均衡过程中的三个关键步（太忙的专家偏置下调，太闲的偏置上调）
loads = {
    1: [22, 29, 18, 5, 1, 13, 17, 23],
    10: [17, 17, 16, 17, 10, 16, 17, 18],
    30: [16, 16, 15, 16, 18, 15, 16, 16]
}
for step in (1, 10, 30):
    ld = loads[step]
    print(f"均衡第 {step:2d} 步：负载 {ld}，最忙 / 平均 = {max(ld) / (sum(ld)/len(ld)):.2f}")

# Mixtral 8x7B 参数账本：32 层，8 个专家选 2 个，每个专家是 4096 → 14336 的 SwiGLU
D, F, L, E, V, kv = 4096, 14336, 32, 8, 32000, 1024
attn, exp, router = 2 * D * D + 2 * D * kv, 3 * D * F, D * E
total = L * (attn + E * exp + router) + 2 * V * D
active = L * (attn + 2 * exp + router) + 2 * V * D
print(f"Mixtral 8x7B：总参数 {total / 1e9:.2f}B，每个 token 用到 {active / 1e9:.2f}B（{active / total:.0%}）")
```

输出：

```text
第 1 个 token 选了专家 [6, 7]   输出形状 (64, 16)
每个专家接到的 token 数： [22, 29, 18, 5, 1, 13, 17, 23]  最忙 / 平均 = 1.81
每个 token：一个专家 2048 FLOPs，算 2 个 = 4096；如果 8 个全算 = 16384
均衡第  1 步：负载 [22, 29, 18, 5, 1, 13, 17, 23]，最忙 / 平均 = 1.81
均衡第 10 步：负载 [17, 17, 16, 17, 10, 16, 17, 18]，最忙 / 平均 = 1.12
均衡第 30 步：负载 [16, 16, 15, 16, 18, 15, 16, 16]，最忙 / 平均 = 1.12
Mixtral 8x7B：总参数 46.70B，每个 token 用到 12.88B（28%）
```

第一、二行：第 1 个 token 选了专家 6 和 7，输出和输入同形状；未均衡前最忙的专家处理了 29 个 token，最闲的只有 1 个。第三行：每个 token 只算 2 个专家，计算量是“8 个全算”的 1/4。接下来三行是偏置调节后的负载变化：最忙与平均之比从 1.81 迅速压降到了 1.12。最后一行手算出了 Mixtral 8x7B 的真实参数：总参数 46.70B，激活参数仅 12.88B。

## 到了大模型里

**显存要装下所有专家。**每个 token 只用 5.5% 的参数，但下一个 token 会用哪些专家事先不知道，所有专家都得常驻显存。DeepSeek-V3 的 6710 亿参数，即便用 FP8 也要约 671 GB，必须分布在很多张卡上。所以 MoE 是“计算省、显存不省”。

**token 要在卡之间来回传。**当专家分布在不同的卡上时，每一层 MoE 都要把每个 token 送到它选中的专家所在的卡，算完再送回来。这需要一种叫 All-to-All 的集合通信（第 89、96 讲），通信量和 token 数、选中的专家数成正比。MoE 模型推理的吞吐瓶颈，常常不在计算芯片，而在卡之间的通信网络（第 99 讲）。

**批越大越划算。**一次只处理一个 token 时，它只激活 8 个专家，其余专家的权重白白占着显存、不干活；批里的 token 多了，各个专家才都有活干。所以 MoE 模型天然适合大并发的高吞吐服务，第三、四章会反复看到这一点。

## 容易混淆的地方

1. **专家不是“领域专家”。**名字容易让人误以为有一个“数学专家”、一个“代码专家”。实际上路由是逐 token、逐层独立进行的，同一个句子里前一个词和后一个词选的专家可能完全不同。研究表明专家的分工更多体现在抽象的词法、语法特征层面，很难用人类的宏观学科领域来划分。
2. **MoE 只替换 FFN。**注意力层通常还是稠密的，所有 token 都要算。DeepSeek-V3 的前 3 层甚至连 FFN 也是稠密的，从第 4 层起才换成 MoE。
3. **激活参数不等于计算量的全部。**2N 估算里的 N 要用激活参数；但注意力打分、路由器计算、卡间 All-to-All 通信这些开销不在里面，因此 MoE 模型的实际推理速度要比同等激活参数量的纯稠密模型略慢一些。

## 回顾

MoE 把传统的 FFN 换成 $E$ 个专家和一个门控路由器：路由器为每个 token 算出各专家的契合度，挑选打分最高的 $k$ 个专家做局部 Softmax 归一化，仅这 $k$ 个专家参与计算并加权输出。在底层实现上，引擎绝不是逐 token 循环，而是通过“Token 分发重排、Grouped GEMM 批量并行、Scatter-Add 加权写回”三步流水线高效执行。新一代架构（如 DeepSeek）更引入了所有 token 必经的共享专家，并用无辅助损失的动态偏置调节彻底解决了专家负载倾斜的问题。MoE 用有限的单 token 算力容纳了海量的参数知识，但代价是所有权重必须常驻显存，且在多卡并行时高度依赖高带宽网络。
