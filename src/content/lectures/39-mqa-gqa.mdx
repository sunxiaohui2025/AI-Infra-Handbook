第 27 讲算过一笔账：KV Cache 里存着每一层、每个 token 的 k 和 v，Llama-3-8B 每个 token 要 128 KiB，8192 个 token 就是 1 GiB，同时服务十几个长请求，KV Cache 就比模型权重还大。而且第 24 讲说过，每生成一个 token，除了要把权重读一遍，还要把这个请求的整个 KV Cache 读一遍。KV Cache 越大，能同时服务的请求越少，每一步也越慢。

可是那个 128 KiB 里，藏着一个我们一直没解释的数字：“8 个 KV 头”。Llama-3-8B 有 32 个查询头，为什么 KV 头只有 8 个？这一讲的 **MQA** 和 **GQA** 就是答案：**让多个查询头共用同一组 K、V**，直接把要缓存的东西砍掉一大截。它是推理优化里收益最大的架构改动之一，所以标了重点。

## 先算一下不共用时有多大

第 28 讲的多头注意力里，每个头都有自己的 q、k、v，这叫 **MHA**（Multi-Head Attention，多头注意力）。如果 Llama-3-8B 用 MHA，32 个头每个都有自己的 k、v，每个 token 的 KV Cache 是：

<div class="ai-formula">2（k 和 v）× 32 层 × 32 个头 × 128 维 × 2 字节 = 512 KiB</div>

一个 8192 token 的请求是 4 GiB；16 个这样的请求就是 64 GiB，是模型权重（约 15 GiB）的四倍多。一张 80 GB 的卡，放下权重以后，只能勉强塞下十几个这样的请求。

## MQA：所有头共用一组

2019 年，Noam Shazeer 提出了一个激进的办法：**MQA**（Multi-Query Attention，多查询注意力）。查询还是多个头，每个头一个 q；但 K 和 V **只有一组**，所有查询头都拿自己的 q，去和这同一组 k 打分，再从这同一组 v 里加权求和。

每个头的注意力权重仍然各不相同（因为 q 不同），所以“从多个角度看”的能力还在一部分；但要缓存的 k、v 一下子变成了原来的 1/32。Llama-3-8B 如果用 MQA，每个 token 只要 16 KiB。

代价是效果会有所下降：32 个头被迫用同一套 k 和 v，能表达的“角度”少了。有的模型（比如 PaLM、Falcon）用过 MQA，但它没有成为主流。

## GQA：分组共用与底层实现机制

2023 年的 **GQA**（Grouped-Query Attention，分组查询注意力）取了一个折中：把查询头**分成几组，每组共用一组 K、V**。Llama-3-8B 把 32 个查询头分成 8 组，每组 4 个头共用一组 k、v，所以是“8 个 KV 头”。

<div class="ai-formula">MHA：n<sub>kv</sub> = n<sub>h</sub>　　GQA：1 &lt; n<sub>kv</sub> &lt; n<sub>h</sub>　　MQA：n<sub>kv</sub> = 1</div>

MHA 和 MQA 是 GQA 的两个极端。GQA 论文的实验显示，8 组左右时效果已经非常接近 MHA，而 KV Cache 只有 MHA 的 1/4，速度接近 MQA。今天的主流开源模型（Llama-2-70B 起的 Llama 系列、Qwen、Mistral 等）几乎都用 GQA。

### 底层算子怎么执行：绝不在显存里复制 KV

很多初学者看到这里会有一个困惑：32 个 Query 头，只有 8 个 KV 头。在矩阵乘法计算注意力时，形状对不上（Q 是 32 个头，K 是 8 个头），底层是怎么算的点积？

在初级的教学代码或高层框架里，常见做法是把 8 个 KV 头沿着头维度**广播（Broadcast）或复制 4 份**（通过 `repeat_interleave` 操作），把张量硬生生扩展成 32 个头再去做矩阵乘法。

**但在真正的底层推理算子（如 FlashAttention-2、FlashInfer、vLLM）里，绝对不会在物理显存里复制这 4 份！**

如果在显存里复制，那省显存和省访存带宽的目标就彻底泡汤了。底层内核的真实做法是：
1. **显存里只存一份**：物理显存中的 KV Cache 严格只保留 8 份物理头的空间。
2. **硬件线程隐式映射**：在启动 GPU Kernel 时，处理第 $h$ 个 Query 头的线程（或 Warp），通过除法计算自己对应的 KV 组号：
   $$\text{kv\_group} = h \div (n_h \div n_{\text{kv}})$$
   以 Llama-3-8B 为例，查询头 0、1、2、3 的线程算出的组号都是 0，它们都去物理显存中读取第 0 个 KV 头。
3. **片上共享内存（SRAM）复用**：当第 0 个 KV 头的数据被从慢速的 GPU 显存（HBM）读入到极高速的片上共享内存后，这 4 个查询头的线程可以在片上直接并发读取它、分别和各自的 $q$ 做点积。读一次，用四次，物理显存的读写开销完全没有增加。

<Note kind="point">MQA 和 GQA 让多个查询头共用同一组 K、V。查询头的个数和各自的注意力权重都不变，需要缓存的 K、V 却按组数成比例减少：Llama-3-8B 用 8 组，KV Cache 是 MHA 的 1/4。底层算子通过线程索引映射直接在片上复用，物理显存中绝不复制。</Note>

TinyLM 有 2 个查询头，本来是 MHA：*W*<sub>k</sub>、*W*<sub>v</sub> 是 4 × 4，前 2 列给头 1、后 2 列给头 2。下面的代码写了一个通用的注意力函数，`n_kv` 设成 2 时，结果和 TinyLM 第 1 层完全一致。

把它改成 MQA：*W*<sub>k</sub>、*W*<sub>v</sub> 只留 2 列，两个查询头共用。从一个已经训练好的 MHA 模型出发，怎么得到这 2 列？GQA 论文的办法是**把同一组里各个头的 K、V 权重取平均**，再用少量数据继续训练一会儿（论文里约为原来训练量的 5%），让模型适应新的结构。

TinyLM 没有训练，所以只做了取平均这一步。结果，“AI”这一行的注意力输出从 (−0.928, −0.698, −0.132, 0.404) 变成了 (−0.181, −0.231, 0.004, 0.23)，差别很大。这正说明了为什么取平均之后必须再训练：硬把两组 K、V 合成一组，模型原来学到的东西被破坏了，需要重新适应。实际中，Llama-3 这样的模型是一开始就按 GQA 结构训练的，不存在这个问题。

## 为什么 GQA 还能让解码更快

省显存只是一半的好处。另一半在速度上。

第 24 讲说过，decode 时每生成一个 token，都要从显存里把这个请求的整个 KV Cache 读出来，和新 token 的 q 做点积。这一步的计算量很小，时间主要花在“读”上（也就是访存受限）。

我们手算一下这个细节：
- 用 MHA 时，从显存读进一个 128 维的 $k$ 向量（FP16 占 256 字节），只被一个查询头的 $q$ 用一次，计算量是 `2 * 128 = 256` FLOPs。读写比（算术强度）只有 `256 / 256 = 1 FLOP/Byte`。
- 用 GQA（8 组，每组 4 个头）时，从显存把同一个 128 维的 $k$ 读进片上缓存，同组的 4 个查询头都拿自己的 $q$ 和它做一次点积，计算量翻成了 `4 * 256 = 1024` FLOPs。而从慢速显存读入的字节数依然只有 256 字节！

算术强度直接翻了 4 倍（提高到了 `4 FLOP/Byte`）。第 62 讲会学到，在显存带宽打满的瓶颈区，算术强度提高 4 倍，意味着单步 Decode 的耗时能直接削减，转化为吞吐的大幅提升。

## 到了大模型里

**KV 头数是推理成本的关键配置。**config 里的 `num_key_value_heads` 就是 n<sub>kv</sub>。Llama-3-8B 和 70B 都是 8；70B 有 64 个查询头，每 8 个一组。读一个模型的 config 时，这个数和层数、每头维度一起，直接决定了每个 token 的 KV Cache（第 71 讲的显存账本）。

**张量并行时的整除陷阱。**多卡推理常按头切分（第 105 讲）。8 个 KV 头切到 8 张卡上（TP=8），每张卡正好分到一个 KV 头和 4 个 Query 头，非常整齐。但如果模型巨大需要 16 张卡（TP=16）呢？8 个 KV 头根本无法整除 16 张卡！此时系统必须在每两张卡之间强行复制一份 KV 头，导致显存无法线性减半。因此，现代大模型在架构设计时，KV 头数往往直接受制于未来部署时的张量并行度。

**还能再省吗？**GQA 靠的是“少存几组”。还有另一条路：不减少组数，而是把每个 token 的 K、V 压缩成一个更短的向量再存，用的时候再还原。这就是 DeepSeek 提出的 MLA，下一讲。

## 容易混淆的地方

1. **查询头没有变少。**GQA、MQA 减少的只是 K、V 的组数，查询头还是 32 个，每个头的注意力权重依然各不相同。所以说“Llama-3-8B 有 8 个头”是不对的，应该说“32 个查询头、8 个 KV 头”。
2. **省的是显存和带宽，计算量几乎不变。**注意力的打分和加权求和的次数取决于查询头的个数，GQA 并没有减少。它省下的是要存、要读的 K、V。
3. **GQA 不能随便套在现成模型上。**把 MHA 模型的 K、V 头直接合并，效果会明显下降（就像 TinyLM 的例子），必须再训练一段时间才能恢复。

## 回顾

KV Cache 的大小和 KV 头的个数成正比。MHA 每个查询头一组 K、V，Llama-3-8B 若用 MHA，每 token 要 512 KiB。MQA 让所有查询头共用一组 K、V，缓存降到 1/32，但效果有损失；GQA 折中，把查询头分组、每组共用一组，Llama-3-8B 用 8 组，每 token 128 KiB，效果接近 MHA。共用 K、V 还让 decode 时每读一次显存做更多的计算，提高了算术强度。查询头的个数和计算量不变，变的是要存、要读的东西。

GQA 是“少存几组”。如果每个 token 的 K、V 能被压缩成一个短得多的向量，是不是能省得更多？DeepSeek 正是这样做的。下一讲：**MLA 多头潜在注意力**。
