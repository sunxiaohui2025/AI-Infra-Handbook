六个版本写完，miniinfer 有了一个推理引擎的主要零件：手写的模型前向、KV Cache、continuous batching、分页和前缀缓存、INT8 量化、投机解码，全部约 400 行 Python，每一版都和 HuggingFace 逐 token 一致（量化版除外，差异也量化过了）。

这一讲回头看三件事：每一版到底换来了什么；现在的时间花在哪里；它和 vLLM 这样的工业级引擎还差多远，差在哪些地方。最后一个问题的答案，就是第 16、17 篇要读的内容。

## 每一版换来了什么

| 版本 | 改了什么 | 实测（Apple M2，CPU，FP32） | 讲 |
| --- | --- | --- | --- |
| v0 | 手写前向，每步整段重算 | 199 个 token 的提示生成 64 个：34.1 s | 106 |
| v1 | KV Cache | 同样的任务 4.55 s，快 7.5 倍；decode 每步约 65 ms | 107 |
| v2 | continuous batching | 16 个请求、792 个 token：27.5 token/s，一个一个跑的 1.9 倍 | 108 |
| v3 | 分页 KV、抢占 | KV 只有 320 个位置时：22.8 token/s，v2 只有 17.0 | 109 |
| v3+ | 前缀缓存 | 共用系统提示的 7 个请求：prefill 从 2356 个 token 降到 116 个，5.5 s → 2.4 s | 110 |
| v4 | INT8 权重量化 | 线性层 1680 MiB → 421 MiB；128 步最高分 token 全部相同；CPU 上慢了约 20% | 111 |
| v5 | n-gram 投机解码 | 改写代码：每次前向 3.66 个 token，9.4 s → 6.6 s；输出不变 | 112 |

代码量是这样长起来的：

<RunOutput cmd=".venv/bin/python bench/loc.py" file="outputs/loc.txt" caption="图 125-2　每个版本的代码行数（不算空行）。v0 只有 119 行；最大的一次增长是 v3 的块管理器（100 行），它同时承担了分页、抢占时的回收和前缀缓存。" />

回头看这张表，有两件事值得记住。第一，**每一版的收益都有前提**：KV Cache 在生成越长时收益越大；continuous batching 要有足够多的请求同时在跑；分页在 KV 空间紧张时才显出优势；前缀缓存要请求真的共用前缀；投机解码要草稿猜得准。脱离负载谈优化，很容易得出错误的结论。第二，**量化在我们这里没有变快**，这不是量化的问题，而是我们没有一个直接读 int8 的 kernel。下面会看到，这是 miniinfer 和工业引擎差距最大的地方。

## 时间花在哪里

用 v5（关掉投机）跑 8 个请求、各生成 64 个 token，把每一步拆开计时：

<RunOutput cmd=".venv/bin/python bench/breakdown.py" file="outputs/bench_breakdown.txt" caption="图 125-3　8 个请求的 decode：注意力占 24%，线性层等其余张量运算占 76%，Python 侧的调度、拼 batch 和采样只占 0.2%。单请求时 miniinfer 和 HuggingFace transformers 的速度相当。" />

**线性层占 76%。**每一步要把约 2.8 GiB 的 FP32 权重读一遍，CPU 的内存带宽决定了这一部分的下限。在 GPU 上，这部分换成 BF16（字节减半）、读 HBM（带宽高一两个数量级），再加上 INT8 或 FP8 的 kernel，能再快几倍。

**注意力占 24%。**这一部分比它“应该”占的多。原因有两个，都是我们为了代码清楚而付的代价：一是按请求用 Python 循环逐个算，8 个请求就是 8 次小的矩阵运算；二是 `SeqKV.read` 每层、每步都把这个请求的块**复制**成一块连续的内存，再交给注意力。工业引擎用一个 PagedAttention kernel（第 85 讲）一次处理所有请求，直接按块表去读，不复制。

**Python 侧只占 0.2%。**在我们这里，一步要 200 ms，调度和拼 batch 的几十微秒可以忽略。可是到了 GPU 上，一步 decode 只要几毫秒，同样的 Python 开销就会占到可观的比例。第 89 讲提到的 vLLM v0.6.0 的剖析里，API 服务器和调度加起来一度占了一步的六成。所以工业引擎要把调度放到单独的进程、和 GPU 计算异步地重叠，还要用 CUDA Graph 把一步里几百个 kernel 的发射合成一次。

**和 HuggingFace 差不多。**单请求生成 64 个 token，HuggingFace 4.15 s，miniinfer 4.76 s。transformers 的 `generate` 也是带 KV Cache 的逐 token 生成，在 CPU 上两者做的事几乎一样；miniinfer 慢一点，主要是分页带来的 KV 复制。我们的优势在多请求时才显现：HuggingFace 的 `generate` 没有 continuous batching，也没有分页和前缀缓存。

<Note kind="point">在 CPU 上，miniinfer 的时间主要花在线性层（76%），其次是注意力（24%），Python 的调度几乎可以忽略。换到 GPU 上，线性层会快得多，注意力里“逐请求循环 + 复制 KV”的写法和 Python 侧的开销就会变成主要矛盾，这正是工业引擎花大力气解决的地方。</Note>

## 离工业级引擎还差什么

把 miniinfer 的每个模块，和工业引擎的做法放在一起：

| 模块 | miniinfer 的做法 | 工业引擎的做法 | 原理讲 | 在哪里读 |
| --- | --- | --- | --- | --- |
| 注意力 | Python 循环逐个请求；按块表把 KV 复制成连续内存 | 一个 kernel 处理整个 batch：prefill 用 FlashAttention 的变长版本，decode 直接按块表读 KV | 75、76 | 第 127 讲 |
| 写 KV | 用下标张量逐位置写 | 一个小 kernel，按“槽位映射”一次写完整个 batch 的 K、V | 76 | 第 127 讲 |
| kernel 发射 | 每个运算一次发射，CPU 上不明显 | CUDA Graph 按 batch 大小分档预先捕获 | 79 | 第 127、129 讲 |
| 量化 | int8 → FP32 再做矩阵乘 | 融合的 W8A16 / FP8 kernel，直接读低位宽的权重 | 80–83 | 第 129 讲 |
| 调度 | 每步先 decode 再 prefill，整个提示一次 prefill | 统一的 token 预算，长提示分块 prefill，和 decode 混在同一步 | 69 | 第 129 讲 |
| 前缀缓存 | 进程内的链式哈希 | 稳定的哈希（可跨进程）、基数树（SGLang 的 RadixAttention）、跨机器的缓存池 | 68、101 | 第 129、131 讲 |
| 投机解码 | n-gram，贪心验证 | 小模型、EAGLE、MTP 起草；树形验证；支持随机采样的接受规则 | 85、86 | 第 129 讲 |
| 采样 | 只有贪心 | 温度、top-k、top-p、惩罚项、约束解码，在 GPU 上批量完成 | 65、71 | 第 129、131 讲 |
| 服务 | 一个 Python 函数 | HTTP / OpenAI 兼容接口、流式输出、调度和执行分进程、异步重叠 | 72、79 | 第 129、130 讲 |
| 多卡 | 不支持 | 张量并行、专家并行、PD 分离 | 93–100 | 第 127、130、132 讲 |

表里的每一行，都可以在 miniinfer 上动手做一版。几个适合练手的方向：

- **分块 prefill**：在调度器里给长提示设一个 token 预算，一步只算提示的一段，下一步接着算。要改的是 `Sequence.new_tokens()` 的切法和调度器的预算，模型不用改（第 77 讲）。
- **top-p 采样**：把引擎里的 `argmax` 换成第 73 讲的采样；投机解码的验证规则也要随之换成第 96 讲的接受-拒绝采样，才能保持分布不变。
- **流式输出**：让 `step()` 返回这一步每个请求新增的 token，外面用一个生成器把它们逐个吐出去。
- **按块表直接读的注意力**：不再复制 KV，而是对每个块分别算打分，用第 84、85 讲的在线 softmax 合并。这是通往 PagedAttention kernel 的第一步。

## 回顾

miniinfer 用约 400 行 Python 实现了一个推理引擎的骨架：v0 手写前向，v1 用 KV Cache 把 64 个 token 从 34 s 降到 4.55 s，v2 的 continuous batching 让吞吐提高到 1.9 倍，v3 的分页在 KV 紧张时再提高 34%，前缀缓存省掉了 95% 的重复 prefill，v4 把线性层的内存降到四分之一，v5 的投机解码在照抄型任务上让每次前向出 3.66 个 token。在 CPU 上，时间 76% 花在线性层、24% 在注意力，Python 的调度可以忽略。

和工业级引擎相比，最大的差距在 kernel（注意力、写 KV、量化矩阵乘）、发射开销（CUDA Graph）和服务化（异步调度、流式接口）。下一篇换一个角度：读一个真实的开源小引擎 nano-vllm，看它用一千多行代码怎么把这些补上。下一讲：**nano-vllm 的整体结构**。
