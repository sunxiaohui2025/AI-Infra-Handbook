上一讲的移植版在 MPS 上跑到了每步 33 ms。这个数字是快还是慢？第 141 讲已经算过一次下限：一步要读 1.19 GB 的权重，按机器的内存带宽，下限远低于 33 ms。差的部分在哪儿，得量。

第 66 讲讲过在 NVIDIA 卡上怎么读 Nsight 的时间线。换一块卡，工具名字和界面全变了，但要回答的问题没变。这一讲给出一套和工具无关的做法：时间线上该看哪几件事；按什么顺序找瓶颈；以及在本机用 PyTorch 的 profiler 真实量一遍，看它能告诉我们什么、不能告诉我们什么。

## 时间线上看三样东西

厂商 profiler 的输出形式各不相同（有的是时间线，有的只有汇总表），但只要能拿到“哪个 kernel、什么时候开始、持续多久”，就能看出三件事。

<ProfilerTimeline caption="图 142-1　一步 decode 的时间线（模拟数据，模型同第 66 讲：Llama-3-8B、TP=4）。两行：上面是 CPU 在发射 kernel，下面是设备在执行。点一个 kernel 看它的耗时和实际带宽；切换 eager / 图捕获看空隙的变化。" />

**第一样：两行之间的关系**。CPU 这一行是发射，设备那一行是执行。设备那一行**有空隙**，说明它在等 CPU——瓶颈在下发，不在硬件。设备那一行**排满**，说明硬件在满负荷干活，这时候才该去看单个 kernel 快不快。

**第二样：最长的那几个 kernel**。按耗时排序，看前五个占了多少。decode 一步里排在前面的应该是几个大矩阵乘；如果排在前面的是类型转换、拷贝、转置这类算子，说明有东西写得不对。

**第三样：空隙的位置**。规律的、每层一次的空隙，通常是同步点（把一个数拷回主机、等一次事件）。一次很长的空隙，通常是主机侧在做慢操作（Python 里的循环、重新分配显存、JIT 编译一个 kernel）。

<Note kind="warn">换到一块新卡时，profiler 本身就是要适配的东西之一（第 134 讲的第九层）。常见的坑：时间线里只有 CPU 侧的时间、没有设备侧；kernel 名字是内部编号，对不上源码里的算子；时间戳的两个时钟没对齐，CPU 和设备的时间线错位。所以 profiler 的数字要和一个你自己写的、只用计时器的粗测互相印证——下面就是这么做的。</Note>

## 按什么顺序找

有了数据，接下来是顺序问题。四类瓶颈——下发开销、访存、计算、通信——该先看哪个？答案取决于负载：

<BottleneckOrder caption="图 142-2　decode 和 prefill 两种负载下找瓶颈的推荐顺序。点一类看它的症状、确认办法和常见改法；切换负载看顺序怎么变。" />

decode 先看下发开销，理由是性价比：去掉一个同步点、开一次图捕获，改动小、收益大，而且这类问题在新硬件上普遍存在（第 141 讲那一行 `int(pos[-1])` 就是 13%）。prefill 反过来：kernel 本身就很长，下发可以忽略，先看算力有没有用上。

两种负载在真实服务里是混在一起的（第 77 讲的分块 prefill），所以要分开量：一次只跑纯 decode，一次只跑长 prefill。混在一起量出来的平均值，既不能解释 TTFT 也不能解释 TPOT。

## 在本机真的量一遍

下面这份脚本在 MPS 上做三件事：用 profiler 按算子汇总，用显式同步按段汇总，再量两个固定开销。

<RunOutput cmd=".venv/bin/python bench/port_profile.py" file="outputs/port_profile.txt" caption="图 142-3　Qwen3-0.6B 一步 decode 在 Apple M2 的 GPU 上的分析（FP16，上下文 199 token，本机真实运行）。" />

这份输出里有三个值得琢磨的地方。

**第一段：`aten::copy_` 占了 63%**。按算子汇总的第一名不是矩阵乘，而是拷贝，844 次。这就是上一节说的“排在前面的是拷贝类算子，说明有东西写得不对”的真实样本。追下去，这些拷贝来自两处：RMSNorm 里为了防溢出做的 `x.float()` 和 `.to(dtype)`（第 139 讲），以及 RoPE 里的类型转换。113 次 RMSNorm、28 次 RoPE，每次两三个拷贝，就是八百多次。

**第二段：注意力 43%、FFN 23%、其余 34%**。这个比例和第一段的算子汇总不矛盾，但角度不同：按算子看，时间散在拷贝里；按段看，时间集中在注意力。两种视角要一起用——按算子能发现“哪类操作有问题”，按段能回答“改哪一部分最值”。

<Note kind="point">在异步后端上，**不显式同步的分段计时是错的**。设备上的 kernel 是排队执行的，CPU 侧的某一次调用会在队列积压时被阻塞，于是这段时间被记到“恰好等到的那次调用”头上，而不是真正慢的那次。这一段的代码在每段边界都调了 `synchronize()`：代价是一步从 33 ms 涨到 54 ms（同步本身要钱），好处是比例可信。第 66 讲在 CUDA 上强调的也是同一件事。</Note>

**第三段：两个固定开销和一个写法对比**。下发一个小 kernel 3.6 μs，把一个数拷回主机 158 μs，相差 44 倍——这个比例在不同硬件上不一样，但量级关系是普遍的，所以“热路径上不要把数据拷回主机”是条通用规则。

最后两行是一次具体的优化判断。RMSNorm 的两种写法：把整个张量升到 FP32（现在的写法，37.0 μs），或者只让归约在 FP32 里做（25.9 μs）。后者快 11 μs，一步调用 113 次，省 1.3 ms，约占一步的 4%；两者数值差 1%，是 FP16 的舍入，在第 139 讲的阈值内。

4% 值不值得改？这是个取舍，不是定论：第 83 讲的 Amdahl 定律说它只能带来 1.04 倍；而它要改的是一处和数值安全直接相关的代码（溢出就是在这里修掉的）。我们这里选择不改，把它记在待办里，等到真正受带宽限制、而且有了融合的 RMSNorm 算子时一起处理。**把判断过程写下来，比改或不改更重要**——第 153 讲的清单里有一项就是“每个被放弃的优化都要记下理由”。

## 判断单个 kernel 够不够好

定位到某个 kernel 之后，还要回答“它还有多少空间”。不管用哪家的工具，判据只有两条，而且都只需要三个数：这个 kernel 的耗时、它读写了多少字节、它做了多少次乘加。

$$
\text{实际带宽} = \frac{\text{读写字节}}{\text{耗时}}, \qquad \text{实际算力} = \frac{2MNK}{\text{耗时}}
$$

把两者分别和官方的带宽、峰值算力比，就知道这个 kernel 卡在哪一边、离上限多远（第 62、67 讲）。几条经验阈值：受带宽限制的 kernel 做到标称带宽的 80% 以上就接近极限了，60% 以下说明访存模式有问题（不连续、跨步、没对齐）；受算力限制的矩阵乘做到峰值的 70% 以上算好，30% 以下通常是分块或对齐的问题（第 143 讲）。

厂商工具里的字段名各不相同，但大多能对应到这几件事：

| 要回答的问题 | 工具里常见的字段 | 看出什么 |
| --- | --- | --- |
| 访存效率 | 内存吞吐、L2 命中率、访存事务数 | 实际带宽占标称的几成；事务数远多于理论值说明访存不连续 |
| 占用率 | 每个计算单元驻留的线程组数、寄存器用量、片上存储用量 | 哪项资源先用完（第 86 讲的 `TileOccupancy`） |
| 指令构成 | 矩阵指令占比、标量/向量指令占比 | 矩阵核心有没有被喂满；标量指令过多说明地址计算或控制流太重 |
| 等待原因 | 停顿分类（等访存、等同步、等依赖） | 哪一类等待最多，决定改访存还是改流水 |

有一点要留意：**占用率高不等于快**。一个把寄存器用得很省、驻留了很多线程组的 kernel，可能因为每个线程手里的累加器太少而反复读写片上存储。第 86、87 讲算过这笔账，第 143 讲会在矩阵单元的形状上再碰到它。

## 没有好 profiler 的时候

新硬件上常遇到的情况是工具还不好用。有四种办法，都只依赖计时器：

**分段计时加同步**。就是上面第二段的做法：在你关心的边界前后同步再计时。能回答“哪一段占时间”，代价是同步本身的开销会让总时间变长。

**删一段再量（差分法）**。把某一段跳过去（比如把 FFN 换成一个形状相同的空操作），量总时间的变化。它的好处是不需要工具支持；坏处是数学变了，只能用于定位，不能用于验证。

**改一个参数看斜率**。这是最可靠的归因办法，因为它不依赖任何内部可见性。把权重精度从 FP32 换成 FP16：如果时间几乎减半，就是受访存限制；如果几乎不变，就是受下发或算力限制。把上下文从 200 加到 2000：如果每步时间按比例涨，注意力就是主项；如果几乎不变，就是权重读取占主导。第 141 讲表里的几行其实都是这种实验。

**数 kernel 和算理论值**。一步有多少次算子调用（第 140 讲的办法），乘上单次下发的开销，就得到下发开销的下限；要读多少字节除以官方带宽，得到访存的下限。两个下限哪个更接近实测，瓶颈就在哪边。

<Note kind="column">第 67 讲提过“实测和理论的差距”这个习惯：每量到一个数，先算出它的理论下限，再看差多少倍。在新硬件上这个习惯更重要，因为你对这块卡没有直觉。本机的例子：FP16 下一步 32.9 ms、要读 1.19 GB，有效带宽 36 GB/s；换成 FP32 是 2.38 GB、49.3 ms，有效带宽 48 GB/s。两个数都远低于这台机器的内存带宽，而且**精度越低效率越差**——这就把“固定开销占比上升”这件事量出来了。</Note>

## 调优的记录该怎么写

性能工作最容易丢的不是数字，而是上下文。一条记录至少要有这些字段，缺了任何一项，几周后就复现不出来：

| 字段 | 例子 |
| --- | --- |
| 硬件与软件版本 | Apple M2，PyTorch 2.15，MPS 后端 |
| 模型与精度 | Qwen3-0.6B，FP16 权重 |
| 负载 | 上下文 199 token，batch 1，纯 decode，64 步 |
| 测的是什么 | 每步 forward 的时间，前后都同步，预热 4 步 |
| 结果 | 32.9 ms/步 |
| 理论下限与差距 | 1.19 GB ÷ 带宽；实测有效带宽 36 GB/s |
| 这次改了什么 | `end` 由参数传入，去掉每层一次的主机同步 |
| 相比上一次 | 49.3 → 32.9 ms（含换精度），其中去同步贡献约 13% |

海光的插件仓库里把这件事做成了公开的 `docs/validation/` 目录：每个配置一份记录，写明冻结的环境、硬件、后端、并行拓扑和各数据集的分数（第 139、149 讲）。做适配时抄这个格式就够用了。

## 回顾

在一块陌生的卡上做性能分析，第一步是从时间线上看三样东西：CPU 和设备两行的关系（有空隙就是下发瓶颈）、最长的几个 kernel（如果是拷贝类算子就说明写法有问题）、空隙的位置（规律的空隙是同步点）。找瓶颈的顺序按负载定：decode 先看下发和同步，再看访存，最后才是算力；prefill 反过来。本机的实测演示了这套做法的结果：按算子汇总第一名是 844 次拷贝（占 63%，来自防溢出的类型转换），按段汇总注意力占 43%；异步后端上分段计时必须显式同步，否则时间会被记到错误的调用上；一次主机同步 158 μs，是一次小 kernel 下发的 44 倍。工具不好用时，靠分段计时、差分、改一个参数看斜率、数 kernel 算下限这四招也能定位。
