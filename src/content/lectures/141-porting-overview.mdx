前五章的每一行代码、每一个数字，背后都默认站着一块 NVIDIA 的卡：第 86 讲的线程网格是 CUDA 的，第 84 讲的 FlashAttention 来自一个只编译 CUDA 的库，第 101 讲的 All-Reduce 走 NCCL。现在把这些东西搬到另一块卡上：一台装了 8 张国产加速器的机器，手里是同一份 Qwen3 权重和同一个 vLLM。

第一个问题不是“快不快”，而是“从哪里开始”。这一讲把模型和芯片之间的东西拆成九层，说清楚每一层是谁的责任、换卡时哪些能原样沿用、哪些有对应物但要翻译、哪些必须从头重写，以及这些工作该按什么顺序做。后面七讲是这张图上的几层各自展开，第 21 篇是把这张图套到海光 DCU 上。

## 九层：从模型文件到驱动

我们从一个具体的调用开始往下看。一个用户请求进来，vLLM 最终要算出 `x @ w`（第 144 讲会逐层追这一次调用）。这一次矩阵乘法要穿过下面这些东西：

<StackMap route="cuda" caption="图 141-1　从模型到芯片的九层。先看 NVIDIA 这一列：每层都有现成的东西，所以“换卡要重做什么”这个问题在 CUDA 上不存在。点任意一层看它负责什么；切换到另外两条路线，看同一层变成了什么、工作量是“沿用”“翻译”还是“重写”。" />

自上而下过一遍，顺便说清每层的职责边界——边界划在哪里，决定了换卡时谁必须改。

**模型代码**。`Qwen3ForCausalLM` 这样的类，只描述张量怎么流动：先 RMSNorm，再投影，再注意力。它不关心张量在哪块卡上。所以这一层是最该原样复用的——除非代码里写死了 `device="cuda"` 或者 `.cuda()`，这类写法在第 143 讲会专门清点。

**推理引擎或训练框架**。vLLM、SGLang、Megatron。它们管的是调度、KV 块、批处理、分布式的组织方式（第 10 篇、第 13 篇）。这些逻辑和硬件无关，但引擎里有一层**平台抽象**：设备叫什么名字、用哪个注意力后端、用哪个通信器、一块卡有多少显存。这一层是厂商插件接进来的地方（第 154 讲）。

**深度学习框架**。PyTorch。它要回答一个很具体的问题：`x @ w` 这个调用，最终执行哪一份机器码？答案由**分发器**（dispatcher）给出：按张量的设备类型和数据类型，查表找到注册在这个设备上的算子实现。换卡时这一层有两种接法——沿用 CUDA 的分发键，或者注册一个全新的设备——第 144 讲细讲。

**图编译**。`torch.compile` 把 Python 代码捕获成一张计算图，做融合、常量折叠，再交给后端生成代码。NVIDIA 上默认的后端是 Inductor + Triton。有的硬件更依赖这一层，因为它要求一次把整张图交给硬件（第 145 讲）。

**算子库**。cuBLAS 管矩阵乘，cuDNN 管卷积，CUTLASS 是写矩阵乘 kernel 的模板库，FlashAttention 是一个专门的注意力库。它们的共同点是：针对某一代硬件的指令形状、缓存容量、线程组宽度，手工调到接近峰值。这意味着它们**不可移植**——不是语法上不能编译，而是调好的参数换一块卡就不再是最优（第 150 讲）。

**kernel 语言与编译器**。CUDA C++ 和 nvcc，往下是 PTX 和机器码。Triton 是另一条路：用 Python 写块级的 kernel，由它的编译器生成各家后端的代码（第 88 讲）。这一层是“手写 kernel”的落脚点，也是迁移时最容易卡住的地方（第 143、151 讲）。

**集合通信库**。NCCL 实现 All-Reduce、All-Gather、All-to-All（第 100 讲），而且知道机内 NVLink、机间网卡的拓扑，会据此选算法（第 102 讲）。每家都有自己的对应物（第 153 讲）。

**运行时与驱动**。设备枚举、显存分配、流和事件、kernel 发射。这一层是纯粹的厂商实现，没有复用的余地；它决定了上面所有层能不能工作。

**工具**。`nvidia-smi` 看卡的状态，Nsight Systems 看时间线，Nsight Compute 看单个 kernel。调优全靠它们，所以这一层缺了的话，第 20 篇讲的所有分析方法都无从下手（第 149 讲）。

层与层之间的接口，决定了换卡时改动能不能被挡住：

| 接口 | 上面的人看到什么 | 下面的人要提供什么 | 换卡时谁改 |
| --- | --- | --- | --- |
| 模型 ↔ 引擎 | `forward(input_ids, positions)` | 一个能执行前向的 runner | 都不改 |
| 引擎 ↔ 平台层 | `current_platform.get_attn_backend_cls()` 等几十个方法 | 一个 Platform 子类 | 厂商写插件 |
| 框架 ↔ 算子 | `torch.matmul(x, w)` | 注册在这个设备上的 kernel | 厂商注册算子 |
| 算子 ↔ 运行时 | `hipLaunchKernel` / `cudaLaunchKernel` | 发射、同步、分配显存 | 厂商实现运行时 |

<Note kind="point">换卡这件事，之所以不是“重写整个栈”，是因为上面四层（模型、引擎、框架的 Python 接口、图的表示）都站在接口的上方；真正要重做的是接口下方的实现。工作量的大小，取决于厂商选择在哪一层接入。</Note>

## 量一下：和硬件绑定的代码有多少

“上面几层能复用”这句话要落到数字上。第 17 篇读过的 nano-vllm 是个好标本：一千多行，功能完整，依赖关系清楚。把它的源码按上面的分层扫一遍，数出每一行里和 NVIDIA 绑定的写法：

<RunOutput cmd=".venv/bin/python bench/port_inventory.py" file="outputs/port_inventory.txt" caption="图 141-2　把 nano-vllm 搬到非 NVIDIA 的卡上要动的代码（只读源码文本统计，不运行）。1195 行里和 NVIDIA 绑定的有 52 行，占 4.4%。" />

52 行，4.4%。这个数字容易让人乐观，所以要马上接一句反直觉的：**这 52 行的改动量很小，它们背后的工作量很大**。

逐类看背后是什么：

- 23 行“设备与运行时”，改法确实只是换个名字（`torch.cuda.set_device` → 新设备的对应方法），前提是**框架已经认识这块卡**。这个前提背后是整个 PyTorch 的后端移植：几千个算子的实现、一个显存分配器、流和事件的语义。
- 3 行“第三方 CUDA 算子库”（`from flash_attn import ...`）是整件事里最重的一条。换卡后这一行要么指向厂商的移植版，要么你自己实现一个变长 FlashAttention。第 84 讲算过它为什么必须手写：注意力矩阵不能落地，要分块在线 softmax。
- 13 行“自写的 GPU kernel”（Triton 写的写 KV 的 kernel，第 133 讲）需要这块卡有可用的 Triton 后端；有后端也不等于性能对得上，为 NVIDIA 调的块大小和 warp 数要重调（第 151 讲）。
- 7 行“图捕获”（CUDA Graph，第 89 讲）可以先关掉，代价是 decode 的每一步多出几百次 kernel 发射的开销；在下发开销占比高的硬件上，这个代价可能是几成的吞吐。
- 6 行“通信”里的 `dist.all_reduce` 本身不用改，改的是初始化时的后端名字和它背后的通信库。
- “精度与数据类型”一行都没匹配到，但它恰恰是第 146 讲整讲在处理的问题：BF16 还是 FP16 来自模型的 `config.json`，换卡后它们在数值上的差别才显形。

所以适配工作的总量，不由仓库里有多少行带 `cuda` 的代码决定，而由**这些行背后的库在新硬件上成熟到什么程度**决定。同一个 vLLM，在一块软件栈完整的卡上可能两天跑通，在一块算子库刚起步的卡上可能要两个月。

## 两种接法，两种工作量分布

把 StackMap 切到另外两条路线，同一张图会换一副面孔。两条路线的区别不在硬件好坏，而在**选择在哪一层和 CUDA 生态对齐**。

<StackMap route="gpgpu" focus={[2, 4, 5]} caption="图 141-3　兼容 GPGPU 路线（以 AMD 的 ROCm 为代表，海光 DCU 也走这条路）。高亮的三层是工作量的大头：框架重新编译、算子库重写或重调、kernel 语言靠工具翻译加手改。" />

**兼容路线**：提供一套和 CUDA 一一对应的运行时接口（HIP），提供一个把 CUDA 源码翻成它的工具（hipify），把 PyTorch 用这套接口重新编译一遍。这样做的回报很直接：PyTorch 对外仍然报告 `cuda` 设备，`torch.cuda.is_available()` 返回真，上面四层的 Python 代码几乎一行不用改。代价是你继承了 CUDA 的全部概念，包括那些和硬件细节绑死的概念——线程组宽度就是最典型的一个，CUDA 的 warp 是 32 个线程，AMD 和海光的波前（wavefront）是 64 个，任何假设“32”的代码都会算错（第 142、143 讲）。

<StackMap route="npu" focus={[3, 5, 7]} caption="图 141-4　NPU 路线（以华为昇腾的 CANN 为代表）。高亮的三层是和 GPGPU 路线最不一样的地方：图模式成了主路径，kernel 语言是另一套编程模型，运行时接口完全不同。" />

**重写路线**：硬件本身就不是 SIMT 的，kernel 里要显式安排数据在片上缓冲之间的搬运，CUDA 的 kernel 没法翻译，只能按厂商的语言重写。框架这一层用 PyTorch 的 `PrivateUse1` 机制注册一个新设备名（第 144 讲），`.cuda()` 变成 `.npu()`，所有写死 `cuda` 的地方都要改。换来的好处是不必背 CUDA 的历史包袱，而且这类硬件往往更吃“整图下发”，图编译那一层能做更激进的融合（第 145 讲）。

两条路线的工作量分布，也就是 StackMap 里“沿用 / 翻译 / 重写”的那一列：兼容路线把工作量压在算子库和 kernel 上，上层基本不动；重写路线在每一层都要出力，但每一层都能按自己的硬件重新设计。

<Note kind="warn">“兼容”不等于“不用改”。hipify 能翻译的是 API 名字，翻不动三样东西：内联汇编（PTX 是 NVIDIA 的指令集）、假设线程组宽度是 32 的写法、CUDA 独有的库（cuDNN 的某些算子、cuSPARSE 的某些格式）。第 143 讲会逐行看这三类。</Note>

## 按什么顺序做

拿到一块新卡，最常见的失败方式是一上来就调性能：还没确认输出是对的，就在量 kernel 耗时，最后发现快了三成的那个 kernel 算错了。可行的顺序是三段，每段有明确的验收标准：

| 阶段 | 做什么 | 验收标准 | 对应的讲 |
| --- | --- | --- | --- |
| 跑通 | 装好驱动和工具包，框架能看见卡；模型能前向一次，不报错 | `单卡单请求能生成 token`，缺失算子都有去处 | 136、137、140 |
| 跑对 | 和一个可信的参考比对输出 | 逐层误差在阈值内，贪心生成逐 token 一致，评测分数不掉 | 139 |
| 跑快 | 找瓶颈、改 kernel、调通信、开图模式 | 达到目标 TPOT 和吞吐，和理论上限的差距可解释 | 142–147 |

这个顺序里有两条不能换：**“跑对”一定在“跑快”之前**，因为优化几乎每一步都在改变数值（融合改变累加顺序，低精度改变舍入，第 146 讲），没有基线就无法判断是优化引入的错误还是本来就有的误差；**“缺失算子有去处”一定在“跑对”之前**，因为一个悄悄回退到 CPU 的算子既会让性能面目全非，也可能掩盖精度问题（第 147 讲）。

第三阶段的内部也有顺序，第 149 讲会用 profiler 的时间线来讲：先看下发开销（CPU 是不是跟不上），再看访存，再看计算，最后看通信。顺序的理由是性价比——关掉一个不必要的同步、开上图模式，这类改动一行代码就能换来几成，而重写一个 kernel 要几天。

## 什么时候这张图会翻转

上面说“模型代码和引擎能复用”，这是针对当下主流的稠密模型和标准注意力说的。有三种情况会让结论变样：

**模型用了专有算子**。DeepSeek-V3 的 MLA（第 40 讲）需要一个把压缩、还原和注意力融在一起的 kernel；MoE 的 All-to-All（第 108 讲）在 DeepEP 这样的库里和网卡深度绑定。这类模型在新硬件上的“适配”，实际上是把几个最关键的 kernel 重写一遍，上层代码复用的比例反而最低。

**负载偏向 decode**。decode 的每一步都是小矩阵乘加大量访存（第 68 讲），kernel 本身很短，发射开销和同步开销占比很高。这时候图模式、下发路径的长度、甚至 Python 侧的代码效率都会直接变成吞吐差异，而这些都在框架和运行时那两层——不在算子库里。第 148 讲会在本机的 Apple MPS 上实测这件事：同一个模型，只是去掉每层一次“把一个数拷回 CPU”的同步，decode 每步就从 55 ms 降到 49 ms。

**要多卡**。单卡跑通和八卡跑通是两件事。通信库的拓扑感知、P2P 能不能用、自定义 All-Reduce 在什么消息大小下才划算（第 153 讲），这些问题在单卡阶段完全看不见。

## 回顾

换一块卡，要重做的不是整个栈，而是九层里接口下方的实现。上面四层（模型、引擎、框架接口、图表示）设计上就和硬件无关，所以 nano-vllm 一千多行里只有 4.4% 需要改；但这 4.4% 背后是框架后端、算子库、kernel 编译器、通信库这几件大工程，它们的成熟度才是适配周期的真正决定因素。两条技术路线的差别在于选择在哪一层对齐 CUDA 生态：兼容路线让上层几乎不改、把压力集中在算子库和 kernel，重写路线每层都要出力、但能按自己的硬件重新设计。工作顺序是跑通、跑对、跑快，三段不能颠倒。

下一讲往硬件里面看一层。同样是“加速器”，GPGPU 和 NPU 的计算单元、线程组宽度、片上存储组织得很不一样——而这些差异会直接改变第 62 讲那张 Roofline 图的形状，以及一个算子该怎么写。一块卡的波前是 64 个线程而不是 32 个，对 kernel 来说到底意味着什么？
