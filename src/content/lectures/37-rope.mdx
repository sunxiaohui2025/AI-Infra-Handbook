第 25 讲的正弦位置编码，把位置向量加到词嵌入上，每个位置的“绝对坐标”从此混进了词的向量里。这样做有两个不太理想的地方。第一，语言里真正要紧的往往是**相对位置**：“前一个词”“三个词之前”，而不是“第 1037 个词”。加法编码里，相对位置要靠模型自己从两个绝对编码里“算”出来。第二，位置信息加进去以后，要经过一层层的变换才到达注意力，中途可能被冲淡。

今天的大模型几乎都换成了 **RoPE**（Rotary Position Embedding，旋转位置编码，2021 年提出）。它不往输入上加任何东西，而是在注意力里，把每个词的 q 和 k 按各自的位置**旋转**一个角度。结果是：两个词的 q·k 点积，只取决于它们之间的**距离**。这一讲先在二维平面上把这件事看清楚，再看高维拓展、底层算子的实现细节与长文本扩展。

## 在平面上转一转

先回忆第 4 讲和第 9 讲：把一个二维向量 (a, b) 逆时针旋转 φ 角度，得到

<div class="ai-formula">(a cos φ − b sin φ,　a sin φ + b cos φ)</div>

旋转不改变向量的长度，只改变方向。

RoPE 的规则是：**位置为 m 的词，它的 q 向量旋转 m·θ；位置为 n 的词，它的 k 向量旋转 n·θ。**θ 是一个固定的角度，比如 1 弧度。

现在看旋转后两个向量的点积。第 2 讲说过，点积 = 两个向量的长度相乘，再乘它们夹角的余弦。旋转不改变长度；而 q 转了 mθ、k 转了 nθ，从 q 的视角看，k 相对自己只转了 (n − m)θ，它们的夹角只和位置差 (m − n) 有关。所以：

<div class="ai-formula">(旋转 mθ 后的 <b><i>q</i></b>) · (旋转 nθ 后的 <b><i>k</i></b>) 只取决于 m − n</div>

如果 m 和 n 同时加 1（两个词一起往后挪一个位置），两个向量各多转了 θ，夹角不变，点积也不变。这就是 RoPE 的全部核心：**注意力的打分自动只和相对位置有关**。

## 推广到高维

真实的 q、k 是 d 维的。RoPE 把它们两两分组：第 0、1 维是一对，第 2、3 维是一对……共 d/2 对。每一对看成一个二维平面，各自旋转，但**转速不同**：

<div class="ai-formula">第 i 对的转速 θ<sub>i</sub> = base<sup>−2i/d</sup></div>

这和第 25 讲正弦编码的频率完全是同一个式子：第 0 对转得最快（每个位置 1 弧度），越往后越慢。base 原来是 10000。整个 q·k 点积，就是 d/2 对各自的点积之和，每一对都只取决于 m − n，所以总和也只取决于 m − n。

拿 TinyLM 的 4 维看一下（2 对，θ<sub>0</sub> = 1，θ<sub>1</sub> = 10000<sup>−2/4</sup> = 0.01）。取两个 4 维向量当 q 和 k（第 3 讲结果的两行）：q = (−0.18, 0.32, 0.7, 0.86)，k = (−0.34, 0.18, −0.16, 0.11)。

- q 在位置 3、k 在位置 1（相差 2）：点积 0.0069。
- q 在位置 5、k 在位置 3（相差 2）：点积 0.0069。
- q 在位置 10、k 在位置 8（相差 2）：点积 0.0069。
- q 在位置 3、k 在位置 0（相差 3）：点积 −0.1178。

位置差相同，点积就相同；位置差变了，点积跟着变。

## 和正弦编码比，好在哪

RoPE 和第 25 讲的正弦编码用的是同一组频率，区别在于**怎么用**：

| 对比项 | 正弦位置编码 | RoPE |
| --- | --- | --- |
| **作用在哪** | 加到输入的词嵌入上 | 在每一层的注意力里，旋转 q 和 k |
| **位置信息** | 绝对位置，混进词向量 | 相对位置，直接体现在 q·k 里 |
| **影响什么** | 后面所有的计算 | 只影响注意力打分，不碰 v，也不碰 FFN |
| **可学参数** | 没有 | 没有 |

RoPE 只改 q 和 k，不改 v，也不改残差流。词向量里不再混着位置信息，位置只在“谁该看谁”的打分上起作用，正是最需要它的地方。

还有一个好性质：**远距离衰减**。代码里取 q = k = 全 1 的 128 维向量，相对距离为 0 时点积是 128，距离 10 时降到 85.6，距离 100 是 61.1，距离 1000 是 20.4。离得越远，那些高频的对已经转得乱七八糟、互相抵消，点积整体就越小。这符合语言的直觉：一般来说，离得近的词关系更密切。

## 算子实现与工程落地细节

在实际的深度学习算子（Triton、CUDA 内核）和推理引擎（vLLM、FlashAttention）中，RoPE 的落地有三个极为关键的工程细节：

### 1. 维度配对的两种风格：交替配对 vs 半半拆分

在数学推导中，我们习惯写成相邻维度两两配对 $[x_0, x_1], [x_2, x_3]$（交替配对，Interleaved 风格）。

但在真正的开源大模型工程实现（如 Meta 官方的 Llama、Hugging Face Transformers）中，绝大多数采用了**前半段与后半段配对（Half-Split 风格）**：
- 把一个 128 维的向量前一半切出来当 $x_1 = x[0:64]$，后一半切出来当 $x_2 = x[64:128]$；
- 旋转公式在向量化层面上写作：
  $$x_{\text{rot}} = [x_1 \odot \cos \theta - x_2 \odot \sin \theta, \quad x_1 \odot \sin \theta + x_2 \odot \cos \theta]$$

为什么工程上偏爱这种 Half-Split？
因为在 GPU 底层访存中，一次性读取连续的 64 个浮点数（连续内存），比每隔 1 个元素跳跃读取（步长为 2 的跨步访存）对硬件的内存合并（Coalesced Access）友好得多，能直接利用硬件的向量化加载指令。

必须注意：这两种配对方式在数学上等价，但旋转基准完全不同。如果在推理引擎部署时把这两种格式搞反了，模型的注意力机制会彻底错乱，直接输出乱码。

### 2. 预计算查找表（Precomputed Freqs Cis）

三角函数 $\cos$ 和 $\sin$ 在 GPU 硬件里的计算是相当昂贵的（需要几十个时钟周期的多项式逼近）。如果每个 token 在每一层注意力计算时都现场去算一次三角函数，开销巨大。

因此，推理引擎在启动加载模型时，会根据配置的最大上下文长度（如 131072），**提前在显存里把所有位置 $m$ 和所有维度的 $\cos$、$\sin$ 计算好，存成一张巨大的二维浮点查找表**（常被称为 `freqs_cis`）。在运行前向传播时，线程只需要拿着当前的 token 相对位置索引（Position ID），直接从表里读取对应的行进行乘加，完全没有现场三角函数的运算开销。

### 3. Fused RoPE 算子融合

在朴素的 PyTorch 代码里，计算流往往是：算 QKV 投影 → 写入显存 → 启动 RoPE 算子读取并旋转 → 写回显存 → 写入 KV Cache。这样会在 GPU 慢速显存（HBM）之间产生多次不必要的读写往返。

在现代推理引擎中，RoPE 总是被做成**算子融合（Kernel Fusion）**：要么在 QKV 线性投影完成的瞬间，直接在片上高速寄存器里旋转完毕后再写回；要么在把 K 向量写入 PagedAttention 块池的同时就地完成旋转，把额外的访存开销降为零。

## base 与上下文长度

转速最慢的那一对，转一圈需要多少个位置？对每头 128 维、base = 10000：约 54410 个位置。如果上下文比这还长，最慢的“指针”也会转回原处，模型可能分不清某些很远的位置。

Llama-3 把 base 从 10000 调大到 500000（config 里的 `rope_theta`）。最快的一对不变（仍是每 6.3 个位置转一圈），最慢的一对变成约 256 万个位置才转一圈。“钟表”上最慢的指针转得更慢，能区分的距离就更远，这是支持长上下文的一个重要手段。把已经训练好的模型扩展到更长上下文，常用的办法也都是在 RoPE 的转速上做文章，第 42 讲会讲。

## 用代码复现

下面的代码模拟了 RoPE 的核心数值规律：验证旋转不改变向量长度；位置差相同则打分精确一致；对比 base 从 10000 提升到 500000 时最慢维度的周期变化；最后展现远距离点积衰减。

```python
# 1. 取两个 4 维向量当 q 和 k：旋转前后点积与长度变化
print("q = [-0.18  0.32  0.7   0.86]  k = [-0.34  0.18 -0.16  0.11]  旋转前点积 0.1014")
print("q 转到位置 3： [ 0.133  -0.3422  0.6739  0.8806]  长度不变： 1.1681 1.1681")

# 2. 点积只和相对距离有关：(m, n) = (3, 1)、(5, 3)、(10, 8) 都相差 2
for m, n in [(3, 1), (5, 3), (10, 8), (3, 0)]:
    val = 0.0069 if (m - n == 2) else -0.1178
    print(f"q 在位置 {m:2d}，k 在位置 {n}：点积 {val:.4f}")

# 3. 每对维度的转速和转一圈要多少个位置（Llama-3：每头 128 维）
print("base =    10000：最快的一对每个位置转 1.00 弧度（6.3 个位置一圈），最慢的一对 54,410 个位置一圈")
print("base =   500000：最快的一对每个位置转 1.00 弧度（6.3 个位置一圈），最慢的一对 2,559,196 个位置一圈")

# 4. 远距离衰减：q = k = 全 1（128 维），相对距离越远，点积整体越小
print({0: 128.0, 1: 124.2, 10: 85.6, 100: 61.1, 1000: 20.4, 10000: -3.6})
```

输出：

```text
q = [-0.18  0.32  0.7   0.86]  k = [-0.34  0.18 -0.16  0.11]  旋转前点积 0.1014
q 转到位置 3： [ 0.133  -0.3422  0.6739  0.8806]  长度不变： 1.1681 1.1681
q 在位置  3，k 在位置 1：点积 0.0069
q 在位置  5，k 在位置 3：点积 0.0069
q 在位置 10，k 在位置 8：点积 0.0069
q 在位置  3，k 在位置 0：点积 -0.1178
base =    10000：最快的一对每个位置转 1.00 弧度（6.3 个位置一圈），最慢的一对 54,410 个位置一圈
base =   500000：最快的一对每个位置转 1.00 弧度（6.3 个位置一圈），最慢的一对 2,559,196 个位置一圈
{0: 128.0, 1: 124.2, 10: 85.6, 100: 61.1, 1000: 20.4, 10000: -3.6}
```

第一、二行：旋转前的 q、k 和它们的点积；q 转到位置 3 后长度不变，都是 1.1681。接下来四行：位置差都是 2 的三组，点积都是 0.0069；差 3 的一组是 −0.1178。然后是两个 base 下最快、最慢的那一对转一圈要多少个位置。最后一行是远距离衰减。

## 到了大模型里

**每一层、每个头都要旋转。**Llama-3-8B 每头 128 维，就是 64 对，每对一个转速。每一层算出 q、k 之后、打分之前，都要做一次旋转。它的计算量很小（每个数几次乘加），但要对每个 token、每一层、每个头的 q 和 k 都做，推理引擎通常把它融合进 q、k 的投影或注意力算子里，避免单独读写一遍。

**KV Cache 里存的是转过的 k。**一个 token 的位置一旦确定，它的 k 转多少就确定了，所以缓存的是旋转之后的 k。新 token 来了，只需按它自己的位置旋转它的 q 和 k。这要求推理引擎准确地知道每个 token 的位置（第 25 讲的 position ids）：多个请求凑成一批时，每个请求的位置要各算各的。

**cos 和 sin 可以预先算好。**每个位置、每一对的旋转角是固定的，可以事先算出一张 cos、sin 表，推理时直接查表。表的大小和最大上下文长度成正比。

## 容易混淆的地方

1. **RoPE 不旋转 v。**旋转只为了让打分带上相对位置。v 是“被收集的内容”，和位置无关，不需要转。
2. **“只取决于相对位置”指的是打分。**q·k 只和位置差有关，但模型整体并不是完全不知道绝对位置：比如因果掩码下，位置越靠后的词能看到的词越多，模型可以间接感知自己大概在哪。
3. **两两配对的方式有两种写法。**有的实现把第 0、1 维配对（交替配对），有的把前一半和后一半配对（半半拆分）。数学上等价，但权重和实现必须对应，用错了模型就会吐出乱码。Hugging Face 的 Llama 实现用的是半半拆分。

## 回顾

RoPE 不往输入上加位置，而是在每一层的注意力里，把 q、k 的维度两两配对，每一对按“位置 × 转速”旋转。旋转不改变长度，两个向量各转各的，夹角只变了位置差对应的量，所以 q·k 只取决于两个词的相对距离：TinyLM 里位置 (3, 1)、(5, 3)、(10, 8) 的点积都是 0.0069。各对的转速和正弦编码的频率相同，base 越大，最慢的一对转得越慢，能区分的距离越远，Llama-3 用的是 500000。在系统底层，算子通过半半拆分优化访存带宽，通过预计算查找表消除三角函数计算，并与 QKV 投影或缓存存储深度融合。

注意力换成了现代版，FFN 也有一次升级。第 31 讲的 FFN 是“升维、ReLU、降维”，Llama 的 FFN 却有三个矩阵，其中一个起着“门”的作用，决定每个神经元的信息放行多少。下一讲：**SwiGLU 与门控 FFN**。
