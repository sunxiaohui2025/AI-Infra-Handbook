上一讲的张量并行每层都要 All-Reduce，适合连接很快的机内。可 405B 这样的模型，一台 8 卡的机器装不下，必须跨机。跨机的网络慢了一个数量级，每层都通信就太慢了。

**流水并行**（pipeline parallelism，PP）换一种切法：不拆矩阵，而是**按层切**。一个 80 层的模型放到 4 张卡上，卡 0 放第 1 到 20 层，卡 1 放第 21 到 40 层……数据从卡 0 流到卡 3，就像工厂的流水线。卡与卡之间只在交界处传一次激活，而且是点对点的 Send/Recv（第 100 讲），通信量很小。

这一讲讲流水并行的核心问题：**气泡**，以及训练和推理里它分别是什么样子。

## 只有一份数据时，大家轮流闲着

假设只有一批数据。卡 0 算完自己的 20 层，把结果传给卡 1；这时卡 1 才开始算，卡 0 就闲着了；卡 1 算完传给卡 2……前向走到卡 3，再开始反向（第 18 讲），梯度又从卡 3 一路传回卡 0。

任何时刻只有一张卡在干活，其他卡都在等。4 张卡的利用率只有 25%，空等的部分叫**气泡**（bubble）。

## 切成微批次

解决办法是把一个批次切成 m 个**微批次**（micro-batch），让它们像流水线上的零件一样依次进入：卡 0 算完微批次 0 交给卡 1，马上开始算微批次 1；卡 1 算微批次 0 的同时，卡 0 在算微批次 1……流水线填满以后，所有卡都在同时工作。

最直接的调度是 **GPipe**（2019 年）：所有微批次先依次做完前向，再依次做完反向，最后统一更新参数。气泡只出现在流水线“灌满”和“排空”的时候。设前向一段耗时 1、反向耗时 2，代码模拟了 4 段的情况：

- m = 1：总时长 12，气泡占 **75%**。
- m = 4：总时长 21，气泡 42.9%。
- m = 16：总时长 57，气泡 **15.8%**。

气泡占比有一个简洁的公式：

<div class="ai-formula">气泡占比 = (p − 1) ÷ (m + p − 1)</div>

p 是段数，m 是微批次数。微批次越多，灌满和排空的那一小段相对越短。所以流水并行要求 m 远大于 p。

## 1F1B：少存一些激活

GPipe 有个问题：所有微批次的前向都做完了才开始反向，每张卡要同时存着 **m 份**激活，等着反向用。m 越大气泡越小，激活却越多，显存吃不消。

**1F1B**（one forward, one backward）调度改了顺序：第 s 段卡先做 p − s − 1 个前向“热身”，之后每做一个前向，就紧接着做一个反向，交替进行。一个微批次的反向做完，它的激活就可以释放。这样每张卡同时存的激活**最多 p 份**，和 m 无关。

代码里 m = 16 时，GPipe 的卡 0 要同时存 16 份激活，1F1B 只要 4 份；而两者的总时长、气泡占比完全一样。

## 推理里的流水并行

推理没有反向，也不用等一整个批次结束再更新参数。连续批处理（第 74 讲）源源不断地有请求进来，可以把正在运行的请求分成几组，像微批次一样依次送进流水线：卡 0 算第 1 组的这一步时，卡 1 在算第 2 组的上一步……只要组数不少于段数，流水线就一直是满的，**吞吐**几乎没有损失。

可是**延迟**不一样。对单个请求来说，它的每个 token 都要依次走过所有的段，一段一段地读权重、计算。Llama-3.1-70B 放在 4 张卡上：

- **流水并行**：一个请求 decode 一步，要依次走完 4 段，每段读 1/4 的权重，加起来还是读了一遍全部权重，约 **42.1 ms**。
- **张量并行**：4 张卡同时各读 1/4，约 **10.5 ms**，再加上通信。

流水并行让模型装得下、让吞吐上得去，但**不能缩短单个请求的延迟**；张量并行能。这是两者在推理中最大的区别。

流水并行的好处是通信极少：段与段之间每步只传 32 个 token 的隐藏状态，约 524 KB，跨机走 InfiniBand 也只要 16 μs 左右。

## 到了大模型里

**和张量并行组合。**典型的做法是机内用张量并行、机间用流水并行。比如 Llama-3.1-405B 用两台 8 卡的机器：每台机器内部 TP = 8，两台之间 PP = 2。vLLM、SGLang 都支持这样组合（`--tp 8 --pp 2`）。第 109 讲会系统地讨论这种映射。

**训练里的更多花样。**大规模训练常用更复杂的调度来压缩气泡：比如每张卡放好几段不相邻的层（交错式 1F1B，interleaved），或者把反向拆成“算输入的梯度”和“算权重的梯度”两部分分开安排（零气泡流水线）。DeepSeek-V3 的训练用了它们自己设计的 DualPipe，让前向、反向和通信相互重叠。

**层数要能均分。**每段的层数和计算量最好相等，否则最慢的那一段决定了整条流水线的速度。第一段有嵌入层、最后一段有输出层，有时要少分几层来平衡。

## 用代码复现

下面的代码模拟 GPipe 和 1F1B 两种调度，统计 4 段、不同微批次数时的总时长、气泡占比和第 0 段同时存的激活份数；最后比较推理时流水并行和张量并行的单请求延迟，以及段与段之间的通信量。

```python
# 流水并行：模型按层切成 p 段（每段一张卡），一个批次切成 m 个微批次。前向一段耗时 1，反向耗时 2
def order(s, p, m, sched):
    """第 s 段卡上的执行顺序。GPipe：先做完所有前向，再做所有反向；1F1B：先做 p−s−1 个前向热身，然后一前一后交替"""
    if sched == "GPipe":
        return [("F", i) for i in range(m)] + [("B", i) for i in range(m)]
    warm = min(p - s - 1, m); seq = [("F", i) for i in range(warm)]
    f, b = warm, 0
    while b < m:
        if f < m: seq.append(("F", f)); f += 1
        seq.append(("B", b)); b += 1
    return seq

def simulate(p, m, sched):
    end, free, peak = {}, [0.0] * p, [0] * p
    seqs = [order(s, p, m, sched) for s in range(p)]
    pos = [0] * p
    while any(pos[s] < len(seqs[s]) for s in range(p)):
        for s in range(p):
            if pos[s] == len(seqs[s]): continue
            kind, i = seqs[s][pos[s]]
            dep = ("F", s - 1, i) if kind == "F" and s > 0 else ("B", s + 1, i) if kind == "B" and s < p - 1 else ("F", s, i) if kind == "B" else None
            if dep and dep not in end: continue                        # 依赖还没算完，这张卡先等
            start = max(free[s], end[dep] if dep else 0)
            end[(kind, s, i)] = free[s] = start + (1 if kind == "F" else 2)
            pos[s] += 1
            done_f = sum(1 for k in seqs[s][:pos[s]] if k[0] == "F"); done_b = pos[s] - done_f
            peak[s] = max(peak[s], done_f - done_b)                  # 这张卡同时存着几个微批次的激活
    T = max(free)
    return T, 1 - p * m * 3 / (p * T), peak[0]

p = 4
print(f"p = {p} 段：")
for m in [1, 4, 8, 16]:
    for sched in ["GPipe", "1F1B"]:
        T, bubble, pk = simulate(p, m, sched)
        print(f"  m = {m:2d}，{sched:5s}：总时长 {T:4.0f}，气泡占 {bubble:5.1%}（公式 (p−1)/(m+p−1) = {(p - 1) / (m + p - 1):5.1%}），第 0 段最多同时存 {pk} 份激活")

# 推理：Llama-3.1-70B 放在 4 张卡上，decode 一个请求，比较流水并行和张量并行
read = 141e9 / 3.35e12 * 1e3                             # 单卡读一遍全部权重的时间
print(f"一个请求 decode 一步：流水并行 4 段要依次走完 = {read:.1f} ms；张量并行 4 卡同时读 ≈ {read / 4:.1f} ms（再加通信）")
print(f"段与段之间每步只传 32 个 token 的隐藏状态：{32 * 8192 * 2 / 1e3:.0f} KB，跨机传一次约 {(6e-6 + 32 * 8192 * 2 / 50e9) * 1e6:.0f} μs")
```

## 容易混淆的地方

1. **流水并行不减少单个请求的计算路径。**每个 token 仍然要依次经过所有的层，只是这些层分布在不同的卡上。它提高的是同时处理多份数据的能力。
2. **微批次不改变训练的结果。**所有微批次的梯度累加起来再更新，等价于用整个批次算一次梯度（第 20 讲的梯度累加）。
3. **气泡公式假设每段耗时相同。**段与段不均衡时，实际的气泡更大。

## 回顾

流水并行按层把模型切成 p 段，段之间只点对点地传激活，通信量小，适合跨机。只有一份数据时，各段轮流工作，气泡很大；把批次切成 m 个微批次依次送入，气泡占比降到 (p − 1)/(m + p − 1)：4 段时 m = 1 为 75%，m = 16 为 15.8%。1F1B 调度让前向和反向交替，每段同时存的激活最多 p 份。推理时连续批处理能让流水线保持满载，吞吐不受影响，但单个请求的延迟不会缩短：70B 放 4 卡，流水并行一步 42.1 ms，张量并行约 10.5 ms。实际部署常常机内张量并行、机间流水并行。

张量并行和流水并行切的都是模型。还有一个维度没有切：序列。上下文长到几十万、上百万个 token 时，一张卡连一个请求的激活和 KV Cache 都放不下。序列怎么切？下一讲：**序列并行与上下文并行**。
