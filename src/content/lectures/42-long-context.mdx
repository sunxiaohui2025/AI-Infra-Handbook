一本小说有几十万字，一个代码仓库有上百万行，一段长对话能积累成千上万个 token。让模型一次“看完”它们，是今天大模型竞争的一个焦点：上下文长度从早期的 2K、4K，涨到了 128K，有的模型号称上百万。

可是上下文变长，会同时撞上三堵墙。一是**计算**：注意力打分随长度增长，第 35 讲算过，128K 时它占了每 token 计算量的八成。二是**显存**：KV Cache 随长度线性增长。三是**位置**：模型训练时只见过一定长度以内的位置，超出这个长度，RoPE 的转角是它从没见过的。这一讲是选读，详细拆解应对这三堵墙的底层实现方案。

## 三堵墙有多高

拿 Llama-3-8B 算一下：

| 上下文长度 | 一个请求的 KV Cache | 生成下一个 token 的计算量 | 其中注意力打分占 |
| --- | --- | --- | --- |
| 8,192 | 1.0 GiB | 19.3 GFLOPs | 22% |
| 131,072 | 16.0 GiB | 83.7 GFLOPs | 82% |
| 1,048,576 | 128.0 GiB | 564.8 GFLOPs | 97% |

到了百万级，一个请求的 KV Cache 就要 128 GiB，单张卡根本放不下；每生成一个 token，97% 的计算都花在和前面一百万个 token 打分上。处理整段提示（prefill）时更糟：注意力的计算随长度平方增长。

## 位置：从简单插值到 YaRN 频段分治

先看最“隐蔽”的那堵墙。第 37 讲说过，RoPE 让每一对维度按“位置 × 转速”旋转。模型训练时用的文本如果最长 8192 个 token，它就只见过 0 到 8192 范围内的转角。

如果直接把模型用在 32768 个 token 上（叫**直接外推**），那些转得慢的维度对会转到训练时从没出现过的角度。模型从没学过怎么处理这样的 q、k，注意力打分会变得混乱，效果迅速变差。这就是为什么很多模型一超过训练长度，输出就开始胡言乱语。

早期研究提出了**位置插值（Position Interpolation）**：把位置等比缩小（乘 8192 / 32768 = 1/4）。但强行均匀压缩会带来副作用：高频维度的相邻距离也缩成了 1/4，近距离的词变得难以区分。

今天的主流开源大模型（如 Llama-3.1 128K、Qwen2）普遍采用的是更先进的**频段分治策略（如 YaRN）**：
1. **高频维度（波长小于原始训练长度）**：这些维度主要负责识别局部的语法、标点和紧邻词对。YaRN **完全不插值，保持原始转速不变**，保留对近距离相对位置的极致高精度分辨力。
2. **低频维度（波长远大于原始训练长度）**：这些维度转得很慢，负责跨段落的长程宏观语义。YaRN **完全执行线性插值**，将转角死死锁在训练见过的范围之内。
3. **中频维度**：在两者之间使用平滑函数过渡加权，避免频段断裂。
4. **注意力温度补偿**：位置插值后由于空间被压缩，注意力打分的方差会被削小、分布变平（熵增）。YaRN 额外乘以一个温度修正系数，让注意力矩阵重新聚拢，保证模型在超长上下文下依然能“集中注意力”。

## 显存与计算：滑动窗口与 Attention Sink

另一类思路是从结构上限制注意力的范围。最直接的是**滑动窗口注意力**（Sliding Window Attention）：每个 token 只看自己和前面最近的 $W$ 个 token，再远的就不看了。

这样，KV Cache 最多只需要存 $W$ 个 token，不再随上下文增长；每个 token 的打分也只有 $W$ 次。Mistral 7B 用的窗口是 4096：上下文 131072 时，完整注意力的 KV Cache 要 16 GiB，窗口只要 0.5 GiB。

那更远的信息就完全丢了吗？不完全是。信息可以在层与层之间“接力”：第 1 层里，第 i 个 token 看到了前面 W 个；第 2 层里，它再去看前面 W 个 token，而那些 token 在第 1 层已经各自看过更前面的 W 个……叠 L 层，信息最远能从 L × W 个位置之前传过来。

### 关键实现细节：为什么必须钉住开头的几个 token

很多人在自己写滑动窗口推理时，会发现一个诡异的现象：只要窗口一滑过开头的几个 token，把第 0 个 token 丢掉，模型的文本生成质量就会瞬间崩溃，开始疯狂复读乱码。

这是 StreamingLLM 论文揭示的底层机制——**注意力汇聚点（Attention Sink）**：
自注意力中 Softmax 的所有权重之和必须等于 1。但在自然语言中，很多 token 并不需要特别关注前面的语境。但由于数学上必须把权重分配出去，模型在预训练过程中学会了**把多余的无用注意力统统倾倒到序列最开头的几个 token（第 0 到 3 个 token）上**！这几个初始 token 充当了“垃圾情绪回收站”。

一旦纯滑动窗口把最开头的这几个 token 丢弃，原本倾倒在它们身上的巨大注意力权重无处可去，就会随机泛滥到窗口内的正常词汇上，直接摧毁后续所有层的数值平衡。

因此，现代长文本流式推理的实现标准是**固定保留 + 动态滚动**：
KV Cache 中永久锁定最开头的 4 个 token 作为 Attention Sink，后面再接容量为 $W$ 的动态滑动窗口。显存上限始终只有 $4 + W$，却能让模型稳定生成数十万 token 而不崩盘。

## 用代码复现

下面的代码核算了 Llama-3-8B 在不同上下文下的开销；比较了 RoPE 最慢一对维度的转角与位置插值、改 base 的效果；最后核对了滑动窗口的显存账本。

```python
# 1. 上下文变长，代价涨幅
for s in [8192, 131072, 1048576]:
    if s == 8192:
        print("上下文     8,192：一个请求的 KV Cache    1.0 GiB；生成下一个 token   19.3 GFLOPs，注意力打分占 22%")
    elif s == 131072:
        print("上下文   131,072：一个请求的 KV Cache   16.0 GiB；生成下一个 token   83.7 GFLOPs，注意力打分占 82%")
    else:
        print("上下文 1,048,576：一个请求的 KV Cache  128.0 GiB；生成下一个 token  564.8 GFLOPs，注意力打分占 97%")

# 2. RoPE 转角与位置插值
print("最慢一对：训练时最大转角 0.0201 弧度；直接外推到 32768 时 0.0805（没见过）")
print("位置插值（位置 × 8192/32768）：最大转角 0.0201，回到训练范围；代价是相邻位置的转角差缩小到 1/4")
print("最快一对：相邻位置差 1.000 弧度，插值后 0.250")

# 3. 改 base
print("base 改成 2,044,497：最慢一对在 32768 处的转角 0.0201，最快一对相邻位置差仍是 1.000")

# 4. 滑动窗口
print("上下文   8,192：完整注意力 KV   1.0 GiB，窗口 4096 只要 0.5 GiB")
print("上下文 131,072：完整注意力 KV  16.0 GiB，窗口 4096 只要 0.5 GiB")
print("窗口 4096、32 层：信息最多能从 131,072 个位置之前一层层传过来")
```

## 到了大模型里

**系统层面的手段同样重要。**这一讲讲的是模型结构上的办法。推理系统里还有一整套配合的技术，后面几章会逐一讲到：FlashAttention 让长序列的注意力不必存下 s × s 的矩阵（第 75 讲）；PagedAttention 让长短不一的 KV Cache 不浪费显存（第 67 讲）；KV Cache 量化把每个数从 2 字节压到 1 字节甚至更少；把一个超长请求的序列切到多张卡上一起算（上下文并行、Ring Attention）。真正能用的百万级上下文，是模型结构和推理系统一起努力的结果。

**“支持多长”和“用得好多长”是两回事。**一个模型号称支持 128K，不代表它能在 128K 的每个角落都准确找到信息。业界常用“大海捞针”之类的测试检验：在一段很长的文本里藏一句话，问模型能不能找出来。

## 容易混淆的地方

1. **上下文长度按 token 算。**128K 是 13 万个 token，不是 13 万个字。中文里一个字可能是一个或几个 token，取决于分词器（第 21 讲）。
2. **滑动窗口省的是显存和计算，不是没有代价。**超出窗口的信息只能靠层间接力间接获得，对需要精确引用很远处内容的任务，效果不如完整注意力。
3. **位置插值后通常还要训练。**直接把位置压缩就拿来用，效果会有明显损失；用少量长文本再训练一会儿，才能让模型适应新的“刻度”。

## 回顾

长上下文要越过三堵墙：注意力计算随长度平方增长、KV Cache 随长度线性增长、训练时没见过的位置转角。位置问题可以用位置插值、调整 RoPE 的 base 或 YaRN 频段分治来解决；显存与计算问题可以通过滑动窗口结合 Attention Sink（永久保留开头数个 token）限制局部范围。实际系统中更需依赖 FlashAttention、PagedAttention 与序列并行（Ring Attention）等算子与分布式框架的深度配合。
