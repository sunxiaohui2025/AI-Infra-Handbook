前面几讲攒下了一堆与硬件相关的决定：用哪个注意力后端、矩阵乘走库还是走专用 kernel、支持哪些量化方法、All-Reduce 走库还是走自定义实现、块大小取多少、要不要开图捕获。现在的问题是：**怎么把这些决定告诉 vLLM，而又不改它的代码**。

为什么不能改？第 18 篇读过 vLLM 的规模——17 万行，几周一个版本。在上游代码里加一个 `if is_my_hardware()` 分支，意味着每次上游更新都要重新合并一遍；而厂商需要支持的模型和特性比上游合并的节奏更快。所以主流做法是**插件**：引擎留出入口，厂商在自己的包里实现，安装之后引擎自动发现。

这一讲讲插件机制本身：引擎留了哪些入口、插件要实现哪些接口、哪些必须实现、不改上游代码怎么替换掉上游的模块，以及版本怎么对齐。第 157 讲会用这套框架逐行读海光的插件。

## 引擎留的三类入口

vLLM 用 Python 标准的 entry point 机制。插件在自己的 `setup.py` 里声明入口，引擎启动时扫描已安装的包，把每一类入口都加载一遍。按官方文档，和硬件适配相关的有两类：

- **平台插件**（`vllm.platform_plugins`）：入口是一个函数，返回平台类的全限定名；这块卡在当前环境不可用时返回 `None`。
- **通用插件**（`vllm.general_plugins`）：用来注册模型类、导入自定义算子。

文档里还强调了一条实现要求：**入口函数必须可重入**——它可能被调用多次（引擎有多个进程，每个进程都要加载插件），所以重复调用不能出问题。这一点在第 157 讲会看到海光是怎么处理的（进程内的注册表 + 失败锁存）。

## 插件要实现什么

<PluginIface caption="图 154-1　一个硬件插件的接口清单，按四层分组（内容按 vLLM 公开文档的插件机制整理）。绿底是不实现引擎就起不来的；点任意一项看它替换了引擎里的什么。" />

四层的分工可以这样理解：

**入口**只做注册，不做实际工作——它要足够轻，不能在这里 import torch 或者初始化设备，否则会在插件发现阶段就把一堆东西拽进来。

**平台类**是引擎问硬件问题的地方。它继承引擎的 `Platform` 基类，回答一长串问题：设备名是什么、分发键是什么、有几张卡、每张卡多少显存、支持哪些量化方法、该用哪个注意力后端、该用哪个通信器、用哪个 worker 类。按官方文档，最少要实现的是 `device_type`、`device_name`、`check_and_update_config`、`get_attn_backend_cls`、`get_device_communicator_cls`；其中 `check_and_update_config` 最关键，因为**worker 类就是在这里指定的**。

**Worker 与执行**是真正跑模型的地方。文档列出的基本方法是：`init_device`、`initialize_cache`、`load_model`、`get_kv_cache_layer_configs`、`determine_available_memory`、`initialize_from_config`、`execute_model`；另外按需实现休眠唤醒、图模式、投机解码、LoRA、数据并行的空步。

**算子与模型**是性能的落点：注意力后端类、自定义算子、特殊模型实现、通信器、PD 分离的 KV 搬运。

<Note kind="point">这张清单有一个重要的性质：**引擎的核心逻辑一项都不在里面**。调度、token 预算、KV 块管理、前缀缓存、请求生命周期（第 135 讲读过的那些）全部由上游负责，插件只回答“在这块卡上这件事怎么做”。所以插件的工作量和引擎的规模无关，只和硬件的差异有关——这也是插件机制能成立的原因。</Note>

## 沿用 CUDA 键的插件能省掉多少

第 144 讲讲的两条接法，在插件这一层的差别很大。

**沿用 CUDA 键**（海光 DCU 这条路）：平台类里 `device_type = "cuda"`、`dispatch_key = "CUDA"`、通信后端叫 `nccl`、设备可见性环境变量用 `CUDA_VISIBLE_DEVICES`。于是引擎里所有“如果是 CUDA 就……”的分支自动走对，worker 可以直接继承引擎自带的 GPU worker，图捕获可以直接复用引擎的 CUDA Graph 包装器。插件要做的事缩小成“替换掉那些性能不够或语义不同的部分”。

**注册新设备**（昇腾这条路）：引擎里每一处判断设备类型的地方都要有自己的分支，worker、注意力后端、KV Cache 的管理、图模式几乎都要重写一遍。插件的体量会大得多。

两者的共同点是：**上游代码都不用改**。差别只在插件自己要写多少。

## 不改上游，怎么替换上游的模块

插件机制能注册新东西（平台、模型、算子），但有些适配需求是“要改上游某个函数的行为”。比如上游的调度器里有一处判断，在这块卡上要换一个阈值；或者上游的某个算子实现用了这块卡不支持的指令，要整体换掉。

这类需求有三种做法，代价依次递增：

**一是把它变成配置**。如果上游已经留了配置项（块大小、注意力后端、自定义算子开关），平台类的 `check_and_update_config` 里改配置就够了。这是最该优先走的路。

**二是运行时替换**。在引擎还没导入某个模块之前，先安排好“当它被导入时，用我的实现替换掉”。Python 的导入机制允许在 `sys.meta_path` 上装一个查找器，拦住指定的模块名；也可以在模块导入之后替换它的某个属性（函数、类的方法）。这就是常说的猴子补丁，但做法上有讲究：

- 只拦**精确的模块名**，不要按前缀匹配，否则会误伤无关模块；
- 每个补丁只应用一次，并记录状态（幂等）；
- 失败要**锁存并抛出**，不能悄悄回退到未打补丁的状态——否则会出现“一半打了补丁、一半没打”的诡异状态；
- 要能**报告**：打了哪些补丁、目标是什么、成功还是失败。

**三是 fork 上游**。维护成本最高，一般只在等不及上游合并时作为过渡。

海光插件选的是第二条路，并且把上面四条做成了明确的机制：一个精确匹配模块名的导入协调器、一个进程内的补丁注册表（记录进程角色、目标符号、状态和失败详情）、以及一份显式排好序的补丁清单。它的 README 里写明两条原则：**安装和启动不会重写 vLLM 的包文件，也不创建源码软链接**；**必需功能不兼容时失败并保留诊断状态，不回退到重写源码**。第 157 讲会逐行读这套机制。

<Note kind="warn">运行时替换的最大风险是**版本错配**：上游改了被替换函数的签名或语义，补丁还按老的写，结果可能是跑错而不是报错。所以这类插件必须有一道版本检查的关卡——在任何补丁注册之前，先确认装的引擎版本在支持的范围内，不在就拒绝启动。</Note>

## 版本对齐

插件夹在引擎和硬件栈之间，两边都在动：引擎几周一个版本，驱动和工具包几个月一个版本，算子库跟着走。所以一个可用的插件必须声明清楚“我支持什么”。

一个完整的版本矩阵包括：驱动版本、工具包版本、PyTorch 版本、引擎版本、插件版本，以及若干算子库的版本。检查的时机要足够早——在打任何补丁、初始化任何设备之前，而且要**只读元数据、不导入被检查的包**（导入会触发一堆副作用）。

匹配的严格程度要分情况。版本号里的主次补丁号通常要求一致（接口可能变），而预发布、开发版、本地构建后缀可以放宽（同一条发布线上的不同构建）。海光插件的做法正是这样：要求已安装的 vLLM 的版本号在主次补丁这一级和目标版本一致，允许 `rc`、`dev`、本地构建后缀不同；并且在文档里明确提醒——**通过版本检查不代表 PyTorch、工具包和算子的二进制接口已验证兼容**。第 156 讲会把这个矩阵的每一层展开。

## 回顾

把一块新卡接进推理引擎，标准做法是插件而不是改上游：引擎用 entry point 机制留出平台插件和通用插件两类入口，插件实现一个平台类（回答设备名、分发键、显存、注意力后端、通信器、worker 类等问题）、一个 worker（设备初始化、加载权重、量显存、执行一步）、以及注意力后端和自定义算子。引擎的调度、KV 管理、请求生命周期一项都不需要插件参与，这是插件机制成立的根本原因。沿用 CUDA 分发键的硬件能白拿引擎里所有 CUDA 分支，插件体量小得多。要改上游行为时，优先改配置，其次用精确匹配、幂等、失败锁存、可报告的运行时替换，最后才考虑 fork；而运行时替换必须配一道版本检查的关卡。海光插件的规模统计给出了这件事的真实成本：25 万行，其中测试 11.5 万行，补丁 195 个文件。
