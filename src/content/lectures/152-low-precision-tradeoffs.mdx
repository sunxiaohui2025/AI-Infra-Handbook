第 12 篇讲过一长串压缩方法：INT8 权重量化、AWQ、SmoothQuant、FP8、KV Cache 量化。它们的收益都基于一个前提——硬件原生支持这种数据类型。换一块卡，这个前提可能不成立，而不成立的后果不是“收益小一点”，而是**完全相反**：第 148 讲量到 CPU 上的 BF16 比 FP32 慢 10 倍。

这一讲把这件事量清楚：各类硬件对各种精度的支持分几档；没有原生 kernel 时替代办法能拿到什么、拿不到什么；量化算子适配要改哪些地方。

## 三档支持，不是两档

“支持”这个词在精度问题上必须分三档，少分一档就会做错判断。

<PrecisionSupport caption="图 152-1　硬件 × 精度的支持矩阵。三列硬件是按路线设的参数，不是某款具体型号——按手上卡的官方文档改这张表。点格子看这种组合该怎么办；切换“能省什么”看同一张表的另一面。" />

**原生支持**：矩阵单元直接吃这种类型。少读的字节同时变成少花的时间。

**能存不能算**：有这个数据类型（能转换、能存显存），但矩阵单元不认它，kernel 里必须先反量化。第 147 讲在 MPS 上遇到的 FP8 就是这一档：`x.to(torch.float8_e4m3fn)` 能跑，`torch._scaled_mm` 不存在。

**完全不支持**：连类型都没有，只能换一种类型。

第二档最危险，因为它看起来是支持的：模型能加载、显存占用确实降了一半、输出也正确。只有量速度时才发现没快，甚至更慢。

## 本机实测：六种做法

下面这份脚本把 decode 的一个线性层（M = 16 个 token、权重 4096 × 4096）用六种精度方案各跑一遍，量耗时、要读的权重字节、实际带宽和误差。

<RunOutput cmd=".venv/bin/python bench/port_precision.py" file="outputs/port_precision.txt" caption="图 152-2　同一个线性层的六种精度方案（Apple M2 的 GPU，M = 16，权重 4096 × 4096，参考答案是 CPU 上的 FP64，本机真实运行）。" />

这张表要横着读，一行一行地看它兑现了什么。

**FP32 → FP16：2.51 倍**。这是“原生支持”该有的样子：权重字节减半，时间也差不多减半（甚至更多，因为固定开销不变而工作量减半）。误差 3.6e-4，远在第 146 讲的阈值内。

**FP16 和 BF16 不等价**（491 μs 对 545 μs）。字节数相同，速度差 11%，误差差一个量级（3.6e-4 对 2.9e-3）。原因在第 10 讲的位布局：BF16 尾数 7 位，FP16 尾数 10 位。**选哪个要看模型在哪一步会溢出**——第 146 讲那个 RMSNorm 的例子说明 FP16 的 5 位指数是真实风险，所以主流权重格式仍是 BF16。

**INT8 的两种做法都比 FP32 基线慢**（4971 μs 和 3922 μs，即 0.23× 和 0.29×）。权重只有 17 MB，比 FP32 的 67 MB 少四分之三，却慢了四倍。这就是“能存不能算”的代价被量化出来了：

- W8A16 那一行的写法是 `w8.half() * sw.half()`——它**先把整个权重反量化成一个新的 FP16 张量**，再做矩阵乘。这一步要写 34 MB、再读 34 MB，比原来直接读 67 MB 还多。
- W8A8 那一行用了 `_int_mm`（MPS 上有这个算子），但 INT8 的输出是 INT32，还要乘回两个缩放系数，又是几次全张量的逐元素运算。

**FP8 反量化成 BF16：0.58×**。比 INT8 的两种做法好一些（只多一次转换），但仍然比不量化慢。第 147 讲那组数（22273 μs 回退 CPU、1459 μs 组合、526 μs 不量化 BF16）说的是同一件事。

<Note kind="point">量化的收益来自“少读字节”，而**少读的字节只有在 kernel 内部被直接喂进矩阵单元时才变成少花的时间**。把反量化写在矩阵乘外面（物化一个高精度权重张量），等于把省下的带宽又花回去，还要再加一次写入。所以在没有原生低精度矩阵乘的硬件上，量化只剩一个收益：**省显存容量**（能放更大的模型、更多的 KV）。这个收益也是真的，但要在这个前提下重新算部署账（第 71、99 讲）。</Note>

## 那量化在新卡上到底怎么用

按三档支持分别给方案。

**原生支持这种类型**：直接用，但要核对三件事。一是**缩放粒度**：按张量、按通道、按分组（第 91 讲），硬件的量化矩阵乘通常只支持其中几种，不支持的粒度要么换方法，要么在 kernel 外补算。二是**累加精度**：INT8 乘积累加在 INT32 里不会溢出，FP8 累加在 FP16 还是 FP32 里对精度影响很大。三是**支持的形状**：量化 kernel 的对齐要求往往比普通矩阵乘更严（第 150 讲）。

**能存不能算**：有两条路。短期路线是把反量化**融进 kernel**——读 INT8 权重、在片上转成 BF16、立刻喂给矩阵单元，这样少读的字节真的变成少花的时间（这正是 miniinfer v4 在第 129 讲做的事，也是所有 W8A16 kernel 的做法）。长期路线是等硬件和库支持原生类型。决定走哪条，看这个模型在这块卡上到底是缺显存还是缺带宽。

**完全不支持**：换类型。FP8 的 checkpoint 在没有 FP8 的卡上，可以转成 INT8（两者都是 8 位，精度特性不同但量级相当，第 93 讲），代价是要重新做校准、重新验精度。

<FPFormats caption="图 152-3　FP8 和 FP4 的位布局（第 93 讲）。换硬件时要确认支持的是哪一种 FP8（E4M3 还是 E5M2）、缩放是整体一个还是按组一个——这两件事不匹配时 checkpoint 没法直接用。" />

## 把这件事放回部署账

量化在一块卡上到底能带来什么，可以在动手之前就算出来。decode 每步的时间下限 = 要读的权重字节 ÷ 带宽（第 68 讲）：

```python
# 一块卡上，权重精度决定 decode 每步的时间下限：下限 = 要读的权重字节 ÷ 带宽
P = 8.03e9                       # Llama-3-8B 的参数量（配置见大纲，第 35 讲）
for bw in (3.35e12, 1.6e12):     # 两种带宽：示例值，换成手上卡的官方规格
    print(f"\n带宽 {bw / 1e12:.2f} TB/s")
    print(f"{'精度':<8}{'权重':>9}{'每步下限':>10}{'每秒 token':>12}  有原生 kernel 时 / 只能存不能算时")
    for name, bytes_per in [("BF16", 2), ("FP8", 1), ("INT4", 0.5)]:
        w = P * bytes_per
        t = w / bw
        # 只能存不能算：权重要先反量化成 BF16 物化出来，读写各一遍 BF16 权重，再读一遍 BF16 做乘法
        t_bad = (w + 2 * P * 2 * 2) / bw
        print(f"{name:<8}{w / 1e9:>7.1f} GB{t * 1e3:>9.2f} ms{1 / t:>12.0f}  {t * 1e3:.2f} ms / {t_bad * 1e3:.2f} ms")
```

```text

带宽 3.35 TB/s
精度             权重      每步下限    每秒 token  有原生 kernel 时 / 只能存不能算时
BF16       16.1 GB     4.79 ms         209  4.79 ms / 23.97 ms
FP8         8.0 GB     2.40 ms         417  2.40 ms / 21.57 ms
INT4        4.0 GB     1.20 ms         834  1.20 ms / 20.37 ms

带宽 1.60 TB/s
精度             权重      每步下限    每秒 token  有原生 kernel 时 / 只能存不能算时
BF16       16.1 GB    10.04 ms         100  10.04 ms / 50.19 ms
FP8         8.0 GB     5.02 ms         199  5.02 ms / 45.17 ms
INT4        4.0 GB     2.51 ms         399  2.51 ms / 42.66 ms
```

最后一列是这张表的重点：有原生 kernel 时，FP8 把每步从 4.79 ms 砍到 2.40 ms；只能存不能算时，三种精度的每步时间挤在 20 到 24 ms 之间——**彼此的差别几乎消失了，而且都比不量化慢四五倍**。位宽越低，这一列反而越平，因为主导项变成了那次反量化的读写，和权重本身的大小关系不大了。

这张表也给出了适配时的决策顺序：先问“有没有原生 kernel”，再问“反量化在 kernel 内部还是外部”，最后才问“用哪种量化方法”。把顺序倒过来做（先挑方法再适配）是常见的弯路。

## 量化算子适配要改什么

把一套量化方法搬到新卡上，要动的地方比“换一个矩阵乘”多。按 vLLM 这类引擎的结构，有四处：

**权重加载时的重排**。量化权重在 checkpoint 里是按某种打包格式存的（4 位两个一字节、按 kernel 要求交错排列）。换卡后 kernel 想要的排列不同，要在加载时重排。这一步出错的症状很典型：输出完全是乱的（不是误差大，是毫无关系），因为权重的每一位都对错位了。

**缩放系数的形状和布局**。按通道的缩放是一个长度为 N 的向量，按分组的缩放是一个 [N, K/group] 的矩阵；kernel 要求它连续、对齐、也许还要转置。

**反量化的位置**。在矩阵乘内部（最优）、矩阵乘前（物化一个高精度权重，最差）、还是矩阵乘后（INT8 的输出乘回缩放）。这决定了收益能不能拿到。

**回退路径**。某个形状不满足 kernel 的对齐要求、或者某一层的量化配置特殊（第一层和最后一层常常保留高精度），要有一条能用的后路。

这四处在海光插件里都能找到对应的代码：平台类里列着支持的量化方法名单（`supported_quantization`，启用 23 种、注释掉 4 种，第 157 讲会读这段），`model_executor/layers/quantization/` 下按方法各有一个实现文件，还有一个 `verify_quantization` 在启动时检查并替换配置（例如用 AWQ 时强制打开 Triton 版的实现）。第 159 讲会把这些展开。

<Note kind="warn">量化模型的精度验收不能和 FP32 原模型比（第 146 讲）。正确的参考是**同一套量化方法在参考平台上的输出**：同样的 checkpoint、同样的缩放粒度，在一块成熟的卡上跑出来的结果。两边都掉同样多，说明是量化方法本身的代价；只有这块卡上掉得更多，才是适配的问题。</Note>

## KV Cache 的精度是另一笔账

权重量化省的是“每步都要读一遍权重”的带宽，KV Cache 量化省的是“每步都要读一遍历史 KV”的带宽和显存（第 94 讲）。它在新卡上有两个额外问题。

**写入和读取都要支持这种类型**。KV 是每步追加写、每步全量读的。写的时候要量化（算缩放、转类型），读的时候要在注意力 kernel 内部反量化。所以 KV 量化不是一个算子的事，而是**写 KV 的 kernel 和注意力 kernel 都要支持**。

**布局更复杂**。FP8 的 KV 常常不是简单地“把 BF16 换成 FP8”，而是一种打包布局：把缩放系数和数据交错存在一起，让注意力 kernel 一次读到。海光插件的说明里就有这样一条：对稀疏 MLA 的后端，平台会把用户写的 `--kv-cache-dtype fp8_e4m3` 转成内部的 `fp8_ds_mla` 格式，并明确说这是该后端专用的打包布局、不是所有注意力后端通用的格式。

所以 KV 量化的适配要按“注意力后端 × KV 类型”的组合来验，而不是只验一个开关。

## 回顾

精度支持要分三档：原生支持（少读的字节变成少花的时间）、能存不能算（只省显存容量）、完全不支持（只能换类型）。中间那一档最容易误判，因为模型能跑、显存确实降了。本机的实测把代价量了出来：FP16 比 FP32 快 2.51 倍（原生支持该有的样子），而 INT8 的两种做法反而只有 0.23× 和 0.29× 的速度，FP8 反量化是 0.58×——因为反量化被写在矩阵乘外面，物化出的高精度权重把省下的带宽又花了回去。要拿到量化的时间收益，反量化必须融进 kernel 内部。量化算子的适配要动四处：权重重排、缩放的形状与布局、反量化的位置、回退路径；KV Cache 量化还要求写 KV 和注意力两个 kernel 都支持，而且常常有专用的打包布局。
