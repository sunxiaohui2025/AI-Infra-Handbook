前两讲分别讲了 GPU 的算力（第 60 讲）和存储（第 61 讲）。一个运算在 GPU 上要多久，取决于两件事：要做多少次运算，要读写多少字节。做运算受算力限制，读写受带宽限制，两者同时进行，较慢的那个决定了总时间。

**Roofline 模型**（屋顶线模型）把这个道理画成了一张图：横轴是一个量，叫**算术强度**；纵轴是能达到的速度。任何一个运算，只要算出它的算术强度，就能在图上找到它的位置，一眼看出它卡在算力上还是带宽上，最快能有多快。第 68 讲以后的所有性能估算，用的都是这张图。

## 算术强度

一个运算做 W 次浮点运算（第 11 讲），从显存读写 Q 字节。它的**算术强度**是

<div class="ai-formula">I = W ÷ Q（单位：FLOPs / 字节）</div>

意思是：每读写 1 字节，做多少次运算。第 61 讲已经算过几个：逐元素运算约 0.25，n × n 的矩阵乘法约 n/3。

## 两个屋顶

设峰值算力是 P（FLOPs/秒），显存带宽是 B（字节/秒）。

- 只看计算：W 次运算至少要 W/P 秒，速度不超过 **P**。
- 只看读写：Q 字节至少要 Q/B 秒。在这段时间里最多完成 W 次运算，速度不超过 W ÷ (Q/B) = **I × B**。

两个限制同时存在，能达到的速度是较小的那个：

<div class="ai-formula">能达到的速度 = min(P, I × B)</div>

画在对数坐标上：I × B 是一条斜线（强度越高越快），P 是一条水平线。两条线组成一个“屋顶”的形状，运算的速度只能在屋顶下面。两条线的交点叫**屋脊点**：

<div class="ai-formula">屋脊点 I* = P ÷ B</div>

H100（BF16 稠密）的屋脊点是 989 TFLOPS ÷ 3.35 TB/s ≈ **295**，就是第 61 讲那个“每读 1 字节能做 295 次运算”。

- 强度**低于**屋脊点：落在斜线上，**卡在带宽**，算力用不满。
- 强度**高于**屋脊点：落在水平线上，**卡在算力**，带宽用不满。

## 把大模型的运算放上去

代码在 H100 上算了几个典型的运算：

- **逐元素运算**：强度约 0.25，最多 0.8 TFLOPS，只有峰值的 0.1%。
- **1 个 token 过一个线性层**（Llama-3-8B 的 4096 × 14336）：要把整个权重矩阵读一遍，却只对每个权重做一次乘加，强度约 **1.0**，最多 3.3 TFLOPS，峰值的 0.3%。这就是 decode 的处境（第 68 讲）。
- **32 个 token 一起过**：权重读一遍，被 32 个 token 共用，强度约 32，最多 106 TFLOPS，峰值的 10.7%。
- **256 个 token**：强度 237，最多 794 TFLOPS，峰值的 80%，还差一点到屋脊点。
- **4096 个 token**：强度 1792，远过屋脊点，可以达到 989 TFLOPS，**卡在算力上**。这是 prefill 的处境。
- **decode 的注意力**：每读一个历史 token 的 k、v，只和 1 个查询做运算，强度约 1；GQA 让 4 个查询共用一份 KV（第 39 讲），强度约 4，仍然深在带宽区。

规律很清楚：**对线性层来说，算术强度约等于一起处理的 token 数**。这也是第 70 讲“批处理能大幅提高 decode 吞吐”的原因：把更多请求放在一起，强度就往右移，速度沿着斜线往上爬，直到撞上算力的屋顶。

下面的演示画出了 H100、A100、B200 的屋顶。拖动算术强度看落在哪个区；拖动线性层的 token 数，看它的点怎么从带宽区移到算力区。

## 怎么用这张图

**判断该优化什么。**一个运算在带宽区，再怎么优化计算也没用，要做的是减少读写（融合、量化、复用）或者提高强度（批处理、GQA）；在算力区，就要用更低的精度（第 63 讲）、更好的 Tensor Core 利用率。

**估算时间。**时间 = max(W ÷ P, Q ÷ B)。第 68 讲的 prefill、decode，第 70 讲的批处理，第 77、110 讲的各种估算，用的都是这个式子。

**看离屋顶还有多远。**实测的速度画到图上，和屋顶的距离就是还能优化的空间（第 67 讲）。如果一个带宽区的运算只达到了带宽屋顶的一半，说明数据搬运的方式还有问题。

**比较硬件。**A100 的屋脊点约 153，H100 约 295，B200 的 BF16 约 281。屋脊点越高，越难喂饱算力，越多的运算会落在带宽区。新一代 GPU 的算力增长通常比带宽快，这让访存优化越来越重要。

## 模型的局限

Roofline 是一个上限模型，它忽略了很多东西：

- 只考虑了一层存储（这里是 HBM）。也可以对 L2、共享内存各画一条屋顶（层次化 Roofline），更细地分析。
- 假设读写和计算可以完美重叠。实际的 kernel 有启动开销、同步、负载不均（第 89 讲），达不到屋顶。
- 峰值算力只对 Tensor Core 能处理的矩阵乘法有意义；逐元素运算用的是 CUDA 核，它的“屋顶”低得多（第 60 讲）。

但作为第一步的判断，它几乎总是对的。

## 用代码复现

下面的代码算出 H100、A100、B200 的屋脊点，再计算几个典型运算在 H100 上的算术强度、能达到的速度和瓶颈。

```python
# Roofline：一个运算能达到的速度 = min(峰值算力, 算术强度 × 显存带宽)
GPUS = {"H100": (989e12, 3.35e12), "A100": (312e12, 2.04e12), "B200": (2250e12, 8e12)}   # BF16 稠密算力、显存带宽

def linear(b, din=4096, dout=14336):                     # b 个 token 过一个线性层（Llama-3-8B 的 FFN 上投影），BF16
    flops = 2 * b * din * dout
    bytes_ = 2 * (din * dout + b * din + b * dout)       # 读权重、读输入、写输出
    return flops, bytes_

OPS = {"逐元素运算（乘常数）": (1, 4)}
for b in [1, 32, 256, 4096]:
    OPS[f"线性层，{b} 个 token"] = linear(b)
OPS["decode 注意力（MHA，1 个查询）"] = (2 * 2 * 4096, 2 * 4096 * 2)  # 每个历史 token：q·k 和 p·v 各 1 次乘加；读 k、v 各 1 个数
OPS["decode 注意力（GQA，4 个查询共用 KV）"] = (4 * 2 * 2 * 4096, 2 * 4096 * 2)

for g, (F, BW) in GPUS.items():
    print(f"{g}：屋脊点 = {F / 1e12:.0f} TFLOPS ÷ {BW / 1e12:.2f} TB/s = {F / BW:.0f} FLOPs/字节")
F, BW = GPUS["H100"]
print("H100 上各运算的算术强度和能达到的速度：")
for name, (fl, by) in OPS.items():
    ai = fl / by
    perf = min(F, ai * BW)
    print(f"  {name:22s}：强度 {ai:7.1f} → {perf / 1e12:6.1f} TFLOPS（峰值的 {perf / F:5.1%}），卡在{'算力' if ai >= F / BW else '带宽'}")
```

输出：

```text

A100：屋脊点 = 312 TFLOPS ÷ 2.04 TB/s = 153 FLOPs/字节
B200：屋脊点 = 2250 TFLOPS ÷ 8.00 TB/s = 281 FLOPs/字节
H100 上各运算的算术强度和能达到的速度：
  逐元素运算（乘常数）            ：强度     0.2 →    0.8 TFLOPS（峰值的  0.1%），卡在带宽
  线性层，1 个 token         ：强度     1.0 →    3.3 TFLOPS（峰值的  0.3%），卡在带宽
  线性层，32 个 token        ：强度    31.7 →  106.1 TFLOPS（峰值的 10.7%），卡在带宽
  线性层，256 个 token       ：强度   237.0 →  793.8 TFLOPS（峰值的 80.3%），卡在带宽
  线性层，4096 个 token      ：强度  1792.0 →  989.0 TFLOPS（峰值的 100.0%），卡在算力
  decode 注意力（MHA，1 个查询） ：强度     1.0 →    3.4 TFLOPS（峰值的  0.3%），卡在带宽
```

前三行是三张卡的屋脊点。后面每一行是一个运算：逐元素运算和 1 个 token 的线性层只能用到峰值的千分之几；256 个 token 时达到 80%；4096 个 token 时卡在算力上。decode 注意力的强度只有 1 到 4。

## 容易混淆的地方

1. **算术强度看的是显存读写，不是总的数据访问。**同一个数在片上被用很多次，只算一次显存读写。所以好的实现（分块、融合）能提高实际的算术强度。
2. **屋脊点和精度有关。**FP8 的算力翻倍，屋脊点也翻倍（H100 约 590），同样的运算更容易落在带宽区。
3. **在带宽区“利用率低”不等于实现得差。**decode 只能用到峰值的不到 1%，这是运算本身的性质决定的，不是 bug；判断实现好坏，要看它离**自己那条屋顶**有多远。

## 回顾

Roofline 模型用算术强度 I（每读写 1 字节做多少次运算）判断一个运算的速度上限：min(峰值算力, I × 带宽)。两条线的交点是屋脊点，H100 约 295 FLOPs/字节。强度低于它卡在带宽，高于它卡在算力。线性层的强度约等于一起处理的 token 数：1 个 token 强度 1.0，只能用到峰值的 0.3%；4096 个 token 强度 1792，卡在算力。decode 的注意力强度只有 1 到 4。这张图告诉我们该优化什么、能快到哪里。

在算力区的运算，想再快只能提高算力。同一张卡，用 FP8 算比 BF16 快一倍，用 FP4 又快一倍。为什么精度越低越快？下一讲：**低精度计算**。
