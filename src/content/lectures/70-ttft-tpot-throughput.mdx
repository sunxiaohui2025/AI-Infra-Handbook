“这个推理服务快不快？”这个问题，用户和服务商的回答可能完全相反。用户关心的是：我提问之后，多久能看到第一个字？之后字是一个个蹦出来，还是流畅地刷出来？服务商关心的是：一张 GPU 每秒能生成多少个 token、能同时服务多少人？

这一讲把“快”拆成三个最常用的指标：**TTFT**、**TPOT** 和**吞吐**，并用上一讲的估算方法说明一个推理系统最核心的矛盾：**同时服务的请求越多，总吞吐越高，但每个请求都会变慢。**

## 三个指标

**TTFT**（Time To First Token，首 token 时间）：从请求发出，到收到第一个生成的 token，要多久。它主要由 prefill 决定（第 68 讲），再加上排队等待的时间。用户在对话界面里“等它开始说话”的那段时间，就是 TTFT。

**TPOT**（Time Per Output Token，每个输出 token 的时间），也叫 ITL（Inter-Token Latency，token 间延迟）：第一个 token 之后，每个 token 之间隔多久。它由 decode 一步的时间决定。TPOT 越小，文字刷得越快。人的阅读速度大约是每秒几个到十几个 token，TPOT 在几十毫秒以内，用户就感觉很流畅。

一个请求的总耗时约是：

<div class="ai-formula">总耗时 ≈ TTFT + TPOT × (生成的 token 数 − 1)</div>

**吞吐**（throughput）：整个系统每秒一共生成多少个 token（有时也按每秒完成多少个请求算）。它是服务商最关心的指标，直接决定了一张 GPU 能服务多少用户，也就决定了每个 token 的成本（第 72 讲）。

前两个是**延迟**指标，从单个请求的角度看；最后一个是**吞吐**指标，从整个系统的角度看。

## 一个人用：延迟低，吞吐也低

先看只服务一个请求的情况。用第 68 讲的方法，Llama-3-8B 在一张 H100 上，提示 1024 个 token，TTFT 约 15.5 ms；decode 时每一步要读一遍 16 GB 的权重，TPOT 约 4.85 ms，也就是每秒约 206 个 token。

对这个用户来说，体验非常好。可对 GPU 来说，这几乎是闲着：decode 的算术强度约为 1，算力只用了 0.3%（第 68 讲），一张昂贵的 H100 每秒只产出 206 个 token。

## 很多人一起用：批处理

第 68 讲提过解决办法：**批处理**。让 b 个请求一起 decode，每一步读一遍权重，同时为 b 个请求各生成一个 token。权重的读取被 b 个请求分摊了。

可是每个请求还有自己的 KV Cache，这部分没法共享，要各读各的。每个请求总长 2048 个 token（提示和生成各 1024），decode 时平均上下文约 1536 个，每个请求每步要读约 192 MiB 的 KV Cache。所以一步 decode 的读写量是：16 GB 的权重，加上 b × 192 MiB 的 KV Cache。

算一下不同的并发数：

| 并发 b | TPOT | 每个请求的速度 | 总吞吐 | 显存（权重 + KV Cache） |
| --- | --- | --- | --- | --- |
| 1 | 4.85 ms | 206 token/s | 206 token/s | 16.3 GB |
| 8 | 5.27 ms | 190 token/s | 1,517 token/s | 18.2 GB |
| 32 | 6.72 ms | 149 token/s | 4,764 token/s | 24.6 GB |
| 64 | 8.64 ms | 116 token/s | 7,407 token/s | 33.2 GB |
| 128 | 12.49 ms | 80 token/s | 10,251 token/s | 50.4 GB |
| 256 | 20.18 ms | 50 token/s | 12,686 token/s | 84.8 GB（放不下） |

规律很清楚：

- **并发从 1 增加到 8**，TPOT 只从 4.85 ms 涨到 5.27 ms，总吞吐却涨了 7 倍多。权重的读取被分摊，几乎是“白捡”的吞吐。
- **并发继续增加**，每个请求的 KV Cache 读取开始占主导，TPOT 明显变长，每个请求变慢了，总吞吐的增长也越来越慢。
- **显存是硬上限。**每个请求的 KV Cache 要 256 MiB，80 GB 的卡放下权重以后，最多同时装约 238 个请求。256 个就放不下了。

注意算术强度：即使并发 256，也只有约 60，远没到 H100 的 295。这是因为每个请求的 KV Cache 读取随并发线性增长，“每读一个字节做的运算”上不去。所以长上下文的 decode 往往**始终是带宽受限**的，靠批处理也只能把权重的那部分摊薄。

下面的演示画出了 TPOT（琥珀色，左轴）和总吞吐（绿色，右轴）随并发数的变化，灰色区域是显存放不下的范围。换不同的请求长度看看。

把请求长度调到 32768：每个请求的 KV Cache 要 4 GiB，显存只够装十几个请求，而且 KV Cache 的读取很快就压过了权重，批处理的收益变得很小。长上下文的服务，吞吐会低得多。

<Note kind="point">TTFT 看第一个 token 等多久，由 prefill 和排队决定；TPOT 看之后每个 token 的间隔，由 decode 一步决定；吞吐看整个系统每秒生成多少 token。增加并发能大幅提高吞吐，代价是每个请求的 TPOT 变长，上限由显存决定。</Note>

## 延迟和吞吐的权衡

这张表说明了推理服务最根本的权衡：**用延迟换吞吐**。服务商希望并发越大越好（每个 token 更便宜），用户希望自己的请求越快越好。

实际的做法是先定一个**服务等级目标**（SLO），比如“TTFT 不超过 500 ms，TPOT 不超过 50 ms”，然后在满足它的前提下，把并发和吞吐推到最高。不同的场景，SLO 很不一样：在线聊天要求 TPOT 低、TTFT 低；离线批量处理（比如给一百万篇文档写摘要）只关心总吞吐，延迟可以很长；推理模型（第 49 讲）生成的 token 很多，TPOT 直接决定用户要等几十秒还是几分钟。

还有一个这张表没体现的细节：新请求要做 prefill。在真实的服务里，请求是陆续到达的，新请求的 prefill 会插进正在进行的 decode 之间。一个很长的 prefill 会让所有正在 decode 的请求“卡”一下（TPOT 突然变长）；而新请求如果要排队等前面的 prefill，TTFT 就会变长。怎么安排这些 prefill 和 decode，是第 10 篇调度的核心问题（第 74、77 讲）。

## 用代码复现

下面的代码用第 68 讲的估算方法，算出单独 prefill 的 TTFT，以及不同并发数下 decode 一步的 TPOT、每个请求的速度、总吞吐、算术强度和显存，最后算出显存能放下的最大并发数。

```python
# Llama-3-8B（BF16）+ 一张 H100（80 GB）。每个请求：提示 1024 个 token，生成 1024 个（decode 时上下文平均约 1536）
N, N_emb, L, d = 8.03e9, 128256 * 4096, 32, 4096
W_BYTES, KV, F, BW, MEM = N * 2, 2 * 32 * 8 * 128 * 2, 989e12, 3.35e12, 80e9
prompt, out = 1024, 1024
ctx = prompt + out / 2

def decode_step(b):
    """b 个请求一起 decode 一步：权重读一遍，每个请求读自己的 KV Cache。返回毫秒。"""
    flops = (2 * (N - N_emb) + 4 * L * d * ctx) * b
    bytes_ = W_BYTES + KV * ctx * b
    return max(flops / F, bytes_ / BW) * 1e3, flops / bytes_

ttft = max(2 * (N - N_emb) * prompt / F, W_BYTES / BW) * 1e3
print(f"TTFT（单独 prefill 一个 1024 token 的提示）≈ {ttft:.1f} ms")
print(" 并发 b | TPOT（ms） | 每个请求的速度 | 总吞吐（token/s） | 算术强度 | KV Cache + 权重")
for b in [1, 8, 32, 64, 128, 256]:
    t, ai = decode_step(b)
    mem = W_BYTES + KV * (prompt + out) * b
    print(f"{b:6d} | {t:9.2f} | {1000 / t:9.1f} tok/s | {b * 1000 / t:15,.0f} | {ai:8.1f} | {mem / 1e9:5.1f} GB{'（超出 80 GB）' if mem > MEM else ''}")

# 显存最多放得下多少个请求（先不管激活值和其他开销，第 71 讲细算）
b_max = int((MEM - W_BYTES) // (KV * (prompt + out)))
t, _ = decode_step(b_max)
print(f"显存上限：最多约 {b_max} 个请求同时 decode；此时 TPOT {t:.1f} ms，吞吐 {b_max * 1000 / t:,.0f} token/s")
```

输出：

```text

 并发 b | TPOT（ms） | 每个请求的速度 | 总吞吐（token/s） | 算术强度 | KV Cache + 权重
     1 |      4.85 |     206.0 tok/s |             206 |      1.0 |  16.3 GB
     8 |      5.27 |     189.6 tok/s |           1,517 |      7.2 |  18.2 GB
    32 |      6.72 |     148.9 tok/s |           4,764 |     22.5 |  24.6 GB
    64 |      8.64 |     115.7 tok/s |           7,407 |     35.0 |  33.2 GB
   128 |     12.49 |      80.1 tok/s |          10,251 |     48.4 |  50.4 GB
```

## 到了大模型里

**这些都是理想值。**实测的吞吐通常只有理论值的一半到七成：算子之间有开销，注意力在长短不一的请求上效率不同，还有调度、采样、CPU 端的处理。第 67 讲会把理论值和实测值放在一起对比。

**看指标要看分布，不只看平均。**线上服务通常报告 TTFT、TPOT 的 P50、P90、P99（50%、90%、99% 的请求不超过多少）。平均值很好看、但 P99 很差，意味着总有一部分用户等得很久。

**压测工具。**vLLM、SGLang 等推理引擎都带有压测脚本：按设定的速率发送请求，统计 TTFT、TPOT、吞吐的分布。调参（并发上限、批大小、chunked prefill 的块大小等）时，就是在这些指标之间找平衡。

## 容易混淆的地方

1. **吞吐高不等于每个用户都快。**并发 128 时总吞吐是并发 1 的 50 倍，但每个用户的速度从 206 token/s 降到了 80 token/s。
2. **TTFT 不只是 prefill 的时间。**还包括排队、分词、网络传输等。系统繁忙时，排队往往是 TTFT 的大头。
3. **“每秒 token 数”要看清是哪个。**有的说的是单个请求的输出速度（1 / TPOT），有的说的是整个系统的总吞吐，有的还把输入 token 也算进去。比较不同系统的数字时要先对齐口径。

## 回顾

衡量推理服务的“快”有三个指标：TTFT（第一个 token 等多久，由 prefill 和排队决定），TPOT（之后每个 token 的间隔，由 decode 一步决定），吞吐（系统每秒生成多少 token）。批处理让多个请求共享一次权重读取：Llama-3-8B 在 H100 上，并发从 1 增加到 128，TPOT 从 4.85 ms 变成 12.49 ms，总吞吐却从 206 涨到 10251 token/s。但每个请求的 KV Cache 要单独读，长上下文时它很快成为主导；而显存决定了并发的上限（每请求 2048 token 时约 238 个）。实际服务在满足延迟目标的前提下，尽量提高吞吐。

“显存能放下多少个请求”这个问题，我们只粗算了权重和 KV Cache。真实的显存里还有激活值、框架开销、碎片……一张 80 GB 的卡，到底每一块都被谁占了？下一讲：**显存账本**。
