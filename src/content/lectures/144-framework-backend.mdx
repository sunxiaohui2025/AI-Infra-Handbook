miniinfer 的模型文件里有一句 `x @ w[p + "q_proj.weight"].T`（第 124 讲）。这一句在 CPU 上能跑，在 Apple MPS 上能跑，换成一块国产加速器也应该能跑——前提是 PyTorch “认识”这块卡。

认识是什么意思？具体说就是：`x.device` 能报出这块卡，`x @ w` 能找到一份在这块卡上执行的实现，`x.to(device)` 能把数据搬上去，显存能分配和回收，流和事件能同步。这一讲把这条路径拆开，看每一站是谁的责任；然后用本机的 PyTorch 真的打印出分发表，注册一份自己的实现，看调用被转到哪里；最后看缺一个算子时有哪几种结局。

## x @ w 的六站

<DispatchPath route="reuse" caption="图 144-1　沿用 CUDA 分发键的接法（ROCm 式，海光 DCU 走这条路）。点“下一站”逐站走，或点任意一站看它做了什么。" />

关键的一站是第三站：**分发器**（dispatcher）。PyTorch 的每个算子（`aten::mm`、`aten::add`、`aten::_softmax` 等几千个）都有一张表，表的行是**分发键**（dispatch key）。键有三类：设备键（CPU、CUDA、MPS、XPU、PrivateUse1……）、功能键（Autograd、Autocast、量化、稀疏……）、以及兜底的复合键。一次调用进来，分发器按张量的设备和当前打开的功能算出要走哪一行，然后调用那一行注册的函数。

所以“让 PyTorch 认识一块新卡”，技术上就是**在这些表里填出一列**。填法有两种。

**沿用 CUDA 键**。把 PyTorch 整个用兼容接口（HIP）重新编译一遍，注册时还是注册到 CUDA 键上。好处立竿见影：`torch.cuda.is_available()` 为真，`tensor.cuda()` 可用，`torch.cuda.synchronize()`、`torch.cuda.mem_get_info()` 全部照旧，上层几万行 Python 代码一个字都不用改。第 157 讲会看到海光的 vLLM 插件把平台声明成 `device_type="cuda"`、`dispatch_key="CUDA"`，正是因为底下这份 PyTorch 就是这样编出来的。代价是语义上的别扭：报错信息里写着 CUDA，环境变量叫 `CUDA_VISIBLE_DEVICES`，但机器里根本没有 NVIDIA 的卡。

**注册新设备（PrivateUse1）**。PyTorch 预留了一个叫 `PrivateUse1` 的键给第三方后端用。厂商把它改名（`torch.utils.rename_privateuse1_backend("npu")`），自动生成 `Tensor.npu()`、`Tensor.is_npu`、`Module.npu()` 这些接口，然后把自己的算子实现逐个注册到这个键上。PyTorch 官方教程里给的步骤就是这几步，外加一句重要的提醒：注册算子的同时**要注册回退**，否则没实现的算子会直接报错。

<DispatchPath route="new" caption="图 144-2　注册新设备的接法（PrivateUse1 式，华为昇腾的 torch_npu 走这条路）。前两站和上一张图完全一样，从第三站开始分叉。" />

两种接法的取舍：

| | 沿用 CUDA 键 | 注册新设备 |
| --- | --- | --- |
| 上层代码 | 几乎不改 | 所有 `cuda` 字样要改 |
| 第三方库（写死 `torch.cuda` 的） | 直接能用 | 要打补丁或等上游支持 |
| 语义 | 名字和实际硬件不符 | 名字干净 |
| 要实现的范围 | 算子 + 库，运行时接口对齐 CUDA | 算子 + 分配器 + 流 + 事件 + 拷贝 + 工具链 |
| 适合 | 硬件是 GPGPU、编程模型接近 CUDA | 硬件不是 SIMT，或希望长期自成体系 |

## 真的打印一次分发表

上面的描述可以在本机验证。下面这段脚本在 CPU 和 Apple MPS 上真实运行：打印 `aten::mm` 的分发表、查几个算子在各键上有没有实现、给 MPS 换一份 `mm` 的实现看调用落到哪里、再注册一个新设备名。

<RunOutput cmd=".venv/bin/python bench/dispatch_probe.py" file="outputs/dispatch_probe.txt" caption="图 144-3　在本机（PyTorch 2.15，CPU + MPS）真实跑出的分发表与注册实验。" />

逐段读这份输出。

**第一段**是 `aten::mm` 的注册位置：CPU 在 `RegisterCPU_0.cpp`，MPS 在 `RegisterMPS_0.cpp`，Meta 在 Python 里，稀疏张量还有单独一行。这就是一块卡接进来后要填的那一列——Register*你的设备*.cpp，几千行注册代码。

**第二段**有两个值得记住的现象。一是 `aten::_scaled_mm`（FP8 矩阵乘）只有 CPU 有、MPS 没有：这正是第 147 讲要处理的算子缺口。二是 `aten::rms_norm` 三个设备键全是空，但它在任何设备上都能跑——因为它注册在**复合键**上：PyTorch 把它拆成 `pow`、`mean`、`rsqrt`、`mul` 这些基础算子，再各自分发。

这第二点对适配很重要：**PyTorch 的几千个算子并不都要实现**。复合算子只要底下的基础算子齐了就自动可用。真正要厂商逐个实现的是那些“原子”算子，加上为了性能而特意覆盖的融合算子。这也解释了第 148 讲的一个结果：miniinfer 整个 Qwen3 前向只用到 31 种 aten 算子，其中要在设备上真正执行的 23 种——一个模型的算子面比“几千个”小得多（第 147 讲会细讲怎么统计）。

**第三段**是一次真实的注册和分发：我们用 `torch.library.Library("aten", "IMPL")` 给 MPS 键挂上自己的 `mm`，然后算 `x @ w`，调用进了我们的 Python 函数；注销之后再算一次，又回到 PyTorch 自带的实现。C++ 里的 `TORCH_LIBRARY_IMPL(aten, MPS, m)` 做的是同一件事。一块新卡的接入，就是这件事重复几千遍。

**第四段**是新设备名：改名并生成接口之后，`Tensor.mychip`、`Tensor.is_mychip`、`Module.mychip` 都出现了，但 `torch.empty(2, 2, device="mychip")` 还不能用——因为显存分配器、流、事件、拷贝都要在 C++ 里实现。这几行输出就是两条路线成本差异的最小演示。

## 缺一个算子，有四种结局

适配中最常见的状况不是“这块卡不行”，而是“这块卡的第 731 个算子没有”。

<DispatchPath route="missing" caption="图 144-4　缺一个算子时的四条岔路。前两条是框架替你决定的，后两条要自己动手；第 147 讲会用实测数字比较后三条。" />

**报错**是默认行为，也是最该保留的行为：问题暴露在当场，不会悄悄变慢或变错。

**回退到 CPU** 是框架提供的兜底。PyTorch 的 MPS 后端用环境变量 `PYTORCH_ENABLE_MPS_FALLBACK=1` 打开，PrivateUse1 式的后端要自己注册一个 `fallback`。它的代价不是“慢一点”这么含糊——第 147 讲在本机量到：一次 FP8 矩阵乘，回退到 CPU 是 22 ms，留在设备上用现有算子组合是 1.5 ms，差十几倍。更麻烦的是它打断了设备上的流水：前后的算子都要等这次往返结束。

**用现有算子组合**是适配期最划算的办法：把缺的算子按定义拆成已有的算子。缺 FP8 矩阵乘就先反量化成 BF16 再乘，缺融合的 RMSNorm 就用 `pow`、`mean`、`rsqrt`、`mul` 写出来（这其实就是 miniinfer 的做法，第 124 讲）。数据留在设备上，正确性有保证，只是省不下本该省的带宽。

**自己写 kernel** 留给那些真正占时间的算子。第 83 讲的 Amdahl 定律在这里直接可用：一个算子占整个前向 2% 的时间，把它写到无穷快，整体也只快 2%。

<Note kind="point">适配一个模型的现实路径是：先让每个缺失算子都有“组合”或“回退”的去处，把模型跑通跑对；再用 profiler 找出哪几个算子真正占时间（第 149 讲），只给它们写 kernel。顺序颠倒的话，很容易花一周优化一个占 1% 的算子。</Note>

## 自定义算子怎么挂进来

厂商写好的 kernel 要让 PyTorch 和推理引擎用上，还要过一道“注册成算子”的手续。现在的标准做法是注册**自定义算子**：给它一个名字（`myvendor::fused_rmsnorm`）、一个签名、一份实现，再加一份只算形状的“假实现”（fake / meta 实现）。假实现是给 `torch.compile` 用的——图编译时要推断每个节点输出的形状和类型，但不能真的去设备上算一遍（第 145 讲）。

海光的插件里就能看到这个模式：BF16 转 FP32 的矩阵乘用 `direct_register_custom_op` 注册成 `hcu_linear_bf16_fp32`，同时给了一个 `_linear_bf16_fp32_fake`，只按输入形状返回一个空张量（第 158 讲会逐行读）。vLLM 的插件机制里还有一类“算子插件”入口，专门用来在引擎启动时导入并注册这些算子（第 154、157 讲）。

<Note kind="warn">注册自定义算子时最容易出错的是**声明它改了什么**（`mutates_args`）。一个原地写 KV Cache 的算子如果声明成“不改任何输入”，图编译会认为它没有副作用，可能把它优化掉或者重排顺序，结果是 KV 写丢。这类 bug 在 eager 模式下看不见，开图模式才炸。</Note>

## 回顾

PyTorch 认识一块新卡，技术上是在每个算子的分发表里填出一列。两种填法：沿用 CUDA 键（重新编译一份 PyTorch，上层不改，名字别扭），或注册新设备（PrivateUse1，名字干净，分配器、流、事件、拷贝都要自己实现）。本机的实验把这条路径坐实了：`aten::mm` 在 CPU 和 MPS 各有一行注册，`_scaled_mm` 在 MPS 上没有，`rms_norm` 三个设备键都空着却照样能跑（它是复合算子），给 MPS 换一份 `mm` 的实现后调用立刻转向我们的代码。缺算子有四条岔路——报错、回退 CPU、用现有算子组合、自己写 kernel——按“先跑通、再按占比优化”的顺序选。

分发器是“一次调用一次查表”，一步 decode 有几千次这样的调用。有的硬件对这种逐个算子下发的方式很不友好，它希望一次拿到整张图。下一讲看图模式：`torch.compile` 怎么接一个新后端，整图下发到底省下了什么。
