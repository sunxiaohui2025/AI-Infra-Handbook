模型在新卡上跑起来了，第一次生成的文本是这样的：

```text
'.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n.\n\n\n\n\n\n\n\n\n\n\n\n\n\n'
```

没有报错，没有崩溃，权重也是同一份。在 CPU 上同样的代码、同样的提示生成的是 `' Paris. The capital of Italy is Rome. …'`。这一讲讲怎么从这种状态定位到具体的一行代码。

上面这段输出不是编造的：本机把 miniinfer 搬到 Apple MPS 上、把精度切到 FP16 时真的会这样（第 141 讲是完整的移植过程）。查下来问题出在 RMSNorm 的一行，和 MPS 没有关系，但只有换到低精度的硬件上才会暴露。下面就用这个真实的例子走一遍方法。

## 先定标准：什么叫“一致”

逐位相同（bitwise identical）这个标准在换卡时**不成立**，而且不应该作为目标。原因有三个，都和硬件有关：

**累加顺序不同**。浮点加法不满足结合律：`(a + b) + c` 和 `a + (b + c)` 的结果可以差一个最低位。一个矩阵乘法的 K 方向怎么切、分几个线程组归约、用不用 split-K，决定了加法的顺序（第 87 讲）。换一块卡就是换一套分块策略，顺序必然不同。

**中间精度不同**。BF16 的矩阵乘通常用 FP32 累加，但“FP32 累加”在不同硬件上可能是不同的实现：有的用全精度 FP32，有的用 TF32 一类的压缩格式。

**同一个数学函数的实现不同**。`exp`、`rsqrt`、`tanh` 在不同硬件上用不同的近似多项式或查表，最后一位常常不一样。softmax 里每个元素都要过一次 `exp`（第 6 讲），这点差别会被带进后面所有层。

所以要换一套标准，分三级：

| 级别 | 检查什么 | 怎么判断 |
| --- | --- | --- |
| 张量级 | 每一层输出和参考的相对误差 | 相对误差 = ‖a − b‖ ÷ ‖b‖，在阈值内；逐层看，找第一个越界的层 |
| token 级 | 贪心生成的 token 序列 | 和参考逐 token 比对（miniinfer 的 `tests/check.py` 一直这么做） |
| 任务级 | 评测分数 | 几个数据集上的分数不低于参考（允许小幅波动） |

三级各有各的盲区，所以要一起用。张量级能定位到层，但“误差 2e-2 算不算大”没有绝对答案；token 级直观，但贪心生成有放大效应——某一步两个候选词打分只差 0.001，一点误差就让它们换位，之后整段话都不同，看起来像灾难，实际上模型质量没变；任务级最接近用户感受，但一次评测要跑几十分钟，没法用来定位代码。

<Note kind="point">换卡后的精度目标不是“逐位一致”，而是“误差来源都能解释”。每一处差异要么归因到已知的硬件行为（累加顺序、超越函数实现），要么归因到一个具体的 bug。解释不了的差异，就是还没找到的 bug。</Note>

## 逐层比对：找第一个偏离的层

方法很直接：同一个提示，在参考实现和待查实现上各走一遍前向，把每一层的输出都留下来，逐层比相对误差，找第一个越过阈值的层。参考实现用 CPU FP32——它慢，但确定性好，而且和 HuggingFace 的输出能对上（第 118 讲建立的基线）。

读这张图的四个结论：

**MPS FP32 的误差稳定在 1e-6 量级，28 层下来没有累积**。这是“同一种精度、不同硬件”的正常状态：误差来自累加顺序和超越函数的实现，每层引入一点，但不放大。这种情况下 token 级检查会完全一致——实测 4 条提示、每条 32 个 token，和 HuggingFace 逐 token 相同。

**BF16 的误差是 2e-2 量级，而且不随层数增长**。BF16 只有 8 位尾数（第 10 讲），相对误差天生在 1e-2 到 1e-3 这个量级，这是精度本身的代价，不是 bug。重点是它**不随层数放大**——曲线是平的。贪心生成也完全一致。

**问题版本的 FP16 曲线从第 4 层起直接跳到 1e0**。相对误差 1.0 意味着输出和参考已经毫无关系。这就是定位结果：**第 4 层**。

**同一组数据的“最差位置”和“整个张量”差别很大**。问题版本的整张量误差在第 4 层只有 4e-3，看起来无关痛痒；而按位置分别算时，最差的那个位置是 1.0。原因是只有 5 个位置中的 4 个坏了，而那个好的位置范数很大，把平均拉了回来。**比对时一定要按位置（或按 token）分别算再取最差**，否则会漏掉这类局部失效。

## 为什么是第 4 层：一个真实的 bug

定位到第 4 层之后，往层里面看。把这一层的输入打印出来，最大绝对值是 6544。

Qwen3 的激活值里有少数几个通道特别大（第 91 讲讲过这种离群值，量化方法都要对付它）。6544 这个数在 FP16 里完全放得下——FP16 的最大值是 65504。问题出在下一步：RMSNorm 要算平方的均值。

$$
\text{RMSNorm}(x) = \frac{x}{\sqrt{\frac{1}{d}\sum_i x_i^2 + \varepsilon}} \odot w
$$

6544 的平方是 4.28 × 10⁷，**超过了 FP16 的上限 65504**。于是 `x.pow(2)` 得到 `inf`，均值是 `inf`，`rsqrt(inf + eps)` 是 0，输出整层变成 0——再往后，残差连接（第 29 讲）让它还能传下去，但这一层的贡献全丢了。

v1 的写法是这样的，在 FP32 和 BF16 上都没事：

```python
var = x.pow(2).mean(-1, keepdim=True)
return x * torch.rsqrt(var + eps) * weight
```

BF16 为什么没事？因为 BF16 和 FP32 的指数位一样多（8 位），能表示到 10³⁸，只是尾数少。FP16 的指数只有 5 位，上限 65504。**同样是 16 位，一个会溢出、一个不会**——第 10 讲的位布局在这里直接决定了成败。

改法是把平方和这一步升到 FP32 再算（`port/model.py` 里的 `rms_norm`）：

```python
def rms_norm(x, weight, eps):
    xf = x.float()                                   # 先升到 FP32：平方不会溢出
    var = xf.pow(2).mean(-1, keepdim=True)
    return (xf * torch.rsqrt(var + eps)).to(x.dtype) * weight
```


改完之后 FP16 的曲线落到 3e-3，而且比 BF16 更低（FP16 尾数 10 位，比 BF16 的 7 位多）；贪心生成的 32 个 token 和参考完全一致。这一处改动在 LayerDrift 里可以直接对比：勾上 `mps float16 naive` 和 `mps float16 fixed` 两条线。

<Note kind="warn">这类“溢出型”错误有三个特征，值得记住：换精度才出现；在残差网络里不会崩溃，只是某层失效；整张量的平均误差看不出来。所以**换精度之后必须重跑逐层比对**，不能因为“上一个精度是对的”就跳过。现实里的高发位置是所有要做平方或求和的地方：RMSNorm、注意力打分、softmax 的分母、loss。</Note>

## 其他常见的偏离来源

把这几年适配中反复出现的来源列一遍，按定位的难度从易到难：

**算子级的实现差异**。某个算子在新卡上的实现有 bug 或语义不同（边界处理、NaN 的传播、`index_put` 的重复下标）。定位办法是单算子对比：同样的输入喂给 CPU 和新卡的同一个算子，比输出。第 140 讲统计的算子清单正好可以拿来做这件事——逐个算子跑一遍对比，比在整个模型里猜要快得多。

**RoPE 的角度**。角度表是用 `arange` 和幂运算算出来的（第 37 讲），有的实现里用 FP16 存角度，长上下文时位置 10 万以上的角度精度不够，注意力就偏了。症状是短提示正常、长提示崩坏。

**掩码和 −inf**。因果掩码把分数设成 `-inf`（第 27 讲）。有的硬件上 `-inf` 参与乘法会产生 NaN，有的实现用一个很大的负数（−65504）代替，在 FP16 里再减一点就溢出。症状是某些长度下出现 NaN。

**归约的范围写错**。第 136 讲讲的线程组宽度问题：归约少走一步，结果偏小。症状是误差稳定在某个倍数上（例如所有值都偏大约 1.4 倍），而不是随机抖动。

**权重加载**。权重在新环境里被转换过一次（BF16 → FP16、转置、分片），某一层的权重错了。症状是某一层的误差突然很大、其他层正常——和上面第 4 层的例子在曲线上很像，所以两者要一起排查：先确认权重的字节和参考一致，再看计算。

**KV Cache 的写入和读取**。写错位置或读少了一段。症状很特别：第一个 token 对，后面逐渐跑偏（第 141 讲的移植里要重点测这条）。

## 阈值定多少

逐层比对的阈值不能拍脑袋，按精度定：

| 待查实现的精度 | 相对误差的量级 | 建议阈值 | 越界意味着 |
| --- | --- | --- | --- |
| FP32 | 1e-7 到 1e-6 | 1e-5 | 一定有 bug |
| TF32 一类 | 1e-3 | 1e-2 | 可能有 bug |
| BF16 | 1e-3 到 1e-2 | 5e-2 | 可能有 bug |
| FP16 | 1e-4 到 1e-3 | 1e-2 | 可能有 bug |
| FP8 / INT8 权重量化 | 1e-2 | 按量化方法单独定基线 | 和量化基线比，而不是和 FP32 比 |

两条实用规则。一是**和同精度的参考比**：待查实现是 BF16 的，参考也要跑一遍 CPU 的 BF16，这样分离出“精度的代价”和“硬件的差异”。本机这组数据正好能看到这件事：MPS BF16 和 CPU BF16 的曲线几乎重合（整张量 2e-3 量级），说明差异来自 BF16 本身，不来自 MPS。二是**看形状，不只看数值**：平的曲线说明每层各自引入一点误差，正常；指数上升的曲线说明误差在被放大，要查是哪一层开始放大的；突然跳一个量级的台阶说明那一层有 bug。

量化模型是个例外，要单独说：量化本来就改变数值（第 90 讲），所以它的参考不是 FP32 的原模型，而是**同一套量化方法在参考平台上的输出**。miniinfer 的 v4 就是这样做的——第 123 讲里 INT8 版本和 HuggingFace 不再逐 token 一致，文章里写明了在第几个 token 开始分叉、为什么。

## 把比对做成例行检查

精度对齐不是一次性的工作。每改一个 kernel、每开一个融合、每打开一次图模式，都可能改变数值。所以要把它做成脚本，和压测一样例行跑：

1. 固定几个提示（短、长、中文、代码各一条），固定贪心解码。
2. 参考答案存成文件（miniinfer 的 `tests/hf_ref.json`），不要每次重新生成。
3. 每次改动后跑两级检查：逐层误差（快，几秒）和 token 级比对（慢一点，但能发现累积效应）。
4. 上线前跑一次任务级评测。
5. 把阈值写进脚本，越界就失败——而不是打印一个数字让人用眼睛判断。

<Note kind="column">海光在插件仓库里把这件事做成了公开的验证记录：`docs/validation/` 下每个配置一份，记录冻结的环境、硬件、后端、并行拓扑和各数据集的分数，并明确写着“模型已注册或存在配置，不代表精度验证已经通过”、“诊断配置不能计为精度验收通过”。这个态度值得抄：**适配到什么程度，要有可追溯的记录，而不是一句“跑通了”**。</Note>

## 回顾

换卡后的精度目标是“误差来源都能解释”，而不是逐位一致——累加顺序、中间精度、超越函数的实现都会带来最低位的差别。检查分三级：逐层相对误差（定位到层）、token 级比对（看累积效应）、任务级评测（接近用户感受）。逐层比对时要按位置分别算再取最差，否则会漏掉局部失效：本机那个 FP16 的例子里，整张量误差只有 4e-3，而最差位置已经是 1.0。定位到第 4 层之后，原因是 RMSNorm 在 FP16 里算平方和溢出——激活值 6544 的平方超过了 FP16 的上限 65504，而 BF16 因为指数位更多完全没事。阈值按精度定，并且要和同精度的参考比，把“精度的代价”和“硬件的差异”分开。

还有一类问题比精度更早出现：某个算子在这块卡上根本没有。下一讲把一个模型要用的算子完整清点一遍，看缺口有多大、每个缺口该用哪种办法补。
