第四章讲了很多让推理集群跑得更快的方法。最后回到一个很实际的问题，也是部署大模型服务时一定要回答的问题：**每秒有多少请求、延迟要满足什么要求，需要多少张卡？**卡少了，延迟超标、用户流失；卡多了，大把的钱花在闲置的 GPU 上。

这一讲把前面的知识串起来，做一次**容量规划**：先把延迟要求写成 SLO，再算一个实例在 SLO 内能服务多少请求，最后算出要几个实例、花多少钱。

## 先把要求写清楚：SLO

第 82 讲引入了 SLO（服务等级目标）。对一个对话服务，常见的 SLO 是：

- **TTFT**：P99 不超过某个值，比如 1 秒。用户发出问题后，最慢的那 1% 也要在 1 秒内看到第一个字。
- **TPOT**：P99 不超过某个值，比如 30 ms（约每秒 33 个 token，比人阅读的速度快得多）。
- 还有可用性等其他目标，这里不展开。

SLO 决定了一个实例能“满载”到什么程度：第 70 讲说过，同时 decode 的请求越多，吞吐越高，每个请求的 TPOT 也越长。**TPOT 的上限，就决定了一个实例最多能同时服务多少请求。**

## 一个实例能服务多少请求

以 Llama-3-8B、一张 H100 为一个实例，沿用第 72 讲的假设：实际效率是理论值的 60%。请求的输入 1000 个 token，输出 300 个。

一个实例每秒能服务 λ 个请求，要同时满足三件事：

1. **prefill 占时间。**每个请求的 1000 个输入 token 要 prefill，这是计算受限的（第 68 讲）。每秒 λ 个请求，prefill 就占掉 λ × 1000 × （每个 token 的计算时间）这么多比例的 GPU 时间，记为 f。decode 只能用剩下的 1 − f。
2. **Little 定律。**排队论里有一个简单而普遍的关系：系统里同时存在的请求数 = 到达率 × 每个请求停留的时间。每个请求要 decode 300 步，每步 TPOT，所以同时在 decode 的请求数 b = λ × 300 × TPOT。
3. **TPOT 由 b 决定。**b 个请求一起 decode 一步要 t(b)（第 70 讲），可 decode 只能用 1 − f 的时间（第 77 讲的分块 prefill 把 prefill 插在 decode 之间），所以实际的 TPOT = t(b) ÷ (1 − f)。

从小到大试 λ，直到 TPOT 超过上限（或 KV Cache 放不下）为止。TPOT 上限 30 ms 时，代码算出：一个实例最多每秒 **15.3 个**请求，此时同时约 136 个请求在 decode，prefill 占掉约 39% 的时间，实际 TPOT 29.7 ms。验证一下 Little 定律：15.3 × 300 × 29.7 ms ≈ 136。

## 需要几个实例

一个实例不能真的跑到上限。第 82 讲说过，接近饱和点时，排队会让延迟急剧上升；流量还会有波动。所以要留**余量**，比如让每个实例只跑到上限的 70%：

<div class="ai-formula">实例数 = ⌈总请求率 ÷ (单实例最大请求率 × 目标使用率)⌉</div>

每秒 50 个请求：50 ÷ (15.3 × 0.7) ≈ 4.7，向上取整，**5 个实例**，也就是 5 张 H100。按 2.5 美元/小时的示例租金，每百万个请求的 GPU 成本约 69 美元。

再看几种变化：

- **TPOT 上限收紧到 15 ms**：同时 decode 的请求只能有约 43 个，每实例每秒 9.7 个，需要 **8 张卡**，成本约 111 美元/百万请求。延迟要求严一倍，成本贵了六成。
- **输入变长到 4000 token**：prefill 占的时间多了四倍，KV 也大了，每实例每秒只有 4.0 个，需要 **18 张卡**，成本约 250 美元/百万请求。
- **流量涨到每秒 200 个**：单实例能力不变，需要 19 张卡，成本基本不变（规模大了，取整的浪费比例更小）。

## 模型之外：要测，也要看峰值

上面的计算是**估算**，用来快速判断量级、比较方案。真正上线前，要用第 82 讲的方法实测：在目标负载下逐级加压，测出每个实例在 SLO 内的 goodput，用实测值代替模型算出的 λ。

还要考虑流量的**形状**：

- **峰值，不是平均值。**对话服务的流量有明显的日夜周期，峰值常是平均的两三倍。容量要按峰值规划，或者配合自动扩缩容。
- **请求的分布。**输入、输出长度不是固定的。长尾的超长请求会占用大量的 KV 和 prefill 时间，要单独评估，或者用不同的实例池处理。
- **扩容要时间。**新实例要下载、加载几十 GB 的权重，捕获 CUDA Graph（第 89 讲），往往要几十秒到几分钟。自动扩缩容要提前一点触发，指标常用排队长度、KV Cache 使用率，而不只是 GPU 利用率。

## 省钱的杠杆

当容量规划的结果太贵时，可以回头看第三、四章的各种方法，它们最终都体现在“单实例的最大请求率”上：

- **前缀缓存**（第 76 讲）：系统提示命中缓存，prefill 的时间大幅减少，f 变小，λ 变大。
- **量化**（第 90–94 讲）：权重和 KV 变小，decode 一步更快，同样的 TPOT 下能放更大的批。
- **投机解码**（第 96 讲）：在低并发、TPOT 要求严的场景，降低延迟。
- **PD 分离**（第 112 讲）：prefill 和 decode 各自按需配卡，TPOT 更稳，余量可以留得更少。
- **调整 SLO 本身**：TPOT 从 15 ms 放宽到 30 ms，成本降了近四成。和业务一起确认真正需要的延迟，往往是最便宜的优化。

## 启动和积压：扩容要多快

前面算的都是稳态：实例已经在跑。扩容、发布新版本或故障恢复时，新实例要先启动，而请求还在不断到来。

**启动要做的事。**新实例要创建进程、初始化分词器、读取并切分权重、编译、探测 KV 容量、捕获 CUDA Graph（第 89 讲）。有的准备换来的是之后每一步更快：比如多花 10 s 捕获执行图，每步省 0.2 ms，要 **50,000 步**才持平；每步 32 个请求，相当于约 160 万个输出 token。这笔账按执行的步数算，实例活得越久越划算。

**积压怎么消退。**设到达率 λ，启动期间服务完全停摆，启动用了 T_s 秒，积压就是 λ·T_s。就绪后服务率是 μ，每秒新来 λ 个，真正能用来消化积压的只有 μ − λ：

<div class="ai-formula">排空时间 = λ·T_s ÷ (μ − λ)</div>

拿第 112 讲的 8 卡异构集群算：每秒 3.5 个请求，启动 10 s，积压 35 个。PD 分离的 4.55 请求/s 每秒只能消化 1.05 个，从开始启动算起第 **43.3 s** 排空；共置加理想的分块捎带是 4.17 请求/s，要到第 **62.2 s**；不分块的共置只有 3.02，低于到达率，积压一直增长。

<BacklogDrain caption="图 116-2　启动 10 s 后三种部署的积压曲线（每秒 3.5 个请求）。下降的斜率是服务率减去到达率；PD 分离第 43.3 s 排空，共置加理想分块第 62.2 s，共置一直积压。把效率调到 90%，PD 也会超过 60 s 的期限。" />

反过来也能求最低服务率：要在第 60 s 前排空，扣掉启动的 10 s，剩下 50 s 要消化 35 个积压，同时处理新到的请求：

<div class="ai-formula">μ ≥ 3.5 + 35 ÷ 50 = 4.20 请求/s</div>

PD 分离的 4.55 只比它高约 8%。如果实际效率只有估算的九成（4.09 请求/s），稳态还撑得住，排空却要到第 **68.8 s**，超了期限。这就是第 82 讲说“不能按上限规划”的另一面：余量不只是为了扛波动，也决定了出事之后恢复得多快。

**在线迁移。**计划内地把一个 decode 实例挪走，可以先在后台复制 KV，源端照常生成，最后短暂停一下补上新增的部分。一张 H20 上 32 个请求的 KV 约 41.1 GB，decode 每秒只追加约 0.172 GB。经 25 GB/s 的网卡约 **1.66 s** 追上源端，经 6.25 GB/s 的 50 GbE 约 **6.76 s**。只要复制带宽远高于状态增长的速度，追赶时间几乎只由初始的状态大小决定。

**软件准备是下限。**把 Qwen3-8B 从 TP4 切到 TP8，要经网络搬约 16.4 GB。50 GbE 要 2.62 s，200 Gbit/s 网卡 0.66 s，相差四倍；但如果建通信组、准备执行图、恢复接收请求还要串行地花 9 s，总时间是 11.6 s 和 9.7 s，只差 17%。即使八张卡在同一台机器、走 NVLink、搬数据只要 0.02 s，总时间也还有 9.0 s。这类时间靠更快的链路省不掉，只能靠软件：提前建好通信组、预先捕获执行图、让准备和传输重叠。

**故障的影响范围。**张量并行组或专家并行组丢了一张卡，整个实例上的请求都会停；其他独立的副本不受影响。所以实例越大，一次故障停掉的服务能力越多（第 115 讲）。恢复还要分清两件事：用户已经收到了哪些 token（要可靠地记录下来，例如预写日志），哪些 KV 已经保存。如果 1025 个输出都记下了，但 KV 只保存了输入部分，恢复时把前 1024 个输出当作一次 prefill 补回去就能接着生成，不必重新采样，用户看到的输出不会变。

## 按合格的请求算成本

上面的成本按“每百万个请求”算。更准确的分母是**满足质量和时限的请求**：

<div class="ai-formula">有效成本 = 统计期间的总成本 ÷ 合格完成的请求数</div>

还是 8 卡异构集群，按每小时 8 元算：满载时共置每千个请求 0.74 元，PD 分离 0.49 元。可如果 PD 分离只有四分之一的请求满足时限，每千个合格请求就涨到 **1.95** 元，比共置还贵。超时、失败、重做的请求都算在分子里、不算在分母里。提前退出的 Agent 少生成了 token，但没有完成任务，也不能算一次合格的完成。

## 到了大模型里

**多模型、多租户。**一个平台常常同时服务很多个模型和客户，不同客户的 SLO 和优先级不同。容量规划要分别评估，再考虑共享资源时的隔离和抢占（第 78 讲）。

**按 token 计价的反推。**API 服务按每百万 token 收费（第 72 讲）。容量规划算出每百万请求、每百万 token 的 GPU 成本，就能判断定价是否覆盖成本、留出多少利润。

**大模型的实例更大。**70B 的实例是 4 到 8 张卡（第 110 讲），DeepSeek-V3 的 decode 实例是几百张卡（第 108 讲）；方法完全一样，只是“一个实例”的单位变大，单实例的最大请求率要按整组卡来测。

## 用代码复现

下面的代码实现了上面的容量模型：对给定的输入、输出长度和 TPOT 上限，从小到大试单实例的请求率 λ，用不动点迭代求出同时 decode 的请求数 b，检查 TPOT 和显存；再按 70% 的使用率算出实例数和每百万请求的成本。

```python
import math
# 容量规划：给定流量和 SLO，需要多少个实例。沿用第 72 讲的假设：实际效率 60%，H100 租金 2.5 美元/小时（示例）
F, BW, EFF, PRICE = 989e12, 3.35e12, 0.6, 2.5
M = dict(N=8.03e9, Ne=525e6, L=32, d=4096, kv=131072)       # Llama-3-8B，一个实例 = 一张 H100

def tpot(b, ctx):                                          # b 个请求一起 decode 一步（第 70 讲）
    flops = (2 * (M["N"] - M["Ne"]) + 4 * M["L"] * M["d"] * ctx) * b
    return max(flops / F, (M["N"] * 2 + M["kv"] * ctx * b) / BW) / EFF

def plan(qps, inp, out, slo_tpot, util=0.7):
    """一个实例每秒最多能服务多少请求 λ，同时满足 TPOT 和显存。
    prefill 是计算受限的，每秒占掉 f = λ·inp·c 的 GPU 时间；decode 只能用剩下的 (1 − f)，所以实际 TPOT = t(b) ÷ (1 − f)。
    同时在 decode 的请求数 b 由 Little 定律决定：b = λ × out × TPOT。"""
    ctx, c = inp + out / 2, 2 * (M["N"] - M["Ne"]) / F / EFF
    best = None
    for k in range(1, 2000):
        lam = k * 0.1
        f = lam * inp * c
        if f >= 1: break
        b = 1.0
        for _ in range(50): b = lam * out * tpot(b, ctx) / (1 - f)      # 不动点迭代求 b
        real = tpot(b, ctx) / (1 - f)
        if real > slo_tpot or M["kv"] * (inp + out) * b > 50e9: break
        best = (lam, b, real)
    lam, b, real = best
    n = math.ceil(qps / (lam * util))                      # 每个实例只跑到 70%，留余量应对波动（第 82 讲）
    cost = n * PRICE / (qps * 3600) * 1e6                  # 每百万个请求的 GPU 成本
    return b, real, lam, n, cost

print("每秒请求 | 输入/输出 | TPOT 上限 | 满载时同时 decode 的请求 | 实际 TPOT | 每实例每秒请求 | 需要实例 | 每百万请求成本")
for qps, inp, out, slo in [(50, 1000, 300, 0.030), (50, 1000, 300, 0.015), (50, 4000, 300, 0.030), (200, 1000, 300, 0.030)]:
    b, t, lam, n, cost = plan(qps, inp, out, slo)
    print(f"{qps:4d} | {inp}/{out} | {slo * 1e3:3.0f} ms | {b:5.0f} | {t * 1e3:5.1f} ms | {lam:5.1f} | {n:3d} | ${cost:6.0f}")
b, t, lam, n, cost = plan(50, 1000, 300, 0.030)
print(f"第一行的含义：一个实例最多每秒 {lam:.1f} 个请求，此时同时有约 {b:.0f} 个在 decode（Little 定律：{lam:.1f} × 300 × {t * 1e3:.1f} ms），"
      f"TPOT {t * 1e3:.1f} ms；按 70% 使用率，每秒 50 个请求要 {n} 个实例")
```

```text
  50 | 1000/300 |  30 ms |   136 |  29.7 ms |  15.3 |   5 | $    69
  50 | 1000/300 |  15 ms |    43 |  14.9 ms |   9.7 |   8 | $   111
```

四行对应上面的四种情况：基准 5 张卡；TPOT 收紧到 15 ms 要 8 张；输入变长到 4000 要 18 张；流量变成每秒 200 个要 19 张。最后一行解释了第一行的数字，并用 Little 定律验证了它。

第二段代码复现“启动和积压”和“按合格的请求算成本”的数字：三种部署的排空时刻、满足期限的最低服务率、执行图的回本步数、在线迁移和重配置的时间，以及有效成本。

```python
# 1. 启动期间的积压：到达率 λ，启动 Ts 秒，就绪后服务率 μ > λ，积压 λ·Ts 要 λ·Ts/(μ−λ) 秒排空
lam, Ts, deadline = 3.5, 10, 60                     # 第 112 讲的 8 卡异构集群：每秒 3.5 个请求
for name, mu in [("PD 分离", 4.55), ("共置 + 理想分块捎带", 4.17), ("共置", 3.02), ("PD，效率只有九成", 4.55 * 0.9)]:
    if mu <= lam: print(f"{name}（{mu:.2f} 请求/s）：服务率低于到达率，积压一直增长"); continue
    drain = lam * Ts / (mu - lam)
    print(f"{name}（{mu:.2f} 请求/s）：积压 {lam*Ts:.0f} 个，从开始启动算起第 {Ts + drain:.1f} 秒排空")
print(f"要在第 {deadline} 秒前排空，服务率至少 {lam + lam*Ts/(deadline - Ts):.2f} 请求/s")

# 2. 启动时多花的准备（比如捕获 CUDA Graph）要多少步才收回
extra, saved = 10, 0.2e-3
print(f"启动多花 {extra} s、每步省 {saved*1e3} ms：{extra/saved:,.0f} 步才持平（批 32 约 {extra/saved*32/1e6:.1f} 百万个 token）")

# 3. 在线迁移一个 decode 实例：后台复制 41.1 GB 的 KV，源端还在以每秒 0.172 GB 增长
kv0, grow = 41.1e9, 1166 * 144 * 1024             # H20 每秒 1166 次 decode，每次追加一个 token 的 KV
for name, bw in [("200 Gbit/s 网卡（25 GB/s）", 25e9), ("50 GbE（6.25 GB/s）", 6.25e9)]:
    print(f"{name}：{kv0/(bw-grow):.2f} s 追上源端")
for name, move in [("50 GbE", 16.4e9 / 6.25e9), ("200 Gbit/s 网卡", 16.4e9 / 25e9), ("机内 NVLink", 4.7e9 / 300e9)]:
    print(f"TP4→TP8 重配置，{name}：搬数据 {move:.2f} s + 软件准备 9 s = {move + 9:.1f} s")

# 4. 按合格请求算成本：8 张卡每小时 8 元
for name, mu, ok in [("共置满载", 3.02, 1), ("PD 满载", 4.55, 1), ("PD，但只有四分之一的请求满足时限", 4.55, 0.25)]:
    print(f"{name}：每千个合格请求 {8 / (mu * ok * 3600) * 1000:.2f} 元")
```

```text

共置（3.02 请求/s）：服务率低于到达率，积压一直增长
```

## 容易混淆的地方

1. **GPU 利用率不是容量的好指标。**decode 时 GPU 可能显示“100% 忙”，算力却只用了一小部分（第 89 讲）。容量要看 SLO 下的请求率，而不是利用率。
2. **余量不是浪费。**接近饱和点时延迟会急剧变差，余量是为了让 P99 守得住。目标使用率定多少，取决于流量的波动和 SLO 的严格程度。
3. **平均延迟满足不代表 SLO 满足。**SLO 通常针对 P99，容量规划和压测都要看尾延迟。

4. **排空积压靠的是余量，不是服务率。**排空时间 = λ·T_s ÷ (μ − λ)。服务率只比到达率高一点时，稳态看着没问题，一次重启或扩容就要很久才能恢复。
5. **链路再快，也省不掉软件准备的时间。**重配置、扩容时，建通信组、准备执行图常常比搬数据更久。

## 回顾

容量规划先把延迟要求写成 SLO（比如 TTFT P99、TPOT P99），再算一个实例在 SLO 内能服务的最大请求率：TPOT 的上限限制了同时 decode 的请求数，Little 定律（b = λ × 输出长度 × TPOT）把它和请求率联系起来，prefill 还要占掉一部分 GPU 时间。Llama-3-8B、H100、每秒 50 个请求（输入 1000、输出 300）：TPOT ≤ 30 ms 时每实例 15.3 个/s，按 70% 使用率要 5 张卡；TPOT ≤ 15 ms 要 8 张；输入 4000 要 18 张。上线前要实测 goodput，按峰值规划，并考虑扩容的时间。前缀缓存、量化、PD 分离和放宽 SLO，都是降低成本的杠杆。

容量规划还要看非稳态：启动 T_s 秒留下 λ·T_s 个积压，排空时间是 λ·T_s ÷ (μ − λ)。8 卡异构集群每秒 3.5 个请求、启动 10 s，PD 分离第 43.3 s 排空，要在 60 s 内排空至少需要 4.20 请求/s，效率差一成就超期。成本的分母应该是合格完成的请求：只有四分之一合格时，0.49 元会变成 1.95 元。
