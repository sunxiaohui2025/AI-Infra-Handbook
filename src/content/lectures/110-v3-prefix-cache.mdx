真实的服务里，大量请求的开头是一样的：同一个应用的系统提示，同一段多轮对话的历史，同一份被反复提问的文档。v3 的每个请求都把自己的提示从头算一遍，哪怕前面 300 个 token 和上一个请求一字不差。

第 68 讲讲过前缀缓存的原理：KV 只取决于“这个位置之前的全部 token”，开头相同，前几个块里的 K、V 就一模一样，后来的请求可以直接用。有了 v3 的块表，这件事变得很自然：**让后来的请求的块表，直接指向已经算好的块**。这一讲在 block_manager.py 里加上它，大约 30 行。

## 设计：怎么认出“同一个块”

要复用一个块，得能快速判断“这个块里存的，就是我要的 KV”。直接比 KV 的数值太慢，我们比它的**来源**：一个块的 KV 由“它之前的全部 token + 它自己的 16 个 token”唯一决定。

所以给每个装满的块算一个哈希：

```text
h(第 0 块) = hash(无,          第 0 块的 16 个 token)
h(第 1 块) = hash(h(第 0 块),  第 1 块的 16 个 token)
h(第 2 块) = hash(h(第 1 块),  第 2 块的 16 个 token)
```

每一块的哈希都把前一块的哈希算进去，链式地连到开头。这样两个块哈希相同，就说明它们的整个前缀都相同，而不只是这 16 个 token 碰巧一样（第 68 讲的链式块哈希）。

块管理器维护一张表：哈希 → 块号。剩下的规则：

1. **只登记装满的块**。没装满的块，后面还会写入，内容没定下来。
2. **算完才登记**。块的 K、V 要真正写进去之后，才能给别人用；所以登记放在每一步 forward 之后。
3. **新请求从头逐块查**，连续命中就继续，第一次没命中就停：前缀缓存只能从开头连续地复用。
4. **一个块可以被多个请求共用**，用引用计数记有几个人在用。
5. **没人用的块，内容先留着**。它回到空闲列表，但哈希表里的登记不删，后来的请求还能命中；只有它被拿去装别的内容时，登记才作废。这让空闲列表自然地变成了一个按释放先后淘汰的缓存。
6. **不复用含最后一个 token 的块**。新请求总得算出最后一个位置的打分，才能得到下一个 token；如果它的提示全部命中，最后一个 token 也就没有被“算”过。所以最后一个 token 所在的块总是自己算。

## 先验证

前缀缓存最怕的是“命中了不该命中的块”：两个请求只是某一块的 16 个 token 相同、前面不同，却共用了块，后面的请求就会读到别人的 KV，悄悄地生成不同的结果。上一讲的小块池检查已经打开了前缀缓存；下面的压测还会比较打开和关闭时的输出。

## 测一测：共用系统提示的 8 个请求

8 个请求共用一段很长的系统提示（约 330 个 token），后面各接一个不同的问题。先跑第 1 个，它的提示块留在块池里；再一起跑后 7 个，比较前缀缓存打开和关闭。

<RunOutput cmd=".venv/bin/python bench/prefix.py" file="outputs/bench_prefix.txt" caption="图 110-2　后 7 个请求的提示共 2356 个 token。打开前缀缓存后，2240 个位置直接命中，只 prefill 了 116 个，用时从 5.5 s 降到 2.4 s；两种情况的输出完全一致。" />

逐项看：

- **命中 2240 个位置** = 7 个请求 × 20 个块 × 16。系统提示加上 “Question: ” 共约 330 个 token，前 20 个满块（320 个位置）对所有请求都一样，全部命中。
- **只 prefill 116 个 token**：每个请求剩下的十几个 token（第 21 块里的系统提示尾巴和它自己的问题）。
- **时间少了一半多，而不是少 95%**：prefill 省掉了，但每个请求还要 decode 8 个 token，这部分时间没变；而且命中的请求在 decode 时，注意力仍要读完整的 330 多个位置的 K、V。
- **输出完全一致**：共用的块里存的 K、V，和自己算出来的一模一样。

第 68 讲提过的多轮对话也是同样的道理：第二轮的输入是“第一轮的全部 + 新问题”，第一轮结束时它的块都还在池子里（引用计数归零，但登记还在），第二轮进来就能命中。

<Note kind="point">前缀缓存建在块表之上：给装满、算完的块按“前一块的哈希 + 本块的 token”算链式哈希并登记；新请求从头逐块查，连续命中的块直接放进自己的块表、引用计数加一，这些位置不用再算。没人用的块内容先留着，被重新拿去用时才作废登记。</Note>

## 回顾

前缀缓存全部写在块管理器里：链式块哈希保证“哈希相同 = 整个前缀相同”；只登记装满并且已经算完的块；新请求从头逐块查，连续命中就复用，最后一个 token 所在的块总是自己算；引用计数让一个块被多个请求共用，归零的块保留内容、被覆盖时才作废。8 个共用系统提示的请求，后 7 个的 prefill 从 2356 个 token 降到 116 个，用时从 5.5 s 降到 2.4 s，输出完全一致。

到这里，KV 的组织已经比较完整了。剩下最大的一块内存是权重：FP32 下线性层就有 1.6 GB 多。能不能用更少的位数存权重？下一讲：**v4 · 权重量化**。
