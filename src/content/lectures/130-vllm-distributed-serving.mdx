第 129 讲读的是“一个 EngineCore”：一个调度器、一个执行器、几张卡。真实的线上服务往往大得多：模型要跨好几张卡做张量并行；为了吞吐，同一个模型要部署好几个副本，分布在多台机器上；做 PD 分离时，prefill 和 decode 还是两组不同的实例，KV 要在它们之间搬运。

这一讲把视野放大到整个服务，跟着一条 curl 请求走一遍：它先到哪台机器、怎么在几个副本里挑一个、在副本里怎么分给几张卡、MoE 模型的副本之间为什么要“锁步”、PD 分离时 KV 怎么从一个实例到另一个实例。每一层都对应第 14 篇讲过的一个原理（数据并行、专家并行、PD 分离、KV 传输、缓存感知路由），这一讲看它们在 vLLM 里是怎么写出来的。

<Note kind="column" title="参考">这一讲的讲法参考了 Aleksa Gordić 的博客 *Inside vLLM: Anatomy of a High-Throughput LLM Inference System*（2025 年 8 月，基于 vLLM 提交 `42172ad`）。我们读的是 2026 年 11 月的提交 `821851e`，一年多里不少细节变了：只有 MoE 模型的副本才锁步运行，负载均衡的打分加入了在途请求数和 KV 压力，博客示例里的 `SharedStorageConnector` 也不在了。下文遇到时会指出来，这本身就是读源码时要注意的事：博客和文档会过时，代码才是准的。和前几讲一样，本讲只读源码，没有运行。</Note>

## 第一层：一个副本里的几张卡

先回到单个副本。第 129 讲提到，EngineCore 通过执行器（Executor）让 worker 跑模型。一个副本用 4 张卡做张量并行时，执行器是 `MultiprocExecutor`：每张卡一个 worker 进程，EngineCore 每一步把调度结果广播给它们。

这件事 nano-vllm 也做过（第 127 讲）：rank 0 把“方法名 + 参数”pickle 后写进 1 MiB 的共享内存，再用事件通知其他进程。vLLM 的做法是同一个思路的工程化版本：

谁来回复？第 683–697 行的 `_get_output_rank` 给出了答案：**最后一个流水线阶段里张量并行编号为 0 的那个 worker**。只有最后一个流水线阶段算出了打分，而同一阶段里各张卡的结果相同，取第一张就够了。worker 那边是一个死循环（第 1188–1218 行）：从广播队列取出调用，执行，如果自己就是指定回复的那一个，就把结果写进自己的回复队列。

和 nano-vllm 相比，差别在细节上：环形队列让 EngineCore 可以连续发出几步（流水线并行、异步调度时需要），不用等上一步的读者读完；回复只走一条队列；所有 worker 共享同一个广播写入，而不是 pickle 一次、通知 N 次。

## 第二层：多个副本

模型放进 4 张卡以后，想要更高的吞吐，就部署更多副本：数据并行（DP）。博客里的例子是两台 8 卡的机器、4 个副本、每个副本张量并行 4 卡。在 vLLM 里这样启动（两台机器各运行一次）：

```bash
# 节点 A：带 API 服务器，副本 0、1
vllm serve <model> --tensor-parallel-size 4 --data-parallel-size 4 --data-parallel-size-local 2 \
  --data-parallel-start-rank 0 --data-parallel-address <节点 A 的 IP> --data-parallel-rpc-port 13345
# 节点 B：只跑引擎，副本 2、3
vllm serve <model> --tensor-parallel-size 4 --data-parallel-size 4 --data-parallel-size-local 2 \
  --data-parallel-start-rank 2 --data-parallel-address <节点 A 的 IP> --data-parallel-rpc-port 13345 --headless
```

## 第四层：MoE 副本的锁步

对稠密模型，副本选好就结束了。MoE 模型多了一个约束：**所有副本必须一起前向**。专家层的 All-to-All 是一个集合通信，每个副本都必须参加；只要有一个副本在算，其余副本就算没有请求，也要跑一个“空批次”陪着，否则正在算的副本会卡在 All-to-All 上等。

## 合起来：一条 curl 的全程

把五层串起来，一条请求在“两个节点、4 个 MoE 副本、每副本 4 卡”的部署里：

1. **API 服务器**（`entrypoints/openai/completion/serving.py` 的 `create_completion`）收到请求，`AsyncLLM.generate` 分词、建输出流。
2. **挑副本**：`DPLBAsyncMPClient.get_core_engine_for_request` 用协调器的快照、本地计数、在途数和 KV 压力打分，选中比如副本 2；本地快照里副本 2 的等待数加一。
3. **发过去**：经 ZMQ 发到节点 B 上副本 2 的输入线程，放进输入队列。如果副本组正处于暂停，副本 2 醒来并通知协调器，协调器广播 START_DP_WAVE 叫醒其余副本。
4. **调度**：副本 2 的调度器为它分配 token 和块（第 129 讲）；PD 分离时先问 connector 外部有多少 KV。
5. **执行**：`MultiprocExecutor` 把调度结果写进共享内存广播队列，4 个 worker 一起前向；MoE 的专家层和其他 3 个副本做 All-to-All（没有请求的副本跑空批次陪着）；输出 rank 把采样结果写回。
6. **更新**：调度器接上新 token、判断结束；副本把新的负载数字发给协调器，协调器发布给前端。
7. **返回**：副本 2 的输出线程把结果发回节点 A，`AsyncLLM` 的输出任务反分词、分发到这个请求的输出流，FastAPI 流式推给客户端。

<Note kind="point">vLLM 的分布式服务是一层套一层：副本内部，MultiprocExecutor 用共享内存广播队列驱动几张卡，只让一个 worker 回结果；副本之间，稠密模型彼此独立，MoE 模型锁步运行（空闲副本跑空批次陪着做 All-to-All，每 16 步 All-Reduce 一次判断是否全体空闲，用“波次”管理启停）；前端在副本之间分请求，用协调器每 100 ms 发布的负载快照，加上本地计数、在途下限和 KV 压力罚分；PD 分离通过 KV connector 接入，调度器一侧回答“外部有多少 KV、写进哪些块、何时释放”，worker 一侧负责加载和保存。</Note>

## 回顾

这一讲从一个副本的几张卡，一路放大到多节点、多副本和 PD 分离。几个要记住的取舍：回复只走一个 worker，省掉重复的序列化；稠密模型的副本互不通信，MoE 的副本必须锁步；负载均衡依赖 100 ms 一次的旧快照，靠本地计数和在途数补偿；全局同步每 16 步一次，用少量空跑换掉大量通信；异步的 KV 加载挪到前向之后，不挡关键路径。这些细节和一年前的博客已经不同，读源码时要以手上的那个提交为准。
