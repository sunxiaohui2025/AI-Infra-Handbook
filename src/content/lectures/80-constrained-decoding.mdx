大模型的输出越来越多地交给程序去读，而不是给人看：从一段话里抽取姓名和年龄，存进数据库；让模型决定调用哪个工具、传什么参数；让一个智能体按固定的格式汇报它的下一步动作。程序需要的是**严格符合格式**的输出，比如一段能被 `json.loads` 直接解析的 JSON，字段名、类型都对。

在提示里写清楚“请只输出 JSON，格式如下……”，大多数时候模型会照做，但不能保证每次都对：它可能在前面加一句“好的，”，可能用 Markdown 的代码块包起来，可能把年龄写成“十二岁”这样的字符串。一万次请求里只要错几次，程序就会出错。这一讲讲推理引擎怎么**从机制上保证**输出符合格式：**约束解码**（constrained decoding）。

## 在选词之前动手脚

回忆第 24 讲和第 73 讲：模型每一步输出词表上每个 token 的打分（logits），经过 softmax 变成概率，再按某种策略（贪心、Top-p……）选出一个 token，接到后面，进入下一步。

约束解码只在“选词”之前加一步：**检查词表里每个 token，如果把它接上去，输出就不可能再符合格式了，就把它的 logit 设成 −∞**（概率变成 0）。剩下的 token 重新归一化，再照常选词。

这样，每一步选出的 token 都保证“到目前为止还合法”；最后只有格式完整时才允许输出结束标记。一步一步下来，整个输出一定符合格式。模型本身一点没改，改的只是每一步的候选范围。

## 怎么判断一个 token 合不合法

要回答“接上这个 token 以后，还能不能符合格式”，需要把格式写成一台**状态机**。以这一讲的例子为准：

<div class="ai-formula">{'{"name": "〈不含引号的非空字符串〉", "age": 〈非负整数〉}'}</div>

把它拆成 5 段：开头的固定文字 `{"name": "`；名字（任意不是引号的字符，至少 1 个）；中间的固定文字 `", "age": `；年龄（数字，至少 1 个）；结尾的 `}`。状态就是“现在在第几段、这一段读了几个字符”。每读进一个字符：

- 在固定文字段，这个字符必须和该位置的字符相同，否则不合法。
- 在名字段，不是引号就留在这一段；是引号，并且名字至少有 1 个字符，就进入下一段（这个引号属于中间那段固定文字）。
- 在年龄段，是数字就留下；不是数字，并且已有至少 1 个数字，就交给下一段（结尾的 `}`）。

判断一个 token 合不合法，就把它的字符一个个送进状态机，中途没有出错就合法。比如已经生成了 `{"name": "小明", "age": `，现在在年龄段：

- `"`：年龄段需要数字，不合法。
- `十二`：不是数字，不合法。
- `12`：两个数字，合法。

注意 token 往往不是单个字符，`", ` 这样的 token 一次跨过了好几个字符，甚至跨过了段的边界，所以要逐字符检查。

## 一个完整的例子

为了看清每一步发生了什么，我们手写一个“模型”：在每个位置给出几个候选 token 的打分，其余 token 的分数很低，忽略不计。这个模型的“习惯”和很多真实模型类似：喜欢先说一句“好的，JSON：”，最后再加个句号，年龄写成“十二岁”。

**不加约束**，每一步选打分最高的，它会写出：

<div class="ai-formula">{'好的，JSON：{"name": "小明", "age": "十二岁"}。'}</div>

这不是合法的 JSON，`age` 也不是数字。

**加约束**以后：

- 第 1 步，候选是“好的，”、“JSON：”和 `{`。前两个不合格式（格式要求以 `{` 开头），屏蔽，只剩 `{`，虽然它原来的概率只有 19%，也只能选它。
- 第 2 到 8 步，模型自己想写的和格式一致，没有被屏蔽的 token，照常选择，写出 `{"name": "小明", "age": `。
- 第 9 步，模型想写引号（准备把年龄写成字符串），引号和 `十二` 都被屏蔽，只剩 `12`，原来的概率只有 13%。
- 第 10 步，模型想接“岁”，屏蔽；选 `}`。
- 第 11 步，模型想在最后加个句号，格式已经完整，后面不能再有字符，屏蔽；选结束。

最终输出 `{"name": "小明", "age": 12}`，`json.loads` 可以直接解析。

## 词表有十几万个，每步都检查一遍？

例子里每步只有两三个候选。真实模型的词表有十几万个 token（Llama-3 是 128256 个），如果每一步都把每个 token 逐字符送进状态机检查一遍，CPU 上要花几十毫秒，比 GPU 算一步还慢。实际的做法有几种：

**提前算好。**状态机的状态是有限的。对每个状态，提前把“哪些 token 合法”算好，存成一个掩码（mask）。生成时只要查一下当前状态对应的掩码，直接用。Outlines 这个库最先系统地这样做：把 JSON Schema 转成正则表达式，再转成状态机，为每个状态建好 token 的索引。

**和 GPU 计算重叠。**下一步的掩码只取决于已经生成的 token，可以在 GPU 算这一步的 logits 时，同时在 CPU 上准备好。

**处理嵌套的结构。**JSON 可以无限嵌套（对象里有数组，数组里又有对象），这种结构用有限状态机描述不了，要用**上下文无关文法**，对应的检查器是带一个栈的状态机（下推自动机）。XGrammar、llguidance 等库专门优化了这件事，大部分 token 的合法性和栈无关，可以提前算好，只有少数要在生成时检查，每步的开销能做到几十微秒。

**跳过确定的部分。**例子里有好几步，屏蔽以后只剩一个合法的 token（比如 `"age"` 后面只能是 `: `）。既然没得选，就不必让模型算一步，可以直接把这段固定文字接上去。SGLang 把这叫作**跳跃式解码**（jump-forward decoding），对字段名很多的 JSON 能省下不少步数。

## 代价：可能把模型“逼”到奇怪的地方

约束解码保证的是**格式**，不保证**内容**。屏蔽改变了模型原本的概率分布：第 9 步模型想写“十二岁”，被逼着写数字，它这次写出了 `12`，原来的概率只有 13%。如果模型对内容本来就没把握，或者格式和它的“习惯”差得太远，被逼出来的内容可能是错的，甚至是胡乱的数字和字符串。

所以实践中两件事要一起做：提示里照样写清楚格式和字段的含义，让模型本来就倾向于写出正确的格式；约束解码作为最后的保证，确保程序不会因为格式而出错。

还有一个和分词（第 21 讲）有关的细节：同样的文字可以被切成不同的 token。格式强制模型写某段文字时，它可能被迫用一种平时很少见的切法（比如本来 `", "` 是一个 token，被约束切成了 `"` 和 `, "`），这也会让模型的表现变差。好的实现会让约束尽量符合模型平时的分词习惯。

## 到了大模型里

**API 里的结构化输出。**很多大模型 API 提供“结构化输出”：请求里给一个 JSON Schema，返回的内容保证符合它。工具调用（function calling）也一样：模型要调用的工具名和参数，必须符合工具定义的格式。它们背后通常就是约束解码。

**推理引擎里的支持。**vLLM 和 SGLang 都支持按 JSON Schema、正则表达式或文法约束输出，后端可以选 XGrammar、llguidance、Outlines 等。在推理引擎里，约束解码发生在采样之前，对每个请求按它自己的格式生成掩码，和连续批处理里别的请求互不影响。

**格式和推理的冲突。**如果要求模型一开口就输出 JSON，它就没有机会先“想一想”（第 49 讲的思维链）。常见的做法是在 Schema 里留一个“推理过程”的字段放在最前面，或者先让模型自由思考，再约束最后的答案部分。

## 用代码复现

下面的代码实现了上面的状态机和手写的“模型”，先不加约束生成一遍，再加约束生成一遍，打出每一步的候选、被屏蔽的 token（✗）和选择。

```python
import json, math

# 要求的格式：{"name": "<不含引号的非空字符串>", "age": <非负整数>}，拆成几段，一个字符一个字符地检查
SEGS = [("lit", '{"name": "'), ("str", None), ("lit", '", "age": '), ("num", None), ("lit", "}")]

def advance(state, ch):
    """状态 = (第几段, 这一段已读了几个字符)。读入一个字符，返回新状态；不合法返回 None。"""
    i, k = state
    if i == len(SEGS): return None                          # 格式已经完整，后面不能再有字符
    kind, lit = SEGS[i]
    if kind == "lit":
        if lit[k] != ch: return None
        return (i + 1, 0) if k + 1 == len(lit) else (i, k + 1)
    ok = ch != '"' if kind == "str" else ch.isdigit()
    if ok: return (i, k + 1)
    return advance((i + 1, 0), ch) if k >= 1 else None     # 这一段结束（至少 1 个字符），交给下一段

def allowed(state, tok):
    if tok == "<结束>": return state[0] == len(SEGS)          # 只有格式完整了才能结束
    for ch in tok:
        state = advance(state, ch)
        if state is None: return False
    return True

# 一个手写的“模型”：根据已经生成的文字，给出几个候选 token 的打分（logits），其余 token 的分数很低，省略
BEFORE = {"": [("好的，", 3.0), ("JSON：", 2.5), ("{", 2.0)], "好的，": [("JSON：", 3.0), ("{", 2.5)], "好的，JSON：": [("{", 4.0)]}
TABLE = {                                                   # 进入 JSON 以后，只看第一个 { 之后的部分
    "": [('"name"', 4.0), ('"', 1.0)],
    '"name"': [(": ", 4.0), (":", 2.0)],
    '"name": ': [('"', 4.0)],
    '"name": "': [("小明", 3.5), ("小红", 3.0)],
    '"name": "小明': [('", ', 4.0), ('"', 2.0)],
    '"name": "小明", ': [('"age"', 4.0)],
    '"name": "小明", "age"': [(": ", 4.0)],
    '"name": "小明", "age": ': [('"', 3.0), ("十二", 2.2), ("12", 1.5)],
    '"name": "小明", "age": "': [("十二", 3.0), ("12", 1.0)],
    '"name": "小明", "age": "十二': [("岁", 2.5), ('"', 2.0)],
    '"name": "小明", "age": "十二岁': [('"', 4.0)],
    '"name": "小明", "age": "十二岁"': [("}", 4.0)],
    '"name": "小明", "age": 12': [("岁", 2.4), ("}", 2.0), ("0", 0.5)],
    '"name": "小明", "age": "十二岁"}': [("。", 3.0), ("<结束>", 2.5)],
    '"name": "小明", "age": 12}': [("。", 3.0), ("<结束>", 2.5)],
}
def model(text):
    if "{" not in text: return BEFORE[text]
    return TABLE.get(text[text.index("{") + 1:], [("<结束>", 3.0)])

def generate(constrained):
    text, state = "", (0, 0)
    while True:
        cands = model(text)
        z = sum(math.exp(s) for _, s in cands)
        ok = [(t, s) for t, s in cands if not constrained or allowed(state, t)]   # 屏蔽：不合法的 token 概率置 0
        tok = max(ok, key=lambda x: x[1])[0]
        if constrained:
            shown = "  ".join(f"{t!r}{'' if allowed(state, t) else '✗'}" for t, _ in cands)
            print(f"  候选 {shown}  → 选 {tok!r}（原概率 {math.exp(dict(cands)[tok]) / z:.0%}）")
        if tok == "<结束>": return text
        text += tok
        if constrained:
            for ch in tok: state = advance(state, ch)

print("不加约束：", repr(generate(False)))
print("加约束，每一步：")
out = generate(True)
print("加约束：", repr(out), "→", json.loads(out))
```

输出：

```text
不加约束： '好的，JSON：{"name": "小明", "age": "十二岁"}。'
加约束，每一步：
  候选 '好的，'✗  'JSON：'✗  '{'  → 选 '{'（原概率 19%）
  候选 '"name"'  '"'  → 选 '"name"'（原概率 95%）
  候选 ': '  ':'  → 选 ': '（原概率 88%）
  候选 '"'  → 选 '"'（原概率 100%）
  候选 '小明'  '小红'  → 选 '小明'（原概率 62%）
  候选 '", '  '"'  → 选 '", '（原概率 88%）
  候选 '"age"'  → 选 '"age"'（原概率 100%）
  候选 ': '  → 选 ': '（原概率 100%）
  候选 '"'✗  '十二'✗  '12'  → 选 '12'（原概率 13%）
  候选 '岁'✗  '}'  '0'  → 选 '}'（原概率 37%）
  候选 '。'✗  '<结束>'  → 选 '<结束>'（原概率 38%）
加约束： '{"name": "小明", "age": 12}' → {'name': '小明', 'age': 12}
```

第一行是不加约束的输出，前面多了“好的，JSON：”，后面多了句号，年龄是字符串。下面 11 行是加约束时的每一步，被屏蔽的 token 后面有 ✗，和演示一致。最后一行是加约束的输出，`json.loads` 成功解析出了 `{'name': '小明', 'age': 12}`。

## 容易混淆的地方

1. **“JSON 模式”和“按 Schema 约束”不一样。**有的 API 的 JSON 模式只保证输出是合法的 JSON，不保证字段名和类型对；按 Schema 约束才保证结构完全符合。
2. **保证格式，不保证内容正确。**约束解码不会让模型知道它不知道的东西，抽取出来的名字、数字仍然可能是错的。
3. **长度上限会打断格式。**如果设的最大生成长度不够，输出写到一半被截断，仍然不是合法的 JSON。约束解码只保证“没被截断时”的合法性。

## 回顾

程序读模型的输出时，需要严格符合格式。光靠提示，模型偶尔会加多余的话、写错类型。约束解码在每一步选词之前，把接上去就不可能符合格式的 token 的概率置 0：格式写成状态机，token 的字符逐个送进去检查，只有格式完整时才允许结束。例子里，手写的模型自己会先说“好的，JSON：”、最后加句号、把年龄写成“十二岁”，加约束后输出 `{"name": "小明", "age": 12}`。真实的词表有十几万个 token，所以要为每个状态提前算好掩码，嵌套结构用下推自动机，确定的部分直接跳过。它保证的是格式，不是内容；屏蔽也会改变模型原来的概率分布，提示里仍要把格式讲清楚。
