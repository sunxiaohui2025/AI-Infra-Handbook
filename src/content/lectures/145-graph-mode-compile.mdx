上一讲的分发器是“一次调用、一次查表、一次下发”。一步 decode 要下发多少次？拿 miniinfer 跑的 Qwen3-0.6B 数一数：28 层，每层几十个算子，一步两千多次（第 148 讲会给出准确数字：2221 次要在设备上算的调用）。每一次都要走分发、算形状、准备参数、交给驱动。

第 89 讲讲过这件事在 NVIDIA 卡上的后果和解法（CUDA Graph）。这一讲从适配的角度重看它：为什么有的硬件几乎非图模式不可；`torch.compile` 怎么接一个新后端；一个图被切成几十段会损失什么；静态形状和动态形状各自的代价。

## 下发开销是怎么变成瓶颈的

<GraphSplit caption="图 145-1　一步 decode 的 CPU 下发开销和 GPU 执行时间（简化模型，默认值按 Qwen3-0.6B 的 28 层 × 79 个算子）。调“每次下发 CPU 时间”，看 GPU 什么时候开始等 CPU；调“图被切成几段”，看中断的代价。" />

默认参数下，CPU 要花 2212 次 × 8 μs ≈ 17.7 ms 做下发，GPU 的活是 13.3 ms——GPU 在等 CPU。这不是假设：第 148 讲在 Apple MPS 上实测，一步 decode 49 ms，而把下发全算上也只有十几毫秒，说明 MPS 上单个算子的执行时间比这个简化模型里的 6 μs 大；但在带宽更高、算子更快的卡上，比例会反过来，下发就成了主角。

新硬件上这个问题往往更严重，原因有三个：

**每次下发的路径更长**。运行时还不成熟时，一次 kernel 发射可能多几层封装、多一次参数拷贝、多一次状态检查。

**同步点更多**。移植初期的实现里常有“为了保险起见”的同步。第 148 讲量到一个具体数字：MPS 上下发一个很小的加法平均 5.4 μs，而把一个数从设备拷回 CPU（`int(tensor)`）平均 141.2 μs——相差 26 倍。miniinfer 的 v1 每层做一次这种拷贝，28 层就是 28 次。

**算子更碎**。缺少融合算子时，一个 RMSNorm 要拆成四五个算子（第 144 讲的复合算子），下发次数成倍增加。

## torch.compile 的三段，和后端挂在哪

`torch.compile` 做三件事：**捕获**（Dynamo 把 Python 字节码翻成一张 FX 图）、**变换**（AOTAutograd 做函数化、分解成更基础的算子）、**生成代码**（后端把图编译成可执行的东西）。厂商要接的是第三段。

一个后端就是一个函数：收到图和示例输入，返回一个可调用对象。PyTorch 文档里的自定义后端就是这个形状。我们在本机写了一个最小的后端，它什么优化都不做，只统计图的大小，然后原样执行：

**v1 编译出 27 张图**，每张只有几十个节点（6、72、17、8、72、17……）；`explain` 报告 25 张图、24 处图中断，第一处中断的原因写得很清楚：`Unsupported Tensor.item() call with capture_scalar_outputs=False`。这就是 `int(pos[-1])` 那一行——它要求把一个张量里的值变成 Python 整数，而 Dynamo 在捕获时并不知道这个值是多少，只能在这里停下来，把图切断、回到 Python 执行一步，再重新开始捕获下一段。28 层里每层切两次，就是二十几张小图。

**port 版编译出 2 张图**，每张 3319、3320 个节点：整个 28 层前向是一张完整的图。差别只在 `model.py` 里的一行——`end` 由调用方以 Python 整数传进来，而不是从张量里取（第 148 讲会用 `CodeDiff` 看这处改动）。

<Note kind="point">图中断（graph break）不是性能的小瑕疵，而是“有没有图模式”的开关。一个被切成 27 段的前向，对需要整图才能优化的硬件来说，等于回到了逐算子执行：段与段之间不能融合、不能跨段规划片上缓冲、不能一次下发。把图中断清零，往往是适配一块依赖图模式的硬件时最先要做的事。</Note>

常见的图中断来源，和它们的改法：

| 中断来源 | 典型写法 | 改法 |
| --- | --- | --- |
| 把张量变成 Python 值 | `int(x[-1])`、`x.item()`、`if x.sum() > 0:` | 把这个量从外面以 Python 数传进来；或打开 `capture_scalar_outputs` 让它变成符号量 |
| 依赖张量值的控制流 | `if seq_len > 512: ...` | 改成和值无关的形式，或把两个分支分别编译 |
| 调用不认识的 C 扩展 | 第三方库的函数 | 注册成自定义算子（第 144 讲），图里就是一个节点 |
| 打印和日志 | `print(x.shape)` | 热路径里去掉 |

## 静态形状和动态形状

图编译的第二个坑是形状。第 88 讲的 `SpecializeCost` 演示讲过这笔账：按形状特化能生成最好的代码，但每换一个形状就要重新编译一次。

推理的形状变化很具体：**decode 的形状稳定**（每步 1 个 token，batch 由调度器决定，vLLM 会把它凑到几个固定档位，第 133 讲的 `GraphBucket`），**prefill 的长度每次都不同**（提示多长就是多长）。

上面脚本的最后两行是这个实验：连续 prefill 8、16、24、8 个 token，再 decode 三步。默认模式下一共编译 3 张图——第一次 prefill（长度 8）编一张按形状特化的图，第二次（长度 16）发现形状变了，重新编译一张**把长度当符号变量**的图，之后长度 24 和回到 8 都直接复用；decode（长度 1）再编一张。这是 Dynamo 的自动动态策略：先赌形状固定，发现变了就退一步，把这一维变成变量。显式写 `dynamic=True` 得到同样的 3 张图。

<Note kind="warn">这个“赌一次再退一步”的策略对服务很重要：如果每个新长度都要编译一次，一个在线服务的前几百个请求会被编译拖慢，而且编译缓存会把内存吃光。接新硬件时要确认厂商的图编译器支持符号形状；只支持静态形状的后端，就必须像 vLLM 那样把形状分档（padding 到档位），用少量几张图覆盖所有情况。</Note>

## 为什么有的硬件更依赖图模式

同样是“整图下发比逐算子好”，不同硬件的程度差得很远。差别来自三件事。

**片上缓冲要显式管理**。第 142 讲说过，NPU 路线上数据进出片上缓冲是写在代码里的。逐算子执行时，每个算子都得自己把输入搬进来、结果搬回去——因为它不知道下一个算子是谁。有了整张图，编译器可以让一个算子的输出留在片上，直接给下一个算子用。省下的是显存往返，这在 RMSNorm、SwiGLU 这类带宽受限的算子上就是成倍的差别（第 83 讲的融合账本）。

**下发路径更贵**。整图下发把几千次下发压缩成一次，省下的 CPU 时间是按比例的。

**编译器需要全局信息才能排流水**。搬运和计算的重叠、双缓冲的安排，都要知道后面还有什么活。逐算子下发时每个算子各自为政，流水排不起来。

这三件事叠起来，就是为什么这类硬件的厂商往往把图模式做成**主路径**而不是优化项：PyTorch 侧接一个自己的 `torch.compile` 后端，把整张图交给厂商的图引擎，由它做融合、内存规划和下发。

GPGPU 路线上的做法不同，更接近 vLLM 在 NVIDIA 上的组合：**分段编译 + 图捕获**。注意力这类带可变长度、要读块表的算子单独留在外面，其余部分按段编译；再用 CUDA Graph 把一步录成一张图，消掉下发开销（第 89、133 讲）。海光的插件就走这条路：平台类里 `support_static_graph_mode` 返回真，图包装器直接复用 vLLM 的 `CUDAGraphWrapper`（第 157 讲会读这几行）。

## 适配时怎么用这一讲

接一块新卡，图模式相关的工作可以按这个顺序推进：

1. **先用 eager 跑通跑对**。图模式会掩盖问题：图中断、形状特化、融合都会改变执行顺序和数值。基线必须是 eager。
2. **数图中断**。`torch._dynamo.explain(fn)(args)` 直接给出图的数量、中断的数量和每处中断的原因。目标是把热路径上的中断清到零，像上面从 27 张图降到 2 张。
3. **确认形状策略**。后端支持符号形状就打开动态，不支持就分档并记录每档一张图，算一下编译时间和内存。
4. **最后开图捕获**。确认数值和 eager 一致（第 146 讲的比对），再量下发开销省了多少（第 149 讲的时间线）。

<Note kind="warn">开图模式之后，一类新错误会出现：原地写 KV Cache 的算子如果没有正确声明副作用，图可能把它优化掉或重排（第 144 讲）。症状是生成的前几个 token 对，后面开始胡言乱语——因为缓存里的内容不对。排查办法是关掉图模式对比一次，再逐段打开。</Note>

## 回顾

一步 decode 有两千多次算子下发，这笔 CPU 开销在新硬件上常常更大，因为下发路径更长、同步点更多、算子更碎。`torch.compile` 把图交给后端，厂商只要实现一个 `(gm, example_inputs) → 可调用对象` 的函数；但能不能拿到一张完整的图，取决于代码里有没有图中断。本机的实验给出了这个对比：miniinfer 的 v1 因为每层一次 `int(pos[-1])` 被切成 27 张小图，去掉这一行后整个前向是一张 3319 个节点的图。形状方面，Dynamo 会先按形状特化、发现变化后把那一维变成符号量，四个长度的 prefill 最终只用两张图。依赖显式搬运的硬件把图模式当主路径，GPGPU 路线更多用分段编译加图捕获。

到这里“跑通”所需的东西差不多齐了：框架认识这块卡，算子有去处，图能编出来。下一讲处理一个更难受的问题——模型跑起来了，输出却和 CPU 上不一样。到底是哪一层开始偏的？
