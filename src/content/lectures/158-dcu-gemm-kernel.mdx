## 一个被关掉的优化，和它的注释

源码里还有一个 split-K 的变体（第 87 讲的 split-K：沿 K 切开凑并行度），用双缓冲、异步搬运、原子加归约。但它被一个宏关掉了，注释写明了原因：

```text
// The current DTK toolchain emits an empty gfx938 code object when the split-K raw
// LDS load path is present in this JIT translation unit. Keep it out of device
// compilation until it can be built as an independent extension.
#define VLLM_HCU_ENABLE_MMAC_SPLITK 0
```

翻译过来：当前的 DTK 工具链在这个即时编译单元里遇到 split-K 那条“直接搬进共享内存”的路径时，会给 `gfx938` 生成一个空的代码对象；所以先把它从设备编译里排除，等能作为独立扩展构建时再说。

这条注释值得单独说，因为它展示了适配工作里最真实的一面：**一个写好的优化，因为工具链的一个问题而暂时关掉**。处理方式有三点可取——用宏整段关闭而不是删掉代码；注释里写清症状（空的代码对象）、条件（在这个即时编译单元里）和重新启用的条件（作为独立扩展构建）；以及关掉之后主路径仍然完整可用。第 149 讲说过“把判断过程写下来”，这就是一个范例。

## 调用方：三层回退

这个 kernel 不是直接被模型调用的，而是放在一个三层回退的链条里（`vllm_hcu/utils/bf16_fp32_gemm.py`）。顺序是：

1. **布局不对就走原生 torch**。如果权重按 `[in_features, out_features]` 存（插件的一个选项），直接用 `torch.mm` 并要求 FP32 输出。
2. **一长串前置条件**：环境变量没关、`torch.version.hip` 不是 None、两个张量都是 BF16、都在设备上、都是二维。任何一条不满足，记下原因、退回 `torch.mm`。
3. **小 M 走 MMAC kernel**：开关打开且 `supported()` 通过时调上面那个 kernel。注释里就写着 `Decode-sized M: hipBLASLt picks a 256x256 tile here (~135us/call)`。调用失败就把这条路**永久关掉**（一个进程内的标志位），记一条警告，退到 hipBLASLt。
4. **再失败退到 `torch.mm`**，同样是永久关掉加一条警告。

最后，整个函数通过 `direct_register_custom_op` 注册成一个自定义算子（`hcu_linear_bf16_fp32`），还配了一个只按形状返回空张量的假实现——第 144 讲讲过这个假实现是给图编译用的。

<Note kind="point">这条链条的设计值得抄：**每一层都有明确的前置条件和失败处理，失败只警告一次（而不是每步刷日志），失败之后永久降级（而不是每次都重试一个已知坏掉的路径）**。适配代码的质量，很大程度上就体现在这种“出错之后怎么办”的处理上。</Note>

## 另一个专用 kernel：lm_head

同一个思路还用在 lm_head 上（`vllm_hcu/model_executor/layers/skinny_lm_head.py`），但实现换成了 Triton。文件开头的注释给了第 150 讲算过的那组数：`M ≤ 64 时这个投影是纯粹的权重流；hipBLASLt 在这里选 256×256 的宏块、在 gfx938 上达到约 0.93 TB/s；这个 kernel 只沿 N 分块、M 方向一个块吃完，达到 1.4–1.7 TB/s（Step5 的 lm_head 分片 32224 × 4096：M=16 时 285 → 153 μs，M=64 时 190 μs）`。

两个 kernel 的对比正好印证第 151 讲的选择逻辑：

| | 压缩投影的 kernel | lm_head 的 kernel |
| --- | --- | --- |
| 语言 | HIP C++（手写，带架构分支和内建指令） | Triton |
| 形状约束 | M ≤ 64，N 取 256 / 512 / 1024 / 2048，K % 128 = 0 | M ≤ 64，K % 128 = 0，N 任意 |
| 分块 | 16 行 × 16 列，波前沿 K 切 | 按 M 分三档选 BM、BN 和 warp 数 |
| 开关 | 环境变量 + `supported()` | 环境变量 `STEP5_SKINNY_LM_HEAD` |
| 为什么这样选 | 要控制矩阵指令、搬运和归约的每一步 | 逻辑简单（纯流式读权重），Triton 够用且好维护 |

**同一个问题（小 M 矩阵乘），两种语言，按复杂度分工**——这比“全部手写”或“全部 Triton”都更实际。

## 回顾

这个 kernel 是前面所有硬件知识的落点。它解决的形状是 decode 的小 M（M ≤ 64），而库在这个区间退化成“不管 N 多大都要约 135 μs”。它的策略是一个块吃 16 行（不补零）、沿 N 分块、块里的波前沿 K 分工最后在共享内存里折半归约。实现里用到的每一个常数都来自硬件：波前 64、MMAC 的 16×16×16、每条通道 4 个 FP32 累加器、一次读 8 个 BF16（16 字节对齐）、按 `gfx928` / `gfx936` / `gfx938` 分支选内建函数、不支持的架构编译出一条陷阱指令。工程上有三处可以直接抄：把假设写成两层检查（Python 侧用来路由、C++ 侧作为保险）、三层回退且失败后永久降级只警告一次、以及用宏关掉一个因工具链问题暂时不能用的优化并把症状和重启条件写进注释。另一个专用 kernel（lm_head）用 Triton 写，说明语言选择要按算子的复杂度分工。

矩阵乘讲完了。下一讲把注意力、量化和通信这三块在 DCU 上的选择一起看：后端按什么顺序挑、支持哪些量化方法、自定义 All-Reduce 在什么条件下才用，以及 PD 分离怎么搭。
