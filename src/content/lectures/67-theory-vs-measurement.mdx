这一篇的所有估算都基于规格表上的数字：峰值算力、显存带宽。它们是硬件在理想条件下的上限，实际的程序能达到多少？手算出来“一步 4.8 ms”，真跑起来是 6 ms 还是 15 ms？如果差得很多，是估算错了，还是程序有问题？

这一讲讲怎么把理论值和实测值对上：先用两个简单的测试“标定”出机器实际的屋顶，再用它预测和核对真实模型的速度。我们以一台桌面级的 **NVIDIA DGX Spark** 为例，和数据中心的 H100 对比。

<Note kind="warn">本讲的实测部分需要在 DGX Spark 上运行下面的测试脚本获得，目前给出的都是**理论预测**，标为“待测”。作者测得结果后，把数字填入代码里的 `measured`，本讲的表格和结论再据此更新。DGX Spark 的 BF16 算力是由公开规格推算的，也需要核实。</Note>

## 两台机器的屋顶

**DGX Spark** 用的是 GB10 芯片（Grace CPU + Blackwell GPU），CPU 和 GPU 共享 **128 GB** 的 LPDDR5x 内存，带宽约 **273 GB/s**。官方公布的 AI 算力是 FP4 约 1 PFLOPS（含稀疏）；按“稀疏是稠密的两倍、精度每升一级算力减半”推算，BF16 稠密约 **125 TFLOPS**（待核实）。

**H100**：BF16 稠密 989 TFLOPS，HBM 带宽 3.35 TB/s。

两者的带宽差约 12 倍，算力差约 8 倍。屋脊点：DGX Spark 约 458，H100 约 295。DGX Spark 的屋脊点更高，意味着更多的运算会落在带宽区；而它的优势是 128 GB 的大内存，能放下 H100 一张卡放不下的模型（比如 4 bit 的 70B）。

## 第一步：测出实际的带宽

最基本的标定是**读写一大块内存**：比如把一个 4 GB 的张量拷贝或求和。这个运算几乎不做计算，时间完全由带宽决定。理论时间：DGX Spark 约 14.7 ms，H100 约 1.2 ms。

实测的带宽通常能达到标称的 70% 到 90%。这个比例很重要：后面所有带宽区的估算（decode、逐元素运算）都应该乘上它。

## 第二步：测出实际的算力

第二个标定是**大矩阵乘法**：4096 × 4096 × 4096 的 BF16 矩阵乘法，算术强度约 1365，远在屋脊点右边，时间由算力决定。理论时间：DGX Spark 约 1.10 ms，H100 约 0.14 ms。

调用 PyTorch 的 `torch.matmul`（背后是 cuBLAS），大矩阵乘法通常能达到峰值的 60% 到 80%。这个比例就是算力区的修正系数。

两个系数测出来以后，就有了这台机器**实际的屋顶**：带宽屋顶 = 实测带宽，算力屋顶 = 实测算力。

## 第三步：扫一遍算术强度

再测线性层在不同 token 数下的时间（第 62 讲：线性层的强度约等于 token 数）。理论上：

- 1 个、8 个、64 个 token：DGX Spark 都约 0.43 ms，因为都在带宽区，时间由读权重决定，多算几个 token 几乎不花时间。
- 512 个 token：约 0.50 ms，开始接近屋脊点。

把实测点画到 Roofline 上，看它们是否沿着屋顶走：带宽区的点应该在斜线下方不远，算力区的点在水平线下方不远。如果某个点离屋顶特别远，就是值得用 Profiler（第 66 讲）深挖的地方。

## 第四步：核对真实模型

最后用标定好的屋顶预测真实模型的速度，再实际跑一遍对比。decode 批 1 时，每个 token 要把权重读一遍，速度上限 = 带宽 ÷ 权重字节数：

- Llama-3-8B，BF16（16.1 GB）：DGX Spark 约 **17 tok/s**，H100 约 209 tok/s。
- FP8（8.0 GB）：约 34 tok/s。
- 4 bit（每组 128 个一个 scale，约 4.5 GB，第 90 讲）：约 **60 tok/s**。
- Llama-3.1-70B，4 bit（39.7 GB）：约 **7 tok/s**。H100 一张卡也放得下 4 bit 的 70B，约 84 tok/s。

实测的速度会低于这些上限：除了读权重，还要读 KV Cache、做注意力、发射 kernel（第 89 讲）、采样。如果实测是上限的 70% 到 80%，说明推理框架已经做得不错；如果只有 30%，就该看时间线找原因了。

<Note kind="point">把理论值对上实测值分三步：用“读写大块内存”标定实际带宽，用“大矩阵乘法”标定实际算力，得到这台机器真实的屋顶；扫一遍不同算术强度的运算，看实测点是否沿屋顶走；最后用屋顶预测真实模型（decode 上限 ≈ 带宽 ÷ 权重字节数），和实测对比。偏差大的地方，就是该用 Profiler 深挖的地方。</Note>

## 测试脚本

下面的脚本在 GPU 上测上面几项，需要 PyTorch 和一张 NVIDIA GPU（在 DGX Spark 上运行即可）。它会做预热、用 CUDA 事件计时、取多次的中位数。

```python
import torch

def bench(fn, warmup=5, iters=20):
    for _ in range(warmup): fn()
    torch.cuda.synchronize()
    times = []
    for _ in range(iters):
        s, e = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
        s.record(); fn(); e.record(); torch.cuda.synchronize()
        times.append(s.elapsed_time(e) / 1e3)               # 秒
    return sorted(times)[len(times) // 2]

x = torch.empty(2 * 1024**3, dtype=torch.bfloat16, device="cuda")   # 4 GB
print("读 4 GB:", bench(lambda: x.sum()))

a = torch.randn(4096, 4096, dtype=torch.bfloat16, device="cuda")
b = torch.randn(4096, 4096, dtype=torch.bfloat16, device="cuda")
print("矩阵乘法 4096³:", bench(lambda: a @ b))

w = torch.randn(4096, 14336, dtype=torch.bfloat16, device="cuda")
for n in [1, 8, 64, 512]:
    t = torch.randn(n, 4096, dtype=torch.bfloat16, device="cuda")
    print(f"线性层，{n} 个 token:", bench(lambda: t @ w))
```

端到端的 decode 速度，可以用 vLLM、SGLang 或 llama.cpp 跑一个批 1 的生成任务，记录稳定后的每秒 token 数。

## 用代码复现

下面的代码给出两台机器的屋顶和各项测试的理论时间，以及几种模型、精度下 decode 的速度上限。作者实测后，把时间填进 `measured`，表格最后一列就会显示实测值和它占理论的比例。

```python
# 理论预测：DGX Spark 与 H100。DGX Spark 的 BF16 稠密算力是由公开的“FP4 约 1 PFLOPS（稀疏）”按每降一级精度翻倍推算的，待核实
GPUS = {"DGX Spark": (125e12, 273e9), "H100": (989e12, 3.35e12)}
measured = {}   # 作者在 DGX Spark 上运行测试脚本后，把实测时间（秒）填在这里，例如 measured["读 4 GB"] = ...

def t(F, BW, flops, bytes_): return max(flops / F, bytes_ / BW)

tests = {"读 4 GB": (0, 4e9), "矩阵乘法 4096³（BF16）": (2 * 4096**3, 3 * 4096**2 * 2)}
for b in [1, 8, 64, 512]:                                # Llama-3-8B 的 FFN 上投影 4096 × 14336
    tests[f"线性层，{b} 个 token"] = (2 * b * 4096 * 14336, 2 * (4096 * 14336 + b * (4096 + 14336)))

for g, (F, BW) in GPUS.items():
    print(f"{g}：BF16 {F / 1e12:.0f} TFLOPS，带宽 {BW / 1e9:.0f} GB/s，屋脊点 {F / BW:.0f}")
print("测试 | DGX Spark 预测 | H100 预测 | 实测（DGX Spark）")
for name, (fl, by) in tests.items():
    p = [t(F, BW, fl, by) for F, BW in GPUS.values()]
    m = measured.get(name)
    print(f"{name} | {p[0] * 1e3:8.3f} ms | {p[1] * 1e3:7.3f} ms | {f'{m * 1e3:.3f} ms（理论的 {p[0] / m:.0%}）' if m else '待测'}")

# 端到端：decode 一个请求（批 1），每个 token 要把权重读一遍
for name, n, bytes_per in [("Llama-3-8B BF16", 8.03e9, 2), ("Llama-3-8B FP8", 8.03e9, 1), ("Llama-3-8B 4 bit", 8.03e9, 0.5625),
                           ("Llama-3.1-70B 4 bit", 70.6e9, 0.5625)]:
    w = n * bytes_per
    print(f"{name}：权重 {w / 1e9:5.1f} GB → DGX Spark 上限 {273e9 / w:5.1f} tok/s，H100 上限 {3.35e12 / w if w < 80e9 else 0:5.1f} tok/s")
```

## 容易混淆的地方

1. **理论值是上限，不是预测的“应该值”。**实测达到 70% 到 90% 是正常的；达到 100% 以上，多半是测量有问题（比如没有同步、数据在缓存里）。
2. **统一内存不是 HBM。**DGX Spark 的 CPU 和 GPU 共享 LPDDR5x 内存，容量大、不用在 CPU 和 GPU 之间拷贝，但带宽远低于 HBM。它适合放大模型做开发和实验，而不是高吞吐的服务。
3. **测出来的效率因运算而异。**带宽区和算力区的效率不同，不同形状的矩阵乘法效率也不同。最好针对自己关心的运算分别测。

## 回顾

规格表给的是理想条件下的上限，实际能达到多少要测。方法是：用读写大块内存标定实际带宽，用大矩阵乘法标定实际算力，得到机器真实的屋顶；扫一遍不同 token 数的线性层，看实测点是否沿屋顶走；再用屋顶预测真实模型的速度（decode 上限 ≈ 带宽 ÷ 权重字节数）并实测核对。DGX Spark 带宽约 273 GB/s，Llama-3-8B BF16 的 decode 上限约 17 tok/s，4 bit 约 60 tok/s，128 GB 的统一内存能放下 4 bit 的 70B（上限约 7 tok/s）。实测值待作者在 DGX Spark 上测量后填入。
