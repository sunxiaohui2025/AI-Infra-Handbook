第 96 讲讲了专家并行怎么工作：专家分到各张卡上，每个 MoE 层用两次 All-to-All 把 token 送过去、再把结果收回来。这一讲算一笔账：在 DeepSeek-V3 这样的大规模 MoE 推理里，时间到底花在哪里？

答案可能有些出乎意料：**专家的计算很快，慢的是网络。**这一讲用一个粗略的模型说明为什么，以及推理系统为此做了哪些努力。

## 专家算得很快

DeepSeek-V3 的每个专家约 4400 万参数（中间维度 2048，d = 7168）。用 EP = 64 部署时，每张卡每层只放 256 ÷ 64 = 4 个专家。decode 时每张卡有 128 个 token，每个 token 选 8 个专家，负载均衡时每张卡每层收到约 128 × 8 = 1024 个 token 副本。

这 4 个专家的 FP8 权重约 176 MB，从显存读一遍约 0.053 ms；1024 个 token 的计算量在 FP8 下更快。所以每层的专家计算约 **0.053 ms**，非常快。

## 网络很忙

再看通信。每个 token 要把隐藏状态（7168 维）复制 8 份发给 8 个专家（FP8，1 字节），算完再收回 8 份结果（BF16，2 字节）：每个 token 每层约 8 × 7168 × 3 ≈ 172 KB。每张卡 128 个 token，一层就是约 22 MB，绝大部分要发到别的卡上。

如果卡之间走 50 GB/s 的 InfiniBand，每层的 All-to-All 约 **0.45 ms**，是专家计算的八倍多。58 个 MoE 层累积下来，一步约 31 ms，其中通信占了 26 ms 左右。

代码扫了几种网络带宽（每卡 128 个 token，EP = 64；假设非专家部分每步 2 ms）：

- **25 GB/s**：一步约 53 ms（通信和计算重叠后），每卡 2405 tok/s。
- **50 GB/s**：约 28 ms，每卡 4560 tok/s。
- **200 GB/s**：约 9.2 ms，每卡 13,892 tok/s。
- **450 GB/s**（NVLink 量级）：约 5.7 ms，每卡 22,371 tok/s。

网络带宽从 50 提到 450 GB/s，吞吐提高了将近 5 倍。而换更快的 GPU，几乎没有帮助，因为 GPU 本来就大部分时间在等数据。

## 网络的“屋顶”

为什么会这样？可以用第 54 讲 Roofline 的思路看。专家计算对每个 token 是 8 个专家 × 2 × 4400 万 ≈ 7 亿次运算，网络流量是 172 KB，**每传 1 字节网络数据，只有约 4096 次运算**。而 H100 的 FP8 算力除以 50 GB/s 的网络，是约 39,580 次/字节。前者比后者小了将近 10 倍：这类负载的“网络算术强度”太低，必然卡在网络上。

更直接的看法是：**每个 token 每步要在网络上走约 10.0 MB**（58 层 × 172 KB），这和批大小、EP 规模都无关。所以每张卡的吞吐有一个硬上限：

<div class="ai-formula">每卡吞吐 ≤ 网络带宽 ÷ 每个 token 的流量 ≈ 50 GB/s ÷ 10.0 MB ≈ 5011 tok/s</div>

换成 450 GB/s，上限变成约 45,100 tok/s。这和稠密模型很不一样：稠密模型加大批大小可以摊薄读权重的成本，MoE 的通信却是按 token 计的，摊不薄。

<Note kind="point">大规模专家并行时，每张卡上只有几个专家，专家计算很快；每个 token 每层却要把 top-k 份隐藏状态送出、收回，DeepSeek-V3 规模下每个 token 每步约 10 MB 的网络流量，和批大小无关。每卡吞吐的上限约等于网络带宽除以这个流量，所以 MoE 推理的瓶颈常在网络。</Note>

## 为什么不少用几张卡

既然通信这么贵，为什么不把专家集中在少数几张卡上？首先是**放不下**：EP = 8 时每张卡每层要放 32 个专家，58 层的专家权重加上非专家部分约 99 GB，超过了 80 GB。其次，专家集中了，每张卡每层要读的专家权重就多，专家计算从 0.053 ms 变成 0.42 ms，同样不快。

而且减少 EP 规模，并不能减少每个 token 的网络流量：只要专家不在本卡上，就得发出去。真正能减少流量的，是让更多的通信**留在快速链路上**，或者**减少每次传的字节**。

## 推理系统的对策

**更快的互联。**把 EP 组放进 NVLink 域里，All-to-All 就从 50 GB/s 变成了几百 GB/s。8 卡的服务器只能容纳很小的 EP；GB200 NVL72 这样 72 张卡共享 NVLink 的超节点，可以把整个 EP 组都放在高速域内（第 103 讲）。

**减少字节。**分发时用 FP8 传（我们已经这样算了）；有的系统合并时也用更低的精度。DeepSeek-V3 训练时还限制每个 token 最多发到 4 个节点，减少跨机的流量。

**计算和通信重叠。**把每张卡的 token 分成两个微批次，一个在做 All-to-All 时，另一个在算注意力或专家。代码里的“重叠”就是取两者中较大的那个。DeepSeek 的推理系统正是这样做的。不过，当通信远大于计算时，重叠也只能藏住一小部分。

**专门的通信库。**DeepEP 等库为 MoE 的分发、合并写了专门的 kernel：decode 用低延迟的版本（直接通过 RDMA 读写对方显存，减少 α），prefill 用高吞吐的版本。

**冗余专家与负载均衡。**第 96 讲说过，最忙的卡决定整层的速度。复制热门专家、动态调整专家的放置，让每张卡收到的 token 尽量相等。

## 一层 MoE 里的两次等待

前面把通信当成一个整体。把一层 MoE 拆开，可以看到决定耗时的不是平均，而是最慢的那一份。下图是一种常见的放法：服务器 A 的 4 张卡做注意力（各自保存自己请求的 KV），服务器 B 的 4 张卡各放四分之一的路由专家。

<MoELayerFlow caption="图 99-2　一层 MoE 的执行顺序。A 卡算完注意力和路由，按每个 token 所选专家的位置把隐藏状态分组发出（dispatch，4 × 4 的 All-to-All，颜色表示去哪张 B 卡）；B 卡收齐后做专家计算；结果原路送回（combine），A 卡收齐一个 token 的 8 份结果才能进入下一层。" />

这条路径上有两处必须等的地方：B 卡要等所有来源的输入到齐才开始算；A 卡要等一个 token 的 8 份结果都回来才能求和。所以一张 B 卡收得多、算得慢，会同时推迟它自己的计算、它的返回，以及所有在等它结果的 A 卡。

算一个具体的例子：1024 个 token、每个选 8 个专家，每行 8 KiB（4096 维 BF16）。dispatch 一共 64 MiB，combine 也是 64 MiB。每张卡经自己的 50 GB/s 网卡收发。

- **均衡**：每个专家组收 2048 行（16 MiB）。dispatch 0.336 ms，专家计算 0.156 ms，combine 0.336 ms，三段串行 **0.827 ms**。
- **热点**：分布变成 [5120, 1024, 1024, 1024]，总字节数一样，组 0 却要收 40 MiB。三段都变成原来的 2.5 倍，共 **2.068 ms**。
- **同样的热点，两池同在一台 HGX（NVLink 450 GB/s）**：两次交换都压到 0.093 ms，共 0.577 ms。这时最长的一段变成热点卡 0.391 ms 的计算，再加带宽已经没用，要减少热点卡的工作。

跨服务器时，两次交换占了总时间的八成。H100 算一行专家只要约 76 ns，网卡传一行 8 KiB 却要约 164 ns。

把一批拆成两个微批次，第一个在算的时候第二个在 dispatch，三段可以流水：均衡时从 0.827 ms 降到 **0.581 ms**。流水的节奏由最长的一段（这里是通信）决定。但重叠也有代价：网卡的 DMA 和同时运行的矩阵乘法会争用显存带宽，如果因此 dispatch 和 combine 各慢约一半，流水就回到 0.827 ms，通信确实重叠了，整层却没有变快。

## 最忙的那张卡

上面的热点是人为设的。实际中热点从哪里来？EP 越大，问题越严重吗？

还是 1024 个 token 各选 8 个专家，共 8192 次分派，256 个专家平均每个 32 行。设专家 0 比较热，收到平均值 4 倍的 128 行，其余均分给另外 255 个专家。专家按编号均分到各张卡：

- **EP8**：每卡 32 个专家，热点卡约 1108 行，只比平均的 1024 行多 8%。热点被同卡的其他 31 个专家冲淡了。
- **EP32**：每卡 8 个专家，热点卡约 349 行，比平均的 256 行多 36%。
- **EP256**：每卡只剩这一个专家，128 行，是平均 32 行的 **4 倍**。专家之间的不均，原样变成了卡之间的不均。

从 EP8 到 EP256，每卡的平均行数缩小到 1/32，最忙卡的行数却只从 1108 降到 128。整层按最忙的卡计时，EP256 中一张平均的卡有四分之三的时间在等。

没有热点也会这样。即使每个 token 完全随机地选专家，各专家的行数也会在 32 附近随机波动；一张卡上专家越多，波动越能互相抵消，卡越多，越可能出现一张特别忙的卡。模拟 300 批：EP8 时最忙的卡平均只比每卡平均多 4%，EP64 多 21%，EP256 多 **53%**。

<EPSkew caption="图 99-3　大 EP 的卡间不均。上：每张卡收到的行数 ÷ 每卡平均（橙色是最忙的卡）；下：最忙卡 ÷ 平均随 EP 的变化。热点专家（橙线）和完全随机（绿线）两种情况，EP 越大都越不均。" />

这就是 DeepSeek 的 decode 部署（EP144，每卡只放 2 个路由专家）要额外放 32 个**冗余专家**、并按负载动态调整的原因。

## 冗余专家多久回本

冗余专家就是给热门专家多放几份副本，让空闲的卡也能分担它的任务。只要副本的权重相同、合并时用对路由权重，就不改变“每个 token 选分数最高的 8 个专家”这条规则，模型的输出不变。vLLM、SGLang 的 EPLB（专家负载均衡）就是按路由统计调整副本的位置。

副本不是免费的：它占显存，复制也要时间。算一个例子：一台 HGX H100 上，一批 128 个 token 都选中卡 0 上的 8 个热点专家，共 1024 次分派。每个专家（Qwen3-235B-A22B 的规模）36 MiB。把其中 7 个各复制一份到卡 1 至卡 7，卡 0 只剩 576 次分派；它是读显存受限的，每批从约 0.550 ms 降到 0.309 ms，省约 0.24 ms。

- **同一台服务器内**复制，走 NVLink，7 份共约 **0.62 ms**，第 **3** 批就回本；热点持续 16 批，净省约 3.2 ms。
- **跨服务器**复制，走 50 GB/s 网卡，约 **5.32 ms**，要到第 **23** 批才回本；热点只持续 16 批的话，反而净亏约 1.5 ms。

所以副本策略要预测的是“热点还会持续多久”。在机器内，复制几乎不花时间，限制副本数的是显存（每卡每层多一个 36 MiB 的专家，94 层就是 3.3 GiB，挤掉的是 KV）；跨机器复制贵，频繁地追着热点搬副本反而亏。研究系统 CRAFT 的做法是按层分配副本预算，把显存花在最拥挤的层上。

## 专家放在 CPU 还是 GPU

还有一种更“省卡”的思路：显存放不下全部专家，就把大部分专家留在 CPU 内存里。这时有两条路：把被选中的专家权重搬到 GPU 上算；或者把输入传给 CPU，让 CPU 用本地的权重算，再把结果传回来。前者花链路带宽换 GPU 算力，后者花 CPU 算力换更少的流量。KTransformers 走的是后一条路。

哪条路快，取决于同一个专家这一批收到多少个 token。用 KTransformers 论文的实验机算：一颗 Xeon 8452Y（同插槽内存带宽实测 220 GB/s，AVX-512 kernel 实测 1.8 TFLOP/s，AMX 矩阵指令 kernel 21.3 TFLOP/s），一张 A100 40GB PCIe（按峰值 50% 计），PCIe 交接 25 GB/s。8 个专家，每个 36 MiB：

- **每个专家只收到 1 个 token**：CPU 读一遍本地的 288 MiB 权重约 1.4 ms，加上传输共 **1.46 ms**；搬到 GPU 光传权重就要约 12 ms，共 **12.5 ms**。专家复用少时，避免搬大块权重最重要。
- **每个专家收到 128 个 token**：计算量涨了 128 倍。AVX-512 的 CPU 要 22.2 ms，不如搬到 GPU 的 12.5 ms；换成 AMX，CPU 只要 2.57 ms，还是 CPU 快。

交点：用 AVX-512 时，每个专家超过约 **71** 个 token 就该搬到 GPU；用 AMX 时要超过约 **688** 个。同一台机器、同一批请求，CPU 用哪套指令就决定了专家该放在哪一侧。这也说明大内存 + 少量 GPU 的机器适合批小的场景：并发一高，CPU 的算力先用完。

## prefill 好一些

prefill 一次处理很多 token，注意力和专家的计算量都大得多，通信相对没那么突出，也更容易被重叠藏住。所以 DeepSeek-V3 的 prefill 用 32 张卡、decode 用 320 张卡（第 96 讲），两个阶段的部署完全不同。这也是下一讲 PD 分离的一个重要动机。

## 用代码复现

下面的代码按上面的粗略模型，估算 DeepSeek-V3 规模的 decode：先扫网络带宽，看每层的专家计算和通信时间、每步的耗时和每卡吞吐；再看 EP 规模和每卡 token 数的影响（标出放不下的情况）；最后算每个 token 的网络流量、吞吐上限和“网络算术强度”。

```python
# DeepSeek-V3 式 MoE 的 decode，粗略模型：注意力部分各卡数据并行处理自己的 B 个 token，专家部分用 N 卡专家并行
D, TOPK, EXPERTS, LAYERS = 7168, 8, 256, 58
EXPERT_BYTES = 3 * D * 2048                              # 一个专家约 44M 参数，FP8 每个 1 字节
F8, BW = 1979e12, 3.35e12                                # H100 的 FP8 算力、显存带宽
ATTN_MS = 2.0                                            # 非专家部分（注意力、共享专家等）每步每卡的耗时，示意值

def step_ms(B, N, beta, alpha=8e-6, overlap=False):
    per_gpu = max(1, EXPERTS // N)                       # 每卡每层放几个专家
    toks = B * TOPK                                      # 负载均衡时，每卡每层收到 B·8 个 token 副本
    expert = max(per_gpu * EXPERT_BYTES / BW, 2 * EXPERT_BYTES * toks / F8)          # 读专家权重 vs 算
    comm = 2 * alpha + B * TOPK * D * 3 * (N - 1) / N / beta                          # 分发 FP8 + 合并 BF16，留在本卡的不传
    layer = max(expert, comm) if overlap else expert + comm
    return ATTN_MS + LAYERS * layer * 1e3, expert * 1e3, comm * 1e3

B, N = 128, 64
print(f"每卡 {B} 个 token、EP = {N}（每卡每层 {EXPERTS // N} 个专家）：")
for beta in [25e9, 50e9, 100e9, 200e9, 450e9, 900e9]:
    t, e, c = step_ms(B, N, beta); to, _, _ = step_ms(B, N, beta, overlap=True)
    print(f"  网络带宽 {beta / 1e9:4.0f} GB/s：每层专家 {e:.3f} ms、通信 {c:.3f} ms；一步 {t:5.1f} ms（重叠后 {to:5.1f} ms），每卡 {B / to * 1e3:6,.0f} tok/s")

print("EP 规模的影响（50 GB/s，重叠）：")
for N in [8, 32, 64, 256]:
    for B in [32, 128]:
        t, e, c = step_ms(B, N, 50e9, overlap=True)
        mem = max(1, EXPERTS // N) * EXPERT_BYTES * LAYERS + 17e9          # 专家权重 + 约 17 GB 的非专家权重（FP8）
        note = "" if mem < 70e9 else f"（每卡 {mem / 1e9:.0f} GB，放不下）"
        print(f"  EP = {N:3d}、每卡 {B:3d} 个 token：每层专家 {e:.3f} ms、通信 {c:.3f} ms，每卡 {B / t * 1e3:6,.0f} tok/s{note}")

# 网络的“屋顶”：每个 token 每层要送出 8 份、收回 8 份隐藏状态，不管 B、N 多大都免不了
per_tok = LAYERS * TOPK * D * 3                           # 字节
print(f"每个 token 一步的网络流量 {per_tok / 1e6:.1f} MB → 每卡吞吐上限 = β ÷ {per_tok / 1e6:.1f} MB：50 GB/s 时 {50e9 / per_tok:,.0f} tok/s，450 GB/s 时 {450e9 / per_tok:,.0f} tok/s")
print(f"专家计算每传 1 字节只有 {2 * EXPERT_BYTES * TOPK / (TOPK * D * 3):,.0f} 次运算；H100 的 FP8 算力 ÷ 50 GB/s 网络 = {F8 / 50e9:,.0f} 次/字节")
```

```text
  EP =  32、每卡  32 个 token：每层专家 0.105 ms、通信 0.123 ms，每卡  3,511 tok/s
  EP =  32、每卡 128 个 token：每层专家 0.105 ms、通信 0.443 ms，每卡  4,625 tok/s
  EP =  64、每卡  32 个 token：每层专家 0.053 ms、通信 0.124 ms，每卡  3,473 tok/s
  EP =  64、每卡 128 个 token：每层专家 0.053 ms、通信 0.450 ms，每卡  4,560 tok/s
  EP = 256、每卡  32 个 token：每层专家 0.013 ms、通信 0.126 ms，每卡  3,445 tok/s
  EP = 256、每卡 128 个 token：每层专家 0.046 ms、通信 0.455 ms，每卡  4,512 tok/s
每个 token 一步的网络流量 10.0 MB → 每卡吞吐上限 = β ÷ 10.0 MB：50 GB/s 时 5,011 tok/s，450 GB/s 时 45,100 tok/s
专家计算每传 1 字节只有 4,096 次运算；H100 的 FP8 算力 ÷ 50 GB/s 网络 = 39,580 次/字节
```

前七行：带宽从 25 GB/s 到 900 GB/s，每层通信从 0.883 ms 降到 0.040 ms，专家计算始终是 0.053 ms。中间八行：EP = 8 放不下；EP 从 32 到 256，每卡吞吐几乎不变（都约 4500 tok/s），因为网络流量按 token 计。最后两行是网络的屋顶：50 GB/s 时每卡最多约 5011 tok/s；每传 1 字节只有 4096 次运算，远低于 39,580。

这个模型非常粗略：它假设负载完全均衡、通信没有拥塞、所有专家流量都走同一种链路，非专家部分用一个固定的 2 ms 代替。但“专家快、网络慢”的结论是可靠的。

第二段代码复现这一讲后半部分的数字：热点专家和随机路由下的卡间不均，冗余专家的回本批数，专家放在 CPU 还是 GPU 的交点，以及一层 MoE 三段的时间。

```python
import numpy as np
# 1. 同一个热点专家，EP 越大，卡间越不均：256 个专家、1024 个 token 各选 8 个，专家 0 收到平均值 4 倍的 128 行
n, k, E = 1024, 8, 256
rows = np.full(E, (n * k - 128) / (E - 1)); rows[0] = 128
for ep in [8, 32, 256]:
    per_card = rows.reshape(ep, -1).sum(1)              # 专家按编号均分到 ep 张卡
    print(f"EP{ep:<3}：热点卡 {per_card.max():6.0f} 行，平均 {per_card.mean():5.0f} 行，最忙 ÷ 平均 = {per_card.max()/per_card.mean():.2f}")

# 2. 没有热点、完全随机地选专家，最忙的卡也会比平均多：模拟 300 批
rng = np.random.default_rng(0)
for ep in [8, 32, 64, 256]:
    r = []
    for _ in range(300):
        pick = np.argpartition(rng.random((n, E)), k, axis=1)[:, :k]   # 每个 token 随机选 8 个不同专家
        cnt = np.bincount(pick.ravel(), minlength=E).reshape(ep, -1).sum(1)
        r.append(cnt.max() / cnt.mean())
    print(f"随机路由 EP{ep:<3}：最忙卡平均比每卡平均多 {np.mean(r)*100-100:.0f}%")

# 3. 冗余专家多少批回本：8 个热点专家挤在卡 0，把其中 7 个各复制一份到卡 1–7
expert = 3 * 4096 * 1536 * 2                              # Qwen3-235B-A22B 一个专家，BF16 36 MiB
t0 = 921e6 / 1675e9                                       # 卡 0 每批读写约 921 MB（显存受限），有效带宽 1675 GB/s
save = t0 - t0 * 576 / 1024                                # 复制后卡 0 只剩 1024 次分派中的 576 次
for name, bw in [("同一台服务器（NVLink 450 GB/s）", 450e9), ("跨服务器（网卡 50 GB/s）", 50e9)]:
    copy = 7 * (expert / bw + 5e-6)
    print(f"{name}：复制 {copy*1e3:.2f} ms，第 {int(copy // save) + 1} 批回本；热点持续 16 批净省 {(16*save-copy)*1e3:+.1f} ms")

# 4. 专家放在 CPU 算，还是把权重搬到 GPU 算：8 个专家，每个收到 m 个 token
P, h = 3 * 4096 * 1536, 4096
def cpu(m, flops): return 8 * (2 * 5e-6 + 2 * m * h * 2 / 25e9 + max(2 * m * P / flops, expert / 220e9))
def gpu(m): return 8 * (5e-6 + expert / 25e9 + max(2 * m * P / 156e12, expert / 778e9))
for m in [1, 128]:
    print(f"每专家 {m:>3} 个 token：CPU(AVX-512) {cpu(m, 1.8e12)*1e3:5.2f} ms，CPU(AMX) {cpu(m, 21.3e12)*1e3:5.2f} ms，搬到 GPU {gpu(m)*1e3:5.2f} ms")
for name, f in [("AVX-512", 1.8e12), ("AMX", 21.3e12)]:
    m = next(m for m in range(1, 5000) if gpu(m) < cpu(m, f))
    print(f"{name}：每专家超过 {m - 1} 个 token，搬到 GPU 更快")

# 5. 一层 MoE 的三段：dispatch → 专家计算 → combine（两台服务器：4 张卡做注意力，4 张卡各放 1/4 的专家）
vec, flop_row, eff = 8192, 6 * 4096 * 1536, 494.7e12            # 每行 8 KiB（BF16），每行专家计算量，H100 有效算力
for name, recv, bw in [("均衡，跨服务器", [2048] * 4, 50e9), ("热点，跨服务器", [5120, 1024, 1024, 1024], 50e9),
                       ("热点，同一台机器 NVLink", [5120, 1024, 1024, 1024], 450e9)]:
    disp = max(recv) * vec / bw                # 最忙的接收方决定 dispatch，combine 同理
    comp = max(recv) * flop_row / eff
    print(f"{name}：dispatch {disp*1e3:.3f} + 计算 {comp*1e3:.3f} + combine {disp*1e3:.3f} = {(2*disp+comp)*1e3:.3f} ms")
d_, c_ = 2048 * vec / 50e9, 2048 * flop_row / eff
print(f"均衡时拆成两个微批次流水：{(2*d_ + c_)/2*1e3 + max(d_, c_)/2*1e3:.3f} ms（原来 {(2*d_+c_)*1e3:.3f} ms）")
```

## 容易混淆的地方

1. **MoE 省的是计算，不是通信。**每个 token 只激活 8 个专家，计算量小；可正因为专家分布在各处，每个 token 都要跨卡旅行。稠密模型的张量并行每层同步的是整个批次的隐藏状态，MoE 每个 token 要传 top-k 份。
2. **加大批次救不了网络。**批越大，网络流量同比例增加，每卡吞吐的上限不变。加大批次只能摊薄读专家权重的成本。
3. **网络带宽要看每张卡的。**一台机器有 8 张网卡，总带宽 400 GB/s，但每张卡分到的是 50 GB/s；All-to-All 时每张卡都在同时收发，看的是每张卡的带宽。

4. **EP 越大不等于越均衡。**EP 越大，每卡的专家越少，专家之间的忙闲越不能互相抵消，最忙卡相对平均越突出。大 EP 一般要配合冗余专家和动态负载均衡。
5. **重叠通信不一定变快。**拆成微批次后通信和计算能并行，但它们会争用显存带宽；争用严重时，重叠后的总时间和不重叠一样。

## 回顾

大规模专家并行时，每张卡每层只放几个专家，专家计算很快（EP = 64 时每层约 0.053 ms）；每个 token 每层却要送出 8 份、收回 8 份隐藏状态，DeepSeek-V3 规模下每个 token 每步约 10.0 MB 的网络流量，和批大小、EP 规模都无关。走 50 GB/s 的网络时，每层通信约 0.45 ms，是专家计算的八倍多，每卡吞吐上限约 5011 tok/s；带宽提高到 450 GB/s，上限约 45,100 tok/s。专家计算每传 1 字节网络数据只有约 4096 次运算，远低于 H100 FP8 算力与网络带宽之比，所以瓶颈在网络。对策是更快的互联（NVLink 域、超节点）、更少的字节、计算和通信重叠、专门的通信库和负载均衡。

把一层拆开看，dispatch、专家计算、combine 三段都由最忙的那份决定：跨服务器时均衡分布 0.827 ms，热点分布 2.068 ms。EP 越大越不均，一个 4 倍热点专家在 EP8 只多 8%，在 EP256 就是 4 倍；完全随机的路由在 EP256 也会让最忙的卡多 53%。冗余专家能分担热点，机内复制第 3 批回本，跨机要第 23 批。专家也可以留在 CPU 上算，每个专家的 token 数超过交点（AVX-512 约 71 个、AMX 约 688 个）才值得搬到 GPU。

prefill 和 decode 在 MoE 推理里的瓶颈如此不同，所需的卡数、并行方式也不同。稠密模型也有类似的问题：第 69 讲说过，prefill 插进来会干扰 decode。能不能干脆把两者放到不同的机器上？下一讲：**PD 分离**。
