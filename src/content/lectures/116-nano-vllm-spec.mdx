前两讲读完了 nano-vllm。读懂一个引擎最好的检验，是往里面加一个它没有的功能。这一讲把第 112 讲的 n-gram 投机解码移植进去。

在 miniinfer 里，投机解码新增了 spec.py，另外改了 4 个文件：引擎里起草和验证，模型多返回几个位置的打分，调度器和块管理器多留几个位置。到了 nano-vllm，同样的想法要穿过调度器、块管理器、请求的序列化、执行器、Context、输出层、CUDA Graph 的判断：新增 spec.py，另外改 7 个文件。这一讲的重点不在代码量，而在**每一处为什么要改**：一个功能在真实引擎里碰到的，往往是你没想到的那些地方。

## 先想清楚六个问题

动手之前，先回答六个设计问题。每个问题的答案都对应 nano-vllm 里一处具体的约束。

**1. 草稿放在哪里？**放在 `Sequence` 的一个新字段 `draft` 里，**不放进 `token_ids`**。`token_ids` 牵动太多东西：`num_tokens`、已生成的数量、前缀缓存的哈希（`seq.block(i)` 直接切 `token_ids`）。草稿随时可能被拒绝，放进去再删，就得保证这期间没有任何代码读到它们。单独放，验证完再把接受的部分 `append_token` 进去，其余代码看到的永远是真实的 token。

**2. 验证走哪条路？**decode 的那条路（`flash_attn_with_kvcache` + CUDA Graph）假定每个请求正好 1 个查询。验证要送“最后一个真实 token + k 个草稿”，每个请求 1 + k 个查询。nano-vllm 里正好有一条现成的路能处理“查询比键少、键在块池里”：**带前缀缓存的 prefill**（第 115 讲）。验证就是一次这样的 prefill：已缓存的是前面的全部 token，这一步算最后一个真实 token 和草稿。所以新写一个 `prepare_verify`，拼出 cu_seqlens 和块表，走 `flash_attn_varlen_func`。代价是验证步不能用 CUDA Graph。

**3. 输出层算哪些位置？**原来 prefill 只算每个请求最后一个位置的打分。验证要的是每个送入位置的打分（第 j 个位置的打分用来验证第 j + 1 个草稿）。在 `Context` 里加一个标志 `all_logits`，输出层看到它就不再只取最后一个位置。

**4. 有温度时怎么接受？**miniinfer 只有贪心，“草稿等于贪心预测”就接受。nano-vllm 只有温度采样。好在 n-gram 草稿是**确定的**（草稿分布在 d 上的概率是 1），这时第 85 讲的接受-拒绝规则会简化成一个非常简单的形式：

<div class="ai-formula">在每个位置照常采样 x ~ p；x = d 就接受 d，否则输出 x，丢弃后面的位置</div>

为什么分布不变：第 85 讲的规则是以 min(1, p(d) ⁄ q(d)) = p(d) 的概率接受；拒绝时从 (p − q)₊ 归一化后的分布里重新采样，也就是 p 去掉 d 之后再归一化。而“采样 x ~ p，看 x 是否等于 d”：x = d 的概率正好是 p(d)；x ≠ d 时，x 的分布正好是 p 去掉 d 再归一化。两者完全相同。所以 `verify` 函数一个字都不用改：把“贪心预测”换成“采样出的 token”就行。nano-vllm 的采样器对每个位置独立加噪声，正好满足要求。

**5. 块怎么管？**草稿要占位置，可能跨进新的块。原来的 `can_append` / `may_append` 假定每步只多一个 token（第 114 讲），要改成“要放下 len + k 个位置，还差几块”。块不够时，**先放弃草稿，再考虑抢占别人**：草稿只是可能的加速，不值得把别的请求赶出去。验证之后，被拒绝的草稿如果独占了末尾的块，把块还回去，让块表重新等于请求的实际块数（`prepare_decode` 用块表的最后一块算写入槽位，多一块就写错地方）。

**6. 回滚和前缀缓存怎么协调？**和 miniinfer 一样，回滚只是让 `num_cached_tokens` 只推进到有效的位置。但 nano-vllm 的 `hash_blocks` 用 `num_cached_tokens + num_scheduled_tokens` 决定登记哪些块，所以验证之后要先把 `num_scheduled_tokens` 改成**有效的位置数**，再登记；而且登记必须在接受的 token 追加进 `token_ids` **之后**，否则算哈希时块里的 token 还不全。

还有两处不改会出错、却很容易漏掉的地方，后面讲到时再说：跨进程序列化请求时要带上草稿；`run_model` 判断要不要用 CUDA Graph 的那个条件。

## 怎么验证

在有 NVIDIA GPU 的机器上：克隆 nano-vllm 并切到 `bb823b3`，按它的 README 装好依赖，把 `miniinfer/nano_spec/nanovllm/` 下的 8 个文件覆盖到同名位置，然后运行 `miniinfer/nano_spec/check_spec.py`：

```bash
python check_spec.py ~/huggingface/Qwen3-0.6B 0
```

```bash
python check_spec.py ~/huggingface/Qwen3-0.6B 4
```

第一次关闭投机，第二次每步最多 4 个草稿，三个请求各生成 256 个 token，温度取 10⁻⁵（效果接近贪心）。第二次运行会打印吞吐、接受的草稿数，以及每个请求和不投机时“前多少个 token 相同”。

为什么不直接要求“完全相同”：在 miniinfer 里，我们在 CPU 上用 FP32，投机和不投机走的是同一段注意力代码，结果逐 token 相同（第 112 讲）。在 GPU 上，验证步走 `flash_attn_varlen_func`，普通 decode 走 `flash_attn_with_kvcache` 和 CUDA Graph，batch 的形状也不同，BF16 下打分会有末位的差异。两个候选的打分很接近时，选择可能翻转，之后的内容就会不同（第 111 讲量化时见过同样的现象）。所以合理的预期是：大多数请求全部相同，少数在很靠后的位置开始不同；如果从前几个 token 就开始不同，那就是移植有 bug。

还应该测的：

- **张量并行**：`LLM(path, num_spec_tokens=4, tensor_parallel_size=2)`，检验草稿的序列化。
- **块很紧的时候**：把 `gpu_memory_utilization` 调小，让抢占和“先放弃草稿”的分支真正跑到。
- **前缀缓存**：同一个提示跑两遍，第二遍应当命中；投机产生的块登记不能出错。
- **长度上限和结束符**：`max_tokens` 取一个很小的数，检查生成的 token 数正好是它。

<Note kind="column" title="在 GPU 上能快多少">第 112 讲在 CPU 上，照抄型任务每次前向出 3.66 个 token，用时只降到七成：CPU 上多算 4 个位置并不便宜。GPU 上小 batch 的 decode 是读权重受限的，多算几个位置几乎不加时间，所以同样的接受率，加速比会更接近“每次前向出几个 token”。但这份移植有两个新的代价：验证步不能用 CUDA Graph，每步多了几百次 kernel 发射的开销（第 79 讲）；调度器每步要在 Python 里为每个请求做一次 n-gram 查找。batch 很大时，decode 本身已经接近计算受限，多算的草稿位置不再免费，投机反而可能变慢。vLLM 的做法是把草稿的验证也录进 CUDA Graph，并在负载高时减少草稿数（第 117 讲）。这些都要实测才知道，本站没有数字。</Note>

<Note kind="point">把投机解码移植进 nano-vllm：草稿单独放在请求的 draft 字段里，不进 token_ids；验证复用“带前缀缓存的 prefill”那条路（变长 FlashAttention + 块表），输出层每个位置都打分；n-gram 草稿是确定的，“每个位置照常采样、等于草稿就接受”就是精确的接受-拒绝采样；块不够先放弃草稿再抢占，验证后退还多余的块；回滚时先追加被接受的 token，再按有效位置数登记哈希、推进 num_cached_tokens。另有两处不改就出错：序列化要带上草稿（张量并行），判断用不用 CUDA Graph 要看 Context。</Note>

## 回顾

同一个投机解码，miniinfer 里新增 1 个文件、改 4 个，nano-vllm 里新增 1 个、改 7 个，一共新增 132 行。多出来的改动几乎都来自 nano-vllm 为了快而做的设计：调度和执行分开（草稿要在两边都看得见）、多进程张量并行（草稿要序列化）、decode 专用的 kernel 和 CUDA Graph（验证要换一条路走）、prefill 只算最后一个位置的输出层（要加开关）、按块登记的前缀缓存（回滚要和登记的顺序配合）。这也是读大型引擎源码时的常态：一个功能的核心逻辑往往只有几十行，难的是它和已有的每一项优化怎么共存。

第 15 篇到这里结束。第 16 篇去读真正的工业级引擎：vLLM 怎么把 prefill 和 decode 统一调度、怎么做投机解码和量化 kernel，SGLang 的 RadixAttention 和零开销调度。下一讲：**vLLM 的架构**。
