前几讲分别算了速度（第 68、70 讲）和显存（第 71 讲）。这一讲把它们串成一个完整的**成本模型**：给定模型、显卡、并发和请求长度，手算出理论速度，再结合显卡的价格，得到**每百万 token 要花多少钱**。

这个数非常有用。它可以和 API 的价格对比，判断自己部署是否划算；可以比较不同的显卡、不同的精度、不同的并发设置，哪种更省；可以估算一个产品上线后每个月的推理开销。它标了重点，因为第三、四章的每一种优化，最终都会落到这个数上：它让成本降了多少。

## 从速度到成本

成本的逻辑很简单：GPU 按时间收费（无论自己买还是租，都可以折算成每小时多少钱），在这一小时里它能处理多少 token，一除就是每个 token 的成本：

<div class="ai-formula">每百万 token 成本 = 每小时租金 / 每小时处理的 token 数 × 10<sup>6</sup></div>

关键是“每小时处理多少 token”。第 68 讲说过，prefill 和 decode 的瓶颈不同，所以分开算：

**输入 token（prefill）**：计算受限。每个输入 token 约需 2 × 75 亿次运算（加上一点注意力的计算），H100 每秒 989 万亿次，理论上每秒能处理约 6.5 万个输入 token。

**输出 token（decode）**：带宽受限，吞吐取决于并发（第 70 讲）。b 个请求一起 decode，一步的耗时是 max(计算, 读写)，吞吐 = b / TPOT。

还有一个现实的因素：**效率**。实际的推理引擎达不到理论的峰值算力和带宽，有各种开销。这里取 60% 作为示例（第 67 讲会用实测来校准这个数）。

## 算一笔账

Llama-3-8B，一张 H100，租金假设为每小时 2.5 美元（示例，实际价格因云厂商和时间差别很大，请换成你自己的），效率 60%，每个请求提示和输出各 1024 个 token：

| 并发 | TPOT | 总输出速度 | 每百万输入 token | 每百万输出 token |
| --- | --- | --- | --- | --- |
| 1 | 8.1 ms | 124 token/s | $0.018 | $5.618 |
| 32 | 11.2 ms | 2,858 token/s | $0.018 | $0.243 |
| 128 | 20.8 ms | 6,151 token/s | $0.018 | $0.113 |

几个结论：

**并发决定输出成本。**只服务一个请求时，每百万输出 token 要 5.6 美元；并发 128 时只要 0.11 美元，便宜了 50 倍。同一张卡、同一个模型，成本差别全在“能不能把并发提上去”。这就是推理系统花大力气做批处理、调度、省显存的原因：每多装一个请求，每个 token 就便宜一点。

**输出比输入贵得多。**并发 128 时，输出 token 的成本是输入的 6 倍多。原因第 68 讲已经说过：prefill 时同一份权重被很多个 token 共用，decode 时每一步都要把权重重读一遍。这也是为什么几乎所有大模型 API 的定价，输出 token 都比输入 token 贵好几倍。

**一个请求的成本。**提示 1024、输出 1024 个 token，并发 128 时约 0.00013 美元，也就是一万次请求约 1.3 美元。

换成 Llama-3-70B，用 4 张 H100（第 71 讲算过，至少要 4 张），并发 64：每百万输出 token 约 0.94 美元，输入约 0.16 美元，大约是 8B 的 8–9 倍，和参数量的比例差不多。

## 哪些因素让成本变化

用这个模型，可以快速判断各种优化“值不值”：

- **量化成 FP8**：权重的字节数减半，decode 每步读的数据减少，带宽受限时 TPOT 接近减半；KV Cache 也减半，能装下更多请求（第 71 讲）。输出成本可能降一半左右。
- **GQA、MLA**：KV Cache 变小，长上下文时 decode 读的数据大幅减少，并发上限提高。
- **更长的输出**（比如推理模型想 8000 个 token）：每个请求的输出 token 多了几倍，KV Cache 也更大，能装的并发变少，每个 token 也更贵。
- **前缀缓存**（第 76 讲）：很多请求共享同一个系统提示时，这部分的 prefill 只需做一次，输入成本大幅下降。很多 API 对“命中缓存的输入 token”打折，原因就在这里。

## 用代码复现

下面的代码实现了这个成本模型：分别算 prefill 的输入吞吐和 decode 的输出吞吐（按并发和上下文），再按租金折算成每百万 token 的成本。

```python
# 推理成本模型：理论速度 × 实际效率 → 每小时生成多少 token → 每百万 token 多少钱
F1, BW1, PRICE1 = 989e12, 3.35e12, 2.5          # 一张 H100：BF16 算力、显存带宽、假设的租金（美元/小时，示例）
EFF = 0.6                                        # 实际能达到理论值的比例（示例，第 67 讲会实测）
MODELS = {"Llama-3-8B": dict(N=8.03e9, Ne=525e6, L=32, d=4096, kv=131072, gpus=1),
          "Llama-3-70B": dict(N=70.55e9, Ne=1051e6, L=80, d=8192, kv=327680, gpus=4)}

def costs(name, b, prompt=1024, out=1024):
    m = MODELS[name]
    F, BW, price = F1 * m["gpus"], BW1 * m["gpus"], PRICE1 * m["gpus"]   # 多卡按总算力、总带宽、总租金算
    ctx = prompt + out / 2
    # prefill：计算受限，每秒能处理的输入 token
    prefill_tps = F / (2 * (m["N"] - m["Ne"]) + 4 * m["L"] * m["d"] * prompt / 2) * EFF
    # decode：b 个请求一起，一步 = max(计算, 读写)
    flops = (2 * (m["N"] - m["Ne"]) + 4 * m["L"] * m["d"] * ctx) * b
    bytes_ = m["N"] * 2 + m["kv"] * ctx * b
    tpot = max(flops / F, bytes_ / BW) / EFF
    decode_tps = b / tpot
    usd_in = price / (prefill_tps * 3600) * 1e6
    usd_out = price / (decode_tps * 3600) * 1e6
    return tpot * 1e3, decode_tps, usd_in, usd_out

for name, b in [("Llama-3-8B", 1), ("Llama-3-8B", 32), ("Llama-3-8B", 128), ("Llama-3-70B", 64)]:
    tpot, tps, ci, co = costs(name, b)
    print(f"{name:11s} 并发 {b:3d}：TPOT {tpot:5.1f} ms，输出 {tps:6,.0f} token/s；每百万 token：输入 ${ci:.3f}，输出 ${co:.3f}")

# 一个请求（提示 1024、生成 1024）在 8B、并发 128 时的成本
_, _, ci, co = costs("Llama-3-8B", 128)
print(f"一个请求：输入 1024 × ${ci:.3f}/M + 输出 1024 × ${co:.3f}/M = ${(1024 * ci + 1024 * co) / 1e6:.5f}")
```

输出：

```text
Llama-3-8B  并发   1：TPOT   8.1 ms，输出    124 token/s；每百万 token：输入 $0.018，输出 $5.618
Llama-3-8B  并发  32：TPOT  11.2 ms，输出  2,858 token/s；每百万 token：输入 $0.018，输出 $0.243
Llama-3-8B  并发 128：TPOT  20.8 ms，输出  6,151 token/s；每百万 token：输入 $0.018，输出 $0.113
Llama-3-70B 并发  64：TPOT  21.6 ms，输出  2,969 token/s；每百万 token：输入 $0.164，输出 $0.936
一个请求：输入 1024 × $0.018/M + 输出 1024 × $0.113/M = $0.00013
```

前四行就是上面的表和 70B 的例子。最后一行是一个请求的成本。

## 到了大模型里

**这个模型故意很简单。**它把 prefill 和 decode 分开，各自按“整张卡都在做这件事”算成本；真实的服务里两者交错进行，会互相影响（第 70 讲）。它也没有考虑请求到达的不均匀：夜里请求少，GPU 闲着，也照样计费。实际的平均成本会比这里算的高，取决于 GPU 的利用率。

**但量级是对的。**用它估算出来的数，通常和实测差在两倍以内。在做技术选型时，这样一个“十分钟就能算出来”的模型，比什么都不算要强得多。第 67 讲会用 DGX Spark 上的实测，把效率这个数校准到你自己的环境。

**自有设备的算法。**如果 GPU 是自己买的，可以把购置价格按使用年限摊到每小时，再加上电费和运维，折算成“每小时的成本”，代进同一个公式。

## 容易混淆的地方

1. **API 价格不等于成本。**API 的定价包含了利润、闲时的浪费、研发成本，以及市场竞争的策略。它和这里算的“理论成本”可以对比，但不必相等。
2. **效率因素影响很大。**60% 和 30% 的效率，成本差两倍。效率取决于推理引擎、算子实现、批大小，要靠实测确定。
3. **低价不代表低延迟。**最便宜的设置是把并发推到显存允许的最大值，但这时每个请求的 TPOT 也最长。成本要在满足延迟目标的前提下比较。

## 回顾

推理成本模型把速度和价格连起来：每百万 token 的成本 = 每小时租金 / 每小时处理的 token 数。输入 token 由 prefill 处理，计算受限，Llama-3-8B 在 H100 上约 $0.018 / 百万（示例租金 $2.5/小时、效率 60%）；输出 token 由 decode 处理，带宽受限，成本取决于并发：并发 1 时约 $5.6，并发 128 时约 $0.11。所以输出远比输入贵，而提高并发是降成本最有效的手段。量化、GQA/MLA、前缀缓存等优化，都可以代进这个模型，算出它们能省多少。

到这里，推理的“账”都算完了。最后还有一个和速度、成本无关，却直接决定输出质量的环节：拿到下一个 token 的概率分布之后，到底选哪一个？下一讲：**解码策略**。
