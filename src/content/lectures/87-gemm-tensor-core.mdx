一个大模型的前向，九成以上的计算是矩阵乘法：每层的 q、k、v、o 四个投影，FFN 的三个矩阵，最后的输出层。第 60 讲说过，H100 的 BF16 峰值 989 TFLOPS 来自 Tensor Core，只有组织成矩阵乘法的计算才用得上它；第 86 讲又讲了矩阵乘法 kernel 的第一个关键：把 A、B 分块搬进共享内存反复用，从显存读的量降到原来的 1/T。

这一讲接着往下走。有了分块，一个矩阵乘法就能跑到峰值了吗？不一定。同样是 4096 维的 K，1408 × 1408 的矩阵乘法和 1536 × 1536 的，后者计算量只多 19%，用时却是前者的两倍；decode 时 16 个请求乘一个 4096 × 1024 的权重，GPU 只用上了峰值的百分之一。这一讲讲清楚这些现象：Tensor Core 是怎么被喂进数据的，矩阵怎么分给 132 个 SM，什么形状会让 GPU 闲着，以及 cuBLAS、CUTLASS 这些库是怎么对付的。

## 三层分块：线程块、warp、Tensor Core 指令

第 86 讲的分块只有一层：一个线程块负责 C 的一个 T × T 小块，每个线程算其中几个元素。真实的矩阵乘法 kernel 有三层，每一层对应一级存储：

- **线程块级**：一个线程块负责 C 的一大块，比如 128 × 128。它沿着 K 方向一段一段地前进，每段把 A 的 128 × 32、B 的 32 × 128 搬进**共享内存**。
- **warp 级**：块里的几个 warp（每个 32 个线程）各分到其中一小块，比如 64 × 64，结果累加在 warp 自己的**寄存器**里。
- **指令级**：warp 把自己那一小块再拆成 Tensor Core 指令能处理的形状。Ampere（A100）上的指令是 `mma.sync.m16n8k16`：一个 warp 一次算 16 × 8 的输出，沿 K 走 16 步，即 16 × 16 的 A 乘 16 × 8 的 B。

Hopper（H100）换了一套更大的指令 `wgmma`：四个 warp 组成一个 warpgroup，一次算 64 × N 的输出（N 最大 256），K 方向一次 16；A、B 可以直接从共享内存读，不必先搬进寄存器，而且是**异步**的，发出指令后可以去做别的事。配合 TMA（张量内存加速器），线程块只要告诉硬件“把这块搬进共享内存”，搬运也由硬件异步完成。这样，搬数据和算数据就能完全重叠起来：第 86 讲讲的双缓冲，在 Hopper 上变成了几段流水，一段在算，几段在搬。

为什么要这么多层？因为每往下一层，存储更小、更快：显存 80 GB、3.35 TB/s；共享内存每个 SM 最多 228 KB；寄存器每个 SM 256 KB，延迟最低。数据每被搬上一层，就在这一层被尽量多地复用，再往上一层只需要很少的流量。分块的形状就是在这几层的容量、复用次数和指令的形状之间找平衡。

## 把矩阵分给 132 个 SM

现在看一个完整的矩阵乘法 C[M, N] = A[M, K] · B[K, N] 怎么跑。输出切成 Mt × Nt 的块，一共 ⌈M/Mt⌉ × ⌈N/Nt⌉ 个，每个块交给一个线程块。H100 有 132 个 SM，我们假设每个 SM 同一时刻算一个块（真实 kernel 有时能放两个，道理一样）。块数超过 132 时，先上 132 个，算完再上下一批，每一批叫一**波**（wave）。

这里藏着两种浪费。

**补零（tile quantization）**：M 或 N 不是块大小的整数倍时，边上的块只有一部分是有用的，但 Tensor Core 照样按整块算。M = 1000、块 128 时，要算 8 × 128 = 1024 行，浪费 2.3%，不大。

**波次（wave quantization）**：块数不是 132 的整数倍时，最后一波只有一部分 SM 有活干，其余的空等。这一项可能很大：

- 1408 × 1408：每边 11 块，一共 121 块，一波就能装下，132 个 SM 里 121 个在算，利用率 91.7%。
- 1536 × 1536：每边 12 块，一共 144 块，第一波 132 块，第二波只有 12 块，另外 120 个 SM 闲着。两波的时间算了 1.09 波的活，利用率 54.5%。

计算量只多了 19%，时间却多了一倍。这就是**波次悬崖**：块数刚过 132 的整数倍，时间就跳一级。下面的演示画出了每一波里有多少个 SM 在干活，可以选几个预设，也可以自己拖 M、N、K：

## decode：块太少，SM 闲着

再看 decode。batch 里有 16 个请求，每个请求一个 token，乘 Llama-3-8B 的 k_proj（4096 → 1024）：M = 16，N = 1024，K = 4096。

先看算术强度（第 62 讲）。计算 2MNK，读的主要是权重 2KN 字节，强度约等于 M：16 FLOP/字节。H100 的拐点是 989 ÷ 3.35 ≈ 295 FLOP/字节，16 远在左边，这一步**受带宽限制**。理想情况下，时间就是把 8.5 MB（权重 8.4 MB，加上很小的输入和输出）读一遍：约 2.6 μs。

可是按普通的分块，输出只有 16 × 1024：块大小 64 × 64 时，只有 1 × 16 = 16 个块，132 个 SM 里只有 16 个在干活。受带宽限制的 kernel 也需要足够多的 SM 同时发出读请求，才能把显存带宽跑满（第 86 讲说的“在途请求”）；16 个 SM 远远不够。

解决办法是 **split-K**：既然 M、N 方向切不出足够的块，就沿 K 方向切。K = 4096 切成 8 段，每个块只算 512 长的一段，得到一个部分和；8 段的部分和最后再加起来。块数变成 128，几乎占满所有 SM。代价是多了部分和的读写和一次归约，但比起让 116 个 SM 闲着，划算得多。第 85 讲的 Flash-Decoding 是同一个思路：decode 注意力的查询只有一行，就沿 KV 的长度方向切开。

顺带一提，M = 16 时 Tensor Core 本身也是浪费的：`wgmma` 的输出一次就是 64 行，只有 16 行有用，四分之三的乘加白算了。但这不要紧：这一步受带宽限制，Tensor Core 本来就在等数据。decode 的矩阵乘法要优化的是读，不是算。

## 用代码算一遍

把上面的简化模型写成代码，几种形状一起算：每波的时间按一个 SM 算完一块计，访存时间按读 A、B、写 C 计，活跃的块少于一半的 SM 时，假设带宽按比例打折。

```python
import math
SM, PEAK, BW = 132, 989e12, 3.35e12            # H100 SXM：SM 数、BF16 稠密峰值、显存带宽

def gemm(M, N, K, Mt=128, Nt=128, split=1):
    tiles = math.ceil(M / Mt) * math.ceil(N / Nt) * split
    waves = math.ceil(tiles / SM)
    t_comp = waves * 2 * Mt * Nt * (K / split) / (PEAK / SM)      # 每波的时间 = 一个 SM 算完一块
    nbytes = 2 * (M * K + K * N + M * N) + (8 * M * N * split if split > 1 else 0)
    t_mem = nbytes / (BW * min(1, min(tiles, SM) / (SM / 2)))     # 活跃的块少于 66 个时带宽打折
    t = max(t_comp, t_mem)
    return tiles, waves, tiles / (waves * SM), t, 2 * M * N * K / t / 1e12

print("形状 M × N × K（块）            块数  波数  波次利用率  时间(μs)  TFLOPS")
for name, args in [("2048 × 4096 × 4096", (2048, 4096, 4096)),
                   ("1408 × 1408 × 4096", (1408, 1408, 4096)),
                   ("1536 × 1536 × 4096", (1536, 1536, 4096)),
                   ("16 × 1024 × 4096（64×64）", (16, 1024, 4096, 64, 64)),
                   ("同上，split-K = 8", (16, 1024, 4096, 64, 64, 8))]:
    tiles, waves, eff, t, tf = gemm(*args)
    print(f"{name:<28}{tiles:>6}{waves:>6}{eff:>10.1%}{t * 1e6:>10.1f}{tf:>8.0f}")
```

```text
形状 M × N × K（块）            块数  波数  波次利用率  时间(μs)  TFLOPS
2048 × 4096 × 4096             512     4     97.0%      71.7     959
1408 × 1408 × 4096             121     1     91.7%      17.9     907
1536 × 1536 × 4096             144     2     54.5%      35.8     539
16 × 1024 × 4096（64×64）         16     1     12.1%      10.5      13
同上，split-K = 8                 128     1     97.0%       2.9      47
```

逐行看：

- **2048 × 4096 × 4096**：prefill 时 2048 个 token 乘 q_proj。512 块，4 波，最后一波 116 / 132，利用率 97%。强度上千，受算力限制，模型估出 959 TFLOPS。真实的 cuBLAS 在这种形状上通常能到峰值的七八成：模型没有算流水的启动和收尾、指令发射和同步的开销。
- **1408² 和 1536²**：一波和两波，时间 17.9 对 35.8 μs，正好两倍，实际算力从 907 掉到 539 TFLOPS。
- **16 × 1024 × 4096**：16 个块，时间 10.5 μs，只有 13 TFLOPS，峰值的 1.3%，比理想的 2.6 μs 慢了 4 倍。
- **split-K = 8**：128 个块，2.9 μs，接近只读一遍的 2.6 μs。

<Note kind="point">矩阵乘法 kernel 有三层分块：线程块（共享内存）、warp（寄存器）、Tensor Core 指令。分块之后，输出的块按“波”分给 SM：块数刚超过 SM 数的整数倍会多出一波（波次悬崖）；块太少时大部分 SM 闲着，连带宽都跑不满，要沿 K 切开（split-K）。</Note>

## 库是怎么对付的

上面这些问题，矩阵乘法库都要处理：

- **按形状选配置。**cuBLAS 内部有很多套 kernel（不同的块大小、流水段数、是否 split-K），根据 M、N、K 用启发式规则或预先测好的表挑一套。CUTLASS 是 NVIDIA 开源的 C++ 模板库，把这些配置都做成模板参数，推理框架可以为自己常见的形状专门实例化。Triton（下一讲）则用自动调优：同一个 kernel 写好几种配置，第一次运行时逐个试，记住最快的。
- **Stream-K。**与其把输出切成块、按波分配，不如把所有块的“K 方向的每一段”加起来，平均分给 132 个 SM，每个 SM 分到的活一样多，最后再把跨 SM 的部分和合起来。这样就没有最后一波的空闲了。CUTLASS 里有这种调度方式。
- **推理引擎里的特化。**decode 的 M（batch 里的请求数）每一步都在变，引擎会把它补齐到几个固定的档位（第 89 讲的 CUDA Graph 也要这样做），每个档位用调好的 kernel。很小的 M 有时直接用专门的矩阵 × 向量 kernel，不走 Tensor Core。
- **形状本身也可以调。**模型设计时把隐藏维度、FFN 宽度、词表大小取成 64 或 128 的倍数，就是为了避免补零；Llama 的词表 128,256 = 128 × 1002 就是一例。

## 容易混淆的地方

- **“用上了 Tensor Core”不等于“跑到了峰值”。**块的形状、波次、流水、数据搬运，任何一项没做好，Tensor Core 都会在等。
- **矩阵大一点不一定更快，也不一定更慢。**同一个 kernel，矩阵从 1408 长到 1536，时间翻倍；再长到 2048，块数 256，2 波，利用率 97%，时间和 1536 一样。性能曲线是阶梯形的，不是平滑的。
- **decode 的矩阵乘法慢，不是因为 Tensor Core 不够快。**它受带宽限制，要优化的是让足够多的 SM 一起读，以及少读（量化，第 90 讲起）。

## 回顾

矩阵乘法 kernel 有三层分块：线程块把 A、B 的一段搬进共享内存，warp 在寄存器里累加自己的小块，Tensor Core 指令一次算一个小矩阵乘加（A100 是一个 warp 算 16 × 8，H100 的 wgmma 是四个 warp 算 64 × N，配合 TMA 异步搬运）。输出的块按波分给 132 个 SM：1408² 一波装下，1536² 多一波、时间翻倍；decode 时 16 × 1024 的输出只有 16 个块，只用了峰值的 1.3%，沿 K 切 8 份后接近只读一遍权重的理想时间。库用按形状选配置、Stream-K、档位特化来对付这些问题。

写一个这样的 kernel，要自己管三层分块、共享内存、同步和流水，用 CUDA 写非常繁琐。有没有办法只描述“一个块怎么算”，其余交给编译器？下一讲：**Triton 入门**。
