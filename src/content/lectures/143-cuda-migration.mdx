上一讲的结论里有一条很具体：这块卡的波前是 64 条通道，不是 32 条。现在把这条结论放回代码里。手上是一个推理引擎，里面有几十个 `.cu` 文件，几千行 kernel，到处是 `threadIdx`、`__shfl_xor_sync`、`cublasGemmEx`，还有几段 PTX 内联汇编。

这一讲回答三个问题：CUDA 生态把人锁在哪里；“兼容”和“重写”两条路线各自要付出什么；一份 CUDA 代码里，哪些行能被工具自动翻译，哪些行工具能换名字但语义会出错，哪些行只能从头重写。

## 锁定不在语言，在三样东西

“CUDA 生态锁定”这句话常被说成“代码是用 CUDA 写的”，这不准确。CUDA C++ 本身就是 C++ 加上几个扩展（`__global__`、`threadIdx`、`<<<>>>`），换一套名字并不难。真正难搬的是另外三样：

**一是调好的库**。cuBLAS 里每种形状该用多大的分块、cuDNN 里每种卷积该用哪个算法、FlashAttention 里针对 Ampere 和 Hopper 分别写的两套 kernel——这些是人多年调出来的参数和代码，不是接口。接口换名字是一天的事，参数重调是几个月的事。

**二是写进 kernel 的硬件常数**。线程组宽度 32、共享内存 228 KB、矩阵指令 `m16n8k16`、L2 的大小。这些数字散落在每一个高性能 kernel 的分块逻辑里，而且往往没有名字，就是一个字面量（第 142 讲的 `% 32`）。

**三是框架之外的那一圈工具**。Nsight 的时间线、CUDA Graph、NVTX 的打点、`nvidia-smi` 的输出格式、依赖 `torch.cuda` 的第三方库。工程习惯和自动化脚本全长在这些工具上。

对应到上一讲的分层：第一样在算子库层，第二样在 kernel 层，第三样在工具层。模型和引擎那两层基本不锁。

## 兼容路线：hipify 能做到哪一步

兼容路线的做法是提供一套和 CUDA 一一对应的接口（HIP），再提供一个源到源的翻译工具。ROCm 的 HIPIFY 有两个版本：`hipify-perl` 按正则替换，不需要能编译就能跑，适合粗扫；`hipify-clang` 用真正的 C++ 前端解析，替换更准，但要求代码能被编译器完整解析（AMD 的 HIPIFY 文档对两者的定位就是这样区分的）。

工具翻完不等于可用。HIPIFY 的文档自己也写了这一点：迁移之后要做代码审查，把不支持的库和写法换掉，再测正确性和性能。下面逐行看一段 kernel，每行标出属于哪一类处理。

<HipTranslate caption="图 143-1　一段 RMSNorm kernel 的缩影逐行翻译。点任意一行看它为什么属于那一类；“只看要人工处理的”按钮过滤掉自动替换的行。代码是按两边公开的接口对应关系写的示意，不是某个真实项目里的片段。" />

挑三行细说。

**`int lane = threadIdx.x % 32;`**。工具不会碰它——在工具眼里这就是一个整数。但在 64 条通道的卡上，这一行把一个波前当成两个 warp 用：`lane` 的取值范围只到 31，而硬件上同一拍执行的是 64 条通道。于是下面所有“同一个 warp 内不需要同步”的假设都不成立。正确做法是用 `warpSize` 这个内建变量，或者按架构定义一个常量。AMD 的 HIP 移植文档把这件事写成一条明确的告诫：不要假设 warp 是 32 或 64，设备代码用 `warpSize`，主机侧通过设备属性查询。

**跨通道归约的步数**。`for (int i = 16; i > 0; i >>= 1)` 是 32 条通道的折半归约，5 步。64 条通道要从 32 开始，6 步。少一步的后果是：每条通道手里只是半个波前的和，RMSNorm 的分母偏小，输出整体偏大——而且程序不报错、不崩溃，生成的文本看起来只是“质量差一点”。这类错误在第 146 讲的逐层比对里会第一时间暴露出来，这也是为什么“跑对”必须有一套机械的检查手段，不能靠看输出顺不顺。

**表决掩码的宽度**。`__ballot_sync` 返回每条通道一位：32 条通道刚好塞进 `unsigned`，64 条通道必须用 64 位整数。沿用 `unsigned` 会静默丢掉编号 32 到 63 的通道。

<Note kind="warn">这三类问题的共同点是**静默**：编译通过、运行不报错、输出有值但是错的。迁移时要主动去搜这些模式（`% 32`、`0xffffffff`、`>> 1` 的归约循环、`unsigned mask`），不能等着测试告诉你。</Note>

这份统计有三个值得注意的地方。

**“沿用 CUDA 的名字”比“换成 hip 前缀”还多**（47 处对 36 处）。原因是 PyTorch 的这类构建对外仍然自称 CUDA：拿当前流的函数叫 `at::cuda::getCurrentCUDAStream()`，守卫叫 `OptionalCUDAGuard`，连 setup.py 里注册扩展用的都是 `CUDAExtension`。底层编译成的是 HIP 代码，上层的名字一个没改。这正是兼容路线最大的收益：调用方不需要知道自己在哪块卡上。

**真正和架构绑定的只有十几处**：11 处架构内建函数（`__builtin_amdgcn_*`、`__builtin_hcu_*`）、4 处按架构代号分支的宏、3 处写死 64 的线程组宽度。它们全部集中在一个文件——那个专门为 decode 写的小 M 矩阵乘 kernel（第 158 讲）。

**这十几处恰好是性能最关键的地方**。这是迁移工作的典型形状：九成的行机械替换，剩下一成在最热的几个 kernel 里，而那一成决定了性能。

## 重写路线：没有线程编号的编程模型

如果硬件不是 SIMT 的（第 142 讲的 NPU 路线），上面整套办法都不适用。那类 kernel 的写法不是“我是第几号线程、我负责哪个元素”，而是：

1. 声明几块片上缓冲，说明它们多大、放什么；
2. 让搬运单元把显存里的一块数据搬进缓冲（搬运途中可能还要做补齐、转置、按矩阵单元要求的排布重排）；
3. 让矩阵单元或向量单元对缓冲里的数据做运算；
4. 把结果搬回显存；
5. 把这几步排成流水：这一块在算的时候，下一块已经在搬，缓冲要开双份。

这种模型里没有 `threadIdx`，自然也没有东西可以从 CUDA 翻译过来。所以这条路线上厂商要做的事多得多：一套 kernel 语言、一个算子库、一套图编译（第 145 讲），还要把 PyTorch 的几千个算子逐个实现一遍（第 144 讲）。换来的是编译器能看到完整的数据搬运计划，可以在图的尺度上做融合和复用。

还有第三种选择，而且在实践中越来越重要：**用能生成多种后端代码的 kernel 语言**。Triton 的 kernel 写的是“一个程序处理一整块数据”（第 88 讲），不写线程编号，所以同一份 Python 代码可以由不同后端编译到不同架构。Triton 项目自己维护 NVIDIA 和 AMD 两个后端，其他厂商也在接。这条路的代价是：能表达的东西比手写汇编少，而且为一种硬件调好的块大小、流水级数到另一种硬件上要重调（第 151 讲）。

## 对应关系表：哪些库有对应物

迁移前先查一遍依赖，看每个库在目标平台上有什么。兼容路线的对应关系大致是这样（名字以 ROCm 这条路线为例，其他厂商各有自己的命名）：

| CUDA 侧 | 作用 | 兼容路线的对应物 | 注意 |
| --- | --- | --- | --- |
| CUDA Runtime | 设备、显存、流、发射 | HIP Runtime | 接口一一对应，`cuda` 换 `hip` |
| cuBLAS / cuBLASLt | 矩阵乘 | rocBLAS / hipBLASLt | 接口对应；默认选的分块不同，小 M 时差别很大（第 158 讲） |
| cuDNN | 卷积等 | MIOpen | 覆盖的算子和格式不完全一致 |
| CUTLASS | 写矩阵乘的模板库 | Composable Kernel、厂商自研模板库 | 概念相近，模板参数和指令形状都要重写 |
| CUB / Thrust | 并行原语 | hipCUB / rocThrust | 模板参数里的线程组宽度要改 |
| NCCL | 集合通信 | RCCL | 接口照抄，PyTorch 里后端名仍写 `nccl`（第 153 讲） |
| FlashAttention | 注意力 | 厂商移植版或 Triton 实现 | 分块参数按片上容量重调（第 142 讲） |
| Nsight Systems / Compute | 时间线、单 kernel 分析 | rocprof 一类的工具 | 能力对应，输出格式和字段名不同（第 149 讲） |
| nvcc | 编译器 | 基于 Clang 的厂商编译器 | 架构代号从 `sm_90` 变成 `gfx938` 这样的串 |

这张表里真正要留意的是“注意”那一列：**有对应物不代表能直接换**。rocBLAS 有 `hipblasGemmEx`，调用能跑通，但它内部按哪一代硬件调过、默认选什么分块，和 cuBLAS 完全是两套结论。第 158 讲会看到一个具体后果：decode 时 M ≤ 64，库选了 256 × 256 的分块，于是不管 N 多大都要约 135 μs，海光只能自己写一个专用 kernel 绕过去。

## 为什么会有人写内联汇编

迁移时最让人头疼的是内联汇编（`asm volatile("..." )` 里的 PTX）。既然这么难搬，为什么还有人写？因为有三类事情用 C++ 表达不出来，或者表达出来编译器生成的代码不够好：

- **拿到硬件状态**：当前通道号、当前时钟、某个特殊寄存器的值。
- **精确控制指令**：让编译器一定用某一条指令（某种舍入模式的乘加、某种宽度的加载），而不是由它自己挑。
- **异步搬运的细节**：从显存直接搬进片上存储、绕过某级缓存、提前预取。这类指令往往比 C++ 的接口早出现一两代。

海光那个小 M kernel 里的 `make_buffer_resource` 和 `__builtin_hcu_raw_buffer_load_lds` 就属于第三类：手工拼出一个描述“一段显存”的四元组，再让搬运指令按它把数据直接送进片上存储（第 158 讲会逐行读）。这类代码在任何架构上都要重写，但它也解释了为什么高性能 kernel 不可能“写一次到处跑”——最后那几个百分点的性能，就藏在这些和架构绑死的指令里。

<Note kind="column">迁移完成后还有一件容易忘的事：**构建系统**。架构代号（`sm_90` → `gfx938`）、编译选项、一份二进制包含哪几个架构的机器码、JIT 编译的缓存位置，都要改。海光那个 kernel 用的是 PyTorch 的 `load_inline` 在运行时即时编译（第 158 讲），好处是不用预编译所有架构，代价是第一次调用会卡住几十秒——在服务里要放进预热阶段。</Note>

## 迁移该按什么顺序做

把上面的内容整理成一个可执行的顺序：

| 步 | 做什么 | 为什么在这一步 |
| --- | --- | --- |
| 1 | 先不迁 kernel：把模型跑在框架的通用算子上（`torch.matmul`、`F.softmax`） | 先拿到一个能跑、能比对的基线，哪怕很慢。第 148 讲在 MPS 上就是这样起步的 |
| 2 | 清点代码里和 NVIDIA 绑定的写法（设备、通信、第三方库、自写 kernel、图捕获） | 第 141 讲的清单给出工作量的全貌和优先级 |
| 3 | 跑翻译工具，处理掉机械替换的部分 | 这部分占行数的九成，先清掉，剩下的才看得清 |
| 4 | 逐个检查“要人工确认”的行：线程组宽度、掩码、同步、共享内存容量、架构代号 | 这些是静默错误的来源，必须人工过一遍 |
| 5 | 重写“工具无能为力”的部分：内联汇编、矩阵核心指令、专有库调用 | 到这一步才动最难的代码，而且有基线可比 |
| 6 | 对齐精度（第 146 讲），再调性能（第 149 讲起） | 顺序不能反 |

第 4 步容易被跳过，因为跑起来“看着是对的”。一个实用的办法是在这一步之前先把第 146 讲的逐层比对脚本准备好：改一个 kernel，就跑一次比对，立刻知道这一层的输出有没有偏。

## 回顾

CUDA 的锁定不在语言上，而在三处：调好参数的算子库、写进 kernel 的硬件常数、框架之外的那一圈工具。兼容路线提供一一对应的接口和翻译工具，让九成的行机械替换掉，代价是继承了 CUDA 的硬件假设——线程组宽度、掩码宽度、同步语义、共享内存容量，这四类是静默错误的高发区。重写路线面对的是另一种编程模型：没有线程编号，数据搬运要显式安排，CUDA 代码无从翻译，但编译器能在图的尺度上优化。真实项目的统计印证了这个形状：海光插件的 kernel 代码里，和架构强绑定的只有十几处，却全部落在最热的那个矩阵乘 kernel 里。

kernel 的事先放一放。往上一层：就算 kernel 都有了，PyTorch 怎么知道这块卡存在？`x @ w` 这句 Python 调用，是怎么找到注册在这块卡上的那份实现的？缺了一个算子又会发生什么？
