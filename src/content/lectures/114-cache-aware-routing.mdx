一个推理服务通常有很多个实例（每个实例是一份完整的模型，可能占一张卡，也可能占一组卡）。请求进来，先到一个**路由器**（也叫网关、负载均衡器），由它决定发给哪个实例。

传统的 Web 服务里，这件事很简单：哪个实例闲就发给哪个，或者干脆轮着发。可大模型推理有一个特殊之处：**每个实例里都有前缀缓存**（第 76 讲）。同一个会话的第二轮、同一个应用的系统提示，如果发到上次处理过它的实例，前缀就能命中，省掉一大段 prefill；发到别的实例，就得从头算。

于是路由面临一个两难：**为了命中缓存，应该把相关的请求集中到同一个实例；为了负载均衡，又应该把请求分散开。**这一讲用一个模拟比较几种策略，看怎么兼顾两头。

## 一个模拟

我们构造一个典型的负载：

- 12 个应用，每个有一段 2000 token 的系统提示。应用的热度很不均匀，第 1 个最热门（热度按 1、1/2、1/3……递减）。
- 300 个用户会话，每个属于某个应用，聊 1 到 8 轮。每一轮的输入是“系统提示 + 这个会话之前的全部历史 + 新问题”，每轮新增 300 token。
- 一共 1288 个请求，各会话交错到达。

4 个实例，每个实例的前缀缓存能放 6 万个 token（显存有限，按 LRU 淘汰）。前缀只能从头连续命中：系统提示命中了，才可能接着命中第 1 轮的历史，依此类推。

每个实例的**工作量**记为：要 prefill 的 token 数，加上 decode 的部分（200 个输出 token，粗略地按每个相当于 20 个 prefill token 计）。我们看两个指标：前缀缓存的**命中率**（命中的 token 占所有输入 token 的比例），和**负载不均衡**（最忙实例的工作量是平均的几倍）。

## 五种策略

**轮询**：依次发给 4 个实例。负载最均匀（1.01 倍），命中率 **71.6%**。命中主要来自系统提示：12 段系统提示很快就在每个实例里都有了一份；可同一个会话的下一轮多半被发到了别的实例，历史部分命中不了。

**最空闲**：发给当前工作量最少的实例。负载完美（1.00 倍），命中率和轮询差不多（71.4%），原因一样。

**按会话固定**：同一个会话的请求总发给同一个实例（按会话编号取模）。会话历史基本都能命中，命中率升到 **84.8%**；但不同会话的长度不同，负载有些不均（1.12 倍）。缓存容量有限，热门会话多的实例上，旧的历史会被挤掉。

**按应用固定**：同一个应用的请求总发给同一个实例。系统提示和会话历史都在一处，命中率 **92.1%**；可应用的热度很不均匀，最热门的应用所在的实例被压垮了：工作量是平均的 **1.86 倍**。整个集群的速度被这一个实例拖住。

**缓存感知（限负载）**：对每个请求，先找出负载不超过平均 1.2 倍的实例，再在其中选**前缀命中最多**的那个（一样多时选更空闲的）。命中率 **96.8%**，负载 **1.12 倍**。热门应用的请求先集中在一个实例上，它一旦过载，新的请求就溢出到别的实例，在那里也建立起缓存。

## 路由器怎么知道谁有缓存

缓存感知路由要知道每个实例里缓存了哪些前缀。常见的做法有两种：

- **路由器自己记账**：路由器为每个实例维护一棵近似的前缀树（第 76 讲的基数树），记录发过去的请求的前缀。它不精确（实例那边可能已经淘汰了），但足够好，而且不需要和实例通信。SGLang 的路由器就是这样做的。
- **实例上报**：实例把自己缓存里的块哈希（第 76 讲）定期或实时地报告给一个中心的索引，路由器查询这个索引。更准确，但要多一些通信。vLLM 生态的一些路由组件（如 llm-d）采用这种方式。

无论哪种，匹配的单位都是前缀：从头开始比，能连续匹配多长。

## 负载怎么衡量

“负载”也不止一种量法：排队的请求数、正在运行的请求数、KV Cache 的使用率、预计还要算多少 token……前缀命中率高的请求，prefill 的工作量小，同样一个请求，发到不同实例，带来的负载也不同。好的路由器会把“发到这里要算多少”算进去：一个命中了 90% 前缀的实例，即使队列稍长，可能也比一个完全不命中的空闲实例更快。

还要注意**突发**。热门应用在某个时刻突然涌入大量请求，缓存感知路由会先把它们都送到有缓存的那个实例。负载上限（这里是平均的 1.2 倍）就是为了防止这种情况：超过上限就溢出。

## 有缓存的实例很忙时

上面的模拟用“负载不超过平均 1.2 倍”这条规则防止热点。把这个问题算细一点：有缓存的实例 A 正在排队，空闲的实例 B 没有缓存，请求发给谁？

只看命中率或只看负载都不够，要比的是**首 token 什么时候出来**。设 GPU 最早能开始算的时刻是 Q（排队），状态准备好的时刻是 R（取回 KV 的时间），状态好了之后还要算 C。如果取回可以和排队同时进行，

<div class="ai-formula">首 token = max(Q, R) + C</div>

依赖关系很重要：Q = 80 ms、取回 60 ms、计算 10 ms，取回和排队同时进行只要 **90 ms**；等 GPU 空了才开始取回就要 **150 ms**。同样的计算、同样的字节，差了 60 ms。所以好的系统在请求还在排队时就开始取回它要的 KV。

算一个具体的例子：Qwen3-8B 的请求带 8192 token 的前缀和 256 个新 token，两个 A100 实例。A 的显存里有这份前缀，但要排队 250 ms；B 只要等 20 ms，但没有缓存。全部重算 8448 个 token 约 888 ms，命中后只算 256 个约 30.9 ms。B 还可以从远端存储取回前缀：查找 10 ms，经网络读到主机内存，再经 PCIe（25 GB/s）搬到 GPU，两段串行。

| 路径 | 首 token |
| --- | --- |
| A：本地命中 | 250 + 30.9 ≈ **281 ms** |
| B：直接重算 | 20 + 888 ≈ **908 ms** |
| B：经 50 GbE（6.25 GB/s）远端取回 | 约 **282 ms** |
| B：经 200 GbE（25 GB/s）远端取回 | 约 **138 ms** |

<RouteTimeline caption="图 114-2　同一个请求的三条路径。A 有缓存但排队 250 ms；B 空闲但要重算 888 ms，或者从远端取回再算。取回和 B 的排队同时进行；远端链路够快时，B 取回最早出首 token。" />

重算几乎总是最慢的。B 要靠取回赶上 A：扣掉命中后的 30.9 ms 计算，状态必须在 250 ms 内就绪；再扣掉查找的 10 ms 和 PCIe 的 48.3 ms，远端读取只剩约 192 ms，所以远端链路至少要 **6.30 GB/s**。50 GbE 的 6.25 GB/s 略低于此，200 GbE 远高于此。这个阈值随 A 的排队时间变化，调一调演示里的滑块就能看到。

**持续到达时还要看总流量。**200 GbE 时单个请求取回最快，但每秒 16 次取回要约 19.3 GB/s，已经用掉这条链路 77% 的能力，突发时取回本身要排队。

**路由器以为的缓存不一定还在。**路由器一般根据实例上报的缓存事件来判断谁有缓存，事件可能延迟，缓存可能已经被淘汰。把 A 的排队改成 80 ms，设缓存只有概率 p 真的还在：在的话 111 ms，不在就只能重算，968 ms。p = 0.9 时平均 196.5 ms，看起来很好；但 10% 的请求要 968 ms，p99 就是 968 ms。要让 p99 也好，命中的把握要到 99% 以上。均值和尾延迟，要分开看。

**优化谁的时间。**把一个请求挪到空闲实例，它自己快了，可能让其他请求更晚完成。决定路由之前，要先确定目标是这个请求的响应时间，还是所有请求一起的完成时间。

## 到了大模型里

**PD 分离时的路由。**PD 分离的系统里，路由器要分两步决定：prefill 发给哪个 prefill 实例（看前缀缓存），decode 交给哪个 decode 实例（看 KV 空间和负载）。如果 KV 存在共享的缓存池里（上一讲的 Mooncake 等），prefill 实例可以从池子里读回别处算过的前缀，路由的约束就松了很多。

**多卡、多机房。**大规模服务还要考虑地理位置、模型版本、LoRA 适配器（第 50 讲）在哪些实例上加载，等等。缓存感知只是路由要考虑的因素之一。

**会话粘性的副作用。**按会话固定的路由简单有效，很多服务在用。它的问题是：实例故障或扩缩容时，大量会话的缓存会失效；某些超长会话会让一个实例特别忙。所以通常要配合负载上限一起用。

## 用代码复现

下面的代码生成上面的负载，实现五种路由策略和每个实例的 LRU 前缀缓存，统计命中率和负载不均衡的程度。

```python
import random
from collections import OrderedDict
random.seed(0)

# 负载：12 个应用，各有一段 2000 token 的系统提示（热度不均）；300 个用户会话，每个会话属于一个应用，聊 1–8 轮，
# 每轮新增 300 token（问题 + 上一轮的回答）。请求的前缀 = 系统提示 + 这个会话之前的全部历史
APPS, SESS, SYS, TURN, OUT = 12, 300, 2000, 300, 200
weights = [1 / (a + 1) for a in range(APPS)]                       # 第 1 个应用最热门
sessions = [(random.choices(range(APPS), weights)[0], random.randint(1, 8)) for _ in range(SESS)]
reqs = [(s, t) for s, (_, turns) in enumerate(sessions) for t in range(turns)]
random.shuffle(reqs); reqs.sort(key=lambda r: r[1])               # 各会话交错到达，同一会话的轮次按顺序

def blocks(s, t):
    """请求的前缀拆成若干“块”（键, token 数）：系统提示一块，之前每一轮一块。前缀缓存只能从头连续命中"""
    app = sessions[s][0]
    return [(("sys", app), SYS)] + [(("turn", s, i), TURN) for i in range(t)]

def simulate(policy, n_inst=4, cap=60_000):
    caches = [OrderedDict() for _ in range(n_inst)]                # 每个实例一个 LRU 前缀缓存（容量按 token 计）
    load = [0.0] * n_inst; hit_tok = all_tok = 0
    for k, (s, t) in enumerate(reqs):
        bl = blocks(s, t)
        def hits(i):                                               # 在实例 i 上能从头连续命中多少 token
            h = 0
            for key, n in bl:
                if key in caches[i]: h += n
                else: break
            return h
        avg = sum(load) / n_inst
        if policy == "轮询": i = k % n_inst
        elif policy == "最空闲": i = min(range(n_inst), key=lambda j: load[j])
        elif policy == "按会话固定": i = s % n_inst
        elif policy == "按应用固定": i = sessions[s][0] % n_inst
        else:                                                      # 缓存感知：命中最多的实例，但负载不能超过平均的 1.2 倍
            ok = [j for j in range(n_inst) if load[j] <= 1.2 * avg + 1] or list(range(n_inst))
            i = max(ok, key=lambda j: (hits(j), -load[j]))
        h = hits(i); total = sum(n for _, n in bl)
        hit_tok += h; all_tok += total
        load[i] += (total - h) + OUT * 20                          # 工作量：要 prefill 的 token + decode（按每个输出 token 约等于 20 个 prefill token 估）
        for key, n in bl + [(("turn", s, t), TURN)]:               # 用过的块放到 LRU 的最新端；这一轮的结果也存进去
            caches[i].pop(key, None); caches[i][key] = n
        while sum(caches[i].values()) > cap: caches[i].popitem(last=False)
    return hit_tok / all_tok, max(load) / (sum(load) / n_inst)

print(f"{len(reqs)} 个请求，4 个实例，每个实例的前缀缓存 6 万 token")
for p in ["轮询", "最空闲", "按会话固定", "按应用固定", "缓存感知（限负载）"]:
    hr, imb = simulate(p)
    print(f"  {p:9s}：缓存命中率 {hr:5.1%}，最忙实例的工作量是平均的 {imb:.2f} 倍")
```

输出：

```text
1288 个请求，4 个实例，每个实例的前缀缓存 6 万 token
  轮询       ：缓存命中率 71.6%，最忙实例的工作量是平均的 1.01 倍
  最空闲      ：缓存命中率 71.4%，最忙实例的工作量是平均的 1.00 倍
  按会话固定    ：缓存命中率 84.8%，最忙实例的工作量是平均的 1.12 倍
  按应用固定    ：缓存命中率 92.1%，最忙实例的工作量是平均的 1.86 倍
  缓存感知（限负载）：缓存命中率 96.8%，最忙实例的工作量是平均的 1.12 倍
```

五行对应五种策略，和演示一致：缓存感知（限负载）的命中率最高（96.8%），负载只比轮询差一点（1.12 倍）；按应用固定虽然命中率也高，最忙的实例却是平均的 1.86 倍。

第二段代码复现“有缓存的实例很忙时”的数字：四条路径的首 token、B 取回追平 A 需要的带宽、取回与排队串行和并行的差别，以及缓存只以概率 p 存在时的均值和慢路径。

```python
# 首 token 时间 = max(GPU 排队 Q, 状态就绪 R) + 剩余计算 C（取回可以和排队同时进行）
# Qwen3-8B 的 8192 token 前缀 + 256 个新 token，A100 按 156 TFLOP/s
V = 8192 * 144 * 1024                                     # 前缀的 KV：1.125 GiB
def prefill(new, ctx):                                   # 线性层 + 因果注意力（第 112 讲）的计算时间
    return (2 * 6.95e9 * new + 4 * 32 * 128 * 36 * (ctx**2 - (ctx - new)**2) / 2) / 156e12
full, hit = prefill(8448, 8448), prefill(256, 8448)       # 全部重算 / 命中后只算 256 个新 token
lookup, pcie = 0.010, V / 25e9                             # 远端查找 10 ms；主机内存到 GPU 经 PCIe 25 GB/s

def first(Q, R, C): return max(Q, R) + C
print(f"A：本地命中，排队 250 ms     首 token {first(0.250, 0, hit)*1e3:5.0f} ms")
print(f"B：空闲 20 ms，直接重算     首 token {first(0.020, 0, full)*1e3:5.0f} ms")
for name, bw in [("50 GbE（6.25 GB/s）", 6.25e9), ("200 GbE（25 GB/s）", 25e9)]:
    R = lookup + V / bw + pcie                            # 先经网络到主机内存，再经 PCIe 到 GPU，两段串行
    print(f"B：从远端取回，{name}  首 token {first(0.020, R, hit)*1e3:5.0f} ms")
budget = 0.250 - lookup - pcie                            # B 要追平 A，远端读取最多能用的时间
print(f"B 取回要追平 A，远端链路至少 {V / budget / 1e9:.2f} GB/s")
print(f"等 GPU 空了才开始取回（串行）：{(0.080 + 0.060 + 0.010)*1e3:.0f} ms；和排队同时进行：{first(0.080, 0.060, 0.010)*1e3:.0f} ms")

# 路由器以为 A 有缓存，但只有概率 p 真的还在（事件延迟、已被淘汰）：A 排队 80 ms
ok, miss = 0.080 + hit, 0.080 + full
for p in [0.5, 0.9, 0.99]:
    print(f"p = {p:.2f}：平均 {(p*ok + (1-p)*miss)*1e3:5.1f} ms；但 {1-p:.0%} 的请求要 {miss*1e3:.0f} ms")
```

输出：

```text
A：本地命中，排队 250 ms     首 token   281 ms
B：空闲 20 ms，直接重算     首 token   908 ms
B：从远端取回，50 GbE（6.25 GB/s）  首 token   282 ms
B：从远端取回，200 GbE（25 GB/s）  首 token   138 ms
B 取回要追平 A，远端链路至少 6.30 GB/s
等 GPU 空了才开始取回（串行）：150 ms；和排队同时进行：90 ms
p = 0.50：平均 539.3 ms；但 50% 的请求要 968 ms
p = 0.90：平均 196.5 ms；但 10% 的请求要 968 ms
p = 0.99：平均 119.4 ms；但 1% 的请求要 968 ms
```

对照正文：281、908、282、138 ms；追平需要 6.30 GB/s；串行 150 ms、并行 90 ms；p = 0.9 时平均 196.5 ms，但 10% 的请求要 968 ms。

## 容易混淆的地方

1. **命中率不是唯一目标。**按应用固定的命中率很高，但热点让整体延迟变差。路由要优化的是整体的吞吐和延迟（第 82 讲的 goodput），命中率只是手段。
2. **轮询不是“没有缓存”。**系统提示这类所有请求共享的前缀，在每个实例里都会被缓存；轮询损失的是会话历史这类“只属于少数请求”的前缀。
3. **缓存容量会改变结论。**缓存很大时，几乎什么都能存下，策略之间的差距变小；缓存很小时，集中路由的价值更大。在演示里调一调缓存容量就能看到。

4. **命中缓存不等于更快。**有缓存的实例可能在排长队。要比较的是首 token = max(排队, 状态就绪) + 剩余计算；空闲实例从够快的远端取回，可能比在有缓存的实例上排队更早。
5. **平均命中率高，尾延迟不一定好。**路由器以为的缓存有一定概率已经不在，这部分请求要整段重算，决定了 p99。

## 回顾

推理服务的路由器要决定每个请求发给哪个实例。把相关请求集中起来能命中前缀缓存，但会造成热点；均匀分散能平衡负载，但缓存命中不了。模拟的 4 个实例、1288 个请求里：轮询命中率 71.6%，负载 1.01 倍；按会话固定 84.8%、1.12 倍；按应用固定 92.1%，但最忙实例是平均的 1.86 倍；缓存感知路由在负载不超过平均 1.2 倍的实例里选命中最多的，命中率 96.8%、负载 1.12 倍。路由器可以自己维护近似的前缀树，也可以让实例上报缓存的块哈希；负载的衡量要考虑命中后实际要算多少。

算得更细时，路由比较的是预计的首 token 时间 max(Q, R) + C。8K 前缀的例子里，有缓存但排队 250 ms 的实例 281 ms 出首 token，空闲实例重算要 908 ms，从 200 GbE 的远端取回只要 138 ms；远端链路要追平本地命中，至少需要 6.30 GB/s。缓存预测有失误时，均值可能很好，p99 却由重算的慢路径决定。

从张量并行、专家并行、PD 分离到 KV 的流动和路由，这一篇反复出现同一个主题：卡与卡之间的通信越快，能做的事情越多。超节点把几十上百张卡放进同一个高带宽域，它对哪类推理负载的收益最大？下一讲：**超节点上的推理**。
