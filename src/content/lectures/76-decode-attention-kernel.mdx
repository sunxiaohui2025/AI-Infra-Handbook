上一讲的 FlashAttention 是为“很多查询”设计的：prefill 时有几千个查询，按每 128 个一块分给不同的计算单元，每个单元把自己那块查询留在片上，再依次读入 K、V。

decode 时情况完全不同。每个请求每一步只有 **1 个**新 token，也就只有 1 个查询；它要和 KV Cache 里所有的历史 token 做注意力。而第 67 讲以后，这些 KV 已经不是连续的一大段，而是按块散落在显存的各个角落，只有块表知道它们在哪。

这一讲讲 decode 阶段的注意力 kernel 要解决的两个问题：**怎么按块表读取分散的 KV**，以及**只有一个查询时，怎么让整块 GPU 都忙起来**。

## decode 的注意力在做什么

先看一个请求、一个头在 decode 一步时做的事（第 61 讲）：拿着这一步的查询 q，和上下文里每个 token 的 k 算打分，softmax，再对 v 加权求和。上下文有 n 个 token，就要把 n 个 k 和 n 个 v 全部从显存读一遍。

每读一个 k（d 个数），只和 q 做一次点积，算术强度非常低。第 39 讲的 GQA 稍微好一点：Llama-3-8B 的 32 个查询头分成 8 组，每组 4 个查询头共用一个 KV 头，读一次 k、v，可以给 4 个查询用。但算术强度也就是个位数，远低于 H100 的 295 FLOPs/字节。

所以 decode 的注意力**完全是带宽受限的**：耗时 ≈ 要读的 KV 字节数 ÷ 带宽。kernel 写得好不好，就看它能不能把显存带宽用满。

## 按块表读取

KV Cache 被切成了每块 B 个 token 的物理块（vLLM 默认 B = 16），一个请求的第 i 个 token 在哪里，由块表决定（第 67 讲）：

<div class="ai-formula">物理块 = 块表[i ÷ B]（取整），块内位置 = i mod B</div>

所以 decode 的注意力 kernel 要多做一件事：它的输入除了 q 和整个 KV Cache 池子，还有每个请求的**块表**和**上下文长度**。kernel 按逻辑块的顺序，一块一块地查块表，算出这一块在池子里的地址，把这一块的 B 个 k、v 读进片上，算打分，用第 75 讲的在线 softmax 更新 m、l、acc。读完最后一块（最后一块可能只用了一部分位置，要按上下文长度截断），输出 acc / l。

一个块里的 B 个 token 是连续存放的，所以只要 B 不太小，每次读的都是一段连续的内存，显存带宽仍然能用得很好。这就是第 67 讲说的“查表开销”：多读一个块表、多算一次地址，代价很小。

看一个缩小的例子：每块 4 个 token，一个请求的上下文有 18 个 token，块表是 [7, 2, 12, 5, 9]。下标为 13 的 token 在逻辑块 13 ÷ 4 = 3，查块表得到物理块 5，块内第 13 mod 4 = 1 个位置。最后一个逻辑块（物理块 9）只用了 2 个位置。

## 只有一个查询：GPU 闲着

现在看并行。GPU 有很多个计算单元（H100 有 132 个 SM），要让它们同时干活，就得把工作切成很多份。

decode 时，最自然的切法是：每个请求的每个 KV 头，交给一个工作单元（GQA 下，共用这个 KV 头的 4 个查询头一起算）。批大小是 b，就有 b × 8 个工作单元。

批大小 64 时，有 512 个工作单元，132 个 SM 都有活干。可是批大小是 1（比如一个长文档的单独请求）时，只有 **8 个**工作单元：132 个 SM 里只有 8 个在读数据，其余的全闲着。上下文越长，这 8 个单元要读的越多，越慢。

代码粗略地估算了一下（只有 u 个单元在搬数据时，带宽按 u / 132 打折）：Llama-3-8B 一层，批大小 1、上下文 32768 个 token，要读 128 MiB 的 KV，只有 8 个单元时约 **661 μs**；如果 132 个 SM 都在读，只要约 40 μs。

## 把上下文切开：Flash-Decoding

解决办法是**沿着上下文再切一刀**：把一个请求的上下文切成若干段，比如每 512 个 token 一段，每一段交给一个工作单元。32768 个 token 切成 64 段，8 个 KV 头就有 512 个工作单元，所有的 SM 都忙起来了。

每一段只看到了上下文的一部分，各自算出这一段的 (m, l, acc)。最后用一个很小的归约 kernel 把各段合并，用的就是第 75 讲在线 softmax 的同一个公式：取所有段的最大值 M，每段的 l 和 acc 乘 e^(m − M) 换算到同一个基准，再分别加起来，输出 acc / l。合并的结果和不切完全相同。

这个做法叫 **Flash-Decoding**（2023 年由 FlashAttention 的作者提出），也叫 split-K（因为切的是 K 的长度方向）。vLLM 早期的 PagedAttention V2 kernel 就是按 512 个 token 切段的。切段之后，批大小 1、上下文 32K 的估算耗时从约 661 μs 降到约 **40 μs**。

切段也有代价：每一段要多写出一组 (m, l, acc)，还要多一个归约的 kernel。批已经很大时，工作单元本来就够多，切段没有好处：批大小 64、上下文 4096 时，切不切都约 321 μs。所以实际的 kernel 会根据批大小和上下文长度，自动决定要不要切、切几段。

## 切开归约的代价：多读一遍，结果还会变

Flash-Decoding 的思路（并行度不够，就沿归约维切开，最后再合并）在 decode 里到处都有。注意力之外最常见的是 RMSNorm：先求一行的平方和，算出缩放因子，再缩放这一行。prefill 有 1024 行，一组算一行就有 1024 个并行任务；decode 只有一行，同样的分法只有 1 个任务，绝大部分 SM 闲着。

把每行切成 8 段，第一阶段的任务就多了 8 倍。代价有两样。

**多读一遍输入。**一组算一行时，输入留在片上，读一遍输入、一遍 gamma，写一遍输出，1024 行共 24 MiB，1 个 kernel。切成 8 段后，要先算局部平方和，再合并成缩放因子，最后归一化时**重新读一遍输入**，共约 32.1 MiB，kernel 也从 1 个变成 3 个。

**结果会变。**浮点加法不满足结合律：FP32 里算 1 + 2⁻²⁴ + 2⁻²⁴，先加前两项还是 1，再加第三项仍是 1；先加后两项得到 2⁻²³，再加 1 才是 1 + 2⁻²³。代码取一行 4096 个 BF16 随机数，它们的平方在 FP32 里都是精确的，所以差别只来自加法的先后。一组从头加到尾，累加器越来越大，每次加进去的小数的末位被反复舍掉，和精确值差约 111 个 ULP（unit in the last place，同一指数下相邻两个浮点数的间距）；切成 8 段，每个累加器只长到八分之一，误差降到约 9 个 ULP。段数不同，结果就不同。

合并的次序也有影响。固定 8 个局部和，40,320 种合并次序得到 4 个不同的 FP32 结果。如果用原子加把局部和加到同一个地址，到达的先后由调度决定，同一份输入跑两次可能得到不同的结果。改成先把局部和写进缓冲，全部写完后由一个线程按固定顺序相加，每次都一样，代价是多一次写出和读回，还要等最慢的一段。

这带来一个更隐蔽的问题：kernel 常常按 batch 大小选择段数（batch 大就一组一行，batch 小就切开），于是**同一个请求，在不同的 batch 里算出的结果不一样**。要让输出只由输入决定（batch invariance），段数和合并次序就不能随 batch 变化，代价是小 batch 时并行度退回到切开之前。强化学习里，生成端和训练端加载同一份权重，同一个前缀算出的概率却可能不同，原因之一就在这里。

## 到了大模型里

**各家的 decode 注意力 kernel。**vLLM 早期自己实现了 PagedAttention 的 kernel；现在的推理引擎更多地使用 FlashAttention（它的新版本支持块表）和 FlashInfer 这类专门的注意力库。FlashInfer 针对推理做了很多优化：支持任意的块大小（甚至每块 1 个 token，SGLang 的前缀树就用这种粒度），针对不同的批大小和长度自动选择切分方式，等等。

**prefill 和 decode 混在一步里。**连续批处理和分块 prefill（第 66、69 讲）让一步里既有 decode 请求（1 个查询），又有 prefill 的块（几百个查询）。注意力 kernel 要能同时处理这两种形状：有的实现分别调用两种 kernel，有的用一个统一的 kernel 按每个请求的查询数调整切分方式。

**MLA 不一样。**DeepSeek 的 MLA（第 40 讲）在 decode 时把所有查询头吸收到一个压缩的 KV 上，等于 128 个查询头共用一份 KV，算术强度高得多，需要专门的 kernel（比如 FlashMLA）。

**KV Cache 量化。**既然 decode 的注意力完全受带宽限制，把 KV Cache 存成 FP8（第 11 篇），要读的字节减半，注意力也就快了将近一倍。kernel 在读进片上以后再转回高精度计算。

## 用代码复现

下面的代码先在一个缩小的块池上实现按块表读取的 decode 注意力，和把 KV 拼成连续一段的标准算法对比；再把上下文切成 3 段分别计算、合并，和不切对比；最后按上面的粗略模型估算 Llama-3-8B 一层的工作单元数和耗时。

```python
import numpy as np
rng = np.random.default_rng(0)
B, d = 4, 8                                              # 每块 4 个 token，每个头 8 维（缩小的例子）

# 1. KV Cache 按块散落在池子里，按块表读取（PagedAttention）
k_pool, v_pool = rng.standard_normal((2, 16, B, d))      # 池子：16 个物理块
table, ctx = [7, 2, 12, 5, 9], 18                        # 这个请求的块表，上下文 18 个 token（最后一块只用了 2 个位置）
q = rng.standard_normal(d)

def paged_attention(q, table, ctx, parts=1):
    """decode：1 个查询。把上下文切成 parts 段（可以并行），每段算出 (m, l, acc)，最后合并。"""
    pieces = []
    for seg in np.array_split(np.arange(ctx), parts):
        blk = [table[i // B] for i in seg]; off = [i % B for i in seg]   # 第 i 个 token：物理块 table[i // B]，块内位置 i % B
        x = k_pool[blk, off] @ q / np.sqrt(d)
        m = x.max(); e = np.exp(x - m)
        pieces.append((m, e.sum(), e @ v_pool[blk, off]))
    M = max(p[0] for p in pieces)                        # 合并：和在线 softmax 一样，按 e^(m − M) 换算
    l = sum(p[1] * np.exp(p[0] - M) for p in pieces)
    acc = sum(p[2] * np.exp(p[0] - M) for p in pieces)
    return acc / l

K = np.concatenate([k_pool[b] for b in table])[:ctx]     # 对照：把 KV 拼成连续的一整段，按标准公式算
V = np.concatenate([v_pool[b] for b in table])[:ctx]
x = K @ q / np.sqrt(d); p = np.exp(x - x.max()); ref = (p / p.sum()) @ V
print("按块表读取 = 连续存放：", np.allclose(paged_attention(q, table, ctx), ref))
print("切成 3 段并行再合并 = 不切：", np.allclose(paged_attention(q, table, ctx, parts=3), ref))
print("下标为 13 的 token 在：物理块", table[13 // B], "的第", 13 % B, "个位置")

# 2. Llama-3-8B 一层的 decode 注意力：要读的 KV 字节数，和能同时开工的计算单元
SM, BW, KV_LAYER = 132, 3.35e12, 8 * 128 * 2 * 2         # H100 有 132 个 SM；每层每个 token 的 KV 是 4096 字节
print("批大小 | 上下文 | 要读的 KV | 工作单元（不切 / 每 512 个 token 切一段）| 估算耗时（不切 / 切）")
for b, ctx in [(1, 32768), (1, 4096), (64, 4096)]:
    nbytes = b * ctx * KV_LAYER
    units = [b * 8, b * 8 * (ctx // 512)]                # 每个请求的每个 KV 头至少是一个工作单元
    t = [nbytes / (BW * min(1, u / SM)) * 1e6 for u in units]   # 粗略：只有 u 个单元在搬数据时，带宽按 u / 132 打折
    print(f"{b:5d} | {ctx:6d} | {nbytes / 2**20:6.0f} MiB | {units[0]:5d} / {units[1]:5d} | {t[0]:6.0f} μs / {t[1]:4.0f} μs")
```

输出：

```text
按块表读取 = 连续存放： True
切成 3 段并行再合并 = 不切： True
下标为 13 的 token 在：物理块 5 的第 1 个位置
批大小 | 上下文 | 要读的 KV | 工作单元（不切 / 每 512 个 token 切一段）| 估算耗时（不切 / 切）
    1 |  32768 |    128 MiB |     8 /   512 |    661 μs /   40 μs
    1 |   4096 |     16 MiB |     8 /    64 |     83 μs /   10 μs
   64 |   4096 |   1024 MiB |   512 /  4096 |    321 μs /  321 μs
```

前两行说明：按块表读取和连续存放的结果相同，切成 3 段再合并和不切的结果也相同。第三行是块表的换算，和演示一致。表格是真实规模的估算：批大小 1、上下文 32768 时，不切段只有 8 个工作单元，约 661 μs，切段后 512 个单元，约 40 μs；批大小 64 时，切不切都约 321 μs。

这个模型非常粗略：实际上一个 SM 能做的不止“1/132 的带宽”，一个工作单元也可能用到多个 SM 的资源。但“工作单元太少，GPU 就闲着”这个结论是可靠的。

第二段代码复现“切开归约的代价”：切成 8 段后的读写量，不同段数下平方和与精确值的差距，以及 8 个局部和的全部合并次序能得到几个不同的结果。

```python
import numpy as np
# decode 只有一行：一组算一行时只有 1 个并行任务。RMSNorm 把一行切成几段，先求局部平方和再合并
rows, H = 1024, 4096
one = rows * H * 2 * 3                                   # 读输入、读 gamma、写输出（BF16）
split = one + rows * H * 2 + rows * 8 * 4 * 2 + rows * 4 * 2   # 多读一遍输入，局部和与缩放因子的写出读回
print(f"一组一行：{one/2**20:.0f} MiB，1 个 kernel；切 8 段：{split/2**20:.1f} MiB，3 个 kernel，任务数 {rows} → {rows*8}")

# 浮点加法不满足结合律：同一行 4096 个 BF16 的平方和，切成几段得到的结果不同
rng = np.random.default_rng(1)
x = (rng.standard_normal(H) * 0.7).astype(np.float32)
x = x.view(np.uint32) & 0xFFFF0000                       # 截成 BF16 能表示的值
x = x.view(np.float32)
sq = (x * x).astype(np.float32)                          # 平方在 FP32 里是精确的
exact = sum(float(v) for v in sq.astype(np.float64))
ulp = float(np.spacing(np.float32(exact)))
for parts in [1, 2, 4, 8, 16, 32]:
    acc = np.float32(0)
    locs = []
    for seg in np.split(sq, parts):
        a = np.float32(0)
        for v in seg: a = np.float32(a + v)              # 每段从头到尾依次累加
        locs.append(a)
    for v in locs: acc = np.float32(acc + v)
    print(f"切 {parts:>2} 段：与精确值相差 {(float(acc) - exact) / ulp:+7.1f} 个 ULP")

# 固定 8 个局部和，只改合并的次序（原子加的到达顺序由调度决定）
from itertools import permutations
locs8 = [np.float32(0)] * 8
for i, seg in enumerate(np.split(sq, 8)):
    a = np.float32(0)
    for v in seg: a = np.float32(a + v)
    locs8[i] = a
res = set()
for order in permutations(locs8):
    acc = np.float32(0)
    for v in order: acc = np.float32(acc + v)
    res.add(float(acc))
print(f"8 个局部和的 40320 种合并次序，得到 {len(res)} 个不同的 FP32 结果，最大相差 {(max(res)-min(res))/ulp:.0f} 个 ULP")
```

输出：

```text
一组一行：24 MiB，1 个 kernel；切 8 段：32.1 MiB，3 个 kernel，任务数 1024 → 8192
切  1 段：与精确值相差  -110.9 个 ULP
切  2 段：与精确值相差   -42.9 个 ULP
切  4 段：与精确值相差   -32.9 个 ULP
切  8 段：与精确值相差    -8.9 个 ULP
切 16 段：与精确值相差    -5.9 个 ULP
切 32 段：与精确值相差    +0.1 个 ULP
8 个局部和的 40320 种合并次序，得到 4 个不同的 FP32 结果，最大相差 3 个 ULP
```

对照正文：24 MiB 变成 32.1 MiB、1 个 kernel 变成 3 个；一组从头加到尾差约 111 个 ULP，切 8 段约 9 个；40,320 种次序得到 4 个不同的结果。

## 容易混淆的地方

1. **PagedAttention 首先是一种显存管理方式。**第 67 讲的分页是“KV 怎么存”，这一讲的 kernel 是“分页存的 KV 怎么读”。两者合在一起，才是 vLLM 论文里的 PagedAttention。
2. **Flash-Decoding 不是给 prefill 用的。**prefill 有很多查询，按查询切分就足够并行了；Flash-Decoding 解决的是查询太少时的并行度问题。
3. **切段合并不是近似。**合并用的是在线 softmax 的精确公式，结果和一次算完相同。

4. **切开归约不只影响速度。**多出来的并行任务要用多读一遍输入、多几个 kernel 来换；段数和合并次序还会改变浮点结果，让同一个请求在不同 batch 里算出不同的输出。

## 回顾

decode 时每个请求只有 1 个查询，要读完上下文里所有的 k、v，注意力完全受带宽限制。KV Cache 按块散落在显存里，kernel 按块表一块一块地读：第 i 个 token 在物理块 块表[i ÷ B] 的第 i mod B 个位置，块内连续，带宽仍能用好。按“请求 × KV 头”分工时，批小、上下文长的情况只有寥寥几个工作单元，大部分 SM 闲着；Flash-Decoding 沿上下文切段并行，最后按在线 softmax 的公式合并，批大小 1、上下文 32K 的一层从约 661 μs 降到约 40 μs。

沿归约维切开是 decode 增加并行度的通用手段，RMSNorm 也一样：切成 8 段让任务数多 8 倍，读写从 24 MiB 增到 32.1 MiB，kernel 从 1 个变成 3 个。浮点加法不满足结合律，段数和合并次序都会改变结果，要让结果与 batch 无关，就得固定段数和次序。
