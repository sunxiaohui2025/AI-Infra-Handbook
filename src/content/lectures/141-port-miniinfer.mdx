前七讲的原理，这一讲全部落到代码上。目标是把第 15 篇写的 miniinfer 搬到一块非 NVIDIA 的加速器上，真实运行、真实比对、真实计时。

本机没有国产卡，但有一块能用的非 CUDA 加速器：Apple M2 的 GPU，PyTorch 通过 MPS 后端支持它。它和一块国产 GPGPU 的处境相似——不是 CUDA，算子库不全，低精度支持有缺口，profiler 工具另一套。所以这一讲的流程、踩的坑和验收标准都可以照搬；只有最后调 kernel 那一步，各家的工具不同。

起点选 **v1**（KV Cache 版，第 119 讲）：它只有五个文件、160 行，prefill 和 decode 两条路径都有，足够暴露移植的问题，又不会被调度、分页这些东西干扰。

<Note kind="warn">能跑通 FP32 不等于能跑通别的精度。下面第四步就会看到 FP16 的翻车。移植的检查要按“每个精度各跑一遍”来做，而不是跑通一次就宣布完成。</Note>

对这次移植，三个结论：

**31 种算子，回退到 CPU 的 0 个**。这条最重要——它意味着后面量到的性能数字是真的在设备上跑出来的。如果这里不是 0，所有性能结论都要作废。

**一步 decode 要在设备上算 2221 次**。这个数字解释了第 138 讲的下发开销：两千多次调用，每次都要走分发、算形状、下发。

**MPS 缺 FP8 矩阵乘和 FlashAttention 内核**。对 miniinfer 的当前版本不影响（它用 `bmm` + `softmax` 手写注意力，用 FP32/FP16 权重），但如果要把第 123 讲的量化版或第 84 讲的 FlashAttention 搬过来，这就是缺口。

## 第五步：性能，以及一行代码值多少

现在量速度。同一个 199 token 的提示（和第 119 讲同一条），生成 64 个 token，分别计时 prefill 和每步 decode：

<RunOutput cmd=".venv/bin/python bench/port_speed.py" file="outputs/port_speed.txt" caption="图 141-6　CPU 与 MPS、三种精度下的 prefill 与 decode 耗时（本机 Apple M2，真实运行；每次计时前后都做了设备同步）。" />

逐行读这张表。

**CPU FP32 → MPS FP32：prefill 355 ms → 170 ms，decode 每步 65 ms → 56 ms**。prefill 快了一倍（它受算力限制，GPU 的算力更高），decode 只快 14%。decode 为什么没跟上？因为它受带宽限制（第 68 讲），而 M2 的 CPU 和 GPU **共用同一块内存**——统一内存架构下，换到 GPU 并不能换来更高的带宽。这个现象在独立显卡上不会出现，但它恰好演示了一件事：**decode 的速度由带宽决定，不由谁在算决定**。

**v1 原样搬到 MPS → port 版：decode 每步 56 ms → 49 ms，快了 13%**。两个版本的数学完全一样，差别只有 `model.py` 里那一行：v1 写 `end = int(pos[-1]) + 1`，port 版把 `end` 作为参数传进来。表最后两行解释了这 7 ms：MPS 上下发一个很小的加法平均 5.2 μs，而把一个数从设备拷回 CPU（`int(tensor)`）平均 139.9 μs——相差 27 倍。28 层每层一次，就是 28 × 140 μs ≈ 3.9 ms；再加上它每次都打断设备上正在排队的 kernel 流水，实际代价更大。

<Note kind="point">这是移植性能问题的典型形状：**不是哪个 kernel 慢，而是 CPU 和设备之间的同步太频繁**。这类问题改起来几乎没有成本（把一个数从外面传进来），收益却是百分之十几。调优时先找这类同步点（`int(tensor)`、`.item()`、`tensor.cpu()`、`if tensor > 0`、打印张量），再去看 kernel，顺序和第 142 讲一致。</Note>

**FP32 → FP16：decode 每步 49.3 ms → 32.9 ms，快 1.5 倍**。理论上应该快 2 倍：decode 一步要读 596 M 个参数的权重（脚本第一行算出来的），FP32 是 2.38 GB，FP16 是 1.19 GB，字节减半。实际只有 1.5 倍，差的那部分是下发开销和没跑满的带宽——按这两个数算，FP32 下达到的有效带宽是 2.38 GB ÷ 49.3 ms ≈ 48 GB/s，FP16 是 1.19 GB ÷ 32.9 ms ≈ 36 GB/s。精度越低，要读的字节越少，固定开销的占比就越高，所以效率反而下降。这是第 67 讲“实测与理论的差距”在一块新硬件上的具体体现。

**BF16 的 prefill 比 FP16 慢**（196 ms 对 128 ms），decode 却一样快（33 ms）。prefill 受算力限制，这个差别说明 MPS 上 BF16 的矩阵乘走的路径不如 FP16 高效；decode 受带宽限制，两者字节数相同，所以没差别。**同样是 16 位，在同一块卡上也可能不等价**——选精度时要实测，不能只看位数。

**CPU BF16 的 prefill 是 3665 ms，比 CPU FP32 慢 10 倍**。这是全表最反直觉的一行。原因是本机 CPU 没有原生的 BF16 矩阵乘指令，PyTorch 只能把 BF16 转成 FP32 再算，每次矩阵乘都多两次类型转换。**低精度在没有原生支持的硬件上会变慢，而不是变快**——第 145 讲会把这件事展开讲，它也是适配国产卡时最常见的误判之一。

## 还差什么

到这里，一个能跑、跑对、知道瓶颈在哪的移植版完成了。离“能上线”还差这些，每一项对应后面的讲：

| 还缺什么 | 为什么现在没做 | 对应的讲 |
| --- | --- | --- |
| 分页 KV、连续批处理、调度 | 这些是引擎层的逻辑，和硬件无关，v3 已经有了，直接套上来即可 | 121、122 |
| 融合算子（RMSNorm、RoPE、SwiGLU） | 现在每个都是几个基础算子拼出来的，一步多上千次下发 | 83、144 |
| FlashAttention 类的注意力 | MPS 缺这个内核；长上下文下现在的写法会让注意力矩阵落地 | 84、143 |
| 图模式 / 图捕获 | 去掉同步点之后整个前向已经能编成一张图（第 138 讲量过：3319 个节点、0 处中断），但还没接后端 | 138 |
| 量化 | MPS 缺 FP8 矩阵乘；INT8 有 `_int_mm`，可以试 | 145 |
| 多卡 | 本机只有一块 GPU，通信这一层完全没碰 | 146 |
| profiler 下的逐 kernel 分析 | 下一讲的主题 | 142 |

在一块真实的国产卡上，这张表还要多两行：**厂商的算子库接进来**（矩阵乘换成厂商的库，注意力换成厂商移植的 FlashAttention），以及**引擎插件**（把这些选择告诉 vLLM 这样的引擎，而不是只在自己的小引擎里用，第 147 讲）。

<Note kind="column">这次移植的全部改动：新增 `port/device.py`（31 行），`engine.py` 改 4 处，`model.py` 改 3 处。总共不到 50 行——和第 134 讲那个“4.4%”的统计是一致的。但要注意这个数字的前提：miniinfer 本来就只用基础算子，没有 CUDA 专有库、没有自写 kernel、没有通信。真实引擎的那 4.4% 里，每一行背后都是一个库。</Note>

## 回顾

一次完整的移植，顺序是：把设备收进一个模块（顺手把同步和精度探测也包进去）→ 跑通并和参考答案逐 token 比对 → 盘点算子确认没有东西回退到 CPU → 逐个精度跑逐层比对（FP16 在 RMSNorm 上溢出，升到 FP32 解决）→ 量性能并先解决同步点。本机的实测给出了几个可以带走的结论：decode 的速度由带宽决定，统一内存下换到 GPU 也快不了多少；一行 `int(pos[-1])` 值 13% 的 decode 吞吐；FP16 只快 1.5 倍而不是 2 倍，因为固定开销占比上升；CPU 上的 BF16 比 FP32 慢 10 倍，因为没有原生支持。

第 18 篇到此结束——模型跑通了、跑对了。第 19 篇开始讲怎么跑快。第一个问题是：在一块没有 Nsight 的卡上，怎么知道时间花在哪里？
