第 26 讲的注意力，写成公式只有一行：O = softmax(QKᵀ / √d) V。照着公式一步步算，要先得到打分矩阵 S = QKᵀ / √d，它的形状是 s × s：序列有多少个 token，它就有多少行、多少列。序列长 8192 时，一个头的 S 就有 6700 多万个数，BF16 下 128 MiB；32 个头就是 4 GiB，这还只是一层、一个请求。

更要命的是读写。上一讲说过，两个 kernel 之间只能经过显存交换数据。缩放、加掩码、softmax、乘 V，每一步都要把这个 s × s 的大矩阵从显存读进来、再写回去。注意力的乘加次数并不少，可时间主要花在了搬运这个中间矩阵上。

2022 年的 **FlashAttention** 把整个注意力融合成一个 kernel，S 从头到尾不写进显存。难点在于 softmax：要算出每个位置的权重，得先知道整行的最大值和总和，看上去必须先把整行打分都算出来。这一讲讲它是怎么绕过这个难点的。

## 标准实现在搬什么

把一个头的注意力按 PyTorch 的写法逐个算子执行：

1. S = Q Kᵀ：读 Q、K，**写 S**（s × s）。
2. S = S / √d：**读 S，写 S**。
3. 加因果掩码（第 27 讲）：**读 S，写 S**。
4. P = softmax(S)：**读 S，写 P**。
5. O = P V：**读 P**、V，写 O。

s × s 的矩阵被读写了 8 遍。代码按 s = 8192、d = 128 算了一下：标准实现一共读写约 **1082 MB**，按 3.35 TB/s 要约 **323 μs**；而这个头真正的计算量（QKᵀ 和 PV 两次矩阵乘法）在 H100 上只要约 **35 μs**。注意力被显存带宽卡住了，计算单元九成的时间在等数据。序列越长越糟：S 的大小和读写量都随 s² 增长。

这正是上一讲说的融合的用武之地：如果能把这 5 步放进一个 kernel，S 只在片上出现，读写就只剩 Q、K、V、O 这几个 s × d 的矩阵。

## 难点：softmax 要先看完整行

融合的思路是**分块**：片上存储只有几百 KB，放不下整个 S，那就一次算 S 的一小块。比如一次取 128 个查询（Q 的一块）和 128 个键（K、V 的一块），算出 S 的一个 128 × 128 的块，用完就扔，再算下一块。

麻烦在 softmax。对一行打分 x₁, …, xₙ，softmax 是

<div class="ai-formula">pᵢ = e^(xᵢ − m) / l，　m = max(x₁, …, xₙ)，　l = Σⱼ e^(xⱼ − m)</div>

（减去最大值 m 是为了数值稳定，第 26 讲。）m 和 l 都要看完整行才知道。如果一块一块地读，读到第一块时，还不知道后面有没有更大的打分，也不知道总和是多少，好像没法算出权重。

## 在线 softmax：先算着，再修正

办法是：**先按目前看到的最大值算，等看到更大的值时，把之前的结果按比例修正**。对一个查询，一边读一边维护三个数：

- m：到目前为止见过的最大打分；
- l：到目前为止的 Σ e^(xⱼ − m)；
- acc：到目前为止的 Σ e^(xⱼ − m) · vⱼ（未归一化的加权和）。

读进新的一块时，先算出新的最大值 m_新 = max(m, 这一块的最大值)。之前累计的 l 和 acc 都是相对旧的 m 算的，要换算成相对新的 m，只需要乘一个系数 e^(m − m_新)，因为 e^(x − m) · e^(m − m_新) = e^(x − m_新)。然后再加上这一块的贡献：

<div class="ai-formula">l ← l · e^(m − m_新) + Σ e^(x − m_新)，　acc ← acc · e^(m − m_新) + Σ e^(x − m_新) · v，　m ← m_新</div>

所有块都读完以后，输出就是 acc / l。这个结果和先算完整行 softmax、再加权求和**完全相同**，不是近似。

用代码里的数字走一遍。一个查询、8 个键，打分是 1.2, −0.5, 2.1, 0.4, 2.2, −1.0, 0.8, 3.4，对应的 v（为了好看，只取 1 维）是 0.5, −1.0, 2.0, 1.5, −0.5, 1.0, 0.0, 3.0。每块 4 个：

- **读第 1 块**：最大值 m = 2.10，l = 1.6635，acc = 2.4030。如果到此为止，输出是 acc / l = 1.4445。
- **读第 2 块**：这一块里有 3.4，比 2.10 大。旧的 l、acc 先乘 e^(2.10 − 3.40) = 0.2725 缩小，再加上第 2 块的贡献，得到 l = 1.8411，acc = 3.5166，输出 acc / l = **1.9100**。
- **一次算完整行**：softmax 再加权，也是 **1.9100**。

## 省了多少

把整个流程连起来：对 Q 的每一块，把它留在片上，依次读入 K、V 的每一块，算 S 的一块、更新这块查询的 m、l、acc；看完所有的键，算 acc / l，把这块查询的输出写回显存一次。

读写量变成：Q 读一遍，O 写一遍，K、V 对每一块查询都要读一遍。代码的估算（s = 8192、d = 128，每块 128 个查询）：

- **标准实现**：约 1082 MB，约 323 μs。
- **FlashAttention**：约 277 MB，约 83 μs，是原来的四分之一。

这还是最坏的估算：同一个头的 K、V 会被好几个查询块先后读取，其中很多次能命中 GPU 的 L2 缓存（H100 有 50 MB），真正从显存读的更少。实际上，FlashAttention 在长序列上能把 GPU 的计算单元用到相当高的比例：FlashAttention-2 的论文报告，在 A100 上达到理论峰值算力的 50% 到 73%。注意力从“卡在带宽”变回了“卡在算力”。

另一个收益是**显存**。S 不再需要存下来，注意力额外占用的显存从 s² 级别降到了 s 级别（每个查询只多存 m 和 l 两个数）。s = 32768 时，一个头的 S 就有 2 GiB，标准实现根本放不下几个请求；有了 FlashAttention，长上下文才变得可行。

## 块切多大：少读数据，还是少做更新

上面按“每块 128 个查询”估算。块到底切多大，要由片上能放多少东西决定。拿一个线程块的共享内存做快速缓冲（RTX PRO 6000 一个线程块最多 99 KB，即 101,376 字节）：一次留 a 行 Q 和它们的 FP32 输出累加器，K 和 V 轮流用同一个 b 行的输入槽，分数和概率共用一个 a × b 的槽，再给每行的 m、l 和临时值留三个 FP32：

<div class="ai-formula">2ad（Q）+ 2bd（K/V 槽）+ 4ab（分数/概率）+ 4ad（输出累加器）+ 12a（逐行状态）≤ 101,376 字节</div>

Q 分成 ⌈8192 ÷ a⌉ 块，每一块都要把整份 K、V（4 MiB）扫一遍。所以 a 越大，K、V 被重读的次数越少。而 b 越小，K/V 槽和分数块越小，能放的 a 就越大：

| K/V 块 b | 能放的 Q 行 a | K/V 扫描次数 | 读写量 | 在线更新次数 |
| --- | --- | --- | --- | --- |
| 1 | 128 | 64 | 260 MiB | 524,288 |
| 64 | 82 | 100 | 404 MiB | 12,800 |
| 128 | 53 | 155 | 624 MiB | 9920 |

从 b = 64 缩到 b = 1，少读 144 MiB，可在线更新从 12,800 次涨到 524,288 次，约 41 倍。每次更新都要比较最大值、算指数、缩放累加器；每次只处理 1 行 K/V，矩阵乘的一个维度只有 1，矩阵单元根本用不上。反过来，b 太大，能放的 Q 行少，K/V 要多读几遍。所以实际的 kernel 一般取 64 或 128，在这两种开销之间折中。不管哪一种，都远小于标准实现把 S、P 写出再读回的 1 GiB。

## 实测：快 33 倍，显存少 800 多 MiB

在 RTX PRO 6000 Blackwell 上，用 PyTorch 同一个注意力接口的两个后端对比：数学后端（`SDPBackend.MATH`）按公式组合矩阵乘和 softmax，保存完整的分数和概率；FlashAttention 后端（`SDPBackend.FLASH_ATTENTION`）分块、在线 softmax。BF16，一个序列、一个头、头维度 128，序列 8192，因果注意力。每次注意力计算，数学后端约 **2.6 ms**，FlashAttention 约 **80 μs**，快约 33 倍。新增的显存峰值（输出加临时工作区）从约 **848 MiB** 降到约 **22 MiB**。

这比上面只按读写量估算的加速大得多，因为数学后端除了搬中间矩阵，还要多发好几个 kernel、做一次完整的 softmax 归约，而 FlashAttention 把这些都放进了一个 kernel。三件事配合在一起：分块让当前数据放得进快速存储，在线 softmax 让归约可以逐块完成，融合省掉了块内中间结果的写回。

## 训练时还多一件事：重算

训练要做反向传播（第 18 讲），反向时要用到前向的 softmax 结果 P。标准实现把 P 存下来，又是 s² 的显存。FlashAttention 不存 P，只存每个查询的 m 和 l；反向时，按块重新算一遍 S 和 P。多做了一些计算，却省下了大量的读写和显存，整体反而更快。这是“用计算换访存”的又一个例子。

推理只有前向，没有这个问题。

## 后来的版本

**FlashAttention-2**（2023）调整了循环的顺序和并行方式：外层按查询块分给不同的计算单元并行，减少了非矩阵乘法的运算（比如把除以 l 推迟到最后），进一步提高了算力利用率。

**FlashAttention-3**（2024）针对 H100 的新硬件特性：用专门的数据搬运单元（TMA）异步地把下一块 K、V 搬进片上，同时计算当前块；让矩阵乘法和 softmax 交替进行，互相掩盖；支持 FP8。

**推理里的变体。**prefill 时查询很多，正好是 FlashAttention 擅长的形状。decode 时每个请求只有 1 个查询，KV Cache 又分散在各个块里（第 67 讲），需要不同的切分方式，这是下一讲的内容。今天的推理引擎通常用 FlashAttention 或 FlashInfer 等库提供的注意力 kernel，它们都基于同样的分块和在线 softmax。

## 用代码复现

下面的代码先用在线 softmax 一块一块地处理上面那 8 个打分，和一次算完的结果对比；再用 NumPy 写一个分块的注意力，和标准实现对比；最后按 d = 128 估算不同序列长度下两种实现的读写量和时间。

```python
import numpy as np

# 1. 在线 softmax：一个查询、8 个键，分成两块，每块 4 个，一块一块地算
x = np.array([1.2, -0.5, 2.1, 0.4, 2.2, -1.0, 0.8, 3.4])     # 打分 q·k / √d
v = np.array([0.5, -1.0, 2.0, 1.5, -0.5, 1.0, 0.0, 3.0])     # 每个位置的 v（取 1 维，方便看）
m, l, acc = -np.inf, 0.0, 0.0                                # 目前的最大值、指数和、加权和
for j in range(0, 8, 4):
    xb, vb = x[j:j + 4], v[j:j + 4]
    m_new = max(m, xb.max())
    scale = np.exp(m - m_new)                                # 最大值变了，旧的累计值要按比例缩小
    l = l * scale + np.exp(xb - m_new).sum()
    acc = acc * scale + (np.exp(xb - m_new) * vb).sum()
    m = m_new
    print(f"读完第 {j // 4 + 1} 块：旧值缩放 ×{scale:.4f}，m = {m:.2f}，l = {l:.4f}，acc = {acc:.4f}，当前输出 acc / l = {acc / l:.4f}")
p = np.exp(x - x.max()) / np.exp(x - x.max()).sum()
print(f"一次算完整行 softmax 再加权：{p @ v:.4f}")

# 2. 分块的注意力（FlashAttention 的思路）和标准实现结果一致
def attention(Q, K, V):
    S = Q @ K.T / np.sqrt(Q.shape[1]); P = np.exp(S - S.max(1, keepdims=True))
    return (P / P.sum(1, keepdims=True)) @ V
def flash(Q, K, V, Br=64, Bc=64):
    s, dd = Q.shape; O = np.zeros_like(Q)
    for i in range(0, s, Br):                                # 外层：一块查询（留在片上）
        q = Q[i:i + Br]; m = np.full(len(q), -np.inf); l = np.zeros(len(q)); acc = np.zeros_like(q)
        for j in range(0, s, Bc):                            # 内层：一块一块地读 K、V
            sb = q @ K[j:j + Bc].T / np.sqrt(dd)
            m_new = np.maximum(m, sb.max(1)); sc = np.exp(m - m_new); pb = np.exp(sb - m_new[:, None])
            l = l * sc + pb.sum(1); acc = acc * sc[:, None] + pb @ V[j:j + Bc]; m = m_new
        O[i:i + Br] = acc / l[:, None]                       # 整行看完，才除以 l，写回一次
    return O
rng = np.random.default_rng(0)
Q, K, V = rng.standard_normal((3, 256, 64))
print("分块计算与标准实现一致：", np.allclose(attention(Q, K, V), flash(Q, K, V)))

# 3. 一个头、序列长 s、d = 128（BF16）时，读写显存的字节数（不考虑因果掩码省下的一半）
d, Br, F, BW = 128, 128, 989e12, 3.35e12
print("序列长 s | 打分矩阵 S | 读写：标准实现 / FlashAttention | 读写时间：标准 / Flash | 计算时间")
for s in [2048, 8192, 32768]:
    qkvo = 4 * s * d * 2
    std = qkvo + 8 * s * s * 2           # S 写出；缩放、掩码、softmax 各读一遍写一遍；乘 V 时读 P
    fl = qkvo + 2 * s * d * 2 * (s // Br)  # Q、O 各一遍；K、V 每块查询都要读一遍
    print(f"{s:7d} | {s * s * 2 / 2**20:5.0f} MiB | {std / 1e6:6.0f} MB / {fl / 1e6:5.0f} MB | {std / BW * 1e6:5.0f} μs / {fl / BW * 1e6:4.0f} μs | {4 * s * s * d / F * 1e6:4.0f} μs")
```

输出：

```text
读完第 1 块：旧值缩放 ×0.0000，m = 2.10，l = 1.6635，acc = 2.4030，当前输出 acc / l = 1.4445
读完第 2 块：旧值缩放 ×0.2725，m = 3.40，l = 1.8411，acc = 3.5166，当前输出 acc / l = 1.9100
一次算完整行 softmax 再加权：1.9100
分块计算与标准实现一致： True
序列长 s | 打分矩阵 S | 读写：标准实现 / FlashAttention | 读写时间：标准 / Flash | 计算时间
   2048 |     8 MiB |     69 MB /    19 MB |    21 μs /    6 μs |    2 μs
   8192 |   128 MiB |   1082 MB /   277 MB |   323 μs /   83 μs |   35 μs
  32768 |  2048 MiB |  17213 MB /  4329 MB |  5138 μs / 1292 μs |  556 μs
```

前三行是在线 softmax：第 2 块出现了更大的打分 3.4，旧值乘 0.2725 修正（第 1 块之前没有旧值，所以系数是 0），最终 1.9100 和一次算完相同。第四行说明分块计算的注意力与标准实现一致。表格是一个头的读写量：s = 8192 时，S 有 128 MiB，标准实现读写 1082 MB、约 323 μs，FlashAttention 约 277 MB、83 μs，计算本身只要 35 μs。

第二段代码复现块大小的取舍：标准实现中间矩阵的读写量，以及三种 K/V 块大小下能放的 Q 行数、扫描次数、读写量和在线更新次数。

```python
# 一个头，序列 8192、头维度 128：标准实现要把 FP32 的 S、P 各写一次、读一次
L, d = 8192, 128
qkvo = 4 * L * d * 2
sp = 2 * 2 * L * L * 4
print(f"Q、K、V、O 共 {qkvo/2**20:.0f} MiB；S、P 写出并读回 {sp/2**30:.0f} GiB")

# 分块：一个线程块的共享内存放 a 行 Q、一个 b 行的 K/V 槽、a×b 的分数块、FP32 输出累加器和逐行状态
CAP = 101376                                        # RTX PRO 6000 一个线程块可用 99 KB
def rows(b):                                        # 容量允许的最多 Q 行数 a
    a = 0
    while 2*(a+1)*d + 2*b*d + 4*(a+1)*b + 4*(a+1)*d + 12*(a+1) <= CAP: a += 1
    return a
for b in [1, 64, 128]:
    a = rows(b)
    scans = -(-L // a)                              # Q 分成几块，每块都要把整份 K/V 扫一遍
    traffic = scans * 2 * L * d * 2 + 2 * L * d * 2 # 每次扫描读 K、V，另加读一次 Q、写一次 O
    updates = scans * (L // b)                      # 每个 Q 块和每个 K/V 块之间做一次在线更新
    print(f"K/V 块 {b:>3} 行：Q 块 {a:>3} 行，扫描 {scans:>3} 次，读写 {traffic/2**20:4.0f} MiB，在线更新 {updates:>6} 次")
```

输出：

```text
Q、K、V、O 共 8 MiB；S、P 写出并读回 1 GiB
K/V 块   1 行：Q 块 128 行，扫描  64 次，读写  260 MiB，在线更新 524288 次
K/V 块  64 行：Q 块  82 行，扫描 100 次，读写  404 MiB，在线更新  12800 次
K/V 块 128 行：Q 块  53 行，扫描 155 次，读写  624 MiB，在线更新   9920 次
```

对照正文：S、P 写出再读回 1 GiB；b = 1、64、128 时分别是 260、404、624 MiB，在线更新 524,288、12,800、9920 次。

## 容易混淆的地方

1. **FlashAttention 不是近似。**它和标准实现在数学上完全等价，结果只有浮点舍入上的微小差别。那些为了省计算而改变注意力定义的方法（滑动窗口、线性注意力，第 42、44 讲）是另一回事。
2. **它没有减少计算量。**乘加的次数和标准实现一样（训练时还因为重算多了一些），省的是显存读写和显存占用。
3. **复杂度仍然是 s²。**计算量仍随序列长度平方增长，FlashAttention 只是让这个 s² 的计算跑在算力的上限附近，而不是被带宽拖住。

4. **块越小不等于越好。**K/V 块切小，能放下更多 Q 行，K/V 重读得少；但在线更新的次数暴涨，矩阵单元也用不满。块大小要在读写量和更新次数之间折中。

## 回顾

标准的注意力要在显存里写出 s × s 的打分矩阵，缩放、掩码、softmax、乘 V 各读写一遍，s = 8192 时一个头就要读写约 1082 MB，计算单元大部分时间在等数据，长序列还放不下。FlashAttention 把注意力切块、融合成一个 kernel：一块查询留在片上，依次读入 K、V 的块，算 S 的一块就用掉。softmax 用在线的方式计算，维护 m、l、acc，最大值变大时把旧值乘 e^(m_旧 − m_新) 修正，结果与标准实现完全相同。读写降到约四分之一，显存占用从 s² 降到 s 级别，注意力重新变成计算受限。

块的大小由片上容量决定：99 KB 的共享内存下，K/V 块取 64 行能放 82 行 Q，读写 404 MiB、在线更新 12,800 次；取 1 行读得最少（260 MiB），更新却多 41 倍。实测在 8192 的因果注意力上，FlashAttention 比保存完整中间矩阵的实现快约 33 倍，新增显存从约 848 MiB 降到约 22 MiB。

prefill 时有很多查询，可以按查询分块并行。decode 时每个请求只有 1 个查询，KV Cache 又按块散落在显存各处，FlashAttention 的切分方式就不合适了。decode 阶段的注意力 kernel 该怎么写？下一讲：**Decode 阶段的注意力 Kernel**。
