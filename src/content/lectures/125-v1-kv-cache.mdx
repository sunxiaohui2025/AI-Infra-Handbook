v0 每生成一个 token，都把整段序列从头算一遍。199 个 token 的提示生成 64 个 token，第 1 步 419 ms，第 64 步 724 ms，一共 34 秒；其中绝大部分计算是在重复上一步已经做过的事。

第 69 讲给出了解决办法：每层把算过的 K、V 存起来，新 token 只需要算自己的 q、k、v，再和存好的 K、V 做注意力。这一讲把它写进 miniinfer。改动不大：新增一个 18 行的 `kv_cache.py`，模型的注意力多两行，生成循环分出 prefill 和 decode 两种调用。

## 为什么只存 K 和 V 就够了

先确认一件事：新 token 的计算到底依赖前面 token 的哪些东西？

沿着一层 Transformer 看。RMSNorm、q/k/v 投影、RoPE、SwiGLU 都是**逐位置**的：位置 p 的输出只依赖位置 p 的输入。只有注意力会跨位置：位置 p 的查询 q_p 要和所有 ≤ p 位置的键 k_j 做点积，再对值 v_j 加权求和。而这些 k_j、v_j 一旦算出来就不会再变（因果掩码保证了后面的 token 不影响前面的计算）。

所以，位置 p 的新 token 需要的“历史”，恰好就是每一层前面所有位置的 K 和 V。把它们存下来，新 token 走完 28 层，每层只多读一次缓存。这就是 KV Cache，第 69 讲的推导这里不再重复。

## 数据结构：一块按最大长度分好的连续内存

最简单的存法：每个请求一开始就按“提示长度 + 最多生成多少个”分配好一整块，形状是 [层数, 最大长度, KV 头数, 头维度]，K、V 各一份。生成时往里写，用到哪里读到哪里。

## 模型：注意力多两行

## 先验证，再测速度

<RunOutput cmd=".venv/bin/python tests/check.py v1" file="outputs/check_v1.txt" caption="图 125-4　v1 和 HuggingFace 逐 token 一致：缓存的读写、位置、掩码都对了。" />

再用和 v0 一样的设置比一比：199 个 token 的提示，生成 64 个，记录每一步 forward 的耗时。

<RunOutput cmd=".venv/bin/python bench/v0_vs_v1.py" file="outputs/bench_v0_v1.txt" caption="图 125-5　v0 每步都在重算，第 64 步比第 1 步慢了七成；v1 只有第 1 步（prefill）慢，之后每步约 65 ms，64 步共 4.55 s，是 v0 的 7.5 分之一。" />

逐项看这组数：

- **第 1 步两者差不多**（419 ms 与 357 ms）：都是把 199 个 token 完整算一遍。v1 稍快，因为输出层只算了最后一行。
- **第 2 步起分道扬镳**：v0 还要算 200 个 token，417 ms；v1 只算 1 个 token，63 ms。
- **v1 的 decode 每步几乎不变**（63 → 66 ms）：每步的计算量只和 1 个 token 有关，注意力多读的 K、V 从 200 个涨到 263 个，在 CPU 上只占很小一部分。
- **v0 越来越慢**：第 64 步要算 263 个 token，724 ms。

一个 token 的 decode 要 63 ms，而 199 个 token 的 prefill 只要 357 ms，也就是每个 token 不到 2 ms。为什么 decode 一个 token 这么“贵”？因为无论算 1 个还是 199 个 token，每一步都要把全部权重（FP32 约 3 GB）从内存读一遍；token 越少，读一遍权重摊到每个 token 上的代价越大。这就是第 70 讲说的：decode 是读内存受限的。

<Note kind="point">KV Cache 把“每步重算整段”变成“每步只算一个新 token”：v1 生成 64 个 token 从 34 s 降到 4.55 s。改动集中在注意力的两行（先写缓存，再读全部）和位置（从 start 开始）。剩下的问题是，decode 每一步都要把全部权重读一遍，却只为一个 token 服务。</Note>

## 回顾

v1 给每个请求按“提示 + 最大输出”分配一块连续的 KV Cache（FP32 下每个 token 224 KiB），注意力里先把新 token 的 K、V 写进去，再读出全部历史；生成循环分成一次 prefill 和之后每步一个 token 的 decode。和 HuggingFace 仍然逐 token 一致，64 个 token 从 34 s 降到 4.55 s，decode 每步稳定在 65 ms 左右。

可这 65 ms 里，绝大部分时间花在把 3 GB 权重读一遍，只为一个请求算出一个 token。如果同时有 8 个请求，能不能让它们共用这一遍读取？下一讲：**Continuous Batching**。
