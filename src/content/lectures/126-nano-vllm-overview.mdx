第 15 篇的 miniinfer 是为了讲清楚而写的：只用 torch 的基本运算，在 CPU 上逐 token 对得上 HuggingFace。它和真正能用的引擎差在哪里，第 125 讲列了一张表。这一篇换个方向：读一个**真实可用、又小到能一口气读完**的开源引擎，看它怎么把那张表上的几项补上。

我们读的是 [nano-vllm](https://github.com/GeeeekExplorer/nano-vllm)（作者 Xingkai Yu，MIT 许可）。它用约 1200 行 Python 实现了 vLLM 的核心：分页 KV、前缀缓存、continuous batching、分块 prefill、CUDA Graph、张量并行，接口也和 vLLM 一样。按它 README 里的测试（RTX 4070 笔记本 GPU，Qwen3-0.6B，256 个请求，输入、输出长度各在 100–1024 之间随机），vLLM 是 1361.84 token/s，nano-vllm 是 1434.13 token/s。这组数字是作者测的，本站没有复现。

这一讲读调度一侧：请求怎么进来、调度器每一步挑谁、块管理器怎么分块和做前缀缓存。这些全是普通的 Python 代码，和 miniinfer 的 v2、v3 一一对应。下一讲读执行一侧：模型怎么在 GPU 上跑、FlashAttention 和 CUDA Graph 怎么接进来、张量并行怎么切。

<Note kind="warn">nano-vllm 依赖 NVIDIA GPU（flash-attn、Triton、NCCL）。本站的机器没有 GPU，这一篇**只读源码，没有运行它**；文中的行数统计只读源码文本。读的是 2026 年 4 月 26 日的提交 `bb823b3`，之后的版本行号可能不同。</Note>

## 全局：三块，两个进程边界

<NanoArch view="cpu" caption="图 126-1　nano-vllm 的架构。左边的引擎在主进程里，跑调度；中间的执行器每张卡一个，拼输入、跑模型、采样；右边是模型。强调色是这一讲读的部分。点模块可以看它在哪个文件、对应 miniinfer 的什么。" />

和 miniinfer 比，最大的结构差别是**调度和执行分开了**。miniinfer 的 `engine.step()` 一个函数里既问调度器、又拼 batch、又跑模型；nano-vllm 把它拆成三段：

1. **调度器**（`Scheduler`）只决定这一步跑哪些请求、每个请求算几个 token，顺带管块。它只碰 Python 对象，不碰张量。
2. **执行器**（`ModelRunner`）拿到这份名单，把它变成 GPU 上的张量（token、位置、写 KV 的槽位、块表），跑模型，采样，返回每个请求的新 token。
3. **引擎**（`LLMEngine`）把两者串起来，再把新 token 交回调度器更新状态。

拆开的原因是张量并行：有 N 张卡时，执行器有 N 份，每张卡一个进程；调度只需要一份，放在主进程里。调度器做完决定，rank 0 的执行器把“要跑哪些请求”广播给其余的执行器，大家一起算同一步。第 127 讲会看到这条广播是怎么做的。

```text

├── llm.py, config.py, sampling_params.py   入口和配置
├── engine/
│   ├── llm_engine.py      引擎：generate() 和 step()
```

## 调度器：scheduler.py

nano-vllm 的调度规则可以概括成一句话：**能 prefill 就只 prefill，没有可 prefill 的才 decode**。一步要么全是 prefill，要么全是 decode，不混在一起。

这和 miniinfer 不同。miniinfer 从 v2 起，每一步先让运行中的请求各 decode 一个 token，再用剩下的预算放新请求进来 prefill，两种混在同一步（第 120 讲）。两种做法的取舍：

| | miniinfer：混在一步 | nano-vllm：prefill 优先，分开跑 |
| --- | --- | --- |
| 新请求的首 token | 要和 decode 分预算 | 最快：有空间就立刻 prefill |
| 正在生成的请求 | 每一步都前进 | 有新请求进来的那一步，全部停一下 |
| 一步的形状 | 长短混杂 | 整齐：要么全是长段，要么每个请求一个 token |
| 对执行一侧的要求 | 注意力要同时处理两种 | prefill 和 decode 各用一个专门的 kernel；decode 可以录成 CUDA Graph |

最后一行是 nano-vllm 这样选的主要原因：decode 步的形状非常规整（每个请求正好一个 token），才能用 CUDA Graph 预先录好（第 127 讲）。vLLM V1 走的是另一条路：把 prefill 和 decode 统一成“每个请求这一步算几个 token”，混在同一步里，靠一个能处理变长查询的注意力 kernel 兼顾两者（第 77 讲的分块 prefill，第 129 讲）。

| | miniinfer v3+ | nano-vllm |
| --- | --- | --- |
| 块大小 | 16 | 256（flash-attn 分页 KV 的要求，第 127 讲） |
| 一步里 | decode 和 prefill 混在一起 | 只 prefill 或只 decode |
| 分块 prefill | 没有 | 有，只用于超过一步预算的长提示 |
| 前缀缓存的哈希 | Python `hash`，单进程内稳定 | xxhash64，可跨进程；命中后再比一遍 token |
| 不复用的块 | 含最后一个 token 的块 | 最后一块（效果相同） |
| 抢占 | 运行队列末尾，释放后重算 | 相同 |
| 空闲块的淘汰 | 先还先用，倒着还 | 相同 |
| 块数 | 手动指定 | 启动时按剩余显存算出 |

块大小 256 有代价：前缀缓存的粒度变粗了，两个请求要有 256 个 token 完全相同的前缀才能共用一块；每个请求最后一块平均浪费约 128 个位置。第 122 讲的例子（共用约 330 个 token 的系统提示）在 nano-vllm 里只能命中 1 块（256 个位置），miniinfer 能命中 20 块（320 个位置）。

<Note kind="point">nano-vllm 把一步拆成三段：调度器（只碰 Python 对象，决定这一步跑谁、算几个 token、管块）、执行器（把名单变成 GPU 张量、跑模型、采样，每张卡一个）、引擎（串起两者）。调度规则是 prefill 优先、一步只做一种，这让 decode 步的形状规整到可以录成 CUDA Graph。块管理和前缀缓存的逻辑和 miniinfer v3 几乎一样，只是块大 16 倍、哈希稳定、命中后多比一次 token。</Note>

## 回顾

nano-vllm 约 1200 行，调度一侧（请求状态、调度器、块管理器）只占 247 行，和 miniinfer 的 180 行差不多，逻辑也几乎一一对应：等待和运行两个队列、按块数放行、块不够就抢占最晚进来的、链式哈希做前缀缓存、引用计数共用块、倒着还块让前缀留得更久。不同的地方有三处：一步只做 prefill 或只做 decode；超长提示可以分块 prefill；块大小是 256。

多出来的约 800 行都在执行一侧。下一讲：**nano-vllm 多做了什么**——FlashAttention、写 KV 的 Triton kernel、CUDA Graph 和张量并行是怎么接进来的。
