## 三个进程

<EngineProcs engine="vllm" caption="图 129-2　vLLM V1 的进程结构。点“下一步”看一个请求经过哪些模块，点模块看它在哪个文件。" />

nano-vllm 只有一个主进程（张量并行时再加几个 worker），调度、分词、执行模型都在主进程里轮流做。vLLM V1 把它们拆到三类进程里：

1. **API 服务器进程**：HTTP 接口、分词、反分词、流式输出。这些都是纯 CPU 的 Python 代码，而且量很大：一个高并发的服务每秒要处理成千上万个 token 的反分词。
2. **EngineCore 进程**：只做调度和驱动执行。它是一个死循环：收请求 → 调度 → 让 worker 执行 → 更新状态 → 发输出。
3. **Worker 进程**：每张卡一个，执行模型。

为什么拆？第 89 讲引过 vLLM 团队对 v0.6.0 的剖析：API 服务器和调度一度占了一步时间的六成，GPU 大部分时间在等 Python。拆成多个进程以后，分词、反分词和调度跑在不同的 CPU 核上，互不阻塞；Python 的全局解释器锁（GIL）也只锁住各自的进程。进程之间用 ZMQ 传消息、msgpack 序列化；EngineCore 里收和发又各放在一个后台线程，主循环只管调度。

第二轮是等待中的请求（第 1065 行起，500 多行，大部分在处理 PD 分离、多模态、LoRA 等情况）。主干和 nano-vllm 一样：查前缀缓存（`get_computed_blocks`，第 1246 行），差额 = 总长 − 命中的部分（第 1356 行），长提示同样受上限约束（第 1382 行），`allocate_slots` 拿块（第 1497 行），拿不到就停（第 1523 行）；拿到了就移进运行队列，`num_computed_tokens` 设成命中的位置数（第 1609–1637 行）。

和 nano-vllm 相比，最关键的差别是：**新请求的 prefill 和老请求的 decode 在同一步里**。一步里可能有 30 个请求各 decode 1 个 token，加上一个新请求 prefill 了 1500 个 token。这对执行一侧提出了要求：注意力 kernel 必须能处理“每个请求查询长度不同”的 batch，CUDA Graph 也要能录这种混合的步。vLLM 的注意力后端统一用“变长查询 + 块表”的接口（第 127 讲的 `flash_attn_varlen_func` 就是这种接口），CUDA Graph 用两种模式：整步录（只适合纯 decode 这类规整的步）和分段录（注意力之外的部分录成图，注意力单独执行，混合的步也能用）。

## 结构化输出：语法在哪里编译，掩码在哪里加

第 80 讲讲了约束解码的原理，第 131 讲会看 SGLang 的做法。vLLM 把它分成三个时机，都由 EngineCore 里的 `StructuredOutputManager`（`v1/structured_output/__init__.py`）管理：

<CodeWalk file="third_party/vllm/vllm/v1/structured_output/__init__.py" from={134} to={205} steps={[

请求进来时状态是 `WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`。调度器每一步检查（`scheduler.py` 第 3685–3697 行）：语法编译好了，就改成普通的 `WAITING`，进入正常的调度；还没好，这一步跳过它，其他请求照常跑。

掩码在每一步计算：上面 `EngineCore.step()` 第 724–725 行，调度结果交给执行器之后，主线程马上调 `get_grammar_bitmask`，让后端按每个请求当前的状态算出“下一个 token 允许哪些”，写成一个位图（每个 token 一位，用 32 位整数存）。这一步和 GPU 的前向同时进行，前向算完、采样之前，worker 把位图展开、把不允许的 token 的打分设成 −∞。采样出 token 后，`accept_tokens`（第 515 行）推进每个请求的状态机。

投机解码和结构化输出同时打开时，还要多一步：草稿 token 也必须符合语法，`trim_spec_tokens`（第 358 行）把不符合语法的草稿截掉，免得验证一个注定被拒的 token。

## 异步调度：让 CPU 的工作藏在 GPU 后面

即使拆成了多个进程，EngineCore 里“调度 → 等 GPU → 处理结果”仍然是串行的：GPU 算的时候 CPU 在等，CPU 调度的时候 GPU 在等。decode 一步只有几毫秒时，调度和处理结果的那一两毫秒就占了可观的比例。

## SchedulerOutput：只发增量

调度器和 worker 在不同的进程里，每一步都要把调度结果发过去。nano-vllm 每步把整个请求列表 pickle 一次（第 127 讲）。vLLM 的 `SchedulerOutput`（`v1/core/sched/output.py` 第 220 行）把请求分成两类：

- **新请求**（`scheduled_new_reqs`）：发完整的信息，提示的全部 token、采样参数、块表。worker 收到后缓存起来。
- **老请求**（`scheduled_cached_reqs`）：只发这一步的变化，新增的块号、这一步算几个 token。

worker 里的 `GPUModelRunner` 维护一个**持久的 batch**：每个请求在固定的大张量里占一行（token、块表等；有的放在显存里，有的放在 GPU 能直接访问的锁页内存里，见 `v1/worker/gpu/states.py`），每一步只按增量修改其中几行，而不是像 nano-vllm 那样每步从 Python 列表重新拼出全部输入张量。batch 很大（几百个请求）时，这一步省下的 CPU 时间很可观。

<Note kind="point">vLLM V1 = 三类进程（前端做分词和反分词、EngineCore 做调度、worker 做执行）+ 统一的 token 预算调度（每个请求只有“已算”和“应有”两个数，prefill、分块、前缀缓存、decode、投机都是补差额）+ 分页 KV（SHA-256 链式哈希，双向链表做 LRU）+ 异步调度（用占位让调度和执行重叠）+ 只发增量的 SchedulerOutput 和持久 batch。核心思想和 nano-vllm、miniinfer 一脉相承，多出来的代码主要在支持更多的模型、硬件和功能。</Note>

## 回顾

一个请求在 vLLM V1 里的路径：API 服务器分词 → ZMQ 发给 EngineCore → 调度器在 token 预算内给它分配 token（查前缀缓存、按块分配 KV，块不够就抢占最晚进来的请求）→ 执行器把 SchedulerOutput 的增量广播给每张卡 → worker 更新持久 batch、跑模型、采样 → 调度器接上新 token、回滚被拒的草稿、释放结束的请求 → 输出发回前端，反分词，流式返回。

和 nano-vllm 比，最根本的变化是调度不再区分 prefill 和 decode：这要求注意力 kernel 能处理变长查询，CUDA Graph 能录混合的步，也换来了更平稳的 decode 延迟。

这一讲停在“一个 EngineCore”的边界上。真实的服务往往有多个 API 服务器、跨多个节点的多个引擎副本，PD 分离时还有两种实例之间的 KV 搬运。下一讲把视野放大到整个服务：一条 curl 请求怎么在多节点的 vLLM 里找到它的引擎、跑完、返回。下一讲：**vLLM 的分布式服务**。
