第六章的最后一讲把二十讲的内容压成一条可执行的路线：从机器上架到服务上线，哪些事必须做、每一步怎么算过关。

清单的价值不在于“别忘了什么”，而在于**每一项都有一个能机械判断的验收标准**。适配工作里最常见的失败不是某一步做不出来，而是某一步“看起来过了”就往下走——跑通了但有算子在回退、输出看着正常但某一层已经失效、压测很快但没预热、多卡能跑但两条通信路径里有一条会死锁。

## 清单

<Checklist caption="图 153-1　上线清单，六个阶段 29 项。点一项看“怎么验”和“为什么在这一步”；点方框或再点一次勾选完成（只存在你自己的浏览器里）。" />

六个阶段的分界线是这样定的，每条分界都对应一个“不往回走”的承诺：

**环境 → 跑通**：版本组合固定下来了。之后再换任何一层版本，精度和性能两关都要重走（第 149 讲）。

**跑通 → 精度**：缺失算子都有去处，而且没有东西在悄悄回退到 CPU。这一条是后面所有数字可信的前提（第 140 讲）。

**精度 → 性能**：有了一个可信的基线。优化几乎每一步都改变数值，没有基线就分不清“优化引入的错误”和“本来就有的误差”（第 139 讲）。

**性能 → 多卡**：单卡的瓶颈都解释清楚了。单卡没弄明白就上多卡，通信的问题和计算的问题会纠缠在一起（第 142 讲）。

**多卡 → 服务化**：并行配置定了，两条通信路径都压过。

**服务化 → 上线**：版本、配置、压测结果都冻结并记录；回滚路径验证过。

## 三个最容易跳过的环节

二十讲写下来，有三件事值得单独强调，因为它们看起来不紧急，但跳过的代价最大。

**第一，算子回退的检查**。一个回退到 CPU 的算子，本站实测慢 15 倍，而且打断设备上的流水（第 140 讲）。更麻烦的是它会掩盖问题：性能数据面目全非，精度问题也可能被它遮住。做法很简单——在分发器那一层记一次账，确认回退计数为 0（第 141 讲的脚本可以直接改用）。

**第二，按精度分别验**。本站那个 FP16 的例子最有说服力：FP32 下四条提示全部逐 token 一致，换到 FP16 立刻生成一串句号——原因是 RMSNorm 的平方和溢出，和硬件没关系，但只在这个精度暴露（第 139 讲）。所以“跑通”和“跑对”都要按精度逐个来，而不是验一种推广到全部。

**第三，把判断过程记下来**。性能工作里丢的不是数字，是上下文：为什么选了这个分块、为什么放弃了那个优化、为什么这个版本组合不能动。第 142 讲给过记录的字段表，第 151 讲那个被宏关掉的 split-K 变体是个好范例——症状、条件、重启用条件全写在注释里。

<Note kind="point">清单里有一类项特别容易被当成“形式”：预热、回滚、版本冻结。它们的共同点是**只在出问题时才体现价值**，而新硬件上出问题的概率比成熟平台高。即时编译一次要几十秒（第 151 讲），落在第一个真实请求上就是一次超时；版本没冻结，三个月后复现不出来当初的结果。</Note>

## 回到那张分层图

<StackMap route="das" caption="图 153-2　九层软件栈（第 134 讲的图，切到海光那一列）。清单里的六个阶段，其实是自下而上把这九层逐层点亮的过程。" />

把清单和这张图对上，能看出适配工作的形状：

| 阶段 | 点亮哪几层 | 典型耗时的来源 |
| --- | --- | --- |
| 环境 | 驱动、运行时、工具链 | 版本错配；每换一次组合都要重来 |
| 跑通 | 框架、算子库 | 缺失算子的处理；少数模型要插件提供实现 |
| 精度 | 算子库、kernel | 低精度下的溢出、累加顺序、自写 kernel 的 bug |
| 性能 | kernel、图编译、运行时 | 小 M 矩阵乘、注意力后端、下发与同步开销 |
| 多卡 | 通信库、互联 | 拓扑探测、自定义通信的适用区间 |
| 服务化 | 引擎与插件 | 预热、配置组合、SLO 下的容量 |

第 134 讲说“要重做的是接口下方的实现”，现在可以把这句话说得更具体：**要重做的工作量集中在算子库和 kernel 两层，而要花掉的时间往往集中在环境和服务化两头**。前者是技术问题，后者是组合问题——而组合问题没有捷径，只能靠记录和自动化压住。

## 整个课程到这里

第一章从向量和矩阵乘法开始，第二章把 Transformer 和现代架构拆开，第三、四章讲单机与分布式推理，第五章手写了一个推理引擎、再读了工业级引擎，第六章把模型搬到另一块芯片上。

如果要用一句话串起来：**上面的每一层都在给下面的层下订单，而下面的每一层都在用自己的物理约束改写上面的设计**。注意力的数学决定了要读多少字节，带宽决定了 decode 的下限，矩阵单元的形状决定了 kernel 怎么分块，而一块卡的波前是 64 而不是 32 这件小事，会一直传上去，变成一行必须手改的归约循环。

接下来往哪走，取决于你关心哪一层：想往下，就挑一个算子在你手上的硬件上写到接近上限；想往上，就挑一个真实负载做一次完整的容量规划和上线复盘。两条路都会回到同一个习惯——**先算理论值，再量实测，解释清楚两者的差距**。
