一家做客服机器人的公司有 100 个企业客户，每个客户都用自己的对话记录微调了一份 Llama-3-8B。如果每份都全量微调、单独部署，就是 100 份 16 GB 的权重，至少要 100 张卡，哪怕大多数客户一天只有几个请求。第 50 讲给了另一条路：每个客户只训练一个 LoRA 适配器，几十 MB，大家共用同一份基座模型。

这一讲讲推理引擎怎么把这条路走通：一个 batch 里的请求属于不同的适配器，怎么一起算？代价在哪里？为什么 vLLM 要给“一个 batch 里最多几个适配器”设上限？

## 一个 batch，几个适配器

回忆第 50 讲：LoRA 不改原来的权重 W，而是在旁边加一条小路，

$$
y = xW + \frac{\alpha}{r}\,(xA)\,B
$$

A 是 d_in × r，B 是 r × d_out，秩 r 通常是 8、16、32。只服务一个客户时，最省事的做法是把小路合并进去：W′ = W + (α/r)AB，推理和原模型一模一样，没有任何额外开销。

可一旦要同时服务很多客户，就不能合并了：合并后的 W′ 是某一个客户专属的，换一个客户就要换一份 16 GB 的权重。所以多 LoRA 服务的基本做法是**不合并**：

- **大路所有请求一起算。**batch 里 B 个请求的 x 拼成 [B, d_in]，乘同一个 W，这一步和没有 LoRA 时完全一样，continuous batching 的收益全部保留（第 74 讲）。
- **小路各算各的。**第 i 个请求用它自己客户的 A_i、B_i，算 (x_i A_i) B_i，加到大路的结果上。

这样，100 个客户只需要显存里放一份基座、加上当前要用的那些适配器。

## 适配器有多大，多算多少

先算一个适配器的大小。Llama-3-8B 有 32 层，把 LoRA 加在全部 7 个线性层上（q、k、v、o 四个注意力投影，gate、up、down 三个 FFN 矩阵）。每个线性层的小路有 r × (d_in + d_out) 个参数：

```python
import numpy as np
d, kv, ffn, L = 4096, 1024, 14336, 32           # Llama-3-8B：隐藏维度、KV 维度（8 个头 × 128）、FFN 宽度、层数
layers = {"q": (d, d), "k": (d, kv), "v": (d, kv), "o": (d, d), "gate": (d, ffn), "up": (d, ffn), "down": (ffn, d)}
io = sum(a + b for a, b in layers.values())
for r in (8, 16, 64):
    p = r * io * L
    print(f"r = {r:>2}：{p / 1e6:5.1f} M 个参数，BF16 {p * 2 / 1e6:6.1f} MB，是基座 80.3 亿参数的 {p / 8.03e9:.2%}")
r = 16
print(f"r = 16 时，每个 token 多算 2 × {r * io * L / 1e6:.1f} M 次乘加，基座是 2 × 8.03 G：多 {r * io * L / 8.03e9:.2%}")
```

```text
r =  8： 21.0 M 个参数，BF16   41.9 MB，是基座 80.3 亿参数的 0.26%
r = 16： 41.9 M 个参数，BF16   83.9 MB，是基座 80.3 亿参数的 0.52%
r = 64：167.8 M 个参数，BF16  335.5 MB，是基座 80.3 亿参数的 2.09%
r = 16 时，每个 token 多算 2 × 41.9 M 次乘加，基座是 2 × 8.03 G：多 0.52%
```

r = 16 的适配器 84 MB，100 个也才 8.4 GB，一张 80 GB 的卡放得下基座加全部 100 个。计算量只多 0.5%：每个 token 只过它自己那一个适配器。看起来几乎是免费的。

## 反直觉的地方：计算免费，读不免费

可是 decode 不受计算限制，受带宽限制（第 68、72 讲）：每一步都要把用到的权重从显存完整地读一遍，读权重的时间就是这一步的时间。

基座的权重每一步读一遍，batch 里有多少请求都一样。适配器不同：**batch 里出现了几个不同的适配器，就要读几个适配器**。一个适配器只占基座的 0.52%，可要是一步里混着 50 个不同的适配器，就要多读 50 × 84 MB = 4.2 GB，是基座的 26%。计算只多 0.5%，时间却多了四分之一。

一个 batch 里会有几个不同的适配器？这取决于请求在客户之间怎么分布。假设一共 N 个适配器，请求落到第 i 个的概率是 pᵢ，batch 里有 B 个请求，那么第 i 个适配器至少出现一次的概率是 1 − (1 − pᵢ)^B，期望出现的不同适配器个数是：

$$
D = \sum_{i=1}^{N} \left(1 - (1 - p_i)^B\right)
$$

真实的流量往往很不均匀：少数大客户占了大部分请求。常用 Zipf 分布来描述：第 i 热门的适配器被选中的概率正比于 1/iˢ，s = 0 是完全均匀，s 越大越集中。

```python
import numpy as np
def distinct(N, s, B):
    w = 1 / np.arange(1, N + 1) ** s
    p = w / w.sum()
    return (1 - (1 - p) ** B).sum()
for N, s, B in [(100, 0, 64), (100, 1, 64), (100, 1.5, 64), (1000, 1, 64), (100, 1, 8)]:
    D = distinct(N, s, B)
    print(f"N = {N:>4}，s = {s}，B = {B:>2}：平均 {D:4.1f} 个不同的适配器，每步多读 {D * 83.9 / 1000:.2f} GB（基座的 {D * 83.9 / 16060:.1%}）")
```

```text
N =  100，s = 0，B = 64：平均 47.4 个不同的适配器，每步多读 3.98 GB（基座的 24.8%）
N =  100，s = 1，B = 64：平均 31.4 个不同的适配器，每步多读 2.64 GB（基座的 16.4%）
N =  100，s = 1.5，B = 64：平均 18.1 个不同的适配器，每步多读 1.52 GB（基座的 9.5%）
N = 1000，s = 1，B = 64：平均 43.9 个不同的适配器，每步多读 3.69 GB（基座的 23.0%）
N =  100，s = 1，B =  8：平均  6.7 个不同的适配器，每步多读 0.56 GB（基座的 3.5%）
```

100 个客户、请求完全均匀时，64 个请求的 batch 里平均有 47 个不同的适配器，每步多读四分之一。流量越集中（s 越大），同一个热门适配器被 batch 里的多个请求共用，D 越小。batch 越大，D 越大，但增长得比 B 慢。

## 小路怎么算：一个 kernel 算完所有适配器

第二个问题是怎么算小路。最直接的写法是按适配器分组：batch 里属于适配器 1 的请求挑出来，乘 A₁、B₁；属于适配器 2 的挑出来，乘 A₂、B₂……有 D 个适配器，每个线性层就要调用 2D 次矩阵乘法，每次都很小（几个请求 × 4096 × 16）。32 层、7 个线性层、D = 30 时，每一步要发 13,440 次 kernel。第 87 讲会看到，这种小矩阵乘法连 GPU 的一个零头都用不满，而每次发射 kernel 本身还有几微秒的开销（第 89 讲 CUDA Graph 讲的就是这个问题）。

2023 年的 Punica 和 S-LoRA 提出了专门的算子：**分段聚集矩阵乘**（SGMV，segmented gather matrix-vector multiplication）。思路是一次 kernel 处理整个 batch：给每个请求附上它的适配器编号，kernel 里每个线程块自己按编号去显存里找对应的 A、B，算完写回对应的行。decode 时每个请求只有一个 token，这个特例叫 BGMV。这样，不管 batch 里混着多少个适配器，每个线性层的小路都只要固定的两次 kernel 调用。

注意它解决的是“调用次数”和“小矩阵用不满 GPU”的问题，**不减少读的字节**：D 个适配器还是要各读一遍。所以适配器个数的上限依然要管。

## 显存里放几个：GPU、CPU 两级缓存

适配器的总数可能有成千上万个，不可能全放在显存里。推理引擎一般做两级缓存：

- **显存里的槽位**：最多放 max_loras 个适配器，正在被 batch 使用的必须在这里。
- **CPU 内存里的缓存**：最多 max_cpu_loras 个，从磁盘加载过的先放在这里，需要时拷进显存的槽位；满了按最近最少使用（LRU）淘汰。

一个 84 MB 的适配器，从 CPU 内存经 PCIe 5.0（约 64 GB/s 单向）拷进显存约 1.3 ms。H100 上一步 decode 光读基座权重就要约 4.8 ms，换一个适配器相当于这一步多了四分之一，所以要尽量别每一步都在换；拷贝也可以和计算重叠着做。S-LoRA 更进一步，把适配器的权重和 KV Cache 放在同一个分页的显存池里统一管理（第 75 讲的分页思路），适配器多的时候就少放一些 KV，反过来也一样。

## 到了真实系统里

- **秩的上限决定显存和速度。**显存槽位按 `max_lora_rank` 预留，混着 r = 8 和 r = 64 的适配器，就按 64 留；秩大的适配器读的字节也多。所以服务方通常会限制客户可用的秩。
- **按适配器调度。**既然代价和 D 成正比，调度时就可以优先把用同一个适配器的请求凑进同一个 batch；集群层面，路由器可以把同一个客户的请求尽量发到同一台机器（第 114 讲的缓存感知路由是同一个思路），每台机器只需要缓存一部分适配器。
- **prefill 的情况不同。**prefill 时每个请求有几百上千个 token，小路的矩阵乘法不再小，计算量也不再可以忽略（但仍然只占约 r / d 的比例）。上面说的“读不免费”主要是 decode 的问题。

## 容易混淆的地方

- **LoRA 不改变 KV Cache 的大小。**适配器改的是线性层的输出，K、V 的维度和个数都不变。但不同适配器算出的 K、V 不同，所以用不同适配器的请求之间不能共享前缀缓存，哪怕提示一字不差（第 76 讲）。
- **“多 LoRA 服务开销很小”只对一半。**计算开销确实小（r = 16 时 0.5%），但 decode 的读权重开销和 batch 里不同适配器的个数成正比，可能是基座的几分之一。
- **SGMV 不是把适配器合并。**它只是把很多次小矩阵乘法合成一次 kernel 调用，每个请求还是只用自己的适配器。

## 回顾

多 LoRA 服务不合并适配器：大路所有请求一起算，小路每个请求用自己的 A、B。r = 16 时一个适配器 84 MB，计算只多 0.52%；但 decode 每步要把 batch 里出现过的每个不同适配器都读一遍，100 个均匀分布的客户、64 个请求的 batch，平均 47 个不同的适配器，多读 4 GB，是基座的四分之一。SGMV / BGMV 把一层里所有适配器的小路合成一次 kernel，解决调用次数的问题；显存槽位和 CPU 缓存两级管理适配器；vLLM 用 `max_loras` 限制一步里不同适配器的个数，调度器超过上限就让请求等一等。

这一篇讲到这里，引擎调度的都是“内容不受限”的生成。还有一类常见需求：模型的输出必须是合法的 JSON、必须符合某个格式。模型一个 token 一个 token地生成，怎么保证最后拼出来的东西合法？下一讲：**结构化输出与约束解码**。
