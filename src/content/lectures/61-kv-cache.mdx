KV Cache 在前面的讲里已经出现过好几次：第 24 讲用它解释为什么生成不必每步重算，第 27 讲说明了它为什么能成立，第 39、40 讲为了压缩它改了注意力的结构。这一讲把它作为一个完整的推理技术来讲：**它具体怎么实现，省了多少计算，又付出了什么代价**。我们会在 TinyLM 上真的写一个带缓存的生成循环，并验证它和“每步重算整句”的结果一模一样。

它标了重点，因为 KV Cache 是推理系统里最核心的数据结构：第 9 篇的 PagedAttention、前缀缓存、连续批处理，第 13 篇的 PD 分离，几乎都围绕着“怎么存、怎么管、怎么传 KV Cache”展开。

## 不缓存要重算多少

先回顾第 34 讲的生成：每生成一个 token，就把整句话从头做一遍完整的前向，取最后一行的概率。提示有 4 个 token，生成第 1 个词时算 4 个位置，生成第 2 个时算 5 个，第 3 个时算 6 个……生成第 n 个时，前面所有 token 都要重新经过每一层。

可第 27 讲已经证明：因为有因果掩码，**每个 token 在每一层的输出，只取决于它自己和它前面的 token**，后面接了什么都不影响它。前面那些 token 上一步算过，这一步再算一遍，结果完全一样，纯属浪费。

## 缓存什么

重算的结果里，后面的计算真正要用到的是什么？新 token 在每一层做注意力时，需要前面每个 token 在这一层的 **k 和 v**（用来打分和加权求和）。前面 token 的 q 用不到（它们不再“提问”），它们在 FFN 里的计算结果也用不到（只影响它们自己）。

所以只需要缓存每一层、每个 token 的 k 和 v，这就是 **KV Cache**。有了它，decode 的每一步变成：

1. 只把**新 token** 送进模型。
2. 在每一层，只算新 token 自己的 q、k、v。
3. 把新的 k、v **追加**进这一层的缓存。
4. 用新 token 的 q，和缓存里所有的 k 打分、对所有的 v 加权求和。新 token 是最后一个，它能看的正是全部缓存，所以**不需要掩码**。
5. 新 token 继续经过这一层的 FFN，进入下一层。

prefill 时，整段提示一起算，把每一层所有 token 的 k、v 一次性写进缓存；之后的 decode 每步只写一组。

下面的演示把每一次前向画成一行：深色是这次要完整计算的位置，浅色是直接用缓存、不再计算的位置。切换“无缓存”和“有 KV Cache”，拖动已生成的步数，看累计计算量的差别。

## 在 TinyLM 上实现一遍

下面的代码给 TinyLM 写了一个 `step` 函数：只处理一个新 token，在两层里各算它的 q、k、v，追加进缓存，再做注意力和 FFN。从“我”开始生成 6 个词，每一步都和“整句重算”（第 34 讲的完整前向）的结果比较。

结果：生成“我 推理 我 推理 推理 推理 AI”（前四个词和第 34 讲一样），**每一步的概率分布都和整句重算完全一致**。缓存里每层存了 7 个 k 和 7 个 v，每个 4 维。处理过的 token 位置：有缓存 7 个，无缓存 28 个（1 + 2 + … + 7）。

注意 `step` 函数里位置编码用的是这个 token 在整句里的位置（第 25 讲），这正是推理引擎里 position ids 的作用：没有了整句，每个新 token 要自己知道自己排在第几。

## 省了多少，花了多少

把账算到 Llama-3-8B 上：提示 1000 个 token，再生成 1000 个。

- **无缓存**：每一步重算整句，一共要处理 1000 + 1001 + … + 1999 ≈ 150 万个 token 位置，约 22.5 PFLOPs（每个位置约 2 × 75 亿次运算）。
- **有缓存**：prefill 1000 个，再 decode 999 步，一共 1999 个位置，约 30 TFLOPs。

计算量相差约 750 倍。没有 KV Cache，大模型的生成在实际中根本跑不动。

代价是**显存**。每个 token 每层要存一组 k、v：Llama-3-8B 每个 token 128 KiB（第 39 讲），这个请求结束时缓存有 250 MiB。它随序列长度线性增长，也随并发请求数线性增长。第 27 讲算过，16 个 8192 token 的请求，KV Cache 就要 16 GiB，和模型权重一样大。而且第 60 讲说过，decode 每一步都要把这个请求的整个 KV Cache **读一遍**，缓存越长，每一步越慢。

KV Cache 本质上是一笔**用显存换计算**的交易。推理系统接下来的很多工作，都是在想办法让这笔交易更划算：让每个 token 的缓存更小（GQA、MLA、KV Cache 量化），让缓存不浪费显存（PagedAttention，第 67 讲），让相同的前缀只存一份（前缀缓存，第 68 讲），显存不够时把缓存挪到别处或丢掉重算（第 70 讲的抢占）。

## 用代码复现

```python
import json
import numpy as np

t = json.load(open("tinylm.json", encoding="utf-8"))
vocab, E, layers, W_lm = t["config"]["vocab"], np.array(t["weights"]["embedding"]), t["weights"]["layers"], np.array(t["weights"]["lm_head"])
P = {k: [np.array(L[k]) for L in layers] for k in ["W_q", "W_k", "W_v", "W_o", "W_1", "W_2"]}

def pe(pos, d=4):                                         # 第 25 讲的正弦位置编码（一个位置）
    i = np.arange(0, d, 2)
    out = np.zeros(d); out[0::2], out[1::2] = np.sin(pos / 10000 ** (i / d)), np.cos(pos / 10000 ** (i / d))
    return out

def ln(x, eps=1e-5):
    mu = x.mean(-1, keepdims=True)
    return (x - mu) / np.sqrt(((x - mu) ** 2).mean(-1, keepdims=True) + eps)

def softmax(z):
    e = np.exp(z - z.max(-1, keepdims=True)); return e / e.sum(-1, keepdims=True)

def step(token, pos, cache):
    """只算一个新 token：每层算它自己的 q、k、v，把 k、v 追加进缓存，再用 q 去看缓存里的全部 k、v。"""
    x = E[vocab.index(token)] + pe(pos)
    for l in range(2):
        q, k, v = x @ P["W_q"][l], x @ P["W_k"][l], x @ P["W_v"][l]
        cache[l]["k"].append(k); cache[l]["v"].append(v)
        K, V = np.array(cache[l]["k"]), np.array(cache[l]["v"])   # [已有 token 数, 4]
        heads = []
        for h in range(2):
            c = slice(2 * h, 2 * h + 2)
            a = softmax(q[c] @ K[:, c].T / np.sqrt(2))              # 新 token 看自己和前面所有：不需要掩码
            heads.append(a @ V[:, c])
        x = ln(x + np.concatenate(heads) @ P["W_o"][l])
        x = ln(x + np.maximum(0, x @ P["W_1"][l]) @ P["W_2"][l])
    return softmax(x @ W_lm)

def full_forward(tokens):
    """不用缓存：每次把整句从头算一遍（第 34 讲），只取最后一行。"""
    s = len(tokens)
    x = np.array([E[vocab.index(w)] + pe(i) for i, w in enumerate(tokens)])
    mask = np.triu(np.full((s, s), -np.inf), 1)
    for l in range(2):
        Q, K, V = x @ P["W_q"][l], x @ P["W_k"][l], x @ P["W_v"][l]
        heads = [softmax(Q[:, 2*h:2*h+2] @ K[:, 2*h:2*h+2].T / np.sqrt(2) + mask) @ V[:, 2*h:2*h+2] for h in range(2)]
        x = ln(x + np.concatenate(heads, 1) @ P["W_o"][l])
        x = ln(x + np.maximum(0, x @ P["W_1"][l]) @ P["W_2"][l])
    return softmax(x @ W_lm)[-1]

# 1. 从“我”开始生成 6 个词：有缓存，每步只算 1 个新 token
cache = [{"k": [], "v": []} for _ in range(2)]
seq, rows_cached, rows_full, same = ["我"], 0, 0, True
p = step("我", 0, cache); rows_cached += 1
for i in range(6):
    nxt = vocab[int(p.argmax())]
    rows_full += len(seq)                                 # 不用缓存时，这一步要把已有的 len(seq) 个 token 全算一遍
    same &= np.allclose(p, full_forward(seq))
    seq.append(nxt)
    p = step(nxt, len(seq) - 1, cache); rows_cached += 1
print("生成：", " ".join(seq))
print("每一步和“整句重算”的结果一致：", same)
print("缓存里每层存了", len(cache[0]["k"]), "个 k 和 v，形状", np.array(cache[0]["k"]).shape)
print(f"处理过的 token 位置：有缓存 {rows_cached} 个，无缓存 {rows_full + len(seq)} 个")

# 2. Llama-3-8B：提示 1000 个 token，再生成 1000 个
p_len, n = 1000, 1000
no = sum(p_len + i for i in range(n)); yes = p_len + n - 1
print(f"Llama-3-8B：无缓存处理 {no:,} 个位置 ≈ {2 * 7.5e9 * no / 1e15:,.1f} PFLOPs；有缓存 {yes:,} 个 ≈ {2 * 7.5e9 * yes / 1e12:.1f} TFLOPs")
print(f"代价：KV Cache 每 token 128 KiB，这个请求结束时 {(p_len + n) * 128 / 1024:.0f} MiB")
```

每一步和“整句重算”的结果一致： True

处理过的 token 位置：有缓存 7 个，无缓存 28 个
Llama-3-8B：无缓存处理 1,499,500 个位置 ≈ 22.5 PFLOPs；有缓存 1,999 个 ≈ 30.0 TFLOPs

## 到了大模型里

**KV Cache 的形状。**在推理引擎里，一层的 KV Cache 通常是 [请求数, KV 头数, 序列长度, 每头维度] 这样的张量，k 和 v 各一个，32 层就是 64 个。Llama-3-8B 每层每个 token：2 × 8 × 128 个数。有了 RoPE（第 37 讲），存的是已经旋转过的 k。

**decode 的注意力是“一行对一片”。**新 token 的 q 只有一行，要和缓存里成千上万个 k 打分，计算很少，读的数据却很多。推理引擎为 decode 专门写了注意力算子（比如 FlashDecoding），把长长的缓存切成几段，让 GPU 的很多计算单元同时去读、去算，再把结果合并。

**缓存要管理。**请求来来去去，长短不一，缓存的显存要不停地分配、释放。如果像普通的张量那样给每个请求预留一整块“最大长度”的连续显存，大部分都会浪费掉。这正是第 67 讲 PagedAttention 要解决的问题。

## 容易混淆的地方

1. **只缓存 K、V，不缓存 Q。**历史 token 的 q 在后面的步骤里永远用不到，不需要存。
2. **缓存的是每一层的。**不只第一层，每一层的注意力都有自己的 k、v，都要缓存。层数越多，缓存越大。
3. **KV Cache 只在一次请求内有效。**请求结束，缓存就释放了。下一个请求即使开头一样，默认也要重新 prefill，除非用前缀缓存（第 68 讲）把它们留下来复用。

## 回顾

因果掩码保证了历史 token 的计算结果不随后面的 token 改变，所以不必每步重算整句。KV Cache 把每一层、每个历史 token 的 k 和 v 存下来；decode 每步只算新 token 的 q、k、v，追加缓存，再用 q 去看全部缓存。在 TinyLM 上，带缓存的生成和整句重算的结果完全一致，计算的位置从 28 个降到 7 个；在 Llama-3-8B 上，提示和生成各 1000 个 token 时，计算量从约 22.5 PFLOPs 降到约 30 TFLOPs。代价是显存：每 token 128 KiB，随长度和并发线性增长，decode 每步还要把它读一遍。

有了 prefill、decode 和 KV Cache 这三个概念，就可以讨论推理系统最关心的问题了：一个推理服务到底“快”不快？用户感受到的快，和服务商关心的快，是同一回事吗？下一讲：**TTFT、TPOT 与吞吐**。
