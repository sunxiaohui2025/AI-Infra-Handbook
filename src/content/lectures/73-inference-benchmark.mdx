“我们的推理服务，单卡吞吐 1 万 token/s。”这句话本身几乎没有信息量。是什么模型、什么显卡？请求的提示多长、输出多长？同时有多少个请求？这时每个用户的 TTFT 和 TPOT 是多少？第 62 讲说过，吞吐和延迟是此消彼长的：把并发堆得足够高，吞吐总能很好看，代价是每个用户都要等很久。

所以一次可信的压测（benchmark），给出的不应该是一个数，而是一条**曲线**：在不同的压力下，吞吐和延迟分别是多少，以及在满足延迟要求的前提下，最多能承受多大的压力。这一讲讲怎么做出这条曲线，以及压测里常见的坑。

## 压测在测什么

先把第 62 讲的指标放到压测的语境里：

- **输出吞吐**：每秒生成多少个输出 token（token/s）。有时也看输入吞吐，或者每秒完成多少个请求。
- **TTFT**：从请求发出到收到第一个 token。它包括**排队**的时间，负载高时排队是大头（第 72 讲）。
- **TPOT**：生成阶段，相邻两个 token 的平均间隔。有的工具也报告 ITL（inter-token latency），即每两个 token 之间的间隔，不先对每个请求取平均。
- **端到端延迟**：从发出到收到最后一个 token。

延迟要看**分布**，不能只看平均：至少报告中位数（P50）和 P99（100 个请求里最慢的那 1 个大约有多慢）。用户的体验往往由尾部决定，一个平均 TTFT 50 ms、P99 却是 3 秒的服务，每一百次请求就有一次让人觉得“卡死了”。

## 怎么加压

压测工具扮演成大量的用户，向服务发请求。有两种加压方式：

**按到达率加压**（开环）：按设定的速率发请求，比如平均每秒 20 个，不管前面的请求有没有完成。到达的时间间隔通常按**泊松过程**随机生成（间隔服从指数分布），因为真实的用户是各自独立、随机地发请求的。这种方式最接近线上服务的真实情况：用户不会因为你的服务慢了就少发请求。

**按并发数加压**（闭环）：固定有 c 个“用户”，每个用户收到回答后立刻发下一个请求。服务越慢，发请求也越慢，所以它永远不会把服务压垮。这种方式简单，适合测“同时 c 个请求时的表现”（第 62 讲的表格就是这种），但它会掩盖排队的问题。

可信的压测通常用前一种：**从低到高逐级提高到达率**，每一级跑足够多的请求，记录各项指标，画成曲线。

## 一条典型的曲线

我们用一个模拟的服务来做一次压测：Llama-3-8B、一张 H100，引擎使用连续批处理和分块 prefill（每步预算 2048 个 token），KV Cache 池约 40 万个 token（第 63 讲），每一步的耗时按第 60 讲的方法估算。请求的提示长度在 200 到 2000 之间、输出在 50 到 500 之间随机，600 个请求按泊松过程到达。

逐级加压的结果（代码在后面）：

- **每秒 5 个**：吞吐 1349 token/s，TTFT 中位 21 ms、P99 50 ms，TPOT 中位 5.5 ms。服务很闲，每个请求几乎都是“单独”在跑。
- **每秒 20 个**：吞吐 5011 token/s，TTFT P99 82 ms，TPOT 中位 9.1 ms。吞吐随压力线性增长，TPOT 开始慢慢变长，因为一起 decode 的请求多了（第 62 讲）。
- **每秒 40 个**：吞吐 8316 token/s，TTFT P99 197 ms，TPOT 中位 21.0 ms。
- **每秒 45 个**：吞吐 8570 token/s，几乎不再增长；TTFT P99 一下子跳到了 1306 ms。
- **每秒 60 个**：吞吐 8780 token/s，只比每秒 40 个时多了 6%；TTFT 中位 906 ms，P99 达到 4176 ms。

曲线的形状是这样的：压力低时，吞吐随到达率线性增长，延迟几乎不变；到了某个点（这里是每秒四十多个），服务的处理能力饱和了，吞吐不再增长，多出来的请求只能排队，TTFT 急剧上升。这个拐点就是服务的**容量**。

## goodput：满足要求的吞吐

线上服务通常有明确的延迟目标，叫 **SLO**（服务等级目标），比如“TTFT 的 P99 不超过 500 ms，TPOT 的 P99 不超过 30 ms”。超过了，就算服务没有挂，用户体验也不合格。

所以真正有意义的是：**在满足 SLO 的前提下，最大的吞吐是多少**。这个数叫 **goodput**（有效吞吐，这个说法来自 2024 年的 DistServe 论文）。按上面的 SLO，模拟的服务在每秒 40 个请求时还满足要求（TTFT P99 197 ms、TPOT P99 25.2 ms），每秒 42 个时 TTFT P99 就超了，所以 goodput 约是 8316 token/s。每秒 60 个时吞吐虽然更高，但 TTFT P99 有 4 秒多，没有意义。

goodput 也直接决定成本（第 64 讲）：一张卡能承担的“合格”流量，就是 goodput。比较两种配置、两个引擎、两种硬件，应该比 goodput，而不是比最大吞吐。

<Note kind="point">压测要逐级提高到达率，测出吞吐和延迟分布（中位数和 P99）的曲线。吞吐会在某个到达率饱和，再加压只会让请求排队、TTFT 暴涨。满足 SLO 的最大吞吐叫 goodput，它才是一次压测最该给出的数字。</Note>

## 压测里常见的坑

**数据集不对。**提示和输出的长度分布，决定了 prefill 和 decode 的比例，也决定了 KV Cache 的用量，结果可以差好几倍。用和线上相近的长度分布，或者公开的对话数据集（比如 ShareGPT）；固定长度的随机 token 只适合测某个特定的点。

**输出长度不受控。**模型可能提前生成结束标记，导致实际输出比设定的短得多。很多工具提供“忽略结束标记”的选项，强制每个请求生成到指定长度，保证不同配置之间可比。

**前缀缓存“作弊”。**如果所有请求的提示都相同，或者有很长的公共前缀，前缀缓存（第 68 讲）会让 prefill 几乎不花时间，结果好得不真实。要么用彼此不同的提示，要么明确地把命中率作为测试条件写出来。

**没有预热。**刚启动的服务要编译、要捕获 CUDA Graph（第 79 讲）、要分配显存，前几个请求会特别慢。压测前先跑一批请求预热，或者丢掉最开始的结果。

**请求太少、时间太短。**P99 需要足够多的样本，600 个请求的 P99 只由最慢的六七个请求决定。另外，过载时队列会一直变长，TTFT 取决于压测跑了多久：跑 10 秒和跑 10 分钟，过载区的 TTFT 会差很多。所以过载区的延迟数字只说明“已经过载”，不要拿来比较。

**压测机自己成了瓶颈。**客户端要处理成千上万个流式连接，解析每个 token 的返回。如果压测程序自己的 CPU 打满了，测出来的延迟里就混进了客户端的时间。

**只报最好看的那个数。**完整地写清楚：模型、精度、硬件、引擎及版本、主要参数（批大小上限、token 预算、是否开前缀缓存）、数据集、加压方式、每一级的吞吐和 P50、P99。别人才能复现，才能比较。

## 到了大模型里

**常用的工具。**vLLM 和 SGLang 都自带压测脚本（`vllm bench serve`、`python -m sglang.bench_serving`），支持按到达率或并发加压，输出吞吐、TTFT、TPOT、ITL 的分布。NVIDIA 的 GenAI-Perf 等工具也做同样的事。它们都通过 OpenAI 兼容的接口发请求，可以测任何引擎。

**离线吞吐和在线服务分开测。**离线批量处理（比如给一百万篇文档打标签）只关心总吞吐，可以把所有请求一次性塞进去，不关心延迟；在线服务要按上面的方法测曲线和 goodput。两者的最优配置往往不同。

**把测出来的数和理论对上。**测出的结果要和第 64 讲的成本模型、第 59 讲的理论值对照：如果实测吞吐只有理论值的一半，就该用 Profiler（第 58 讲）去找时间花在了哪里。

## 用代码复现

下面的代码模拟了这一讲的压测：生成泊松到达的请求，按连续批处理和分块 prefill 的规则模拟服务（每步耗时按第 60 讲估算），逐级提高到达率，统计输出吞吐和 TTFT、TPOT 的中位数与 P99。为了每次结果一样，随机数用了固定的种子。

```python
import math
# 被测的“服务”：Llama-3-8B + 一张 H100，连续批处理 + 分块 prefill（每步预算 2048），KV 池约 40 万个 token（第 63 讲）
N, NE, L, d = 8.03e9, 128256 * 4096, 32, 4096
W, KV, F, BW = N * 2, 2 * 32 * 8 * 128 * 2, 989e12, 3.35e12
POOL, BUDGET, MAX_SEQS = 403_865, 2048, 256

def lcg(seed):                                           # 固定种子的伪随机数，保证每次运行结果一样
    while True:
        seed = (seed * 1103515245 + 12345) % 2**31
        yield seed / 2**31

def workload(rate, n=600):
    """n 个请求，按泊松过程到达（平均每秒 rate 个）；提示 200–2000 个 token，输出 50–500 个。"""
    r, t, reqs = lcg(42), 0.0, []
    for _ in range(n):
        t += -math.log(1 - next(r)) / rate
        reqs.append({"at": t, "p": 200 + int(next(r) * 1800), "o": 50 + int(next(r) * 450)})
    return reqs

def serve(reqs):
    now, i, waiting, running, used = 0.0, 0, [], [], 0
    while i < len(reqs) or waiting or running:
        while i < len(reqs) and reqs[i]["at"] <= now: waiting.append(reqs[i]); i += 1
        if not waiting and not running: now = reqs[i]["at"]; continue
        while waiting and len(running) < MAX_SEQS and used + waiting[0]["p"] + waiting[0]["o"] <= POOL:
            q = waiting.pop(0); q.update(done=0, gen=0); running.append(q); used += q["p"] + q["o"]
        budget, flops, ctx, work = BUDGET, 0.0, 0, []
        for q in running:                                # 先 decode，再用剩下的预算做 prefill
            if q["done"] == q["p"]: work.append((q, 1)); budget -= 1
        for q in running:
            if q["done"] < q["p"] and budget > 0:
                c = min(budget, q["p"] - q["done"]); work.append((q, c)); budget -= c
        for q, c in work:
            past = q["done"] + q["gen"]
            flops += 2 * (N - NE) * c + 4 * L * d * c * (past + c / 2); ctx += past + c
        now += max(flops / F, (W + KV * ctx) / BW)       # 这一步的耗时（第 60 讲）
        for q, c in work:
            if q["done"] < q["p"]:
                q["done"] += c
                if q["done"] < q["p"]: continue
            q["gen"] += 1
            if q["gen"] == 1: q["first"] = now
            if q["gen"] == q["o"]: q["end"] = now; running.remove(q); used -= q["p"] + q["o"]

def pct(xs, p): xs = sorted(xs); return xs[min(len(xs) - 1, int(p / 100 * len(xs)))]

print("到达率(个/s) | 输出吞吐(token/s) | TTFT 中位/P99 (ms) | TPOT 中位/P99 (ms)")
for rate in [5, 10, 20, 30, 40, 45, 50, 60]:
    reqs = workload(rate); serve(reqs)
    ttft = [(q["first"] - q["at"]) * 1e3 for q in reqs]
    tpot = [(q["end"] - q["first"]) / (q["o"] - 1) * 1e3 for q in reqs]
    span = max(q["end"] for q in reqs) - reqs[0]["at"]
    print(f"{rate:9d}    | {sum(q['o'] for q in reqs) / span:12,.0f}    | {pct(ttft, 50):7.0f} / {pct(ttft, 99):6.0f}  | {pct(tpot, 50):5.1f} / {pct(tpot, 99):5.1f}")
```

        5    |        1,349    |      21 /     50  |   5.5 /   6.3
       10    |        2,639    |      23 /     65  |   6.4 /   7.3
       20    |        5,011    |      27 /     82  |   9.1 /  11.1
       30    |        6,972    |      36 /    131  |  14.6 /  17.6

表格就是上面引用的各级结果。注意每秒 40 个和 45 个之间：吞吐只多了 3%，TTFT 的 P99 却从 197 ms 跳到了 1306 ms，这就是饱和点。

这个模拟是理想化的：它不考虑 CPU 上的调度开销、通信、采样，也没有抢占。真实服务的饱和点会更早，但曲线的形状是一样的。

## 容易混淆的地方

1. **吞吐的分母要说清楚。**“token/s”可能是输出 token、输入 token 或两者之和；可能是整台机器的，也可能是每张卡的。报告时写清楚。
2. **TPOT 和 ITL 的平均方式不同。**TPOT 先对每个请求求平均再看分布，ITL 把所有间隔放在一起看分布。分块 prefill 带来的偶尔一次长间隔，在 ITL 的 P99 里看得更清楚。
3. **饱和点之后的延迟没有意义。**过载时延迟会随压测时长无限增长，比较两个系统时，要比的是饱和点在哪里、饱和之前的延迟，以及 goodput。

## 回顾

一次可信的推理压测，给出的是一条曲线：按泊松过程逐级提高到达率，每一级测输出吞吐和 TTFT、TPOT 的中位数与 P99。吞吐先线性增长，在服务的容量处饱和；再加压，请求开始排队，TTFT 急剧上升。模拟的 Llama-3-8B + H100 在每秒 40 个请求时吞吐 8316 token/s、TTFT P99 197 ms，每秒 60 个时吞吐只多了 6%，TTFT P99 却超过 4 秒。满足 SLO 的最大吞吐叫 goodput，比较配置、引擎和硬件时应该比它。压测还要注意数据集、输出长度、前缀缓存、预热、样本量和压测机本身，并把测试条件完整地写出来。
