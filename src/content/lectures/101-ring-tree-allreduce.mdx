上一讲说，All-Reduce 每张卡至少要收发 2(p − 1)/p · n 的数据。最直接的实现却远远达不到：所有卡把数据发给卡 0，卡 0 加起来，再发回给所有卡。卡 0 要依次收 p − 1 份、发 p − 1 份，一共 2(p − 1)·n；其他卡大部分时间在等。卡越多，卡 0 越忙，时间随卡数线性增长。

问题出在**负担全压在一张卡上**，其他卡的链路都闲着。这一讲讲两种让所有卡、所有链路一起干活的组织方式：**Ring**（环）和 **Tree**（树），以及它们各自适合什么情况。

## Ring：大家排成一个圈

把 p 张卡连成一个环：卡 0 → 卡 1 → 卡 2 → … → 卡 p−1 → 卡 0。每张卡只和下一张卡说话。每张卡的数据切成 p 块。

**第一阶段：Reduce-Scatter，p − 1 步。**第 1 步，卡 i 把自己的第 i 块发给下一张卡，下一张卡把它加到自己的第 i 块上。第 2 步，每张卡把刚刚加过的那一块继续往下传，对方再加上自己的……每一块沿着环走了 p − 1 步，经过了所有的卡，每张卡都往上加了一份。p − 1 步之后，**每张卡恰好有一块是所有卡的总和**。

**第二阶段：All-Gather，p − 1 步。**每张卡把自己那块完整的结果传给下一张卡，对方直接覆盖；再继续往下传。p − 1 步之后，每张卡都有了全部 p 块完整的和。

用上一讲的 4 张卡走一遍（卡 r 的数据是 [10r, 10r+1, 10r+2, 10r+3]，最终结果应是 [60, 64, 68, 72]）：

- Reduce-Scatter 3 步之后：卡 0 的第 1 块是 64，卡 1 的第 2 块是 68，卡 2 的第 3 块是 72，卡 3 的第 0 块是 60，各自恰好有一块完整的和。
- All-Gather 3 步之后：4 张卡都是 [60, 64, 68, 72]。

数一数每张卡发了多少：2(p − 1) 步，每步发一块，一块是 n/p，一共 **2(p − 1)/p · n**，正好是上一讲说的下限。而且每一步里，所有 p 条链路**同时**在传，没有谁闲着，也没有谁特别忙。4 张卡时每张卡发 1.5n，朴素做法里卡 0 要收发 6n。

## 两个代价：延迟和带宽

估算通信时间，要区分两种代价（第 102 讲会细讲）：

- **延迟** α：每发一次消息的固定开销，不管消息多小，都要几微秒（启动传输、同步、经过交换机……）。
- **带宽** β：每秒能传多少字节。传 m 字节，要 m/β 的时间。

一步的耗时 ≈ α + 这一步的数据量 ÷ β。于是：

<div class="ai-formula">朴素：2(p−1)·(α + n/β)　　Ring：2(p−1)·(α + n/(p·β))</div>

Ring 的**带宽项** 2(p−1)/p · n/β 几乎不随卡数增长，非常好；可它的**延迟项** 2(p−1)·α 随卡数线性增长。

代码按 α = 5 μs、β = 50 GB/s（跨机网络的量级）算了几种情况：

- **1 GB 的数据**（比如训练时同步梯度）：8 张卡时朴素做法 280 ms，Ring 35 ms；512 张卡时朴素做法要 20 秒，Ring 只要 45 ms。数据大，带宽项占主导，Ring 几乎完美。
- **64 KB 的数据**（比如推理时张量并行同步一层的输出）：512 张卡时 Ring 要 5.1 ms，几乎全是延迟（2 × 511 × 5 μs）。数据小，延迟项占主导，Ring 的步数太多了。

## Tree：用树来压缩步数

**Tree**（树形）All-Reduce 的思路是减少步数：把卡组织成一棵二叉树，数据从叶子往根逐层相加（Reduce），再从根往叶子逐层广播（Broadcast）。树的深度是 log₂p，所以只要大约 2·log₂p 步。512 张卡时，Ring 要 1022 步，树只要 18 步。

朴素的树有个问题：根节点和靠近根的节点要收发整份数据，带宽利用不好。实际的实现会把数据切成很多小块，像流水线一样一块一块地沿着树往上、往下送，让带宽项也接近 2n/β。NCCL 用的是**双二叉树**（double binary tree）：两棵互补的二叉树，各处理一半的数据，让每张卡在一棵树里当叶子、在另一棵树里当中间节点，负担均衡。

代码里，64 KB、512 张卡时，树约 **0.09 ms**，比 Ring 的 5.1 ms 快了五十多倍；1 GB 时两者都在 35 到 45 ms 之间，差不多。

<Note kind="point">朴素的 All-Reduce 把负担压在一张卡上，时间随卡数线性增长。Ring 让 p 张卡排成环，先 p−1 步 Reduce-Scatter 再 p−1 步 All-Gather，每步所有链路同时传 n/p，带宽项达到下限、几乎不随卡数增长，但要 2(p−1) 步，延迟项随卡数线性增长。Tree 只要约 2·log₂p 步，适合小消息、多卡数。NCCL 会根据消息大小和拓扑自动选择。</Note>

## 到了大模型里

**NCCL 自动选。**NCCL 内置了 Ring、Tree 等多种算法，会根据卡数、消息大小、拓扑自动选择，也可以用环境变量（`NCCL_ALGO`）强制指定。大消息多用 Ring，小消息、跨很多台机器时多用 Tree。

**机器内部另有捷径。**一台 8 卡的 H100 服务器里，所有卡都接在 NVSwitch 上，任意两张卡之间都有高速通路。NVSwitch 还支持在交换芯片里直接做加法（NVLink SHARP），All-Reduce 的数据不用在卡之间绕一圈，进一步减少了步数和流量。InfiniBand 交换机也有类似的网内计算（SHARP）。

**分层的通信。**跨很多台机器时，常常先在每台机器内部做一次 Reduce-Scatter（走快速的 NVLink），再在机器之间对各自的一份做 All-Reduce（走网络），最后在机器内部 All-Gather。这样慢速网络上只传 1/8 的数据。

**推理的通信大多是小消息。**decode 时张量并行每层同步的只是几十个 token 的隐藏状态，几十 KB，延迟是主要矛盾。这也是为什么推理引擎里有专门为小消息优化的 All-Reduce 实现（比如 vLLM 的自定义 All-Reduce），并且尽量把张量并行限制在一台机器内部（第 109 讲）。

## 用代码复现

下面的代码模拟 4 张卡的 Ring All-Reduce，打出每一步之后各卡的数据，统计每张卡发了多少；再按 α-β 模型比较朴素、Ring、Tree 三种做法在不同消息大小、不同卡数下的耗时。

```python
import numpy as np, math

# 1. Ring All-Reduce：4 张卡连成环（0→1→2→3→0），数据切成 4 块。先 p−1 步 Reduce-Scatter，再 p−1 步 All-Gather
p = 4
buf = [10 * r + np.arange(p) for r in range(p)]         # 和第 100 讲一样：卡 r 的数据 [10r, …, 10r+3]
sent = [0] * p
for s in range(p - 1):                                   # Reduce-Scatter：第 s 步，卡 i 把第 (i − s) 块发给下一张卡，对方加到自己的那块上
    msgs = [(i, (i - s) % p, buf[i][(i - s) % p]) for i in range(p)]
    for i, c, v in msgs: buf[(i + 1) % p][c] += v; sent[i] += 1
    print(f"Reduce-Scatter 第 {s + 1} 步：" + "  ".join(f"卡{r}:{buf[r].tolist()}" for r in range(p)))
for s in range(p - 1):                                   # All-Gather：第 s 步，卡 i 把已经算完的第 (i + 1 − s) 块发给下一张卡，对方直接覆盖
    msgs = [(i, (i + 1 - s) % p, buf[i][(i + 1 - s) % p]) for i in range(p)]
    for i, c, v in msgs: buf[(i + 1) % p][c] = v; sent[i] += 1
    print(f"All-Gather     第 {s + 1} 步：" + "  ".join(f"卡{r}:{buf[r].tolist()}" for r in range(p)))
print(f"每张卡一共发了 {sent[0]} 块 = 2(p−1)/p · n = {2 * (p - 1) / p:.2f}n；朴素做法（都发给卡 0 再发回）卡 0 要收发 {2 * (p - 1)}n")

# 2. 耗时估算：每一步的耗时 = α（启动延迟）+ 这一步的数据量 ÷ β（单向带宽）
alpha, beta = 5e-6, 50e9                                 # 示意：α = 5 μs，β = 50 GB/s（一张卡的跨机网卡）
def naive(n, p): return 2 * (p - 1) * (alpha + n / beta)                 # 卡 0 依次收、依次发
def ring(n, p):  return 2 * (p - 1) * (alpha + n / p / beta)
def tree(n, p):  return 2 * math.ceil(math.log2(p)) * alpha + 2 * n / beta   # 流水化的树：延迟项 log p，带宽项约 2n
print("数据量 | 卡数 | 朴素 | Ring | Tree")
for n in [64e3, 1e9]:
    for pp in [8, 64, 512]:
        print(f"{n / 1e6:7.3f} MB | {pp:3d} | {naive(n, pp) * 1e3:9.3f} ms | {ring(n, pp) * 1e3:8.3f} ms | {tree(n, pp) * 1e3:8.3f} ms")
```

## 容易混淆的地方

1. **Ring 的“环”是逻辑上的。**它不要求物理上真的连成一个圈，只要相邻两张卡之间能通信。NCCL 会根据实际的连接（NVLink、PCIe、网卡）安排环的顺序，尽量让每一跳都走最快的路径。
2. **“带宽最优”不等于“最快”。**Ring 的带宽项达到了下限，但延迟项很大；消息小的时候，延迟项占主导，Tree 更快。
3. **All-Reduce 的时间和卡数的关系，取决于消息大小。**大消息时几乎不随卡数增长；小消息时，Ring 随卡数线性增长，Tree 按 log p 增长。

## 回顾

朴素的 All-Reduce 让一张卡收发 2(p − 1)·n，时间随卡数线性增长。Ring All-Reduce 把卡排成环，数据切成 p 块：先 p − 1 步 Reduce-Scatter（每块沿环走一圈、被每张卡加一次），再 p − 1 步 All-Gather；每步所有链路同时传 n/p，每张卡共发 2(p − 1)/p · n，达到下限。但它要 2(p − 1) 步，延迟项随卡数增长：1 GB、512 张卡时 Ring 约 45 ms，64 KB 时却要 5.1 ms。Tree All-Reduce 只要约 2·log₂p 步，64 KB、512 张卡时约 0.09 ms。NCCL 会根据消息大小和拓扑自动选择，机器内部还有 NVSwitch 的网内计算。
