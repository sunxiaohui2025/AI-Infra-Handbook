前面几讲让推理引擎变得越来越“贪心”：连续批处理（第 74 讲）让请求随时进来，分页（第 75 讲）让 KV Cache 一块一块按需分配，几乎不浪费。可是按需分配有一个隐患：一个请求进来时只分配了提示需要的块，它后面要生成多少个 token，事先不知道。几十个请求同时在生成，KV Cache 一起增长，池子总有被占满的时候。

这时某个请求要写下一个 token，却拿不到新块了。怎么办？这一讲讲推理引擎的**调度器**（scheduler）怎么回答两个问题：**新请求什么时候放进来**，以及**块不够时，让谁先让出位置**。

## 两种放行的态度

调度器手里有三个队列：

- **等待队列**（waiting）：已经到达、还没开始的请求，以及被抢占后等着重来的请求。
- **运行队列**（running）：正在 prefill 或 decode 的请求，每一步都要算。
- **已完成**：生成了结束标记或达到长度上限，块已经还回池子。

每一步开始时，调度器要决定能不能从等待队列里再放一些请求进来。这里有两种态度。

**保守：按最终长度预留。**一个请求进来时，就按“提示长度 + 最多生成的长度”把它将来要用的块全部预留好。这样它进来以后永远不会缺块，也就不会被打断。缺点和第 75 讲的连续预留一样：大部分预留的块在很长一段时间里是空着的，能同时运行的请求少，后来的请求只能等。而且真实的请求往往设了一个很大的长度上限（比如 4096），实际却只生成几百个 token，按上限预留浪费更多。

**乐观：按需分配。**请求进来时只分配提示需要的块，之后每写满一块再要一块。池子里能同时运行的请求多得多，GPU 的批也更满。代价是：一旦池子被占满，有人要新块却拿不到，就必须让某个请求**让出**它的块。这叫**抢占**（preemption）。

vLLM、SGLang 等推理引擎都选了乐观的做法，再用抢占兜底。

## 用一个小例子看抢占

我们用一个缩小的池子模拟一下：16 个块，每块 4 个 token；6 个请求，各自的到达时间、提示长度和要生成的 token 数如下。

| 请求 | A | B | C | D | E | F |
| --- | --- | --- | --- | --- | --- | --- |
| 第几步到达 | 0 | 0 | 1 | 2 | 3 | 4 |
| 提示长度 | 7 | 5 | 9 | 6 | 8 | 4 |
| 要生成的 token 数 | 9 | 12 | 6 | 10 | 5 | 7 |

调度的规则是这样的，每一步依次做三件事：

1. **运行中的请求先拿块。**按加入的顺序，每个请求要写 1 个新 token；最后一块写满了，就从池子里取一块新的。如果池子空了，就抢占**最后加入**的那个请求：把它的块全部释放，放回等待队列的最前面。
2. **放新请求进来。**如果这一步没有发生抢占，就按顺序看等待队列的第一个请求，池子里的空闲块够放下它，就放进来，做 prefill 并出第 1 个 token。
3. **生成完的请求离开**，块还回池子。

**按需分配时**，A 到 F 在第 0 到 4 步都顺利进来了，每个只占提示需要的两三块。到第 5 步，16 块已经全部用完，D 写满了它的最后一块，要一块新的，池子空了。调度器抢占了最后加入的 F：F 的块全部释放，F 回到等待队列的最前面。第 6 步，A 也要新块，又不够了，这次抢占的是 E。第 7 步，C 生成完毕还回了块，E 和 F 重新进来。它们之前算过的 KV Cache 已经扔掉了，要把提示和已经生成的部分重新 prefill 一遍：E 要重算 11 个 token（提示 8 个 + 已生成 3 个），F 要重算 5 个。全部请求在 **13 步**完成，平均延迟 **8.7 步**，一共抢占 2 次、重算 16 个 token。

**按最终长度预留时**，A、B、C 进来就各占了 4 到 5 块，13 块已经被预留，D 要 4 块，放不下，只能等。D 一直等到第 7 步 C 结束才进来，E、F 等到第 9 步。没有任何抢占，但全部完成要 **17 步**，平均延迟 **10.8 步**。

这个小例子里，抢占带来的重算代价（16 个 token），远远小于多运行几个请求带来的收益。实际系统也是这样：抢占偶尔发生，大部分时间池子都被充分利用。

## 抢占谁

块不够时，牺牲谁？最常见的做法是抢占**最后加入**的请求（或者在带优先级的调度里，优先级最低的请求）。理由是：

- **公平。**先到的请求已经等了更久，按先来先服务（FCFS）的原则应该先完成。
- **代价小。**最后加入的请求通常算得最少，扔掉它的 KV Cache，要重算的也最少。
- **不会饿死。**被抢占的请求回到等待队列的**最前面**，一有空位就最先回来，不会被后来的请求一直插队。

还有一个细节：发生抢占的那一步，调度器**不再放新请求进来**。道理很简单：刚因为块不够把别人赶出去，又放新人进来，马上又会不够，请求在进进出出之间来回折腾（这叫“抖动”，thrashing）。有些实现还会在池子里留一小部分块作为“水位线”（watermark），空闲块少于它时就不再放新请求，提前避免抢占。

## 重算还是换出

被抢占的请求，它的 KV Cache 怎么处理？有两种办法：

- **重算**（recompute）：直接扔掉。请求重新回来时，把提示和已经生成的 token 一起重新 prefill 一遍，KV Cache 就又有了。
- **换出**（swap）：把它的 KV Cache 块复制到 CPU 内存里，块还回池子；请求回来时，再从 CPU 内存复制回显存。

哪个更快？代码估算了 Llama-3-8B 上一个 2000 token 的请求：它的 KV Cache 有 **262 MB**，重算（prefill 2000 个 token）约 **30.3 ms**，换出再换回（按 PCIe 5.0 约 50 GB/s 估算）约 **10.5 ms**。只看这一个数字，换出更快。

可实际的推理引擎更偏向重算。vLLM 的 V1 引擎只保留了重算这一种方式（具体以所用版本的文档为准）。原因有几个：

- **换出要占 PCIe 带宽和 CPU 内存**，抢占往往发生在负载最高的时候，大量请求同时换进换出，PCIe 很快成了瓶颈，还要管理一个 CPU 端的块池，实现复杂得多。
- **重算可以顺便利用前缀缓存。**被抢占的请求释放的块，只要还没被别人覆盖，仍然留在前缀缓存里（第 76 讲）。它回来时，前面的部分很可能直接命中，真正要重算的只有一部分。
- **重算的 prefill 可以切块**（第 77 讲），和别的请求的 decode 一起进行，不会卡住别人。
- **抢占本来就应该很少发生。**如果频繁抢占，说明负载已经超过了这张卡的能力，该做的是限流或者加卡，而不是优化抢占本身。

## 先服务谁：调度策略

除了“块不够时抢占谁”，调度器还要决定等待队列里**谁先进来**。最常见的是**先来先服务**（FCFS），简单、公平、不会饿死人。但它不一定是最好的：

- **队头阻塞。**一个很长的请求排在前面，池子放不下它，后面一串短请求即使放得下，也只能干等。有的调度器允许短请求“越过”放不下的长请求先进来，但要防止长请求被一直越过、永远轮不到。
- **优先级。**付费用户、在线交互的请求，可能比离线批量任务更重要。vLLM 支持按优先级调度：优先级高的先进来，块不够时优先抢占优先级低的。
- **缓存感知。**SGLang 的调度器可以优先放进**和前缀缓存重叠最多**的请求（最长前缀匹配，第 76 讲），让缓存的命中率更高，整体吞吐更高。代价是有些请求可能要多等一会儿。

调度策略没有对所有场景都最好的答案，它总是在吞吐、平均延迟、尾延迟和公平之间做取舍。

## 到了大模型里

**几个关键的参数。**vLLM 里和调度直接相关的有：`max_num_seqs`（同时运行的请求数上限）、`max_num_batched_tokens`（每一步的 token 预算，第 77 讲）、`gpu_memory_utilization`（多大比例的显存给模型和 KV Cache，决定了池子有多大，第 71 讲）。

**看日志里的抢占。**vLLM 在发生抢占时会打出警告，监控指标里也有抢占次数。偶尔出现没关系；如果持续出现，说明 KV Cache 的池子相对于负载太小了：可以调小 `max_num_seqs`，调大 `gpu_memory_utilization`，换更大显存的卡，或者用 KV Cache 量化（第 12 篇）、多卡并行（第 13 篇）扩大池子。

**调度器自己要够快。**每一步都要跑一遍上面的逻辑：遍历几百个请求、分配和释放块、整理块表。decode 一步只有几毫秒，调度如果花上一两毫秒，GPU 就会空等。所以推理引擎在调度器的实现上花了很多功夫，比如让调度和 GPU 计算重叠进行（第 81、89 讲）。

## 用代码复现

下面的代码实现了上面的调度规则，模拟这 6 个请求在两种放行方式下的过程，打出按需分配时发生的抢占；最后估算 Llama-3-8B 上重算和换出的代价。

```python
B, NB = 4, 16                                            # 每块 4 个 token，池子一共 16 块（64 个 token）
# 请求：名字、第几步到达、提示长度、要生成的 token 数
REQS = [("A", 0, 7, 9), ("B", 0, 5, 12), ("C", 1, 9, 6), ("D", 2, 6, 10), ("E", 3, 8, 5), ("F", 4, 4, 7)]
need = lambda n: -(-n // B)                              # n 个 token 要几块

def simulate(mode, log=False):
    """mode = "reserve"：按最终长度一次预留，不会被抢占；"preempt"：按需分配，块不够就抢占最后到的请求（重算）。"""
    gen = {r[0]: 0 for r in REQS}; kv = {}; blocks = {}; free = NB
    waiting, running, finish, preempts, recompute, step = [], [], {}, 0, 0, 0
    while len(finish) < len(REQS):
        waiting += [r for r in REQS if r[1] == step]
        # 1. 正在运行的请求各要写 1 个新 token；块不够就抢占队尾的请求
        preempted_now = False
        for r in list(running):
            if r not in running: continue
            n = r[0]
            while need(kv[n] + 1) > blocks[n] and free == 0:
                v = running.pop()                        # 最后加入的请求让出全部块，回到等待队列最前面
                free += blocks.pop(v[0]); kv.pop(v[0]); waiting.insert(0, v)
                preempts += 1; recompute += v[2] + gen[v[0]]; preempted_now = True
                if log: print(f"  第 {step:2d} 步：块不够了，抢占 {v[0]}（释放它的块，之后要重算 {v[2] + gen[v[0]]} 个 token）")
                if v is r: break
            if r in running:
                if need(kv[n] + 1) > blocks[n]: blocks[n] += 1; free -= 1
                kv[n] += 1; gen[n] += 1
        # 2. 没有发生抢占时，按到达顺序放等待的请求进来（prefill 提示和已生成的部分，并出 1 个 token）
        while waiting and not preempted_now:
            r = waiting[0]; n = r[0]
            want = need(r[2] + r[3]) if mode == "reserve" else need(r[2] + gen[n])
            if want > free: break
            waiting.pop(0); running.append(r); free -= want; blocks[n] = want; kv[n] = r[2] + gen[n]; gen[n] += 1
        # 3. 生成完的请求离开，块还回池子
        for r in [r for r in running if gen[r[0]] == r[3]]:
            running.remove(r); free += blocks.pop(r[0]); kv.pop(r[0]); finish[r[0]] = step + 1
        step += 1
    lat = [finish[r[0]] - r[1] for r in REQS]
    return step, sum(lat) / len(lat), preempts, recompute, {r[0]: finish[r[0]] for r in REQS}

for mode, name in [("reserve", "按最终长度预留"), ("preempt", "按需分配 + 抢占")]:
    steps, avg, pre, rc, fin = simulate(mode, log=(mode == "preempt"))
    print(f"{name}：全部完成 {steps} 步，平均延迟 {avg:.1f} 步，抢占 {pre} 次，重算 {rc} 个 token；完成时刻 {fin}")

# 真实规模：Llama-3-8B 一个 2000 token 的请求被抢占，重算 vs 换出到 CPU 内存再换回
KV, F, Nn, PCIE = 2 * 32 * 8 * 128 * 2, 989e12, 7.5e9, 50e9          # PCIe 5.0 x16 按约 50 GB/s 估
n = 2000
print(f"2000 个 token 的 KV Cache = {KV * n / 1e6:.0f} MB；重算（prefill）≈ {2 * Nn * n / F * 1e3:.1f} ms；"
      f"换出再换回 ≈ {2 * KV * n / PCIE * 1e3:.1f} ms")
```

输出：

```text
按最终长度预留：全部完成 17 步，平均延迟 10.8 步，抢占 0 次，重算 0 个 token；完成时刻 {'A': 9, 'B': 12, 'C': 7, 'D': 17, 'E': 14, 'F': 16}
  第  5 步：块不够了，抢占 F（释放它的块，之后要重算 5 个 token）
  第  6 步：块不够了，抢占 E（释放它的块，之后要重算 11 个 token）
按需分配 + 抢占：全部完成 13 步，平均延迟 8.7 步，抢占 2 次，重算 16 个 token；完成时刻 {'A': 9, 'B': 12, 'C': 7, 'D': 12, 'E': 9, 'F': 13}
2000 个 token 的 KV Cache = 262 MB；重算（prefill）≈ 30.3 ms；换出再换回 ≈ 10.5 ms
```

第一行是按最终长度预留：17 步、平均延迟 10.8 步、没有抢占。接下来两行是按需分配时的两次抢占，和演示里第 5、6 步的事件一致；然后是它的结果：13 步、8.7 步、抢占 2 次、重算 16 个 token。最后一行是真实规模下重算和换出的代价。

## 容易混淆的地方

1. **抢占不是取消。**被抢占的请求不会失败，也不会被丢掉，只是暂停，之后从断开的地方接着生成。用户看到的最多是一次停顿。
2. **重算的结果和原来完全一样。**被抢占前已经生成的 token 会被保留，重新 prefill 时作为输入的一部分，所以接下来的生成和没被抢占时一致（不考虑浮点误差）。
3. **抢占解决的是 KV Cache 不够，不是算力不够。**算力不够时，每一步变慢，TPOT 变长；显存不够时，才会触发抢占。两者都是过载的表现，但处理方式不同。

## 回顾

按需分配让 KV Cache 的池子能同时装下更多请求，但请求的长度事先不知道，池子总可能被占满。调度器每一步先让运行中的请求拿块，块不够时抢占最后加入的请求，释放它的块，让它回到等待队列的最前面；发生抢占的那一步不放新请求进来，避免来回折腾。6 个请求、16 块的例子里，按需分配加抢占 13 步完成，按最终长度预留要 17 步。被抢占的请求可以重算或换出，现在的推理引擎多用重算，因为它简单，还能利用前缀缓存和分块 prefill。放请求进来的顺序默认是先来先服务，也可以按优先级或缓存命中来排。

到这里，推理引擎的核心机制已经齐了。调度时我们一直默认所有请求用同一份模型；可如果几百个客户各有一个微调过的版本，一个 batch 里的请求要用不同的权重，又该怎么算？下一讲：**多 LoRA 服务**。
