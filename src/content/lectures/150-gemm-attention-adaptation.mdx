上一讲把瓶颈定位到了最热的那几个算子。推理里最热的永远是两个：矩阵乘法（权重投影，一步要把全部权重读一遍）和注意力。这一讲讲它们在一块新卡上为什么需要重做，以及怎么重做。

先把结论摆在前面，它很反直觉：**厂商的矩阵乘库在 decode 时往往是最糟的选择**。不是因为库写得差，而是因为库默认的那套分块是为训练和 prefill 那种大矩阵调的，decode 的形状（M 只有几十）恰好落在它最不擅长的区间。下面用海光插件源码注释里给出的真实数字算这笔账。

## 矩阵单元的三个硬约束

第 142 讲说过矩阵核心按固定形状吃数据。这件事对 kernel 提出三个要求。

**指令形状与对齐**。一条指令算 im × in 的输出、沿 K 走 ik 步。输出块的行数必须补齐到 im 的倍数、列数补齐到 in 的倍数，K 方向也要对齐。海光那个小 M kernel 的约束条件写得很直白：`M 在 [1, 64]`、`N 只支持 256 / 512 / 1024 / 2048`、`K 必须是 128 的倍数`（`vllm_hcu/utils/bf16_fp32_mmac.py` 的 `supported()`，提交 81cbe8f）。这不是偷懒，而是把对齐要求显式写成了入口检查：不满足就走别的实现，而不是悄悄算错。

**数据排布**。矩阵核心要求参与运算的数据在寄存器或片上存储里按特定方式摆放（哪条通道拿哪几个元素）。所以 kernel 里常见两件事：把权重**预先转置**成 kernel 想要的方向，以及按 16 字节对齐做向量化加载。海光的代码里两种布局都有：一个环境变量控制权重按 `[in_features, out_features]` 还是 `[out_features, in_features]` 存，入口处先判断布局再决定走哪条路（`vllm_hcu/utils/bf16_fp32_gemm.py`）。注意力的 KV Cache 也有同样的问题，插件的文档里要求用 FlashAttention 后端时设 `VLLM_KV_CACHE_LAYOUT=HND`，并提醒混合注意力的模型不要全局强制这个布局。

**每条通道持有多少累加器**。输出块的元素分摊在线程组的通道里，通道数不同，每条通道手里的累加器个数就不同（第 142 讲的 16×16 指令：32 条通道每条 8 个，64 条每条 4 个）。这个数字直接决定寄存器压力和一个计算单元能驻留几个块。

## decode 的小 M：库为什么会选错

现在算那笔账。场景取海光插件注释里的例子：一个 lm_head 分片，权重 32224 × 4096（BF16）。decode 时 M ≤ 64。

```python
# 海光插件源码注释里的一组数（vllm_hcu/model_executor/layers/skinny_lm_head.py 开头，提交 81cbe8f）：
# lm_head 分片 32224 × 4096 的 BF16 权重，M ≤ 64 属于“纯读权重”的形状；
# hipBLASLt 在这里选 256×256 的宏块，M=16 时 285 μs；只沿 N 分块的专用 kernel 153 μs，M=64 时 190 μs。
N, K = 32224, 4096
bw_w = N * K * 2                                  # BF16 权重的字节数：decode 时要读的主要数据
print(f"权重 {N} × {K} BF16 = {bw_w / 1e6:.0f} MB（decode 时每步都要整读一遍）")
for name, m, us in [("库选的 256×256 宏块", 16, 285), ("只沿 N 分块的专用 kernel", 16, 153), ("只沿 N 分块的专用 kernel", 64, 190)]:
    print(f"  {name}，M = {m:2d}：{us} μs → 实际带宽 {bw_w / (us * 1e-6) / 1e12:.2f} TB/s，"
          f"实际算力 {2 * m * N * K / (us * 1e-6) / 1e12:.1f} TFLOPS")

print("\n同一个 M = 16 的输出，两种分块的账")
for mt, nt in [(256, 256), (16, 64)]:
    rows = -(-16 // mt) * mt                      # 行方向补齐到块的倍数
    blocks = -(-16 // mt) * -(-N // nt)
    print(f"  输出块 {mt:3d} × {nt:3d}：补到 {rows:3d} 行（有效 16，浪费 {1 - 16 / rows:4.0%}），"
          f"{blocks:3d} 块，矩阵指令算的格子 {blocks * mt * nt / 1e6:.1f} M（有用的只有 {16 * N / 1e6:.1f} M）")
```

```text
权重 32224 × 4096 BF16 = 264 MB（decode 时每步都要整读一遍）
  库选的 256×256 宏块，M = 16：285 μs → 实际带宽 0.93 TB/s，实际算力 14.8 TFLOPS
  只沿 N 分块的专用 kernel，M = 16：153 μs → 实际带宽 1.73 TB/s，实际算力 27.6 TFLOPS
  只沿 N 分块的专用 kernel，M = 64：190 μs → 实际带宽 1.39 TB/s，实际算力 88.9 TFLOPS

同一个 M = 16 的输出，两种分块的账
  输出块 256 × 256：补到 256 行（有效 16，浪费  94%），126 块，矩阵指令算的格子 8.3 M（有用的只有 0.5 M）
  输出块  16 ×  64：补到  16 行（有效 16，浪费   0%），504 块，矩阵指令算的格子 0.5 M（有用的只有 0.5 M）
```

三行数字说明了全部问题。

这个形状**受带宽限制**：要读 264 MB 权重，算的只有 16 × 32224 × 4096 × 2 ≈ 4.2 GFLOP，算术强度约等于 M = 16，远在拐点左边（第 142 讲算过）。所以唯一该看的指标是**实际带宽**：库选的分块跑出 0.93 TB/s，专用 kernel 跑出 1.73 TB/s——**快了 1.9 倍，而计算量一模一样**。

为什么库会慢？因为 256 × 256 的宏块在行方向上补了 94% 的零。补零不仅浪费矩阵单元的格子（算了 8.3 M 个格子，有用的只有 0.5 M），更关键的是它改变了访存模式：一个 256 行的块要为那 16 行真实数据准备 256 行的空间和流水，片上存储和寄存器都按 256 行配，于是一个计算单元能驻留的块数变少，在途的读请求也变少——而受带宽限制的 kernel 恰恰需要尽可能多的在途请求才能把带宽喂满（第 86 讲）。

专用 kernel 的做法是**只沿 N 分块，M 方向一个块吃完**：块的行数就等于 M（或 16 的倍数），一行零都不补，块数从 126 变成 504，刚好让更多计算单元同时发出读请求。

这解释了另一条注释里更极端的数字：DeepSeek V4 的压缩投影在 decode 时每卡 M ≤ 64，`hipBLASLt 选了 256×256 的块，不管 N 多大都要约 135 μs`（`vllm_hcu/utils/bf16_fp32_mmac.py` 开头）。“不管 N 多大”是关键——时间完全由分块的固定代价决定，和真实工作量脱钩了。于是海光为 M ≤ 64、N ∈ {256, 512, 1024, 2048}、K 是 128 倍数的这一类形状写了专门的 kernel，第 158 讲会逐行读它。

<Note kind="point">这就是第 87 讲“小 M 矩阵乘”问题在一块新卡上的样子，而且比在 NVIDIA 上更严重：cuBLAS 为 decode 形状准备了多套 kernel 和启发式规则，一个年轻的库往往只有为大矩阵调好的那几套。**适配时要专门测一遍 decode 的形状**（M = 1、8、16、32、64），而不是只测大矩阵的 TFLOPS——后者好看，前者才是服务里真正跑的。</Note>

## 什么时候该自己写、怎么选形状

把上面的逻辑整理成可操作的判断：

| 形状 | 谁更合适 | 理由 |
| --- | --- | --- |
| M ≥ 512（prefill、训练） | 厂商库 | 大块复用充分，库里为这类形状调过 |
| 64 < M < 512 | 先测库，再决定 | 过渡区，和库的启发式规则有关 |
| M ≤ 64（decode） | 往往要专用 kernel | 受带宽限制，库的大分块补零太多 |
| N 很大、M 很小（lm_head、MoE 路由） | 专用 kernel | 纯读权重，只沿 N 分块最优 |
| K 特别大（压缩投影、MLA） | 考虑 split-K | 块数不足时沿 K 切开凑并行度（第 87 讲） |

写专用 kernel 时，形状的选法有几条经验：输出块的行数取 max(M 补齐到指令行数, 指令行数)，不要更大；列数按“一个块能驻留、且块数足够盖住所有计算单元”来定；K 步长按片上存储容量定，留出双缓冲的余量（第 142 讲的 `WaveTile` 可以直接试）。

## 注意力：三种实现，按条件选

注意力的适配比矩阵乘复杂，因为 prefill 和 decode 要的是两种不同的 kernel（第 84、85 讲）。

**prefill 要 FlashAttention 式的实现**：注意力矩阵不落地，分块扫过 K、V，在线更新 softmax 的 m、l 和累加器。它的移植难点不在算法，而在分块参数——块大小由片上存储容量决定，而容量换一块卡就变了：

<FlashTileSize caption="图 150-3　FlashAttention 的块大小受片上存储容量约束。把容量从 228 KB 调到 64 KB，看能放的 Q 行数、扫描次数和读写量怎么变（第 84 讲的模型）。" />

**decode 要 Flash-Decoding 式的实现**：查询只有一行（或几行），要沿 KV 的长度方向切开并行，最后归约（第 85 讲）。在新卡上这一步常常是性能缺口最大的地方，因为它的并行度来源和 prefill 完全不同。

**兜底是“打分矩阵落地”的朴素实现**：`bmm` + `softmax` + `bmm`，就是 miniinfer 的做法。正确，但长上下文下显存和带宽都吃不消。

所以厂商插件里通常不是一个注意力实现，而是**一组后端加一套选择顺序**。海光插件的平台类里就写着这个顺序（`vllm_hcu/platforms/hcu.py` 的 `_get_backend_priorities`，提交 81cbe8f）：稀疏注意力的模型先试稀疏 MLA 的两个后端；MLA 模型先试 FlashMLA，退而用 Triton 版的 MLA；普通的 MHA / GQA 模型先试 FlashAttention，退而用 Triton 版。每个候选都要先通过一次 `validate_configuration` 检查（头数、块大小、数据类型、这块卡的架构支不支持），不通过就换下一个，全都不通过就报错而不是悄悄降级。第 159 讲会读这段代码。

<Note kind="warn">注意力适配里最容易踩的两个坑。一是**块大小和 KV 分页的块大小耦合**：注意力 kernel 支持的块大小有限（例如只支持 16、32、64），而引擎的 KV 块大小是配置项，两者不匹配时要么报错要么性能很差——海光插件专门有一个 `update_block_size_for_backend` 来调和这件事。二是**布局**：K、V 在显存里按“头优先”还是“序列优先”摆，不同后端的要求不同，混合注意力的模型里可能同时存在两种要求。</Note>

## 适配这两个算子的顺序

1. 先用框架的通用实现（`torch.matmul` + 朴素注意力）跑通跑对，拿到基线（第 148 讲）。
2. 换上厂商库和厂商移植的 FlashAttention，重新跑精度比对（第 146 讲）——库换了，累加顺序就变了。
3. 按真实负载测形状矩阵：prefill 的几个长度、decode 的 M = 1 到 64、几种上下文长度。每个格子记下实际带宽或实际算力占上限的比例。
4. 只给“占比高且离上限远”的格子写专用 kernel。decode 的小 M 几乎总是第一个。
5. 写完之后再跑一遍逐层比对和 token 级比对。

<Note kind="column">这个顺序里第 3 步最容易被跳过，但它是全部判断的依据。做成一张表：行是形状，列是实现（库、厂商 kernel、自写 kernel），格子里是耗时和实际带宽。表一摆出来，“该写哪个 kernel”就不用争论了——海光插件里那两个专用 kernel（lm_head 的和压缩投影的），注释里写的正是这张表上的几个格子。</Note>

## 回顾

矩阵单元给 kernel 三个硬约束：指令形状与对齐、数据排布、每条通道持有的累加器数。decode 的小 M 形状上，厂商库默认的大分块会补掉九成以上的行，于是实际带宽只有专用 kernel 的一半——海光插件注释里的 lm_head 例子是 0.93 TB/s 对 1.73 TB/s，1.9 倍的差距而计算量完全相同；另一处注释更极端：M ≤ 64 时库选的 256 × 256 分块“不管 N 多大都要约 135 μs”。注意力要按 prefill 和 decode 分别准备实现，块大小随片上容量重选，并且做成一组后端加一套带校验的选择顺序。适配顺序是先通用实现拿基线、再换库、再按形状矩阵测、最后只给值得的格子写 kernel。

自己写 kernel 就要选语言。下一讲比较三条路：Triton、新兴的块级 kernel 语言、厂商自己的 C++ 模板库和 kernel 语言，用同一个 RMSNorm 把几种写法摆在一起看。
