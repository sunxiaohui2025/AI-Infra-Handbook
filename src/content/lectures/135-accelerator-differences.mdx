上一讲把软件栈拆成了九层，其中算子库和 kernel 那两层要重写。重写之前得先知道：这块卡和 H100 到底哪里不一样？“不一样”不是指快慢——参数表上的峰值算力和带宽只是两个数——而是指**同一个算子在这块卡上该怎么组织**。

这一讲回答三件事：两条硬件路线（GPGPU 和 NPU）的内部结构差在哪；线程组宽度从 32 变成 64、片上存储从 228 KB 变成 64 KB，对一个矩阵乘或注意力 kernel 具体意味着什么；这些差异怎么改变第 62 讲那张 Roofline 图上各类算子的落点。

## 两条路线：一块卡里面的分工

<AccelArch route="gpgpu" caption="图 135-1　GPGPU 路线的卡内结构（示意图，不按比例）。点任意部件看它负责什么；切到另一条路线，看同一件事由谁来做。" />

GPGPU 这条路线上，NVIDIA 的 SM、AMD 的 CU、海光 DCU 的计算单元，分工是一样的：**一个 kernel 启动成千上万个线程，线程按固定宽度编成线程组，组内所有通道同一拍执行同一条指令**（第 86 讲的 SIMT）。搬数据的代码由线程自己写：谁读哪一段显存、要不要先搬进共享内存给同块的线程共用，都写在 kernel 里。矩阵乘法的峰值算力来自专门的矩阵核心，它按固定形状吃矩阵块（第 87 讲）。

<AccelArch route="npu" caption="图 135-2　NPU / DSA 路线的卡内结构（示意图，不按比例）。核的数量比 GPGPU 少一个量级，但每个核里有明确分工的三类单元和几级软件管理的缓冲。" />

NPU（也叫 DSA，领域专用架构）这条路线放弃了 SIMT。一个核里是三类单元各管一摊：**标量单元**管控制流和地址，**向量单元**管逐元素运算和归约，**矩阵单元**管矩阵乘；数据进出片上缓冲由专门的**搬运单元**负责，kernel 里要显式写“把这块搬进来、算、搬回去”，并自己把搬和算流水起来。写这类 kernel 的感觉更接近写 DMA 驱动，而不是写并行循环。

两者的差别带来两个直接后果。

一是**代码不能翻译，只能重写**。CUDA kernel 的核心是 `threadIdx` 和 `blockIdx`：每个线程根据自己的编号算出负责哪个元素。NPU 上没有这个概念，所以第 136 讲说的 hipify 这类工具在这条路线上完全派不上用场。

二是**“把卡占满”的办法不同**。GPGPU 靠块数：132 个计算单元要 132 个以上的线程块才能都有活干，块数不够就得 split-K（第 87 讲）。NPU 的核只有几十个，一个核的矩阵单元却更大，所以并行度要靠“每个核处理一个足够大的块”获得；块太小时，吃亏的不是空闲的核，而是搬运和算没法重叠起来。

## 线程组宽度：32 和 64 差在哪

GPGPU 路线内部最常踩的坑，是线程组宽度。NVIDIA 的 warp 是 32 个线程；AMD 和海光的波前（wavefront）是 64 个。海光 vLLM 插件里的小 M 矩阵乘 kernel 开头就写着 `constexpr std::int32_t kWaveSize = 64;`（第 151 讲会读这个 kernel）。宽度不同，四处要改：

**跨通道归约的步数**。一个线程组内做求和（softmax 的分母、RMSNorm 的平方和），用的是跨通道移位指令，步数是 log₂w：w = 32 要 5 步，w = 64 要 6 步。写死 5 次循环的代码在 64 宽度的卡上只归约了一半的通道，结果是错的——而且不会报错。

**掩码的类型**。投票和表决类指令返回每条通道一位的掩码：32 宽度放得进一个 `uint32_t`，64 宽度必须用 `uint64_t`。CUDA 代码里到处是 `unsigned` 的掩码，这是 hipify 翻不动、只能手改的一类。

**每条通道持有的累加器个数**。一条矩阵指令算一块固定形状的输出，这块输出分摊在组内所有通道的寄存器里。16×16 的输出有 256 个元素：32 条通道时每条拿 8 个，64 条通道时每条拿 4 个。

**块内的线程数怎么凑**。一个线程块常用 256 个线程：在 32 宽度上是 8 个线程组，在 64 宽度上是 4 个。于是“每个线程组负责输出块的哪一片”这件事要重新分，同步的粒度也跟着变。

# H100 用第 60 讲一直用的官方规格；另外两行是按两条路线的量级设的参数，换成你手上卡的官方规格即可

    ("H100 SXM", 989, 3.35, 132, 32, 228),
    ("GPGPU 示例", 1300, 5.3, 304, 64, 64),
    ("NPU 示例", 400, 1.6, 24, 0, 512),
]
print("拐点（FLOP/字节）= 峰值算力 ÷ 带宽；decode 一步 M 个 token 的线性层，强度约等于 M")
for name, tf, tb, cu, w, smem in cards:
    reach = min(tf, 16 * tb)                       # M = 16 时能达到的 TFLOPS
    print(f"{name}：拐点 {tf / tb:.0f}，M=16 最多跑到 {reach:.0f} TFLOPS，占峰值 {reach / tf:.1%}")

print("\n一条 16×16×16 的矩阵指令，每条通道要持有几个 FP32 累加器")
for w in (32, 64):
    print(f"  线程组宽度 {w}：{16 * 16 // w} 个")

print("\nM=16 的 decode，输出块越大、补的零越多")
for mt in (16, 64, 128, 256):
    print(f"  输出块 {mt} 行：有效 {min(16, mt)} 行，浪费 {1 - min(16, mt) / mt:.1%}")

print("\nFlashAttention 的 K/V 块能开多大（head_dim 128，BF16，K、V、Q 各一份）")

最后一组数值得停一下。片上存储从 228 KB 掉到 64 KB，FlashAttention 一次能装下的 K/V 行数从 304 掉到 85——这意味着扫一遍 4096 长的上下文，分块次数从 14 次变成 49 次，每次都要重做一轮在线 softmax 的更新（第 84 讲的 `FlashTileSize` 演示里能看到这个关系）。所以“把 FlashAttention 移植过来”这件事，不只是把语法翻译一遍，分块参数要按新的容量重新选。

## Roofline 的形状变了

第 62 讲用拐点把算子分成两类：算术强度在拐点左边的受带宽限制，右边的受算力限制。拐点 = 峰值算力 ÷ 带宽，所以换卡就是换拐点。

<RooflinePlot gpus={[['H100 SXM', 989e12, 3.35e12], ['GPGPU 示例', 1300e12, 5.3e12], ['NPU 示例', 400e12, 1.6e12]]} points={[['逐元素运算（RMSNorm、SwiGLU）', 0.25], ['decode 注意力（GQA×4）', 4], ['decode 线性层（16 个请求）', 16], ['prefill 线性层（2048 token）', 1792]] } caption="图 135-4　同一组算子落在三条路线的 Roofline 上。切换卡看拐点怎么动；拖算术强度和线性层的 token 数，找出这块卡上 decode 开始受算力限制的批大小。三组参数的来源见上面的代码注释，非 NVIDIA 的两行按官方规格替换。" />

有意思的是上面代码算出的那三个拐点：295、245、250。它们差别不大——因为峰值算力和带宽往往一起涨。这就引出一个反直觉的结论：**换一块卡，算子“卡在哪一边”这件事通常不变**。decode 的线性层在三块卡上都只能跑到峰值的 5% 到 7%，因为它的算术强度约等于批大小，而批大小远小于任何一个拐点。换卡不改变这个事实，第 68 讲的结论（decode 受带宽限制）在新硬件上照样成立。

真正变的是三件更具体的事：

**绝对带宽**。decode 一步的时间下限 = 要读的权重字节数 ÷ 带宽。带宽从 3.35 TB/s 到 5.3 TB/s，同一个模型的 TPOT 下限直接差 1.6 倍，和算力无关。

**达到上限的难度**。受带宽限制的 kernel 要跑满带宽，需要足够多的计算单元同时在途发出读请求（第 86 讲）。计算单元数、每单元能在途多少字节、L2 的组织方式都不一样，所以“理论带宽的几成”这个效率因子换卡后要重新测——第 67 讲强调过它，第 142 讲会用 profiler 量它。

**哪些算子有现成实现**。Roofline 只说上限，不说有没有人把这个上限做出来。注意力在 H100 上有 FlashAttention 的多代实现，换一块卡可能只有一个 Triton 版本，实测离上限很远。这是适配阶段最常见的差距来源，而它在 Roofline 图上完全看不见。

<Note kind="warn">参数表上的峰值算力有两个容易混的点：一是稀疏算力（NVIDIA 的 Tensor Core 规格常给 2:4 稀疏下的数字，是稠密值的两倍），二是不同数据类型（FP16 / BF16 / FP8 / INT8 的峰值依次翻倍）。比较两块卡时，要确认比的是同一种类型、同样是稠密值。第 63 讲列过各精度的关系。</Note>

## 片上存储和互联

除了线程组宽度，还有两处差异会改变算子设计。

**片上存储的容量和层次**。GPGPU 上是“寄存器 + 共享内存 + L2”三级，共享内存由块内线程共享，容量几十到几百 KB。NPU 上是几级软件管理的缓冲（L1 大缓冲、紧贴矩阵单元的 L0 A/B/C），容量往往更大，但**必须显式填充**：没有“自动缓存命中”这回事，搬运的时机和粒度都写在代码里。这解释了为什么 NPU 更依赖图模式（第 138 讲）——编译器拿到整张图，才能在图的尺度上安排搬运和复用；逐个算子下发时，每个算子都得自己把数据搬进来再搬出去。

**互联拓扑**。第 102 讲算过，All-Reduce 的代价由每轮固定开销 α 和带宽 β 决定，而算法的选择取决于拓扑：机内全连接（每张卡到每张卡都有直连）时 Ring 和一步到位都可行；如果是环状或立方体直连，跳数就要算进延迟（第 115 讲的 `TorusVsSwitch`）。换卡时这部分完全重来：通信库换了、拓扑换了、P2P 能不能用也换了，第 146 讲专门讲。

## 什么时候这些差异会反过来

上面说的“NPU 核少块大、GPGPU 核多块小”，有两种负载会让结论反转。

**极小 batch 的 decode**。一步只有十几个 token，矩阵乘的 M 很小。这时候矩阵单元越大越吃亏：指令形状要求 M 补齐到 16 或 32 的倍数，库选的输出块可能是 256 行，于是 94% 的行在算补的零（上面代码的最后一组数）。第 151 讲会看到海光为此专门写了 M ≤ 64 的 kernel，绕开库的大分块。**矩阵单元大是优势还是负担，取决于 M**。

**长上下文的注意力**。prefill 一个 128K 的上下文，注意力的计算量按序列长度的平方涨，算术强度很高，这时拼的是峰值算力和片上存储容量，片上缓冲大的设计反而占优：块开得大、扫的轮数少、在线 softmax 的更新次数少。

**通信密集的 MoE**。第 111 讲的结论是大 EP 的瓶颈常在网络。这时候卡内的差异几乎不起作用，决定吞吐的是互联带宽和 All-to-All 的实现质量。

<Note kind="point">换卡后要重新算的，不是“算子卡在算力还是带宽”（这个结论通常不变），而是三组硬件常数：线程组宽度（决定归约步数、掩码类型、累加器分配）、矩阵指令形状与对齐（决定小 M 时补多少零）、片上存储容量（决定分块和注意力的块大小）。把这三组数填进 kernel 的分块公式，就知道该怎么重新选参数。</Note>

## 回顾

两条硬件路线的分工不同：GPGPU 用 SIMT，线程自己搬数据，靠很多小块占满卡；NPU 把标量、向量、矩阵单元分开，数据靠搬运单元显式进出片上缓冲，靠大块喂饱少数几个核。GPGPU 路线内部最具体的差异是线程组宽度 32 对 64，它改变归约步数、掩码类型、每通道累加器数和块内线程的分组方式。片上存储容量决定了分块和 FlashAttention 的块大小：从 228 KB 到 64 KB，一次能装的 K/V 从 304 行掉到 85 行。Roofline 的拐点在不同卡上反而接近，所以算子受带宽还是受算力限制这件事通常不变，变的是绝对带宽、达到上限的难度，以及有没有人把这个上限实现出来。
