第 63 讲的显存账本算出：Llama-3-8B 在一张 80 GB 的卡上，留给 KV Cache 的空间约 49 GiB，能放约 40 万个 token。可是“能放 40 万个 token”和“能同时服务多少个请求”之间，还隔着一个问题：**这 40 万个 token 的空间，怎么分给一个个请求？**

连续批处理（第 66 讲）让请求随时进出，每个请求的 KV Cache 一边生成一边增长，长度事先不知道，结束的时间也不知道。如果分配的方式不好，大量的显存会被浪费在“预留了但没用上”的地方，能同时服务的请求数就会远低于账本上的数字。

2023 年 vLLM 提出的 **PagedAttention** 解决了这个问题。它借用了操作系统管理内存的经典思路：**分页**。这一讲先看传统做法浪费在哪里，再看分页是怎么做的、为什么几乎不浪费，以及它顺带带来的“共享”能力。它是今天几乎所有推理引擎管理 KV Cache 的基础。

## 传统做法：给每个请求预留一整块

最直接的做法，是像普通的张量那样，给每个请求分配一块**连续**的显存来存它的 KV Cache。问题是：请求刚开始时，不知道它最终会有多长。为了保险，只能按**最大可能的长度**预留，比如模型支持的最大上下文 4096 个 token。

这会带来三种浪费：

1. **预留了没用上**：一个请求最终只有 1500 个 token，却占了 4096 个 token 的空间，剩下的 2596 个位置一直空着，别的请求也不能用。这叫**内部碎片**。
2. **还没生成的部分**：即使事先知道最终长度、按最终长度预留，在请求生成到一半时，后一半的空间也已经被占着，暂时空闲。
3. **外部碎片**：请求来来去去，释放出来的空间大小不一、位置分散。新请求需要一整块连续的 4096 个 token，即使空闲的总量足够，也可能找不到一块足够大的连续空间。

下面的代码模拟了一个快照：64 个请求正在运行，提示长度在 200 到 2000 之间，最终输出 50 到 1000 个 token，各自生成到了一半左右。它们实际一共有 86151 个 token 的 KV Cache。

- **按最大长度（4096）连续预留**：占用 262144 个 token 的空间，利用率只有 **32.9%**。
- **按最终长度连续预留**（理想情况，实际做不到）：占用 100758 个，利用率 85.5%。
- **分页，每块 16 个 token**：占用 86560 个，利用率 **99.5%**。

vLLM 的论文报告，在它之前的推理系统里，KV Cache 的显存有 60% 到 80% 被浪费掉了，和这里的模拟是一个量级。

## 分页：像操作系统管理内存那样

操作系统早就遇到过同样的问题：很多程序同时运行，各自需要的内存大小不一、随时变化。它的解决办法是**分页**：把物理内存切成大小固定的小块（页），程序看到的是一段连续的“虚拟地址”，实际却可以分散在任意的物理页上，由一张**页表**记录“虚拟的第几页在物理的第几页”。

PagedAttention 照搬了这个想法：

- **切块**：把整个 KV Cache 池子切成大小固定的**块**（block），每块存固定个数 token 的 KV，vLLM 默认 16 个。推理引擎启动时，就把第 63 讲算出的 KV Cache 空间全部切成块，放进一个空闲列表。
- **按需分配**：请求需要存更多 token 时，才从空闲列表里取一个块，**不需要和前面的块相邻**。请求的最后一块写满了，再取下一块。
- **块表**：每个请求有一张**块表**（block table），记录它的第 0、1、2……个逻辑块分别放在哪个物理块。
- **用完归还**：请求结束，它的所有块还回空闲列表，立刻可以给别的请求用。

查找某个 token 的 KV 时，用块表换算一下：第 i 个 token 在逻辑上的第 i ÷ 16 块（取整），块内第 i mod 16 个位置；查块表就知道它在哪个物理块。比如一个请求的块表是 [7, 2, 9]：它的第 0 到 15 个 token 在物理块 7，第 16 到 31 个在物理块 2，第 40 个 token 在物理块 9 的第 8 个位置。

这样一来：

- **几乎没有内部碎片**：每个请求浪费的只是最后一块里还没写满的那几个位置，最多 15 个 token。
- **没有外部碎片**：所有块一样大，任何一个空闲块都能给任何请求用，不需要找连续的大空间。
- **不需要预知长度**：长度增长到哪，块就分配到哪。

## 引擎底层是怎么实现的：启动、调度与计算三件事

很多初学者看到这里会有一个疑问：显存不是一块平整的物理芯片吗？软件层面上怎么把它切成块，又怎么在运行中精准调度呢？对应到推理引擎的底层实现，其实就是三件事：启动时的显存池化、调度时的块管理器，以及计算时专门定制的注意力算子。

### 1. 启动时：Profiling 与全局显存池化

大模型推理系统有一个铁律：**运行时绝不频繁向操作系统申请显存**。

在 GPU 上调用显存分配函数（如 `cudaMalloc`）不仅开销昂贵，每次可能耗费数毫秒甚至几十毫秒，而且频繁申请、释放不规则大小的显存，很快就会在 GPU 物理显存中制造出无法消除的碎片，最终在显存总量明明充足的情况下抛出 OOM（Out of Memory）异常。

所以，推理引擎在正式对外服务之前，会先做一次“摸底测量”（Profiling）：

引擎把模型本身的全部权重加载进 GPU 显存（例如 Llama-3-8B 的 FP16 权重约占 16 GiB）。接着，引擎使用一个模拟的最大批次输入跑一次前向传播，或者根据公式测算出模型运行时峰值激活值与临时缓冲区所需要的显存大小（例如约占 2 GiB）。

用整张显卡的物理总容量（例如 80 GiB）减去权重和激活值的占用，剩下的空间乘上一个安全利用率系数（通常是 `gpu_memory_utilization = 0.9`，保留 10% 作为应对突发开销的安全缓冲），剩下的全部显存**一次性**向系统申请为一个巨大的连续张量。这个大张量就是整个系统的**物理 KV 池**（Physical KV Pool）。

申请完成后，引擎在软件层面上把这个池子一次性划分成 $N$ 个固定大小的物理块（例如每个块装 16 个 token 的 KV）。在引擎后续长达数天甚至数月的运行过程中，**再也不会向 CUDA 运行时申请任何新的 GPU 显存**。所有请求对 KV Cache 的申请与释放，完全是由引擎内部自己维护的“账本”在用户态完成。

### 2. 调度时：Block Manager 的状态机与具体流转

这个负责记账与分发物理块的调度中枢，叫做 **Block Manager（块管理器）**。

Block Manager 内部维护了三个核心数据结构：
- **空闲物理块列表（Free List）**：启动时把所有的物理块编号 `[0, 1, 2, ..., N-1]` 全部放进一个队列或链表中。
- **请求块表（Block Table）**：每一个正在运行的请求都有一张属于自己的块表，记录该请求的逻辑块映射到了哪些物理块（例如请求 A 的块表是 `[7, 2, 9]`）。
- **物理块引用计数（Reference Count）**：每个物理块记录当前有几个请求在读写它。

在整个请求的生命周期中，Block Manager 就像一个严谨的仓库管理员，执行以下四步流转：

第一步是**请求到达（Prefill 阶段）**。假设用户发来一段长度为 35 个 token 的提示词，块大小设为 16。请求需要 $\lceil 35 / 16 \rceil = 3$ 个块。Block Manager 立即从空闲列表的头部弹出 3 个空闲物理块（例如编号 7、2、9），写入该请求的块表中，并将这 3 个块的引用计数都设为 1。Prefill 算完后，这 35 个 token 的 KV 会分别存进物理块 7（装前 16 个）、物理块 2（装中间 16 个）和物理块 9（装最后 3 个，此时该块还剩 13 个空位）。

第二步是**逐步生成（Decode 阶段）**。模型每生成一个新 token，就需要把这个新 token 的 KV 存入缓存。Block Manager 检查该请求块表的最后一个物理块（物理块 9）：当前只存了 3 个 token，容量上限是 16，显然还有空余槽位！于是新 token 的 KV 直接追加写入物理块 9 的第 4 个位置，**不需要分配任何新块**。

第三步是**块写满与按需追加**。当模型自回归生成到第 14 个 token 时，物理块 9 的 16 个槽位全部被填满。到了生成第 15 个 token 的瞬间，Block Manager 发现最后一个块已满，便再次从空闲列表里弹出一个新的空闲物理块（例如编号 15），追加到该请求的块表尾部（块表变为 `[7, 2, 9, 15]`），新 token 写入物理块 15 的第 0 个槽位。

第四步是**请求结束与归还**。当模型输出了终止符 `<eos>` 或达到最大长度，请求宣告完成。Block Manager 遍历该请求的块表，把物理块 7、2、9、15 的引用计数各自减 1。因为没有其他请求共用它们，四个块的引用计数全部降为 0。Block Manager 随即把这 4 个编号重新放回空闲列表中。整个过程完全是 CPU 内存中的几个整数和列表操作，耗时不到一微秒。

### 3. 计算时：PagedAttention Kernel 到底怎么读分散内存

现在显存被切成了成千上万个散落在各处的物理块，问题来了：GPU 的注意力算子（Attention Kernel）原本是假设矩阵在显存里连续排列的，它怎么去读取这些东一块西一块的 KV 数据？

这正是需要专门编写 **PagedAttention Kernel** 的原因。

在普通的注意力算子中，KV Cache 在显存里像一张平整的长方形地毯，第 $i$ 个 token 的内存地址只要用基地址加上 `i * 步长` 就能一步算出，所有线程按固定步长连续读取显存。但在 PagedAttention 里，物理显存是打散的，比如逻辑上的前 16 个 token 在物理地址 `0x1000`，接下来的 16 个 token 却跑到了 `0x8000`。

为了让 GPU 算子能正常计算，调度器在启动 GPU Kernel 时，除了传入当前新 token 的查询向量 $Q$，还会把调度层维护的 `block_tables`（一个二维整数张量，形状为 `[批大小, 最多块数]`）一起作为参数传入 GPU 显存。

在 GPU 内部，计算被分配给成千上万个线程。以 Decode 阶段计算注意力为例，一个 Warp（包含 32 个线程的线程束）负责处理一个注意力头：
1. 当线程需要去读取历史上的第 t 个 token 的 Key 向量时，它在硬件寄存器里执行快速整数换算：
   - 先算逻辑块号：`逻辑块 = t // 16`；
   - 查块表找出真实的物理块号：`物理块号 = block_table[请求 ID, 逻辑块]`；
   - 算块内相对偏移：`块内偏移 = t % 16`；
2. 拿到物理块号后，乘以一个物理块的字节大小，就能定位到该物理块在全局显存池中的基地址，再加上块内偏移，就精准找出了该 token 对应的显存物理位置，把向量读进寄存器与 $Q$ 做点积。

看到这里你可能会问：每个 token 都要查表换算地址，GPU 读取不会变慢吗？

答案是：**块内连续保证了极高的硬件效率**。虽然块与块之间在物理显存上是不连续的，但在**每一个块的内部**，这 16 个 token 的数据是紧凑、连续存放的。GPU 的内存总线每次是以 32 字节或 128 字节的缓存行（Cache Line）为单位读取显存的。当同一个 Warp 内的线程读取同一个块内的相邻 token 时，依然能够触发硬件的**合并访存（Coalesced Memory Access）**，吞吐量几乎打满显存带宽。只有每隔 16 个 token 跨越边界时，才会发生一次块表查询跳转。

我们手算一下一个物理块到底有多大。以 Llama-3-8B 为例（32 层 Transformer，8 个 KV 头，每头维度 128，采用 FP16 精度占用 2 字节）：
跨所有层合计的一个 token 的 KV 大小为：
2(K 和 V) × 32(层) × 8(头) × 128(维) × 2(字节) = 131,072 字节 = 128 KiB。

如果一个物理块存 16 个 token，那么跨所有层合计的一个物理块大小正好是：
16 × 128 KiB = 2048 KiB = 2 MiB。

在 GPU 显存架构中，2 MiB 是一个非常干净的对齐单位（很多 GPU 的二级缓存行和内存分页映射刚好是 2 MiB 级别）。既保证了内部碎片极小（最多只浪费不到 2 MiB），又让硬件访存足够连续高效。

## 省下来的显存变成了什么

省下来的显存，直接变成了**更多的并发**。用第 63 讲的数字：KV Cache 池子能放约 40.4 万个 token。

- 按最大长度 4096 连续预留：每个请求占 4096 个，最多 **98 个**请求。
- 分页：按上面那个快照，平均每个请求实际占约 1352 个 token，能放约 **299 个**请求。

并发数是原来的三倍左右，第 62 讲说过，并发越高，权重的读取被分摊得越多，吞吐越高（直到 KV Cache 的读取成为主导），第 64 讲的输出成本也随之下降。这就是 vLLM 论文报告的吞吐提升的主要来源。

## 共享：同一个块，多个请求一起用

分页还带来了一个额外的好处：**一个物理块可以同时出现在好几个请求的块表里**。

一个常见的场景是**并行采样**：同一个提示，让模型生成 4 个不同的回答，让用户挑选，或者做第 49 讲的多数投票。4 个回答共用同一段提示，提示部分的 KV Cache 完全相同。用分页，只需要存一份提示的块，4 个请求的块表都指向它们；各自生成的部分再分配各自的块。提示 1000 个 token、每个回答 200 个：不共享要存 4800 个 token，共享只要 1840 个，省了 62%。

为了安全地共享，每个块记录有几个请求在用它（**引用计数**）。如果某个请求要往一个共享的块里写新的 token（比如提示的最后一块还没写满，各个回答的第一个 token 要写在这里），就先把这个块**复制**一份给自己，再写，这叫**写时复制**（copy-on-write），也是操作系统里的老办法。引用计数降到 0，块才真正还回空闲列表。

这种共享不局限于同一个请求的多个回答。不同的请求如果开头相同（比如同一个系统提示），也可以共享前面那些块，这就是下一讲的前缀缓存。

## 代价：注意力算子要改

分页不是没有代价的。原来一个请求的 KV Cache 在显存里是连续的一整块，注意力算子按顺序读就行；现在它们散落在各个物理块里，注意力算子要**一边查块表、一边去不同的地方读**。这正是 “PagedAttention” 这个名字的由来：它本质上是一个能按块表读取分散 KV Cache 的注意力算子。

查表和分散读取会带来一点额外开销，块越小，开销越大；块越大，最后一块的浪费越多，共享的粒度也越粗。16 个 token 是一个经验上的折中。今天的注意力算子库（比如 FlashInfer、FlashAttention 的分页版本）都原生支持块表，这点开销已经很小了。

## 用代码复现

下面的代码先演示用块表换算 token 的位置；再模拟 64 个请求的快照，比较三种分配方式的利用率；然后算出池子能容纳的请求数；最后算并行采样时共享提示块能省多少。

```python
import math

B = 16                                                   # 每个块存 16 个 token 的 KV（vLLM 的默认值）

# 1. 块表：逻辑上第 i 个 token → 物理上第几个块、块里第几个位置
block_table = [7, 2, 9]                                  # 这个请求的 3 个逻辑块，分别放在物理块 7、2、9
for i in [0, 15, 16, 40]:
    print(f"第 {i:2d} 个 token → 物理块 {block_table[i // B]}，块内第 {i % B} 个")

# 2. 某一时刻，64 个请求正在运行（快照统计：提示 200~2000，输出 50~1000，已生成到一半）
n = 64
MAX_LEN = 4096
used = 86151                                             # 64 个请求当前实际拥有的 token 总数
contig_max = n * MAX_LEN                                  # 每个请求按最大长度预留一整块连续空间
contig_final = 100758                                    # 就算事先知道最终长度，也要按最终长度预留
paged = 86560                                            # 分页：按块分配，只有最后一块可能没装满

for name, alloc in [("按最大长度连续预留", contig_max), ("按最终长度连续预留（理想）", contig_final), ("分页（每块 16 个 token）", paged)]:
    print(f"{name}：占用 {alloc:,} 个 token 的空间，真正用上 {used:,}，利用率 {used / alloc:.1%}")

# 3. 49.3 GiB 的 KV Cache 池（第 63 讲，Llama-3-8B 每 token 128 KiB）能同时放多少个这样的请求
pool = int(49.3 * 2**30 / (128 * 1024))
avg_paged = paged / n
print(f"池子 {pool:,} 个 token：连续预留 {MAX_LEN} 时能放 {pool // MAX_LEN} 个请求；分页时平均每个请求 {avg_paged:,.0f}，能放约 {pool / avg_paged:.0f} 个")

# 4. 并行采样：同一个提示（1000 个 token）生成 4 个不同的回答（各 200 个 token）
p, o, k = 1000, 200, 4
no_share = k * (p + o)
share = math.ceil(p / B) * B + k * math.ceil(o / B) * B   # 提示的块共享，各自的回答单独分配
```

## 到了大模型里

**块的大小和形状。**vLLM 的块大小默认是 16 个 token（参数 `block_size`）。一个块里存的是所有层的、这 16 个 token 的 K 和 V；实际实现里，每层的 KV Cache 是一个 [块数, 2, 16, KV 头数, 每头维度] 之类的大张量，块号就是第一维的下标。启动日志里的 “GPU blocks: xxxx”，就是第 63 讲那本账算出的块数。

**块表随请求一起送进算子。**每一步，调度器把这一步每个请求的块表整理成一个整数矩阵，和 token 一起送进模型；注意力算子根据它去读写 KV Cache。新 token 的 k、v 也按块表写到对应的物理位置。

**分页是后面很多技术的基础。**前缀缓存（第 68 讲）靠块的共享；抢占（第 70 讲）以块为单位换出、换回；PD 分离（第 13 篇）以块为单位在机器之间传输 KV Cache。

## 容易混淆的地方

1. **分页不减少 KV Cache 本身的大小。**每个 token 的 KV Cache 还是 128 KiB（Llama-3-8B），分页减少的是“预留了但没用上”的浪费。要减少每个 token 的大小，靠的是 GQA、MLA、KV Cache 量化。
2. **“虚拟”的连续只存在于块表里。**模型的计算逻辑没有任何变化，注意力还是在和这个请求的全部历史 token 做计算，只是读数据的地址要查表。
3. **共享的块是只读的。**一个块被多个请求引用时，谁也不能直接改它，要写就先复制。这保证了共享不会让一个请求影响另一个请求的结果。

## 回顾

KV Cache 随请求增长、随时释放，长度事先不知道。传统做法按最大长度给每个请求预留连续的显存，造成大量内部碎片、外部碎片和预留浪费，模拟的快照里利用率只有 32.9%。PagedAttention 借用操作系统的分页：把 KV Cache 切成固定大小的块（常用 16 个 token），按需分配，用块表记录逻辑块到物理块的映射，浪费只剩每个请求最后一块的空位，利用率达到 99.5%，同样的显存能装下约三倍的请求。在底层，引擎通过启动时的全局预分配池化彻底杜绝运行时显存碎片，调度器维护空闲块列表与引用计数，定制的算子则拿着块表在连续的块内高效读取分散显存。

块可以共享，就意味着：如果很多请求的开头相同，比如同一个系统提示、同一份长文档、同一段多轮对话的历史，它们的 KV Cache 只需要算一次、存一份。怎么找到这些可以共享的前缀？下一讲：**Prefix Cache**。
