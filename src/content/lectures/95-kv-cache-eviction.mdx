上一讲把 KV Cache 存成 FP8，每个 token 的缓存从 128 KiB 减到 64 KiB，并发翻倍。可上下文一长，减半也不够看：Llama-3-8B 的一条 128K 上下文的请求，BF16 的 KV 是 16 GiB，FP8 也有 8 GiB，一张 80 GB 的卡放不下几条。

量化是让每个 token 存得更省；另一条路是**不存所有的 token**。生成下一个 token 时，它真的需要前面 13 万个 token 的 K、V 吗？如果注意力只集中在其中一小部分上，其余的能不能扔掉？这一讲用 Qwen3-0.6B 做一次真实的实验，看几种“扔法”的效果。

## 先算一下能省多少

```python
per_token = 2 * 32 * 8 * 128 * 2            # Llama-3-8B：K、V × 32 层 × 8 个 KV 头 × 128 维 × 2 字节
print(f"每个 token {per_token / 1024:.0f} KiB")
for ctx in (8_192, 32_768, 131_072):
    print(f"上下文 {ctx:>7,}：一条请求的 KV {ctx * per_token / 2**30:5.1f} GiB；只留 4096 个：{4096 * per_token / 2**30:.2f} GiB，是原来的 {4096 / ctx:.1%}")
import math
for d in (0.539, 0.134, 0.013):
    print(f"损失多 {d:.3f}，困惑度变成原来的 {math.exp(d):.2f} 倍")
```


只留 4096 个 token 的 KV，一条 128K 请求的缓存从 16 GiB 降到 0.5 GiB，是原来的 3%。缓存的大小不再随上下文增长，decode 每一步读的 KV 也只有这么多（第 71 讲：长上下文时，decode 的时间大半花在读 KV 上）。代价是什么，要看扔掉的是哪些。

## 注意力集中在哪里

实验是这样的：取一段 512 个 token 的讲义，前 448 个当作“已经在缓存里的上下文”，后 64 个当作“接下来要生成的部分”（尾巴）。先完整地跑一遍，看尾巴里的每个 token 把注意力分给了上下文的哪些位置；然后按几种策略只保留上下文里的 B 个位置，再算尾巴每个 token 的预测损失（负对数似然，第 16 讲），和全部保留时比较。损失多得越少，说明扔掉的东西越不重要。

第一个数最惊人：**尾巴的注意力里，63.5% 落在上下文的前 4 个 token 上**，而它们只占 448 个位置的 0.9%。最近的 64 个 token 拿到 15.2%，剩下的 380 个位置分剩下的约五分之一。

第 42 讲讲过这个现象，叫**注意力汇聚点**（attention sink）：softmax 要求每一行的权重加起来是 1，很多时候当前 token 并不需要看前面的什么内容，模型就学会了把“用不掉”的注意力倒给开头那几个 token。它们本身的内容不重要，可它们的 K、V 承担了“吸收多余注意力”的作用。

## 四种扔法

**只留最近 B 个。**最直接的想法：越近的越重要，像滑动窗口一样只留最后 B 个。结果是灾难：B = 32 时损失多 4.49，B = 256（留了一半多）还多 2.81。原因就是丢了开头。汇聚点没了，本该倒给它们的注意力只能分给别的 token，每一层的输出都偏了。

**汇聚点 + 最近（StreamingLLM）。**永远保留开头 4 个，其余预算给最近的 token。B = 32 时损失只多 0.54，B = 128 时 0.13。只是多留了 4 个 token，效果天差地别。

**H2O（heavy-hitter oracle）。**不按位置，按“谁收到的注意力多”来留：把上下文里每个位置从所有查询那里收到的注意力加起来，分数高的就是“重击者”（heavy hitter）。预算的一半给最近的 token，另一半给分数最高的。开头的汇聚点分数最高，自然被留下了。B = 256 时损失只多 0.013，几乎无损。

**SnapKV。**只用上下文最后 32 个查询（观察窗口）的注意力来打分：离生成最近的那些查询看的地方，最能预测接下来要看的地方。再做一次池化，选中一个位置时把它的邻居也带上，保住完整的词。B = 32 时损失最小（0.50），B = 256 时 0.034。

**随机**作为对照：B = 128 时损失多 4.72，因为随机抽的 128 个里恰好没有第 0 个 token；B = 32、64、256 时抽中了第 0 个，损失就小得多。这个“意外”很说明问题：**汇聚点比其他所有位置加起来都重要。**

## 这个实验的局限

这只是一个小实验，有几处比真实方法更苛刻，也有几处更宽松：

- **所有层、所有头共用一份保留名单。**真实的 H2O、SnapKV 是每层、每个 KV 头各选各的，不同的头关注的地方不同。我们用一份名单（四维注意力掩码实现）是为了能直接算出真实的损失，代价是每个头都只能看同一批位置。
- **H2O 是简化版。**真实的 H2O 在生成的每一步都更新累计分数、逐步驱逐；我们只用上下文内部的注意力打一次分。
- **只测了 64 个 token 的尾巴、一段讲义。**驱逐的真正风险在于：**扔掉的 token 再也找不回来**。如果后面的问题恰好要用到上下文中间某个早被扔掉的细节（比如“大海捞针”测试里藏的那句话），任何策略都救不了。语言建模的损失看起来很好，不代表长文问答也好。

## 到了真实系统里

- **和分页 KV 的冲突。**vLLM 的 PagedAttention 按块管理 KV（第 75 讲），一块 16 个 token，所有头一起分配。按头、按 token 驱逐会在块里留下一个个洞，块表和 kernel 都要改。所以主流引擎默认不做逐 token 的驱逐；更常见的是模型结构本身带滑动窗口（如 Mistral 7B 的滑动窗口注意力、Gemma 2 隔层使用的局部注意力），引擎为它专门管理。
- **SnapKV 更适合 prefill 很长、生成较短的场景。**比如长文档问答：读完提示后一次性压缩 KV，之后的 decode 只用压缩后的缓存。它只在 prefill 结束时选一次，和引擎的配合比 H2O 简单。
- **按层分配预算。**PyramidKV 等工作发现低层的注意力比较分散、高层比较集中，于是低层多留、高层少留，同样的总预算效果更好。
- **扔掉之外，还可以挪走。**把不常用的 KV 从显存挪到 CPU 内存或 SSD，需要时再读回来（第 113 讲）。这样没有信息损失，代价是读回来的时间。

## 容易混淆的地方

- **驱逐和量化可以叠加。**量化让每个 token 小一半，驱逐让 token 少几倍，两者独立。
- **汇聚点不是“重要的内容”。**它们通常是开头的特殊符号或第一个词，内容无关紧要；重要的是它们在注意力里的“位置”。换成别的 token 放在开头，模型一样把注意力倒给它。
- **驱逐不省 prefill 的计算。**prefill 时所有 token 都要参与注意力（SnapKV 正是用 prefill 的注意力来选），省的是之后 decode 的显存和读 KV 的时间。

## 回顾

只留 4096 个 token 的 KV，128K 上下文的缓存能从 16 GiB 降到 0.5 GiB。在 Qwen3-0.6B 上，尾巴 63.5% 的注意力落在开头 4 个 token 上：只留最近的 token、丢掉它们，留 256 个也要多 2.81 的损失；保留汇聚点再加最近的，32 个只多 0.54。H2O 按累计注意力挑、SnapKV 按观察窗口挑，B = 256 时损失只多 0.013、0.034。驱逐的代价是扔掉的信息找不回来，而且和分页 KV 的块管理有冲突，所以主流引擎默认不做，更多用在长文档读完再答的场景。

到这里，压缩讲的都是“每一步读得更少”。可 decode 还有一个更根本的限制：一步只能生成一个 token，每一步都要把权重完整地读一遍。能不能一步生成好几个 token？下一讲：**投机解码**。
