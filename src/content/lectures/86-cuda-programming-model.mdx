前三讲反复出现了“kernel”“工作单元”“片上存储”“SM”这些词：融合是把几个 kernel 合成一个，FlashAttention 让一块查询留在片上，Flash-Decoding 要让 132 个 SM 都有活干。这一讲把它们背后的东西讲清楚：在 GPU 上写程序，到底是怎么组织的。

NVIDIA GPU 的编程模型叫 **CUDA**。它的核心思想只有一句话：**写一段只处理一小份数据的代码，让成千上万个线程同时执行它，每个线程根据自己的编号决定处理哪一份。**这一讲先用最简单的向量加法看清“线程、块、网格”三层结构，再看它们怎么对应到硬件上，最后用矩阵乘法看共享内存为什么重要。

## 一个线程，算一个元素

先从最简单的例子开始：两个长度为 n 的向量相加，c = a + b。在 CPU 上，我们写一个循环，从第 0 个元素算到第 n − 1 个。在 GPU 上，我们只写“一个元素怎么算”：

```cpp
__global__ void add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 我是第几个线程？
    if (i < n) c[i] = a[i] + b[i];                   // 越界的线程什么也不做
}

// CPU 端启动：每块 256 个线程，块数向上取整
add<<<(n + 255) / 256, 256>>>(a, b, c, n);
```

`__global__` 表示这是一个 kernel：在 GPU 上执行、由 CPU 启动的函数。启动时 `<<<块数, 每块线程数>>>` 指定要开多少个线程，GPU 会让这么多个线程**同时**执行这同一段代码。每个线程的代码一模一样，区别只在于几个内置变量的值不同：

- `threadIdx.x`：我在自己的块里是第几个线程（0 到 blockDim.x − 1）；
- `blockIdx.x`：我所在的块是第几个块；
- `blockDim.x`：每个块有几个线程（这里是 256）。

于是 `i = blockIdx.x * blockDim.x + threadIdx.x` 就是这个线程在全体线程里的编号，它负责第 i 个元素。

## 线程、块、网格

这三层结构是 CUDA 的骨架：

- **线程**（thread）：执行 kernel 代码的最小单位，有自己的寄存器。
- **线程块**（block）：一组线程，最多 1024 个。同一个块里的线程可以通过**共享内存**交换数据，也可以互相等待（同步）。
- **网格**（grid）：一次 kernel 启动的所有块。

n = 1000、每块 256 个线程时，要 ⌈1000 / 256⌉ = 4 个块，一共 1024 个线程。最后 24 个线程的 i 是 1000 到 1023，超出了向量的范围，`if (i < n)` 让它们什么也不做。比如块 1 的第 5 个线程负责第 1 × 256 + 5 = 261 个元素；块 3 的第 231 个线程负责第 999 个，也就是最后一个元素。

块和网格都可以是二维、三维的，处理矩阵时很方便。一个 M × N 的矩阵，每个线程负责一个元素，块取 16 × 16 个线程，网格就是 ⌈M / 16⌉ × ⌈N / 16⌉ 个块。线程用两个下标定位：

<div class="ai-formula">row = blockIdx.y × blockDim.y + threadIdx.y，　col = blockIdx.x × blockDim.x + threadIdx.x</div>

20 × 30 的矩阵、16 × 16 的块，网格是 2 × 2 个块；块 (1, 1) 里的线程 (2, 13) 负责第 18 行、第 29 列。

## 对应到硬件上

为什么要分“块”这一层？因为它对应着硬件。

GPU 由很多个 **SM**（流式多处理器）组成，H100 有 132 个。每个 SM 有自己的计算单元（包括做矩阵乘法的 Tensor Core）、寄存器和共享内存。kernel 启动后，GPU 把网格里的块一个个分配给 SM：**一个块整个放在一个 SM 上运行，直到结束**；一个 SM 可以同时运行好几个块，只要寄存器和共享内存够用。

这带来两个重要的性质：

1. **同一个块里的线程能合作。**它们在同一个 SM 上，可以通过这个 SM 的共享内存交换数据，可以用 `__syncthreads()` 互相等待。
2. **不同的块之间不能直接合作。**块的执行顺序没有保证，它们可能在不同的 SM 上同时运行，也可能先后运行。一个块不能等另一个块的结果。所以上一讲 Flash-Decoding 要把各段的结果先写回显存，再用**另一个 kernel** 合并。

块要足够多，所有 SM 才都有活干。上一讲批大小为 1 时只有 8 个块（工作单元），132 个 SM 里大部分闲着，就是这个原因。

再往下一层，SM 实际执行时，把一个块里的线程按编号每 **32 个**编成一组，叫一个 **warp**。同一个 warp 的 32 个线程在同一时刻执行**同一条指令**，只是作用在各自的数据上（这种方式叫 SIMT，单指令多线程）。由此有两条写 kernel 的基本规则：

- **避免分支发散。**如果同一个 warp 里一半线程走 `if`、一半走 `else`，两条路径只能先后执行，速度减半。
- **合并访存。**同一个 warp 的 32 个线程如果读的是显存里相邻的 32 个元素，硬件能把它们合成一次大的读取；如果读的地址七零八落，就要分成很多次。所以矩阵按行存放时，让相邻的线程处理同一行里相邻的列。

## 三种存储

线程能用的存储，和上一讲的“显存 / 片上”对应起来：

- **寄存器**：每个线程私有，最快。kernel 里的局部变量通常就放在这里。
- **共享内存**：每个块私有，在 SM 的片上，块内所有线程都能读写，几乎和寄存器一样快，但容量只有几十到两百多 KB。
- **全局内存**：就是显存（HBM），所有线程都能访问，容量大，但慢得多。kernel 的输入输出都在这里。

写高性能 kernel 的核心问题，几乎总是：**怎么让数据尽量少地从全局内存读，尽量多地在寄存器和共享内存里复用。**融合（第 83 讲）是这样，FlashAttention（第 84 讲）是这样，下面的矩阵乘法也是这样。

<Note kind="point">CUDA 程序是一个 kernel 加一次启动配置：网格里有很多块，块里有很多线程，每个线程用 blockIdx、threadIdx 算出自己负责的数据。一个块整个跑在一个 SM 上，块内线程可以用共享内存合作，块与块之间不能直接合作。线程按 32 个一组（warp）执行同一条指令。</Note>

## 矩阵乘法：共享内存的用处

C = A · B，A、B 都是 K × K 的方阵（第 13 讲）。最直接的写法：每个线程算 C 的一个元素，自己从显存读 A 的一整行、B 的一整列，做 K 次乘加。

问题是重复读取。A 的第 r 行，要被算 C 第 r 行的所有 K 个线程各读一遍；B 的每一列也一样。一共要从显存读 2K³ 个元素。K = 4096、BF16 时，约 **274.9 GB**，按 3.35 TB/s 要约 82 ms；而计算本身只有 2K³ ≈ 137 GFLOP，用 Tensor Core 只要约 0.14 ms。

**分块**解决了这个问题。让一个线程块负责 C 的一个 T × T 小块。它沿着 K 方向一段一段地前进：每一段，块里的线程一起把 A 的一个 T × T 小块和 B 的一个 T × T 小块搬进共享内存，`__syncthreads()` 等大家都搬完，然后每个线程从共享内存里取数，累加自己那个元素的部分和；再搬下一段。

这样，每个从显存读进来的元素，在共享内存里被 T 个线程复用。从显存读的总量降到原来的 1/T：

- 块大小 1（不分块）：274.9 GB，约 82 ms；
- 块大小 16：17.2 GB，约 5.1 ms；
- 块大小 64：4.3 GB，约 1.3 ms。

块越大，复用越多，但共享内存和寄存器装得下的块有限。真实的矩阵乘法库（cuBLAS、CUTLASS）用好几层分块：线程块级的大块放在共享内存，warp 级的小块放在寄存器里交给 Tensor Core，再加上 L2 缓存的复用，最终能让矩阵乘法跑在算力的上限附近。这也是为什么第 68 讲可以把大矩阵乘法看作“计算受限”。

## 一个线程块在 SM 上住不住得下

上一节的矩阵乘法 kernel 能跑多快，要看 SM 里同时住着多少个线程块。线程块要在 SM 上**驻留**，必须同时分到三样东西：线程槽、寄存器、共享内存。哪一样不够，块就只能排队等前面的块结束。

拿一个实际尺寸的矩阵乘 kernel 算：每个线程块负责 128 × 128 的输出块，沿 K 每次搬 64；A 块和 W 块（BF16）各 16 KiB，FP32 累加器 64 KiB，三者都放在共享内存里，共 96 KiB。每块 256 个线程，每线程用 128 个寄存器。一个 H100 的 SM 最多 2048 个线程、65,536 个寄存器、228 KB（233,472 字节）共享内存、32 个线程块。每类资源能放几块，等于总量除以每块的需求，向下取整：

| 资源 | SM 总量 | 每块需求 | 放得下 |
| --- | --- | --- | --- |
| 线程槽 | 2048 | 256 | 8 |
| 寄存器 | 65,536 | 256 × 128 = 32,768 | 2 |
| 共享内存 | 233,472 B | 96 KiB + 1 KiB 预留 | 2 |
| 块数上限 | 32 | 1 | 32 |

取最小值，SM 上驻留 2 个块，16 个 warp。驻留的 warp 数占 SM 上限（64 个）的比例叫**占用率**（occupancy），这里是 25%。

改哪一项才有用，要看哪一项最紧。比如把 64 KiB 的累加器从共享内存挪进寄存器：每块的共享内存降到 32 KiB，能放 6 块了；可每个线程要多存 128 × 128 ÷ 256 = 64 个 FP32 值，寄存器从 128 个涨到 192 个，寄存器只允许 1 块，反而更少。要让更多块驻留，得同时压低寄存器和共享内存，或者把块做小。

## 占用率为什么重要：在途请求

为什么要多驻留几个 warp？因为读显存要等很久（这里取 600 ns），而访存请求都是驻留的 warp 发出的。一个请求在等的时候，别的请求要把接口占满，这叫**延迟隐藏**。第 61 讲的 Little 定律给出了需要多少在途字节：带宽 × 延迟。H100 是 3.35 TB/s × 600 ns ≈ 2.01 MB，平摊到 132 个 SM，每个 SM 要保持约 **15.2 KB** 在途。

驻留的 warp 能提供多少？一个 warp 的一条加载指令让 32 个线程各取 16 字节，共 512 字节；每个 warp 最多挂 4 条没完成的加载；16 个 warp 合计 **32 KiB**，是需求的 2.15 倍，够用。

但这个结论会翻转：如果延迟涨到 1000 ns，每个 warp 只能挂 2 条加载，每个 SM 就要 25.4 KB 在途，16 个 warp 只能提供 16 KiB，只有需求的 0.65 倍。这时有效带宽只有接口的六成多，接口再快也用不上。要么把块做小换更多驻留块，要么改用异步批量复制（Hopper 的 TMA），一个线程一次请求一整块，在途字节就不再取决于 warp 数。

## 块多大：读得少，但住得少

再看块的大小对显存读写的影响。拿 Qwen3-8B 的一个 FFN 投影：C = A·W，A 是 [1024, 4096]，W 是 [4096, 12288]，BF16。三份矩阵各读写一次只要 128 MiB。可如果每个输出块各自读自己的输入，N 方向有 N/t 个列块，每个都要把 A 读一遍；M 方向有 M/t 个行块，每个都要把 W 读一遍：

<div class="ai-formula">读写量 = 2MK · N/t + 2KN · M/t + 2MN</div>

| 输出块 | 局部存储（K 步 32） | 读写量 | 算术强度 |
| --- | --- | --- | --- |
| 32 × 32 | 8 KiB | 6168 MiB | 15.9 FLOP/byte |
| 64 × 64 | 24 KiB | 3096 MiB | 31.8 FLOP/byte |
| 128 × 128 | 80 KiB | 1560 MiB | 63.0 FLOP/byte |

块边长翻倍，输入重读减半；可局部存储涨得更快，因为累加器随 t² 增长。三种块的算术强度都远低于 H100 的峰值算力 ÷ 带宽 ≈ 295 FLOP/byte（第 62 讲的拐点），只靠这一级分块越不过拐点，剩下的复用要靠 L2 和更大的块。

块变大还有一个代价：同时驻留的块变少，在途请求变少，实际拿到的带宽可能下降。读写量减半，时间不一定减半：如果大块只拿到小块四成的带宽，时间反而是原来的 0.504 ÷ 0.4 ≈ 1.26 倍。所以选块要先按容量排除放不下的，再按读写量缩小范围，最后实测。

## bank 冲突：一列数据挤进一个 bank

共享内存不是一块整体，而是分成 32 个 **bank**，每个 bank 每个周期只能给出一个 32 位的字，字地址除以 32 的余数就是它所在的 bank。一个 warp 的 32 个线程同时读 32 个地址：落在 32 个不同的 bank，一轮就完成；落在同一个 bank，要排 32 轮。

32 × 32 的 FP32 块按行存放，读一行没问题；读一列时，相邻两行的同一列相差 32 个字，全部落在同一个 bank 里，要 **32 轮**。在每行末尾补一个字（padding），行跨度变成 33，同一列相邻行的 bank 号依次加一，32 个请求分到 32 个 bank，**1 轮**完成，只多占 3.1% 的空间。

也可以不多占空间，只改存放位置：把第 r 行第 c 列放到第 c ⊕ r 列（⊕ 是按位异或）。读一列时，32 个 lane 取到的列号互不相同，同样一轮完成。CUTLASS 把这叫 **swizzle**。TMA 这类整块搬移的硬件不能在行间插 padding，所以用 swizzle。

## 搬和算错开：双缓冲与 warp 分工

最后看一个 K 块从显存搬进来、再被矩阵单元用掉的过程。按 H100 一个 SM 分到的份额（显存带宽的 1/132 约 25.4 GB/s，矩阵算力的 1/132 约 7.5 TFLOP/s），一个 K 块的 A、W 共 32 KiB，搬进来约 **1.29 μs**；块乘 2,097,152 FLOPs，算完约 **0.28 μs**。搬比算慢 4.6 倍，因为这个块每搬 1 字节只做 64 次运算。

先搬后算，四块要 4 × (1.29 + 0.28) = 6.28 μs。用两个缓冲槽：算槽 A 里的块时，搬下一块进槽 B，交替使用。总时间是

<div class="ai-formula">T = t_搬 + (n − 1) × max(t_搬, t_算) + t_算 = 1.29 + 3 × 1.29 + 0.28 = 5.44 μs</div>

只少了 13%：搬移首尾相接，计算单元只有约两成时间在干活。这时再加第三个槽也没用（CUTLASS 把槽数叫 stage 数），只能减少每块要搬的字节，比如把块做大。

Hopper 上的 kernel 常让 warp 分工（**warp specialization**）：一个 warp 只负责发异步复制（生产者），其余 warp 只做矩阵计算（消费者）。两边靠共享内存里的**栅栏**交接：每个槽一对栅栏，“满”栅栏由复制完成触发，消费者等它；“空”栅栏由计算结束触发，下一次复制等它。FlashAttention-3 就是这样安排的：一个 warpgroup 搬 K、V，两个 warpgroup 交替做矩阵乘和 softmax。

## 用代码复现

GPU 代码要在 GPU 上才能跑。为了看清楚线程怎么分工，下面用 Python 模拟：先算向量加法里几个线程负责的下标，再算二维网格里一个线程负责的行列；然后用 NumPy 实现分块的矩阵乘法，统计从“显存”读了多少个元素；最后估算 K = 4096 时不同块大小的读取量。

```python
import numpy as np

# 1. 一维：n 个元素的向量加法，每个线程负责一个元素。用 Python 模拟 GPU 上的“网格 → 块 → 线程”
n, blockDim = 1000, 256
gridDim = (n + blockDim - 1) // blockDim                 # 向上取整：要几个块才能盖住 n 个元素
print(f"n = {n}，每块 {blockDim} 个线程 → {gridDim} 个块，共 {gridDim * blockDim} 个线程，{gridDim * blockDim - n} 个线程越界、什么也不做")
for blockIdx, threadIdx in [(0, 0), (1, 5), (3, 231), (3, 255)]:
    i = blockIdx * blockDim + threadIdx                  # 每个线程算出自己负责的全局下标
    print(f"  blockIdx = {blockIdx}，threadIdx = {threadIdx:3d} → i = {i:4d}{'（越界，跳过）' if i >= n else ''}")

# 2. 二维：矩阵按 16 × 16 的块切开，线程 (ty, tx) 负责第 row 行、第 col 列
M, N, BX = 20, 30, 16
by, bx, ty, tx = 1, 1, 2, 13
row, col = by * BX + ty, bx * BX + tx
print(f"{M}×{N} 的矩阵、16×16 的块 → 网格 {(M + 15) // 16}×{(N + 15) // 16} 个块；块 ({by}, {bx}) 里的线程 ({ty}, {tx}) 负责 ({row}, {col})")

# 3. 矩阵乘法 C = A·B（K = 4096 的方阵，BF16）：每个线程算 C 的一个元素，要从显存读多少
def matmul_tiled(A, B, T):
    """按 T×T 分块：一个块的线程先把 A、B 的一小块搬进共享内存，大家一起用，再搬下一块。返回结果和从“显存”读的元素个数。"""
    n = A.shape[0]; C = np.zeros((n, n)); loads = 0
    for i in range(0, n, T):
        for j in range(0, n, T):                         # 每个 (i, j) 是一个线程块，负责 C 的一个 T×T 小块
            for k in range(0, n, T):
                a, b = A[i:i + T, k:k + T], B[k:k + T, j:j + T]   # 搬进共享内存
                loads += a.size + b.size
                C[i:i + T, j:j + T] += a @ b
    return C, loads
A, B = np.random.default_rng(0).standard_normal((2, 8, 8))
for T in [1, 2, 4]:
    C, loads = matmul_tiled(A, B, T)
    print(f"8×8 矩阵乘法，块大小 {T}：结果正确 {np.allclose(C, A @ B)}，从显存读了 {loads} 个元素")
K = 4096
for T in [1, 16, 64]:
```

```python
# 1. 一个线程块能不能驻留：每类资源各允许几块，取最小（H100 一个 SM）
SM = {"线程槽": 2048, "寄存器": 65536, "共享内存": 233472, "块数上限": 32}
def resident(threads, regs, smem):
    need = {"线程槽": threads, "寄存器": threads * regs, "共享内存": smem + 1024, "块数上限": 1}
    per = {k: SM[k] // need[k] for k in SM}
    n = min(per.values())
    return per, n, n * threads // 32 / 64
per, n, occ = resident(256, 128, 96 * 1024)               # 128×128 输出块、K 步 64：A、W 块各 16 KiB + FP32 累加器 64 KiB
print("每类资源允许的块数：", per, f"→ 驻留 {n} 块，占用率 {occ:.0%}")

# 2. 在途字节够不够隐藏 600 ns 的显存延迟（Little 定律：带宽 × 延迟）
need = 3.35e12 * 600e-9 / 132
have = n * 8 * 4 * 512                                      # 每块 8 个 warp × 每 warp 4 条未完成加载 × 512 字节
print(f"每个 SM 需要 {need/1e3:.1f} KB 在途，驻留的 warp 能提供 {have/1024:.0f} KiB（{have/need:.2f} 倍）")
need2, have2 = 3.35e12 * 1000e-9 / 132, n * 8 * 2 * 512
print(f"延迟 1000 ns、每 warp 只挂 2 条：需要 {need2/1e3:.1f} KB，只有 {have2/1024:.0f} KiB（{have2/need2:.2f} 倍）")

# 3. 输出块越大，输入重读越少，但局部存储越大（C = A·W，M=1024, K=4096, N=12288，BF16，k=32）
M, K, N, k = 1024, 4096, 12288, 32
for t in [32, 64, 128]:
    smem = 2 * t * k * 2 + 4 * t * t
    traffic = 2 * M * K * N / t + 2 * K * N * M / t + 2 * M * N
    print(f"{t:>3}×{t:<3}：局部存储 {smem/1024:3.0f} KiB，接口读写 {traffic/2**20:5.0f} MiB，算术强度 {2*M*K*N/traffic:4.1f} FLOP/byte")

# 4. 共享内存 bank：32 个 lane 读一列，行跨度 32 个字时全落在同一个 bank
for stride in [32, 33]:
    banks = {(r * stride) % 32 for r in range(32)}
    print(f"行跨度 {stride}：用到 {len(banks)} 个 bank，要 {32 // len(banks)} 轮")
print("异或 swizzle（第 r 行第 c 列放到 c^r 列）：用到", len({(r * 32 + (0 ^ r)) % 32 for r in range(32)}), "个 bank")

# 5. 双缓冲：每块搬 1.29 μs、算 0.28 μs，4 块
tm, tc, n4 = 1.29, 0.28, 4
print(f"串行 {n4*(tm+tc):.2f} μs；双缓冲 {tm + (n4-1)*max(tm, tc) + tc:.2f} μs；计算单元忙的比例 {n4*tc/(tm + (n4-1)*max(tm, tc) + tc):.0%}")
```

## 容易混淆的地方

1. **CUDA 的“块”和 PagedAttention 的“块”不是一回事。**这里的块（block）是一组线程；第 75 讲的块是 KV Cache 的一段存储。英文里都叫 block，要看上下文。
2. **线程多不等于快。**线程只是把工作切开的方式。如果每个线程都在等显存，开再多线程也快不了；性能取决于数据怎么在各级存储之间流动。
3. **共享内存要手动管理。**它不像 CPU 的缓存那样自动工作，什么时候搬什么数据进来、什么时候同步，都要在 kernel 里写清楚。这正是写 CUDA kernel 难的地方，也是下一讲 Triton 要简化的地方。

4. **占用率高不等于快，低也不一定慢。**占用率的作用是提供足够的在途请求去隐藏延迟；在途字节已经够了，再提高占用率没有收益。反过来，块做大省了读写，却可能因驻留块变少而拿不到带宽。
5. **双缓冲只能藏住较短的那一段。**搬比算慢时，重叠之后的时间由搬移决定，加更多的槽也没用。

## 回顾

CUDA 的程序是一个 kernel：写清楚“一个线程做什么”，启动时指定网格有几个块、每块几个线程，所有线程执行同一段代码，用 blockIdx、blockDim、threadIdx 算出自己负责的数据，越界的线程跳过。一个块整个跑在一个 SM 上，块内线程通过共享内存合作、可以同步；块与块之间不能直接合作。线程每 32 个一组成为 warp，同时执行同一条指令，所以要避免分支发散、让相邻线程读相邻的数据。存储分寄存器、共享内存、全局内存三级；矩阵乘法按 T × T 分块、在共享内存里复用，从显存读的数据降到 1/T，K = 4096 时从 274.9 GB 降到 4.3 GB（T = 64）。

写真实的 kernel 还要算 SM 的资源：128 × 128 的矩阵乘块每块要 96 KiB 共享内存、每线程 128 个寄存器，H100 的一个 SM 只住得下 2 块，占用率 25%，在途字节仍是需求的 2.15 倍。块越大输入重读越少（64 × 64 要 3096 MiB，128 × 128 只要 1560 MiB），但住得下的块越少。读一列时用 padding 或 swizzle 避开 bank 冲突；双缓冲让搬和算错开，可搬比算慢时，总时间仍由搬移决定。

分块解决了“从显存读多少”。可一个矩阵乘法真的能跑到峰值吗？Tensor Core 怎么被喂进数据，矩阵怎么分给 132 个 SM，什么形状会让大部分 SM 闲着？下一讲：**矩阵乘法 Kernel 与 Tensor Core**。
